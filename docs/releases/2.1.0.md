# TurfLang 2.1.0 (draft)

Status: draft. Filled in as 2.1.0 work lands; the website's release-notes
section is built from this file.

No breaking changes. Every program that compiled with 2.0 compiles with
2.1.0 and behaves the same; some programs 2.0 rejected now compile, and some
warnings 2.0 printed by mistake are gone.

## Language

### Fixed-size arrays are assigned from their declaration

`mut a: int[1000];` declares an array whose elements all read as the zero
value of the element type (`0`, `0.0`, `false`, `""`, `null` for `&?T`, a
zero-filled struct) until something writes them. Reading one before any
write is no longer E008.

```turflang
import io;

fn main(): int {
    mut squares: int[10];
    for i in 0..10 {
        squares[i] = i * i;     // filling the array in a loop
    }
    io::printline(squares[3]);  // 9 (2.0: E008, the loop might not run)
    return 0;
}
```

In 2.0 an array was tracked as a whole: one element write (`a[0] = 1;`)
counted as assigning every element, so `a[3]` then read a zero that nothing
wrote, while an array filled completely in a loop was rejected. Elements
can't be tracked one by one, so 2.1.0 states what the storage already did:
the array is zero-filled from its declaration. An array whose element type
holds a non-null reference (`(&T)[N]`, or a struct with a `&T` field) still
needs an initializer (E128), and an unsized `T[]` still needs one too.
(FREEZE.md §6.4.)

### An array literal of `null`s takes a `(&?T)[N]` type

`a = [null, null];` for `a: (&?N)[2]`, and the same literal as an argument,
a `return` value or a field value, compiles. So does `[&n, &m]` where a
`(&?N)[2]` is expected. 2.0 accepted these only in a declaration.

### Size parameters

A generic function can take an array's length as a parameter, written
`N: size`. `N` is used as an array dimension and reads as an `int` in the body.
A call gets it from an array argument, or else from the type the result is
stored into.

```turflang
fn<T, N: size> fill(value: T): T[N] {
    mut r: T[N];
    for i in 0..N {
        r[i] = value;
    }
    return r;
}

fn main(): int {
    mut zeros: int[8] = fill(0);   // N is 8
    return zeros[7];
}
```

When nothing gives `N` the call is E129; a size parameter on a struct, method
or operator, or one used as a type or assigned, is the new E150. (GEN-001.)

### `recover` and assignment

`recover` binds more loosely than `=` and `+=`: `v = f() recover run { ... };`
is `(v = f()) recover ...` and E066. Write `v = (f() recover run { ... });`.
The parser is unchanged; the reference now says so.

## Diagnostics

### Fixes in diagnostics, in every build (TDP-2-001)

When the compiler knows the exact edit that removes an error, the diagnostic
now ends with a `Fix:` block showing the corrected line. It needs no flag and
no model, and it is printed by the plain build and the `--no-smart` build alike:

```text
── error at line 6, col 27 [E040 · undeclared variable]

  I can't find anything named 'nmae'.

  Hint: It may be from the current file: 'name'

  6 │     printline("Hello, " + nmae + "!");
    │                           ^~~~ Here!

  Fix: replace 'nmae' with 'name'
  6 │     printline("Hello, " + name + "!");
    │                           ~~~~

  Run `turf --explain E040` for more details.
```

A fix is shown only after it has been checked: the compiler applies the edit to
a copy of the program in memory, analyses the copy (type checking, lint and
flow analysis) and prints the fix only if the original error is gone and no
error appeared that the original program did not have. Your files are never
changed. A fix is offered only for an error (never a warning), never inside the
standard library, and only when there is exactly one candidate: a typo with two
equally close names keeps its hint listing both and has no `Fix:`. At most ten
fixes are checked in one compile, and a clean compile does none.

These errors can carry a fix: E014 (misspelled keyword), E026 (unknown module
function), E029 (`x::m` on an instance becomes `x.m`), E030 (unknown import
symbol), E031 (unknown scope qualifier), E039 (unknown enum or error variant),
E040 (undeclared name), E041 (unknown function), E042 (unknown type), E046
(`static` on a constructor), E048 (`Type.m` becomes `Type::m`), E052 (static
method called through an instance), E054 (unknown method), E060 (assigning to
an immutable variable: its declaration's `immutable` becomes `mutable`, `immut`
becomes `mut`), E068 (unknown field), E087 (misplaced `pub`), E102 (missing
`;`) and E138 (a method of a generic struct without its type parameters). Error
codes are unchanged.

- **`--smart`:** the compiler's own fix comes first, and when an error has one
  the model is never called. The model is asked only when there is no compiler
  fix. Its suggestion is now labelled `[Model Suggestion]` (it was
  `[AI Suggestion]`). The `[Deterministic Fix] ... the model was never called`
  status line is gone: compiler fixes are no longer part of `--smart`.
- **`--smart-write-fix=<path>`** writes your program with every `Fix:` the
  compiler showed applied, in any build and without `--smart`; with `--smart`
  and no compiler fix, it writes the model's validated suggestion. The flag and
  the `turfc` interface version are unchanged.
- **Test authors:** a new marker, `// EXPECT-FIX: replace 'nmae' with 'name'`,
  pins a printed `Fix:` line. In a test that has one, `turf test` requires each
  marker to match a printed `Fix:` exactly, then applies the fixes and checks
  that the fixed program has fewer errors and none the original lacked. Tests
  without the marker behave as before. `TURF_FIX_DEBUG=1` prints a `[fix]` line
  for each error with fix-its the fix path looks at, and why its fix was not
  shown.
- **Tools that match diagnostic text** see the new `Fix:` lines. Diagnostic
  wording is outside the compatibility promise; the error codes are the stable
  part.

### Analysis

- **No false "dead store" or "never used" inside a `recover run { }`
  block.** A loop in the block, and `return`/`break`/`continue` in it, are
  part of the function's control flow, so a value carried round such a loop,
  or set before a `continue`, is read.
- **Writing one element doesn't make the array's earlier value dead.**
  `mut x: int[3]; x[0] = 1; x[1] = 2; print(x[0]);` no longer warns that
  `x[0] = 1` is never read, and `mut y = [1, 2, 3]; y[2] = 9;` no longer
  warns about `y`'s initializer.
- **A dead initializer says so.** `mut x: int = 0;` whose value every path
  overwrites before reading now reports "The initial value of 'x' is never
  read: every path assigns 'x' again before reading it.", with a hint to
  declare `mut x: int;`. 2.0 printed "Variable 'x' is assigned but the value
  is never read (dead store)", which read as if `x` itself were unused.
- **No false "infinite loop" warning** for a `while true` whose only `break`
  or `return` is inside a `recover` block, a `compare` arm or an `unsafe`
  block.

## Standard library

- **`arrays`** (`import arrays;`): `fill`, `generate`, `reversed` and `map` build
  whole fixed-size arrays. Each returns a new `T[N]` and changes nothing it is
  given: `mut zeros: int[1000] = arrays::fill(0);`. The length comes from the
  type the result is stored into, or from an array argument. It is not in the
  prelude. (Not the prelude's `array` module, whose helpers read an existing
  array.)

## Compiler crashes fixed

- An `if`/`else` whose branches differ only in an `INT_MIN` literal
  (`x = -9223372036854775808;` against `x = -7;`) crashed the compiler (found
  by turf-fuzz, `findings/crash/lint-branch-compare-int-min-literal` and
  `findings/crash/84e0cb6e67`).

## Tooling

- `scripts/dev/diagnostic_fix_coverage.py` counts, per error code, how many
  `fail_*` tests print a hint and a fix.
- turf-lsp shows the same warnings as `turf`: it runs the compiler's own
  analysis, so the fixes above reach the editor once turf-lsp is rebuilt
  against 2.1.0. No turf-lsp source change is needed.
