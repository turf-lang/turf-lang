TURF E081 -- POSSIBLE NULL DEREFERENCE:

CAUSE:
  A field of a nullable reference `&?T` ("a T, or nothing") was read where the
  compiler cannot prove the value is non-null. The `?` forces the null check
  to happen BEFORE the access. The proof lasts only as far as the check: if the
  variable is reassigned in between, or the check was in a different branch,
  the compiler asks again.

INCORRECT:
    struct Box { val: int }

    fn bad(b: &?Box): int {
        return b.val;            // b might be null here
    }

CORRECT:
    struct Box { val: int }

    fn good(b: &?Box): int {
        if b != null {
            return b.val;        // b is known non-null inside the check
        }
        return 0;
    }

FIX:
  Wrap the access in `if b != null { ... }`. A method call (`b.grow()`) needs
  the same check as a field read. A deferred use (`defer f(b.val);`) runs
  when the block ends: if the block later assigns `b`, move the use out of
  the `defer`. If the value can never be null, declare it
  `&Box` (no `?`) and no check is needed.

  Only a VARIABLE can be checked. If the message says "this '&?T' value" (the
  `&?T` is a field, a call result or a list element, as in `n.next.val`),
  store it in a variable first and check that:

    struct Node { val: int, next: &?Node }

    fn good(n: &Node): int {
        mut r: &?Node = n.next;
        if r != null {
            return r.val;
        }
        return 0;
    }

RELATED: E082 (converting `&?T` to `&T` with `to` without the same proof).
