# INVARIANTS.md — named, checkable invariants

Each row is a property the compiler is supposed to keep true, the thing that
**enforces** it (an assertion, a pass, a type-level construction — a test
alone is not enforcement), and whether it holds today.

Why named invariants rather than a list of fixed bugs: a bug fix protects one
input, an invariant protects a class. `docs/archive/ARCHITECTURE_OVERHAUL.md`
§19 derives this list from the handbook's `pitfall` blocks plus the audit —
each pitfall was asked "what property, structurally enforced, would have made
this impossible?"

**Status vocabulary**

| Status | Meaning |
|---|---|
| `holds` | true today, with the enforcing mechanism named and the claim checked |
| `holds (audited)` | recorded as fixed by the §19 audit; not independently re-verified here |
| `planned` | not true yet; the feature group that will make it true is named |

An invariant moves to `holds` only in the change record of the session that
built the thing enforcing it, and that session demonstrates it — per
`SESSION_PROTOCOL.md`, by compiling the input that would prove it wrong.

## Numbers and constants

| ID | Invariant | Enforced by | Status |
|---|---|---|---|
| **INV-NUM-1** | `bool` never participates in numeric coercion, implicit or explicit. | `typesCompatible()` Rule 4 | `holds (audited)` — deliberate, not an omission (F-NUM-4's neighbourhood; see FREEZE.md §6.2). |
| **INV-NUM-2** | A literal's value is never lost between the lexer and the type check, and an out-of-range value is a hard error at the point its destination type is fixed. | Arbitrary-precision literal representation (SEM-001, landed) + `TypeChecker::checkLiteralRepresentable()` at every type-fixing site (SEM-002, landed) + `TypeChecker::untypedLiteralAcquiresInt32()` at the same sites (OVH-005, landed) | `holds` — **SEM-002**, landed 2026-09-19; **OVH-005**, landed 2026-09-26, closed a gap SEM-002 left specifically for the `int32` destination. Verified live: `mut x: int = 999999999999999999999999999999999999999999999999;` is now `E076` (was: silent 64-bit truncation); `9223372036854775807 + 1` (both untyped literals) is `E076` too, via `tryFoldUntypedIntConstant()`'s arbitrary-precision fold, checked only at the point the result's destination is fixed (FREEZE.md §6.2 row 6). Narrower than the frozen ideal in two disclosed, now-**accepted-narrowing** ways (OVH-014, 2026-09-27, FREEZE.md §6.2 — recorded there as an explicit, requested exception rather than left as an unrecorded gap): a literal nested inside a larger literal-only arithmetic expression is rejected the moment it fails to fit int64 on its own, rather than deferred to "maybe the whole expression's final value still fits"; and an untyped literal assigned directly to `double` is checked against int64 representability first, rejecting a literal wider than int64 but exactly representable as a `double`. Both trace to the same root cause — Codegen truncates every literal through 64 bits before any arithmetic or `double` conversion runs, unconditionally, since SEM-001 (see SEM-002's change record, *Known pitfalls*, for the full mechanism). OVH-005: before that fix, `checkLiteralRepresentable()` ran at every type-fixing site as this row always claimed, but only AFTER `typesCompatible()` had already rejected an untyped literal reaching an `int32` destination outright (`mut n: int32 = 5;` failed with a plain type-mismatch error, `E066`, never reaching the representability check at all) — so this invariant's `int32` case did not actually hold before OVH-005 despite the row's unqualified "holds". `untypedLiteralAcquiresInt32()` now lets `typesCompatible()`'s mismatch be overridden specifically when the source is an untyped-literal-only expression and the destination is `int32`, so `checkLiteralRepresentable()` is reached and can do its job; a genuinely `int`-TYPED value narrowing to `int32` is unaffected and still rejected (FREEZE.md §6.2 row 4). |
| **INV-CONST-1** | All compile-time arithmetic uses checked, arbitrary-precision operations. | `evalConstExpr` on checked `APInt` ops (`sadd_ov`/`ssub_ov`/`smul_ov`/`sdiv_ov`) (SEM-001, landed) | `holds` — **SEM-001**, landed 2026-09-18. `ValueRange.cpp`'s `evalConstExpr` no longer performs `lv + rv` on plain `long long` (the confirmed signed-overflow UB this row was about) -- every binary op is now a checked 65-bit `APInt` operation, with `Overflow` (or a result that no longer fits `isSignedIntN(64)`) collapsing to the same conservative `nullopt`/"unknown" fallback this pass already used for division by zero. 65 bits, not literally unbounded, is a deliberate choice, not a shortfall: this pass's own domain (`std::optional<long long>`, array-index/loop-bound constant folding) is bounded to `long long` range by construction, so one guard bit above 64 is sufficient to detect every provable overflow in the values it ever handles -- see this fix's own comment in ValueRange.cpp for why. |
| **INV-NUM-3** | Runtime signed integer arithmetic on `int` never wraps silently: `+ - * <<` and unary negation trap (panic) on overflow; `/` (and, alongside its existing zero-check, `%`) traps on the one signed-division overflow case, `INT64_MIN / -1`. | `EmitCheckedIntArith`/`EmitCheckedIntNegate`/`EmitCheckedShl`/`EmitSignedDivOverflowGuard` (`CodegenCore.cpp`), called from `BinaryExprAST`/`UnaryExprAST` (`CodegenExpr.cpp`) and independently from `CompoundAssignmentExprAST`/`PostfixExprAST` (`CodegenVar.cpp`, which do not desugar through the former) | `holds` — **SEM-002**, landed 2026-09-19. Verified live for all four codegen paths (a plain expression, `+=`-family compound assignment, `x++`/`x--`, and unary `-`) and all five operators, plus a same-session regression pass confirming ordinary in-range arithmetic across every one of them does not trap (`tests/36_numeric_semantics/03_no_false_positive_overflow_traps.tr`). Scoped to `int` only — `int32` arithmetic overflow is not checked (SEM-002's own text names only `int`; not in this group's file list). `double` deliberately keeps wrapping to IEEE `inf`/`-inf` with no trap (FREEZE.md §6.2 row 7's asymmetry, on purpose). A *typed constant reference* whose value is compile-time-knowable now DOES get FREEZE.md §6.2 row 6's promised compile-time error, as of **OVH-014** (landed 2026-09-27) — `immut a: int = INT64_MAX; immut b = a + 1;` is `E076` at compile time, not this runtime trap — for the case its own change record scoped: a local `immut`/`export immut` of type exactly `int` whose initializer is itself a pure literal-arithmetic tree (`TypeChecker::tryFoldUntypedIntConstant()`'s existing recognized shapes), recorded on `VariableSymbol::HasFoldedIntConstant`/`FoldedIntConstant` (a plain decimal string, `ResolverSymbolBase.h` is LLVM-free) at the point the local's OWN declaration is checked, then read back by a later reference. Still falls through to this runtime trap, correctly (not a gap — no compile-time value exists to check): a `mut` variable of any kind, or an `immut` whose initializer is not literal-arithmetic (e.g. a function call, or a chain through a `mut`). |
| **INV-CAST-1** | `to`-cast legality is enforced in the TypeChecker, not Codegen — Codegen only ever receives a cast it can already dispatch on cleanly. | `TypeChecker::visitCast()`'s pairwise legality check (`TypeCheckerExpr.cpp`, mirrors `CastExprAST::codegen()`'s dispatch pair-for-pair) | `holds` — **SEM-002**, landed 2026-09-19 (Rule B1).
