## Why

`docs/planning/OVERHAUL_REMAINING_WORK.md` OVH-014 is a **DECISION** item:
four gaps between FREEZE.md's numeric-semantics text and the live compiler,
all found by SEM-002/TYPE-002's own *Known pitfalls* sections, none of them
a miscompile (each only rejects or traps earlier/more strictly than the
frozen wording promises). For each, the user chooses *implement* or *record
as an accepted narrowing*. Re-verified live before starting (all four
reproduced exactly as the handoff doc describes):

1. `immut a: int = 9223372036854775807; immut b = a + 1;` compiled and
   **trapped at runtime** — FREEZE.md §6.2 row 6 says "compile-time on typed
   constants: error."
2. A >int64 literal *leaf* nested inside a larger untyped-literal-arithmetic
   expression is rejected immediately, not deferred to whether the
   expression's *final* value fits — reproduced as `99999999999999999999 +
   1`, rejected citing `int` at the leaf.
3. An untyped literal wider than int64 assigned to `double` is rejected
   citing `int` representability, even when it would be exactly
   representable as a `double` — reproduced with `immut a: double =
   99999999999999999999;`.
4. `E079`'s "chain" is a dump of the entire instantiation cache
   (`Collector.cache().all()`, `src/Monomorphize.cpp`), not the actual
   request chain that hit the depth cap — confirmed by reading the four
   `GenericInstantiationDepthError` call sites directly.

Given the user's choice — follow the handoff doc's own recommendation —
this item: **implements** row 1, **records** rows 2 and 3 as accepted
narrowings in `FREEZE.md`, and confirms row 4 needs no new roadmap entry (it
is already `docs/development/ROADMAP_v2.0.0.md` LEC-005's own item 1, D25,
word-for-word — see *Unresolved questions*).

## Language semantics

### Old behaviour
```turf
fn main(): int {
    immut a: int = 9223372036854775807;
    immut b = a + 1;
    return b to int;
}
// compiled; panic: runtime check: Integer overflow (exit 134)
```

### New behaviour
```turf
// same program:
// ── error at line 3, col 5 [E076]
//   Integer literal is not representable in type 'int'.
//   The literal's value is 9223372036854775808.
```
Also closes the `export immut` twin of the same gap (SEM-002's own bullet
named both; this fix's `VariableExprAST` case does not distinguish them):
`export immut MAXV: int = 9223372036854775807; immut b = MAXV + 1;` is now
the same compile-time `E076`, was the same runtime trap before.

### Is this breaking?

No new rejection of a program that previously *ran to completion* — every
newly-rejected program previously panicked (`abort()`, exit 134) at runtime,
unconditionally, on every execution; this item only moves that same,
inevitable failure earlier, to compile time, with a more specific
diagnostic. A `mut` variable, or an `immut` whose initializer is not itself
pure literal arithmetic (a function call, a value chained through a `mut`),
is completely unaffected — still an ordinary runtime trap, correctly (no
compile-time value exists to check).

## Compiler architecture

- **Symbol tables** (`include/ResolverSymbolBase.h`): `VariableSymbol`
  gains two fields, `bool HasFoldedIntConstant` and `std::string
  FoldedIntConstant` — the local's exact decimal value, set only for an
  `immut` of resolved type exactly `int` whose initializer is a pure
  literal-arithmetic tree. A plain decimal string, not an `llvm::APSInt`,
  for the same reason `ResolverConstantSymbol::IntVal` (same file) is a
  string: this header is deliberately LLVM-free.
- **TypeChecker** (`src/TypeCheckerCore.cpp`):
  `tryFoldUntypedIntConstant()` gains a `VariableExprAST` case, tried after
  the existing `NumberExprAST`/`UnaryExprAST`/`BinaryExprAST` cases: reads
  `ResolvedConstant->IntVal` (an `export immut` of type `int`) or
  `ResolvedSymbol->FoldedIntConstant` (a local `immut` with
  `HasFoldedIntConstant` set), parses the decimal string back into an
  `llvm::APSInt` via the identical `getBitsNeeded()`-then-`APInt(bits,
  digits, 10)` pattern `CodegenConstantValue()` (`CodegenCore.cpp`) already
  uses for the same string-to-APInt conversion, and returns it — from that
  point on it folds through `+`/`-`/`*`/unary `-` exactly like a literal,
  no other code in this function needed to change.
- **TypeChecker** (`src/TypeCheckerDecl.cpp`): `visitVarDecl()`, immediately
  after `checkLiteralRepresentable()` passes (an error there `raise()`s —
  `longjmp`/`exit(1)` — so nothing after it runs on failure), for an
  `immut` of resolved type exactly `int`: calls
  `tryFoldUntypedIntConstant()` a second time on the SAME initializer and,
  if it folds, writes the result's decimal string onto
  `Node.ResolvedSymbol` — the identical `VariableSymbol` object every later
  reference to this local's `VariableExprAST::ResolvedSymbol` also points
  at (same `shared_ptr`), so the value becomes visible immediately.

No Resolver, Codegen, or Monomorphizer changes — this is a purely
TypeChecker-side compile-time-detection improvement; the runtime-checked
codegen path (`EmitCheckedIntArith`, INV-NUM-3) is completely untouched and
still runs for every case this fix does not newly catch.

## Removed assumptions

- **"A reference to an `immut` local or `export immut` constant is opaque
  to `tryFoldUntypedIntConstant()` — only a literal expression tree folds."**
  False as of this item, for the scoped case (type exactly `int`,
  literal-arithmetic-foldable initializer). A future session extending this
  further (e.g. an `immut` chained through a non-`int` type, or an
  initializer that calls a `const`-evaluable function once such a thing
  exists) should know the pattern to extend is `VariableSymbol`'s two new
  fields plus `tryFoldUntypedIntConstant()`'s `VariableExprAST` case — not a
  parallel mechanism.
- **"`ResolverSymbolBase.h`'s LLVM-free constraint means a symbol can never
  carry an exact-value compile-time constant."** False — a plain decimal
  string (`ResolverConstantSymbol::IntVal`'s own precedent, now mirrored by
  `VariableSymbol::FoldedIntConstant`) carries it without an LLVM
  dependency; the LLVM-specific reconstruction step lives entirely in the
  TypeChecker/Codegen files that already depend on LLVM.

## Known pitfalls

- **This only folds a LOCAL `immut`'s or `export immut`'s DIRECT
  initializer, once, at its own declaration.** It does not re-derive a
  value transitively through anything other than
  `tryFoldUntypedIntConstant()`'s own existing recognized shapes (a literal,
  unary `-`, or `+`/`-`/`*` of two foldable operands) — `immut a: int =
  someFunction();` or `immut a: int = someMutVar;` never sets
  `HasFoldedIntConstant`, correctly (there is no compile-time value to
  record), and a later reference to `a` still only gets the runtime trap.
  This is by design, not a narrower-than-intended implementation: the
  frozen text's "typed constants" only ever meant compile-time-KNOWABLE
  ones.
- **`VariableSymbol::FoldedIntConstant` is never cleared once set.** Not a
  live bug (a `VariableSymbol` is created once per declaration and never
  reused for a different variable), but a future session adding any kind of
  symbol-table entry reuse/pooling should know this field would need
  resetting.
- **The two-field-storage design (`bool` + `std::string`) instead of
  `std::optional<std::string>` mirrors `ResolverConstantSymbol`'s own
  existing shape exactly** (that struct also uses a bare `IntVal` string
  with no separate "is this the active variant" flag beyond `Type`) —
  chosen for consistency with the precedent this item explicitly follows,
  not because `std::optional` was unavailable or wrong.
- **Recording rows 2/3 as accepted narrowings in `FREEZE.md` does not make
  them permanent** — nothing in `FREEZE.md` §6.0 says an accepted narrowing
  can never later be implemented; it only says implementing something
  DIFFERENT from what's written needs the same explicit-request process.
  Fully realizing either row would need Codegen-side exact constant folding
  (SEM-002's own *Known pitfalls*, bullets 2 and 3, spell out exactly what
  that would take) — genuinely more machinery than a TypeChecker-only fix,
  which is why they were not bundled into this item's row-1 implementation.
