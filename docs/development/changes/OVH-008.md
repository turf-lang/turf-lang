## Why

The implicit `&T → &?T` widening (FREEZE.md §6.6) never worked when the
pointee is, or contains, an open generic type parameter. Verified live
against `refactor/architecture` (the 2026-09-26 closure audit):

```turf
struct Node<T> { val: T, next: &?Node<T> }
fn<T> len(n: &?Node<T>): int { /* walk */ }
fn main(): int { mut a: Node<int> = Node::default(); return len(&a); }
// error: No overload of 'len' matches argument types (&Node<int>).
//   candidate: len(&?Node<T> n) -> int
```

The non-generic equivalent (`fn len(n: &?Node)`, `len(&a)`) already
compiled.

**Root cause.** `typesCompatible()` (`Types.cpp`) has a "candidate-matching
generic-parameter leniency" block for **unwrapped** type pairings: a bare
`T` matches any concrete type, `T[]` matches any `concrete[]`, `T*`
matches any concrete pointer, and — the specific rule this bug needed —
two `GenericType`s of the same base name are compatible when compared
argument-by-argument with a per-argument generic-parameter skip (so
`Node<int>` already correctly matches `Node<T>`, directly, unwrapped).

Separately, Rule 2.5/2.6 — the actual rules that let a `&T`/`&?T` argument
widen into a target pointer-shaped parameter — compare the two POINTEES
with plain `isEquivalent()` (structural `getName()` equality), which never
runs any part of `typesCompatible()` itself and therefore never got the
leniency above. A pointee shaped `Node<T>`/`Node<int>` — exactly the shape
`&?Node<T>`/`&Node<int>` wrap — never matched: `"Node<int>" ==
"Node<T>"` is false by plain string comparison, with no generic-parameter
awareness at all.

`TypeCheckerCall.cpp`'s `collectGenericSubstitution()` (the OTHER function
the plan named as a candidate location) was investigated and found
**already correct**: its pointer-wrapper branch `dynamic_cast`s to the
base `TurfPointerType`, which `&T`/`&?T`/`T*` all satisfy via inheritance,
so it already recurses into a reference's pointee the identical way it
recurses into a raw pointer's — confirmed by inspection and by the fix
below working end-to-end with no changes to that function at all. The
Resolver's `substituteTypeParams()` and the Monomorphizer's
`substituteConcreteTypes()` were checked the same way (per the plan's own
"check all five [STD-003 Fix 2] names" instruction) and are also already
correct — both have explicit `TurfReferenceType`/`TurfNullableReferenceType`
branches (added by LANG-002) that recurse into the pointee, and the
pointee's own `GenericType` branch (added by TYPE-002) recurses into each
type argument — so a monomorphized clone's `&?Node<T>` parameter already
substitutes correctly to `&?Node<int>` once a candidate is actually
accepted. The bug was isolated entirely to `typesCompatible()`'s Rule
2.5/2.6 pointee comparison — the one and only place standing between
"the pairing would match if unwrapped" and "the pairing is ever offered
the chance to be unwrapped at all."

## Language semantics

### Old behaviour
`&ConcreteInstantiation<...>` (a call site's own, always-non-null
argument) failed to match a declared `&?GenericBase<T>`/`GenericBase<T>*`
parameter whenever the pointee was a generic instantiation — regardless of
whether the call went through a free function or a struct method.

### New behaviour
The same pairing now matches, and `T` substitutes to the concrete
instantiation's own type arguments correctly (verified live: a real,
walked linked list of `Node<int>`, not just a type-check).

### Is this breaking?
No. Only removes a false rejection; no previously-accepted program is
affected — the fix narrowly extends ONE pointee-comparison helper with the
same leniency this file already grants everywhere else; it does not touch
which widening DIRECTIONS are permitted (see *Non-goals*/*Known pitfalls*).

## Compiler architecture

- **Types** (`src/Types.cpp`) — new static helper
  `referencePointeeGenericMatch(const TurfType *, const TurfType *)`,
  defined just above `typesCompatible()`: exact match (`isEquivalent()`),
  OR either side is a bare `TurfGenericParamType`, OR both sides are
  `GenericType`s of the same base name with each type-argument pair
  recursively matching by this same predicate. Rule 2.5 (`&T` → raw
  pointer) and Rule 2.6 (`&?T` → raw pointer) now call this instead of
  `isEquivalent()` directly for their pointee comparison.
- **TypeChecker, Resolver, Monomorphizer** — no changes; all three were
  already correct for this shape (verified live, see *Why*).

## Removed assumptions
- **"Rule 2.5/2.6's pointee comparison only ever needs exact structural
  equality."** True for every previously-tested pointee shape (a plain
  struct, a primitive, another pointer) but not for a pointee that is
  itself a still-open generic instantiation — the leniency this file
  already grants a bare/unwrapped generic pairing has to be reachable from
  *inside* a reference-wrapper comparison too, not just at the top level.
- **A wholesale swap of `isEquivalent()` for a recursive `typesCompatible()`
  call was considered and rejected**, not merely overlooked: `Types.cpp`'s
  own Rule 2.5 doc comment already explains why (it would also ride along
  on the numeric-widening rule further down the same function, letting
  `&int` implicitly widen into `double*` — unsound, since a reference's
  pointee type is never itself widened, only its pointer-kind/nullability
  is). `referencePointeeGenericMatch()` is deliberately narrower: it only
  ever recurses through the two shapes an open type parameter can actually
  appear in a pointee (bare, or nested one level inside a matching
  `GenericType`), never through the general numeric/struct-widening rules
  the rest of `typesCompatible()` has.

## Known pitfalls

- **A generic method body doing arithmetic directly on its own struct's
  open type parameter is a separate, pre-existing, unrelated restriction**
  (the same one OVH-007's change record documents) — a first draft of the
  positive test included `fn<T> sumOf(n: &?Node<T>): T { ... total = total
  + cur.val; ... }`, which fails with `"cannot apply '+' to 'T' and 'T'"`
  inside the template's own check, nothing to do with this item's fix
  (F-OP-1's exact-match requirement; `+` cannot resolve against a bare,
  still-open `T`). Removed from the test in favor of `lenOf`/`lengthFrom`,
  which only walk the chain and never operate on `T`'s own value
  arithmetically.
- **The fix is narrowly scoped to Rule 2.5/2.6's pointee comparison only**
  — it does not touch which of the two rules fires for a given
  direction, or add any new widening direction. `&?T → &T` (narrowing)
  was never reachable through either rule before this fix (Rule 2.5 only
  matches a `TurfReferenceType` source; Rule 2.6 only widens into a target
  that is neither reference kind) and remains unreachable after it —
  confirmed live via the new negative test, not merely reasoned about.
- **`referencePointeeGenericMatch()` recurses through `GenericType`
  arguments only** — a pointee nested behind an intermediate pointer or
  array wrapper one level *inside* the reference (e.g. `&(T*)`, an
  unusual but not-yet-seen shape) is not covered by this helper and would
  need its own branch if it ever comes up live; not added speculatively.
