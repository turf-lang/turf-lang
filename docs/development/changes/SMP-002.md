## Why

`ARCHITECTURE_SIMPLIFICATION.md` §1 (and `ROADMAP_v2.0.0.md`'s SMP-002
entry) diagnosed this compiler's notion of "what a generic type parameter
looks like, and where it might be hiding" as implemented independently, by
hand, in at least seven recursive functions across four files:
`Resolver::substituteTypeParams`, `typesCompatible()` (Rules 1/3/4),
`collectGenericSubstitution()`/`collectGenericParamNameOrder()`,
`Monomorphize::substituteConcreteTypes()`, `visitCast`'s legality bypass,
and `isOrWrapsGenericParam()`/`isFullyConcreteType()`. Three were
independently, silently incomplete, discovered only by hitting them in
practice across TYPE-002's 8 sessions and everything built since (STD-003
alone found three in one session). Phase 2 of the roadmap (pattern
matching, payload types, generic operators) adds more call sites that each
need this same "walk a type looking for `T`" logic — unifying it first
means adding a new type shape once, not seven times.

## Language semantics

No user-visible language change. This is a pure internal refactor: every
program that compiled and ran correctly before this session still does,
with two exceptions that only make PREVIOUSLY-BROKEN programs compile
correctly now (see *Removed assumptions* — both are additive fixes, not
behaviour changes to anything that worked before).

### Old behaviour / New behaviour / Is this breaking?

Not applicable in the usual sense — see *Removed assumptions* for the two
concrete cases where behaviour actually changed (both bug fixes, not
breaking changes: nothing that compiled and ran correctly before now
behaves differently or is rejected).

## Compiler architecture

New file: **`include/TypeWalk.h`** / **`src/TypeWalk.cpp`** (added to
`CMakeLists.txt`'s `turfcore` target). Five free functions, all exhaustive
over the same set of `TurfType` subclasses (pointer, reference, nullable
reference, array, generic-argument list, error-union success type,
func-type parameter/return list):

- `containsOpenParam(Ty, ParamScope, IsKnownNamedType?)` — a predicate,
  parameterized by how far to look (`Bare` / `ThroughWrappers` /
  `ThroughGenericArgs`), since the functions it replaces deliberately did
  not all look equally far.
- `substitute(Ty, SubstMap)` — a name → replacement-type rewrite, serving
  both the declaration direction (`Resolver::substituteTypeParams`) and the
  instantiation direction (`Monomorphize::substituteConcreteTypes`) with
  one implementation.
- `unify(Pattern, Concrete, SubstMap&)` — the call-site binder
  `collectGenericSubstitution()` used to be.
- `collectParamOrder(Pattern, Order)` — the companion order-recovery walk
  `collectGenericParamNameOrder()` used to be.
- `collectOrderedFieldSubstitution(Pattern, TypeArgs, SubstMap&,
  IsKnownNamedType?)` — the generic-struct field-scan technique
  `TypeCheckerCall.cpp` had duplicated verbatim in two places
  (`visitMethodCall`, `visitFieldAccess`).

**Resolver** (`ResolverCore.cpp`) — `substituteTypeParams()` is now a
6-line wrapper: builds `{name -> TurfGenericParamType(name)}` and calls
`TypeWalk::substitute()`.

**TypeChecker** (`TypeCheckerDecl.cpp`) — `isOrWrapsGenericParam()` and
`isFullyConcreteType()` are now thin wrappers calling
`TypeWalk::containsOpenParam()` with `ThroughWrappers`/`ThroughGenericArgs`
respectively, both supplying `GlobalSymbolTable->LookupType()` as the
`NamedType` fallback classifier.

**TypeChecker** (`TypeCheckerCall.cpp`) — `collectGenericSubstitution()`/
`collectGenericParamNameOrder()` deleted outright; every call site now
calls `TypeWalk::unify()`/`TypeWalk::collectParamOrder()` directly. Both
generic-struct field-substitution "Scan" lambdas (`visitMethodCall`,
`visitFieldAccess`) replaced by `TypeWalk::collectOrderedFieldSubstitution()`
calls. `orderedTypeArgs()` (unrelated helper, just consumes the walkers'
output) is unchanged.

**TypeChecker** (`TypeCheckerExpr.cpp`) — `visitCast()`'s
`EitherSideIsGenericParam` bypass now calls
`TypeWalk::containsOpenParam(..., ParamScope::Bare)` instead of an inline
bare `dynamic_cast`.

**Types** (`Types.cpp`) — every bare `dynamic_cast<const
TurfGenericParamType *>` inside `typesCompatible()`'s Rule 1 (top-level,
array-element, pointer-pointee, `GenericType`-argument-position leniency
checks) and `referencePointeeGenericMatch()` now calls
`TypeWalk::containsOpenParam(..., ParamScope::Bare)`. `typesCompatible()`'s
own numeric-widening/null/pointer-coercion/enum-isolation/exact-name-match
logic is UNCHANGED and untouched — those are TypeChecker-specific
compatibility rules, not "does this contain/match an open generic
parameter," and deliberately stay outside `TypeWalk.h` (see the header's
own top-of-file doc comment).

**Monomorphizer** (`Monomorphize.cpp`) — `substituteConcreteTypes()` is now
a 1-line wrapper around `TypeWalk::substitute()`.

## Removed assumptions

**Two REAL, previously-latent bugs were found and fixed while unifying
these walkers — not just a rename.** This is exactly the pattern
`ARCHITECTURE_SIMPLIFICATION.md` §1 predicted ("three of the seven were
independently, silently incomplete").

1. **`collectGenericParamNameOrder()` had no `GenericType` case at all** —
   an asymmetry with its sibling `collectGenericSubstitution()`, which
   always did. Confirmed live: a generic free function taking a
   generic-struct-typed parameter (`fn<T> unwrap(b: Box<T>): T`) called at
   two different type arguments (`unwrap(boxOfInt)`, `unwrap(boxOfDouble)`)
   recovered an EMPTY canonical-order list for that parameter either way
   (even though the SEPARATE `Subst` map, built by
   `collectGenericSubstitution()`, correctly held `T=int`/`T=double`), so
   both call sites' instantiation requests collapsed to the identical
   bogus key `unwrap<>` (no type arguments) — one monomorphization cache
   entry wrongly serving two call sites that need two different clones.
   Reproduced live against the pre-unification code (temporarily removing
   the new `TypeWalk::collectParamOrder()`'s `GenericType` case): `turf
   --dump-instantiations` reported a single merged `unwrap<>  (2 call
   sites)` instead of two separate entries, and the merged clone failed to
   compile at all (`Cannot access field on non-struct type` on `b.val`).
   `TypeWalk::collectParamOrder()` now has a `GenericType` case (mirroring
   `unify()`'s, which always had one), closing this for good. Regression
   test: `tests/38_monomorphization/30_generic_struct_typed_param_order.tr`.
2. **`Resolver::substituteTypeParams()` had no `TurfErrorUnionType` case**
   — `Monomorphize::substituteConcreteTypes()` always did. A generic
   declaration's own `!T` return/parameter type never got its `T` marked
   as an open `TurfGenericParamType` at DECLARATION time (only at each
   instantiation site, via the other function). This was usually masked in
   practice by `isOrWrapsGenericParam()`'s `NamedType`-fallback
   classification and `typesCompatible()`'s Rule 1 (both tolerate the
   stale pre-substitution representation), so no user-visible failure was
   found for it — but it is exactly the class of gap this unification
   exists to close, and the shared `TypeWalk::substitute()` now has the
   case, so both directions are exhaustive over the identical set of type
   shapes. Covered by
   `tests/38_monomorphization/31_generic_walker_type_shapes.tr`'s
   `wrapFallible<T>` case.

**A separate, already-fixed gap was verified closed, not re-fixed**: the
`self.v to int` field-access cast-legality gap `28_generic_cast_legality.tr`
used to document as a deliberately-deferred, known limitation (STD-003's
Fix 3, "the narrower, still-open gap this fix does NOT reach") is confirmed
fixed as a side effect of OVH-006 (landed 2026-09-26, before this session)
— `GlobalSymbolTable`'s registered struct type now carries the real
`TurfGenericParamType` for a generic field, not a permanently-stale
`NamedType`. The test file's stale trailing note was rewritten and a live
assertion for this case added, per this project's "verify claims live"
rule (`AGENTS.md`) — it was documented as broken but wasn't, any more.

## Known pitfalls

- **`ParamScope` is not a "pick the most correct one" enum.** `Bare` exists
  because `typesCompatible()`'s per-position leniency checks and
  `visitCast`'s bypass never unwrapped anything — using `ThroughWrappers`
  there instead would be a genuine, silent behaviour WIDENING (e.g. a `T*`
  operand would newly bypass cast-legality checking it doesn't today).
  Always match the scope to what the ORIGINAL call site actually did, not
  to what "looks more thorough."
- **`collectOrderedFieldSubstitution()` consumes `TypeArgs` by
  first-occurrence order, not by matching a parallel `Concrete` type.**
  Unlike `unify()`, there is nothing to structurally validate against — a
  struct whose fields mention its OWN type parameters in a different order
  than the declaration's parameter list would still "work" by accident
  today (this was already true of the two hand-rolled `Scan` lambdas it
  replaces; not a new limitation, just inherited).
- **`TypeWalk::substitute()`'s `TurfErrorUnionType` case is new for
  `Resolver::substituteTypeParams()`'s call path specifically.** If a
  future consumer of a generic declaration's DECLARED (not yet
  instantiated) `!T` signature starts caring about the difference between
  `TurfGenericParamType` and stale `NamedType` in a way `isOrWrapsGenericParam()`'s
  fallback doesn't already paper over, re-check this fix's own test
  (`31_generic_walker_type_shapes.tr`) still exercises the actual failure
  mode, not just the happy path.

## Unresolved questions

**`CodegenCore.cpp`'s own, separate `getExprType()` type-inference engine
independently reimplements the identical pattern at (at least) three more
sites, found live during this unification, deliberately NOT migrated:**

- A free-function call-site return-type recovery (`Unify` lambda, ~line
  977) — mirrors `TypeWalk::unify()` exactly, but keyed on raw
  `const TurfType *` (from `getExprType()`, non-owning) rather than
  `TurfTypePtr`.
- Two generic-struct field-substitution scans (`Scan`/`ApplySubst` lambda
  pairs, ~lines 1253 and ~1410/1452) — mirror
  `TypeWalk::collectOrderedFieldSubstitution()` exactly, same raw-pointer
  friction.

These were NOT in SMP-002's own `Subsystems` list (`ROADMAP_v2.0.0.md`:
"Types, Resolver, TypeChecker, Monomorphizer... Runtime/stdlib/tooling
none" — Codegen is absent), and `ARCHITECTURE_OVERHAUL.md` §25 item 4
explicitly cautions against casually touching Codegen's separate
`getExprType()` engine ("a large refactor with no user-visible benefit").
Migrating them would need either a raw-pointer-typed sibling API in
`TypeWalk.h` or wrapping each call site's raw pointers in non-owning
`shared_ptr`s (the existing code already does this once, at the `Unify`
lambda's own `Subst.emplace()` call) — a small, mechanical, but genuinely
separate follow-on. **Recommendation**: a future session (its own ID, e.g.
continuing the `SMP-0NN` numbering `ROADMAP_v2.0.0.md` Part III already
proposes for post-2.0 Simplification work) should do this specifically,
not as a drive-by inside an unrelated Codegen change. `check_boundary.sh`
check 6 names `CodegenCore.cpp` as an explicit, tracked exception so this
gap stays visible rather than silently drifting out of INV-GEN-2's stated
scope.
