## Why

The compiler had no module-level optimization at all. `main.cpp`'s Phase 5
was a fixed `legacy::FunctionPassManager` running five hardcoded passes
(mem2reg, instcombine, reassociate, GVN, simplifycfg) unconditionally on
every compile, with no `-O` flag, no way to see across functions, and
therefore no way to delete a whole unused one. Measured baseline
(`ARCHITECTURE_OVERHAUL.md` §1.9, re-verified live on this machine before
touching anything, see *Tests*): an empty `main` compiled to a
**29,968-byte** binary carrying **84 unused `turf_*` functions** — every
function of every imported module (six prelude modules auto-imported into
every file, plus whatever the program itself imports) got emitted and
linked in whether the program used it or not. `emitObjectFile()` also built
its own throwaway `TargetMachine` from a hardcoded host triple and
`CPU="generic"`, invisible to the optimizer (which never saw a
`TargetMachine` at all) and with no way to target anything else.

This also sets the baseline TYPE-002's monomorphization code-growth will be
judged against — monomorphizing without `GlobalDCE` running first would
look far worse than it actually is.

## Language semantics

### Old behaviour

No `-O` flag existed at all; every compile ran the same fixed five-pass
sequence.

### New behaviour

```
turf prog.tr -O0   # verify + AlwaysInliner only — fast builds, faithful -g later
turf prog.tr -O1   # PassBuilder::buildPerModuleDefaultPipeline(O1) — LLVM's REAL O1, not a hand-picked subset
turf prog.tr        # -O2, the default — PassBuilder::buildPerModuleDefaultPipeline(O2)
turf prog.tr -O3    # …(O3)
turf prog.tr -Os    # …(Os), tuned for size
turf prog.tr --target=<triple> -mcpu=<cpu>   # cross-target codegen (see Known pitfalls — linking is not)
```

`-O1` initially shipped as a small hand-picked ~8-pass subset (the
pre-OPT-001 5-pass sequence ported to the new PM, plus `EarlyCSE`, plus
`Internalize`+`GlobalDCE`) rather than LLVM's own `default<O1>`. Measured
live via `opt -passes="default<O1>" -print-pipeline-passes`: LLVM's real
`-O1` runs ~109 pass invocations, not ~8 — widened to the real pipeline by
explicit request once that gap was measured and reported; see *Compiler
architecture* and commit `9db30e4`.

An unrecognized level (`-O4`, `-Ox`) is a hard compile error, never a
silent fallback. No language semantics changed — this section is entirely
about the CLI surface.

### Is this breaking?

No, to Turf source code. `-O2` is the frozen default (F-OPT-1), so a
program that compiled and ran correctly before this change compiles and
runs identically now with no flags at all — verified live per-program
below (*Tests*). The one behavioural change visible to a user is variance
in **wall-clock/CPU-tick timing measurements**, which was never a language
guarantee: see *Known pitfalls* for the one existing test this broke and
why that is expected, not a regression.

## Compiler architecture

- **Driver (`src/main.cpp`)** — the only file touched.
  - New `OptLevelKind` enum (`O0`/`O1`/`O2`/`O3`/`Os`) and three new
    `CompilerOptions` fields: `OptLevel` (default `O2`), `TargetTriple`
    (`--target=`, empty = host), `MCPU` (`-mcpu=`, empty = `"generic"`,
    unchanged from before).
  - `createTurfTargetMachine(opts, M)` — the ONE `TargetMachine`
    construction, replacing two independent ones (Phase 5 previously had
    none at all; `emitObjectFile()` built its own). Derives
    `CodeGenOptLevel` from `-O` (`None`/`Less`/`Default`/`Aggressive`, `Os`
    shares `Default` — LLVM has no size-tuned `CodeGenOptLevel`; size
    tuning lives entirely in the IR pipeline via
    `OptimizationLevel::Os`). Sets the module's target triple and data
    layout, which previously only happened inside `emitObjectFile()`,
    strictly AFTER Phase 5 optimization had already run — so the optimizer
    used to run against a module with NO target triple/data layout at all.
    Building the `TargetMachine` first and threading it into both phases
    means SROA/vectorization-adjacent passes now see the real target's
    pointer size/alignment. Not an observable-behaviour change (F-OPT-1):
    it is the same host target `emitObjectFile()` always linked against.
  - `runOptimizationPipeline(M, Level, TM)` — the new pipeline itself, one
    `switch` arm per level:
    - `O0`: `PassBuilder::buildO0DefaultPipeline(OptimizationLevel::O0)`
      verbatim — real LLVM API, not a hand-assembled equivalent, so it
      stays correct if a future LLVM release changes what "O0" requires.
    - `O1`/`O2`/`O3`/`Os`: one shared branch. `InternalizePass` run FIRST,
      in its own `ModulePassManager::run()`, strictly BEFORE
      `PassBuilder::buildPerModuleDefaultPipeline(Level)` — see *Known
      pitfalls* for why this ordering is load-bearing, not cosmetic.
      `O1` originally had its own hand-picked ~8-pass branch (the old
      5-pass sequence ported to the new PM, plus `EarlyCSE`, plus a
      separate `InternalizePass`+`GlobalDCEPass` run) instead of calling
      `buildPerModuleDefaultPipeline(O1)` like the other three levels —
      folded into the shared branch (commit `9db30e4`) once measuring
      LLVM's real `default<O1>` pipeline (~109 pass invocations via `opt
      -passes="default<O1>" -print-pipeline-passes`, vs. the ~8 the
      hand-picked list ran) showed a real gap between what "`-O1`" meant
      in this compiler and what it means everywhere else. This is an
      ordinary engineering judgement, not a frozen decision (§6.10/F-OPT-1
      only pin the CORRECTNESS contract — identical observable behaviour
      across levels — never the literal pass list per level), so revising
      it did not require stopping to ask under FREEZE.md §6.0; it was
      still made only once explicitly requested rather than on this
      session's own initiative.
    - The must-preserve predicate for `InternalizePass` in every branch is
      `GV.getName() == "main"` and nothing else — see *Removed
      assumptions* for why that is the whole set.
  - `emitObjectFile()` no longer builds a `TargetMachine`; it takes one by
    reference from the caller. The legacy `legacy::PassManager` used for
    `TM.addPassesToEmitFile()` (MC-layer object emission) is UNCHANGED —
    that is LLVM's own backend codegen entry point and still requires the
    old PM in this LLVM version; OPT-001 only replaces the IR-level
    optimization pipeline, not backend instruction selection.
  - CLI: `-O0`/`-O1`/`-O2`/`-O3`/`-Os`, `--target=<triple>`,
    `-mcpu=<cpu>` parsed in `parseArgs()`; usage string updated.
- **Resolver / TypeChecker / Codegen** — unchanged, and structurally CANNOT
  see the optimization level: neither receives `CompilerOptions` at all
  (verified live, `grep -rln "OptLevel\|opts\." src/Codegen*.cpp
  include/Codegen*.h` — no match). Every language-mandated runtime check
  (array bounds, division/modulo by zero) is emitted unconditionally by
  Codegen regardless of `-O`, satisfying F-OPT-2 by construction rather
  than by a `-O0`-only code path someone could accidentally extend.

## New invariants

**INV-OPT-1**: optimization levels never change a program's observable
behaviour (stdout + exit code). Enforced by `scripts/opt_levels_smoke.sh`
(a deterministic program set diffed byte-for-byte across all five levels)
plus the structural fact that Codegen never receives an opt level, so no
runtime check can be gated on one. Added to `INVARIANTS.md`, status
`holds`.

## Removed assumptions

- **"Every `turf_*` function that got emitted also got linked in and kept
  around."** No longer true at `-O1` and above — `InternalizePass` +
  `GlobalDCEPass` now delete any function unreachable from `main` within
  this translation unit. A future pass that assumes "a function existing
  in the final binary" implies "something calls it" needs to account for
  this; conversely, nothing should assume the OPPOSITE either — `-O0`
  still ships every emitted function, unreferenced or not, exactly as
  before, specifically so `-g` (TOOL-001, not yet landed) has a faithful,
  undeleted function to attach debug info to.
- **"The module has no target triple/data layout until `emitObjectFile()`
  sets one."** True before this change (Phase 5 ran on a triple-less
  module), false now — `createTurfTargetMachine()` sets both BEFORE
  optimization runs, for the non-`--emit-llvm` path. A future pass reading
  `TheModule->getDataLayout()` during Phase 5 or later can now assume it is
  the REAL target's layout, not LLVM's built-in default. The
  `--emit-llvm` path is the one deliberate exception — see *Known
  pitfalls*.
- **"`g_RequiredLibs` (the set of `-l<name>` link flags collected from
  `extern from "libname" fn`) is a source of Turf SYMBOL names to
  preserve."** It is not — it is external C LIBRARY names, not Turf
  function names, and has nothing to feed an `InternalizePass`
  must-preserve predicate with. §8's own OPT-001 text names it as the
  starting point for the must-preserve set; this session determined live
  that it is not usable for that purpose and used `{main}` alone instead
  (see *Compiler architecture* and the next bullet). A future session
  should not re-derive `g_RequiredLibs` as a preserve-set source without
  re-deriving why it doesn't apply.
- **"A function whose address is taken and passed to an `extern fn`
  callback needs external linkage to survive."** False, and worth being
  explicit about since the §8 risk text raises exactly this scenario.
  Internal linkage only affects whether the LINKER can find a symbol BY
  NAME from a DIFFERENT translation unit; TurfLang never separately
  compiles (every import is re-parsed/re-codegenned into the one module
  being built, §27 D7), so nothing outside this module ever looks up a
  Turf function by name. A function pointer passed to a C callback is a
  real in-IR `Function*` USE regardless of linkage, which is what keeps it
  alive through `GlobalDCE` — internalizing it changes nothing about that.
  Verified live against `showcase/llvm_ffi_selfhost_demo.tr` (§8's own
  named risk case) at every level (see *Tests*).

## Known pitfalls

- **Running `InternalizePass` AFTER `buildPerModuleDefaultPipeline()`
  instead of before deletes nothing.** `buildPerModuleDefaultPipeline()`
  runs its own internal `GlobalDCE`, but `GlobalDCE` only deletes a
  definition that is BOTH unreferenced AND not externally visible. Every
  `turf_*` function has EXTERNAL linkage coming out of Codegen unless
  something has already internalized it — Codegen itself only internalizes
  `main`'s siblings implicitly via `Function::InternalLinkage` at creation
  time for ordinary functions (see next bullet), but the module-level
  Internalize pass this session added is the thing meant to catch anything
  that slips through that. Getting the ORDER wrong (default pipeline
  first, Internalize after) was confirmed live while implementing this:
  the resulting `-O2` binary was NOT smaller than `-O0`'s at all, because
  by the time Internalize ran, `buildPerModuleDefaultPipeline`'s own
  `GlobalDCE` had already run and found nothing eligible.
- **Codegen already gives every non-`main` function `InternalLinkage`**
  (`CodegenFunc.cpp`, the `Name == "main"` branch around line 240) — this
  session's `InternalizePass` is therefore mostly a no-op in today's
  compiler, not the thing single-handedly making dead functions
  deletable. It is still the architecturally correct piece to add: (1) it
  is what the design in §8 explicitly calls for, as a structural guarantee
  independent of Codegen's own linkage choice; (2) the one place Codegen
  DOES emit a function with a body AND external linkage besides `main` is
  `ExternFuncDeclExprAST::codegen()`'s Windows-only `PlatformExternForward`
  wrapper path (e.g. `malloc_usable_size` → `_msize`) — untested on this
  Linux dev machine, but if that wrapper is ever unused, `InternalizePass`
  (not Codegen's own linkage choice) is what makes it deletable. A future
  session should NOT remove the explicit `InternalizePass` call on the
  theory that "Codegen already does this" — it does, for the common case,
  but the explicit pass is the actual enforced invariant, not an
  accident of the current Codegen implementation.
- **A timing-measurement test can look like a flaky test but is actually a
  correct optimizer doing exactly what it's supposed to.**
  `tests/29_time_stdlib/03_clock_ticks_and_elapsed_ms.tr`'s original busy
  loop (`while i < 500000000 { i = i + 1; }`, `i` never read afterward) is
  the textbook input for `LoopDeletion`/`IndVarSimplify` — a real `-O2`
  pipeline is CORRECT to delete it entirely, because it provably has no
  observable effect. The old ad hoc 5-pass pipeline never included loop
  deletion, so the loop "worked" by accident, not by any guarantee the
  test's own assertions ever depended on. Confirmed live: the assertion
  failure (`elapsed_ms() must be positive`) reproduced on the FIRST attempt
  at real `-O2`, before this session had done anything wrong — it is what
  `-O2` is supposed to do to that exact code shape. The fix was NOT "keep
  the loop pure and hope the optimizer doesn't get smarter" (it will, and
  the test would break again on some future LLVM upgrade); it was to give
  the loop a genuine side effect (a periodic opaque extern call) that
  makes its execution structurally impossible to prove unobservable. A
  future session adding a NEW timing-sensitive test should assume a real
  optimizer WILL try to delete anything with no observable effect and
  design the test to have one, rather than relying on the optimizer being
  too weak to notice.
- **`--target` genuinely cross-compiles OBJECT CODE, but not a working
  binary, and that is by design, not a bug in this change.** `linkObject()`
  always execs the HOST `cc`/`gcc`, which cannot link a foreign-architecture
  `.o` file — confirmed live (`aarch64-unknown-linux-gnu`): the object file
  IS real aarch64 machine code (the linker's own error,
  `"incompatible with i386:x86-64 output"`, is proof the `.o` is NOT
  x86-64), but the link step fails. This is exactly D20's already-recorded
  limitation (`ARCHITECTURE_OVERHAUL.md` §27.3): cross-compilation needs a
  runtime built for the TARGET, which does not exist until RT-001 links a
  real `libturfrt`. `--target`/`-mcpu` exist here because OPT-001 owns the
  `TargetMachine`/CLI surface, not because end-to-end cross-compilation is
  claimed to work — do not "fix" the link step by trying to shell out to a
  cross `cc` as a follow-on inside this group; that decision belongs to
  RT-001, per D20's own text.
- **The `--emit-llvm` path deliberately still has no real `TargetMachine`.**
  `PassBuilder(nullptr)` is well-defined (no target-aware transform runs),
  and this matches the flag's pre-existing meaning ("just show me the IR",
  never target/backend-specific) rather than a gap this session should
  have closed. Do not "fix" this by building a `TargetMachine` for
  `--emit-llvm` too — nothing before this change ever set a target triple
  for that path either, and doing so now would silently change what
  `--emit-llvm`'s output looks like (a target triple line, target-specific
  attributes) for a flag whose entire contract is "unoptimized-for-any-
  specific-target IR dump".
