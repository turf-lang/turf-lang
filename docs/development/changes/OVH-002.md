## Why

`docs/development/OVERHAUL_CLOSURE_AUDIT.md` §3 finding F-02 (reproduced
live, 2026-09-26): four places store a GC-heap pointer (a `string`, a
nested collection) *inside* manually-managed (`malloc`/`mem::alloc`)
memory, which the collector's mark phase never traces into (F-MEM-3). This
was correct while nothing was ever freed (the pre-collector era); MEM-002's
real collector turned it into a live use-after-free — the object such a
pointer names can be freed the moment the collector fails to find it as a
root, even though it looks perfectly reachable from Turf source.

The four sites, each reproduced live before the fix:
1. `lib/std/json/json.tr` — `JsonValue.push()`/`.set()` heap-boxed each
   array element/object value with `mem::alloc(sizeof(JsonValue))`,
   storing a `JsonValue*` in `arr_val`/`obj_vals` instead of `JsonValue` by
   value. Parsing 40 objects, forcing a collection, then reading a nested
   string back reliably corrupted it (SIGSEGV under the reproducer
   `tests/41_gc/07_json_values_survive_collection.tr` is now built from).
2. `showcase/kv_store_server.tr` — the exact same pattern, boxing `Entry`
   with `mem::alloc(16)`.
3. `src/CodegenCore.cpp`'s `CodegenErrorVariantConstructWithMessage()` —
   `ErrorType::Variant(messageExpr)`'s runtime-message construction
   mallocked the `TurfErrorValue{tag, message}` struct; `message`'s
   GC-heap `string` pointer lived only inside that block.
4. `src/CodegenCore.cpp`'s `BoxToI64Slot()` — an oversized `!T` success
   value (a struct or fixed-size array wider than 64 bits) was mallocked
   and boxed by pointer into the `FallibleValue`'s `successBits` slot; any
   GC-heap field inside that `T` (e.g. a `string`) was equally hidden.

While fixing #4, live-tested and confirmed working correctly regardless
(not part of this item, but immediately adjacent): `held: !Rec` — a
`!T`-typed local holding the STILL-BOXED fallible value across a forced
collection, before `recover` unboxes it — is legal Turf syntax and exactly
the shape #4's regression test exercises.

**Additional finding, fixed at the user's explicit request (not one of
OVH-002's own four named sites, discovered while investigating them):**
`CastToType()`'s `int → string`/`double → string` branches
(`src/CodegenExpr.cpp`) built their `snprintf` destination buffer with a
bare `malloc(32)` — not a hidden-pointer bug (the buffer holds only
formatted digits, no outgoing pointer), but a violation of the same
underlying rule from the other direction: FREEZE.md §6.5 says "`string`
values produced by any operation" belong on the GC heap, and a `malloc`'d
one is permanently invisible to `gc_collect()`/`turf_rt_stats()` — a
silent, permanent leak, not a use-after-free, but a real, verified-live
deviation (`TURF_RT_STATS_DUMP` showed `alloc_count=0` for a program that
does nothing but `42 to string`, before this fix; `alloc_count=1,
live_count=1` after).

## Language semantics

### Old behaviour

No Turf-level language change of any kind — every fix in this group is
compiler-internal or stdlib-implementation detail. `JsonValue`'s public
API (`.push`/`.set`/`.get`/`.at`/`.length`/`stringify`/`parse`) is
byte-for-byte unchanged; `kv_store_server.tr`'s wire protocol is unchanged
(verified live: a real SET/GET/miss round trip over the actual TCP
protocol, matching the pre-fix behaviour exactly); `int`/`double to
string`'s formatting is unchanged (`%lld`/`%g`, same buffer size).

### New behaviour

Identical from a Turf source perspective. Internally: a `JsonValue` tree
and a `kv_store_server.tr` entry are now precisely traced through their
containing `List<T>` (by value) rather than hidden behind an untraced
manual-heap box; a message-carrying error value and an oversized `!T`
success box are GC-heap-allocated with a real descriptor instead of a
bare `malloc`; an `int`/`double to string` result is a real, GC-tracked
allocation instead of a permanent leak.

### Is this breaking?

No. No signature, no field name, no wire format, no observable output
changed for any of the fixed sites — verified by the full suite (unchanged
pass count before/after, modulo the new regression tests), the existing
`tests/34_http_and_json/*` suite (unaffected), and a manual client/server
round trip against the rewritten `kv_store_server.tr`.

## Compiler architecture

- **Codegen** (`src/CodegenCore.cpp`):
  - New `getOrCreateTurfRtAllocFn()` (replaces the deleted
    `getOrCreateMallocFn()`) declares/looks up `turf_rt_alloc` instead of
    `malloc`. Exported (`CodegenInternal.h`) since `CodegenExpr.cpp`'s
    `int`/`double → string` fix also needs it.
  - `BoxToI64Slot()`'s oversized-value branch now GC-heap-allocates with a
    real descriptor: `getOrForwardDeclareTurfTypeDescGlobal(ST)` for a
    named struct `T` (the descriptor `EmitAllTurfTypeDescs()` already
    emits for it as an ordinary struct type), `getOrCreateElementTurfTypeDesc(Ty)`
    for anything else (a fixed-size array `T`, which has no named struct
    descriptor to hook into).
  - `CodegenErrorVariantConstructWithMessage()` now GC-heap-allocates
    `TurfErrorValue` the same way, via `getOrForwardDeclareTurfTypeDescGlobal()`
    (both of `TurfErrorValue`'s fields are pointers — descriptor
    `{size=16, word_count=2, bitmap=[3]}`, verified live via `--emit-llvm`).
- **Codegen** (`src/CodegenStruct.cpp`): new
  `getOrForwardDeclareTurfTypeDescGlobal(llvm::StructType*)` — lets a
  function body reference a NAMED struct type's own whole-struct
  `TurfTypeDesc` global (via `Module::getOrInsertGlobal`, a forward
  declaration if nothing has emitted it yet) at a point in codegen that
  runs BEFORE `EmitAllTurfTypeDescs()`'s deliberately-late single pass
  (INV-RT-3). `emitTurfTypeDesc()` itself now routes through the SAME
  helper (filling in the initializer on whatever global object already
  exists) rather than unconditionally constructing a new one — the fix
  that makes a forward reference and the late sweep agree on one global
  instead of the sweep's definition silently landing under a renamed
  `.1` symbol nothing references.
- **Codegen** (`src/CodegenExpr.cpp`): `int`/`double → string`'s buffer
  allocation calls `getOrCreateTurfRtAllocFn()` with a `NULL` descriptor
  (a raw byte buffer, no outgoing pointer) instead of `malloc`.

## Runtime changes

None. No `runtime/*.c`/`turfrt.h` change — this group is entirely about
which allocation ENTRYPOINT compiler-emitted/stdlib code reaches for, not
the entrypoints themselves.

## Standard-library changes

- `lib/std/json/json.tr`: `JsonValue.arr_val`/`.obj_vals` are `List<JsonValue>`
  by value (were `List<JsonValue*>`, each element individually
  `mem::alloc`'d). `.push()`/`.set()`/`.get()`/`.at()`/`stringify_array()`/
  `stringify_object()` simplified accordingly (no more box/unbox). `import
  mem;` removed (no longer used). Header comment rewritten: no longer
  claims `List<JsonValue>` by value fails to compile (stale — TYPE-002
  already made it legal; this group is the first to actually rely on it).
- `showcase/kv_store_server.tr`: `store`/`findIndex()` use `List<Entry>` by
  value (were `List<Entry*>`, each entry individually `mem::alloc(16)`'d).
  No `unsafe { }` remains anywhere in the file — `store.data[idx]` now
  yields an `Entry` by value directly, so `.key`/`.value` access is
  ordinary struct field access, never a dereference through a raw
  `Entry*` base. `import mem;` removed.

## New invariants

Added to `INVARIANTS.md`: **INV-MEM-3** — "No compiler-emitted or
standard-library allocation holds a GC-heap pointer ONLY inside
manually-managed memory," enforced by `scripts/check_boundary.sh` checks 4
(no `getOrCreateMallocFn()` caller remains) and 5 (a best-effort
`mem::alloc(sizeof(...))`-boxes-a-string/collection-field scan), with an
explicitly disclosed exception (`mem::Pool<T>`, below) the row itself
names rather than silently claiming to cover.

## Removed assumptions

- **"A `!T` box / a message-carrying error value is plain `malloc`
  memory."** (The exact sentence OVERHAUL_REMAINING_WORK.md's own text
  named as the assumption to remove.) Both are now real, registered
  GC-heap blocks with a real descriptor.
- **"`List<StructName>` by value doesn't work for a struct over 8 bytes,
  so box it with `mem::alloc` and store a pointer."** Stale even before
  this group (TYPE-002's monomorphization made it false back on
  2026-09-21/22 — `List<T>.data: T*` means a `List<T>` field is never a
  by-value layout cycle regardless of `T`'s size), and actively dangerous
  once MEM-002's collector existed: the box hid every GC-heap pointer
  inside the boxed struct. `json.tr` and `kv_store_server.tr` both
  carried this exact stale comment; both are now corrected and reference
  this record.
- **"`mem::Pool<T>` is always instantiated at a pointer type, so its
  manual-heap `items` array never holds a GC-heap pointer."** Verified
  live to be FALSE as a type-system guarantee: `T` is unconstrained
  (F-GEN-3, no trait/constraint system), so `Pool<string>` compiles and
  stores a GC-heap pointer inside manual memory today. Not fixed here
  (OVH-002's own non-goal list explicitly scopes `Pool<T>` out; there is
  no live call site in `tests`/`lib/std`/`showcase` that actually does
  this) — recorded as a disclosed, unfixed gap, `docs/architecture/boundary.md`
  §6, so it is not "discovered" again later as if new.
- **(Additional finding) "An `int`/`double to string` result's own buffer
  can stay a bare `malloc` because it holds no outgoing pointer, so the
  hidden-pointer rule doesn't apply."** True that it holds no outgoing
  pointer, but irrelevant — the buffer IS the `string` value itself, and
  FREEZE.md §6.5 places every `string` produced by any operation on the GC
  heap, unconditionally. `malloc`-based strings never being freed is a
  silent, permanent leak, not merely an odd implementation choice.

`-O` level `-O0`..`-O3`/`-Os`):
- `tests/41_gc/07_json_values_survive_collection.tr` — parses one JSON
  array of 40 objects (genuinely runtime-built text) into a `JsonValue`,
  forces a collection with size-matched allocation pressure in between,

## Known pitfalls

- **A freed block that hasn't been REUSED yet still reads back
  correct-looking bytes.** `free()` doesn't zero or scramble memory, so a
  regression test that only checks content after ONE collection, with no
  intervening allocation pressure, can falsely pass even against
  genuinely broken code — confirmed live while developing tests 07/08/09:
  an early draft of 08/09 with `junk()` allocating small (8-byte)
  throwaway strings passed even against the reverted, bare-`malloc` code,
  because the freed ~16-40-byte target block was never reused by any
  8-byte junk allocation (a different glibc size class/bin). Sizing
  `junk()`'s allocations close to the target's own size (not just
  "a lot of allocations") was what made the regression actually
  reproduce. `docs/planning/OVERHAUL_REMAINING_WORK.md` §1's own "allocate
  a few thousand throwaway strings" guidance doesn't call out the size-
  matching detail explicitly — a future GC regression test author should
  match allocation SIZE, not just volume.
- **Introducing two independent `List<JsonValue>` instantiations (one
  byval, one still pointer-shaped) in the same compiled program is a
  genuine, separate compiler crash**, unrelated to this fix: discovered
  while verifying test 07 against the pre-fix boxed `json.tr` — an early
  draft of the test declared its own OUTER `List<json::JsonValue>` (byval)
  ALONGSIDE the boxed `json.tr`'s internal `List<JsonValue*>`, and the
  monomorphizer resolved a `.push()`/`.length()` call against the WRONG
  clone's mangled name ("Call parameter type does not match function
  signature," an ICE). Not investigated further (an artifact of testing
  methodology, not a scenario that can arise once `json.tr` itself no
  longer uses the pointer form) — the final test avoids it by only using
  `json.tr`'s OWN public API, never declaring an outer `List<JsonValue>`
  of its own. Worth knowing if a future session ever needs to test two
  instantiations of the same generic at different element shapes
  simultaneously.
- `getOrForwardDeclareTurfTypeDescGlobal()` only works for a NAMED struct
  type (one `getIdentifiedStructTypes()` will eventually reach). An
  anonymous type (a fixed-size array `T` in `BoxToI64Slot()`'s branch) has
  no such global to forward-declare — `getOrCreateElementTurfTypeDesc()`
  (the eager, per-`llvm::Type*`-memoized mechanism MEM-002 already built
  for collection elements) is the right tool there instead; the two are
  not interchangeable.
