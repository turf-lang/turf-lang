Issue #319.

## Why

Walking a string byte by byte needed an index loop over `s[i]`, and for-each
over a `string` was E005.

## Language semantics

`for c in s` and `for (i, c) in s` take a `string`. The string and its length
are taken once, before the first iteration; `c` is a `char`, the byte at `i`
as it is when the iteration starts. A `'\0'` reached by the loop means the
body made the string shorter than the loop's position, and the read panics
with `String index out of bounds`. Bytes, not code points, as `s[i]`.

### Is this breaking?

No. Every program it accepts was E005.

## Compiler architecture

- **TypeChecker** · `visitForEach()` (`TypeCheckerStmt.cpp`) accepts a
  `string` and gives the value variable `char`.
- **Codegen** · `ForEachExprAST::codegen()` (`CodegenControlFlow.cpp`) takes
  the string pointer once, calls `strlen` once for the bound, and reads each
  byte with an inbounds GEP plus a `'\0'` test that panics. The rest (counter,
  scopes, `break`/`continue`, the paired index variable) is the array path.

The long-hand `s[i]` read calls `strlen` on every read
(`EmitStringBoundsCheck()`), which makes an index loop quadratic when its body
calls a function, since LLVM cannot hoist `strlen` across the call. The
for-each loop does not repeat that: one `strlen`, one compare per byte. A
string's allocation never shrinks, so every byte below the starting length
stays inside it whatever the body writes.

## Removed assumptions

- "A for-each iterable is an array." It is an array or a string; the
  TypeChecker and Codegen both check for the two.

## Tests

- `tests/12_string_ops/15_string_for_each.tr`: empty, one-byte, literal and
  run-time strings against the long-hand loop, UTF-8 (one iteration per
  byte), the paired form with `return`, `break` and `continue`, nesting, a
  reassignment of the variable inside the loop, a byte changed ahead of the
  loop.
- `tests/12_string_ops/fail_string_for_each_shortened_runtime.tr`: a `'\0'`
  written ahead of the loop panics.

## Known pitfalls

- A `'\0'` written *behind* the loop's position does not stop it; the
  long-hand loop would panic at its next read. Measuring on every byte would
  close the gap at the cost of a quadratic loop (TDP-2-021, Drawbacks).
