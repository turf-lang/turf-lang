## Why

Two small, independent defects, both named in `ARCHITECTURE_OVERHAUL.md`
§8's HYG-001 section:

1. **`SymbolTable.h` pulls in `llvm/IR/Instructions.h`** for a single field,
   `llvm::AllocaInst *Alloca`, used only ever as a pointer (stored, passed,
   compared — never dereferenced anywhere in `SymbolTable.h`/`.cpp`). This
   forces the entire LLVM IR type hierarchy into every translation unit that
   includes `SymbolTable.h`, whether or not that TU has anything to do with
   Codegen.
2. **Unreachable-code and dead-branch warnings bypass `DiagnosticEngine`.**
   `CFG::reportFlowDiagnostics()` wrote both straight to `std::cerr` as plain,
   uncolored strings — no `[E0NN]` code, no color, no caret, no source
   snippet, no hint — even though `UnreachableBlockWarning`/
   `DeadBranchWarning` (`include/ErrorsFlow.h`) already existed, fully
   written, and were simply never constructed by anything. Confirmed live
   before this fix (`fn main(): int { while true { return 1; } return 2; }`):
   exactly `Warning: Unreachable code in block 'while.end' of function
   'main'`, sitting directly above a properly-rendered warning from `lib/std`
   in the same output.

## Language semantics

No language semantics changed. Item 1 is a build-time-only header hygiene
fix (zero effect on compiled-program behavior or compile-time diagnosis).
Item 2 changes only *rendering* — the exact same conditions warn, with the
exact same meaning; see *Tests* for a live before/after comparison proving
`when` did not change, only `how`.

### Is this breaking?
No. No `.tr` program's accepted/rejected status changed, and no compiled
program's runtime behavior changed.

## Compiler architecture

- **`include/SymbolTable.h`** — `#include "llvm/IR/Instructions.h"` replaced
  with `namespace llvm { class AllocaInst; }`. The real include moved to
  `src/SymbolTable.cpp` (the file the `HYG-001` spec names, even though —
  see *Removed assumptions* — that TU turns out not to need the complete
  type either; kept there anyway as the natural, conventional home for it
  per the spec's own instruction, not re-derived from first principles).
- **`src/CFG.cpp`, `CFG::reportFlowDiagnostics()`** — the two raw `std::cerr
  <<` calls replaced with `UnreachableBlockWarning(BB->getTerminatorLoc(),
  FunctionName, BB->getName()).warn()` and
  `DeadBranchWarning(BB->getTerminatorLoc(), FunctionName).warn()`. Anchored
  at the unreachable block's own *terminator* location (see *Removed
  assumptions* for why, not the first statement's).
- **`include/Errors.h`, `TurfWarning`** — gained a `getCode()` method,
  mirroring `TurfError::getCode()` exactly (`typeid(*this)` demangled name
  looked up in `ErrorCodes::lookupByClassName()`), and `emit()` now passes
  it through to `DiagnosticEngine::add()`. This was **not** in the spec's
  explicit file list, but is required to satisfy its own completion
  criterion ("both warnings render like every other diagnostic" — which
  includes the `[E0NN]` code): `TurfWarning::emit()` had never called
  `getCode()` at all before this session, because no `TurfWarning` subclass
  had ever been registered in `ErrorCodes.h` — `UnreachableBlockWarning`/
  `DeadBranchWarning` are the first. Every other, pre-existing warning class
  is unaffected (still renders with no code, exactly as before — confirmed
  live, see *Tests*) since only these two now have a registry entry.
- **`include/ErrorCodes.h`** — two new entries appended at the end (per this
  file's own stated convention — never resorted in): `E074`
  (`UnreachableBlockWarning`) and `E075` (`DeadBranchWarning`), both routed
  to the existing `CONTROL_FLOW` category (F-DIAG-3 — no new category).
- **`docs/errors/codes/E074.txt`, `E075.txt`** — new per-code human docs,
  following the existing files' established shape (title line, indented
  code sample, body prose). Verified live via `turf --explain E074`/`E075`.

## Removed assumptions

- **"Fixing `SymbolTable.h`'s `llvm/IR/Instructions.h` include measurably
  speeds up `ParserDecl.cpp`'s syntax-check, per §3.4/§8's cited numbers
  (182,910 → a ~65% cut, 3.07s)."** This does **not** reproduce today —
  verified live, both before and after, on this exact toolchain:
  `ParserDecl.cpp` preprocesses to **224,582 lines before this fix and
  224,585 after** (no meaningful change; note this is already a higher
  baseline than §3.4's own cited 182,910, independent of this fix — a
  different measurement environment, not a regression this session caused).
  Root cause, confirmed by grep: `ParserDecl.cpp` (and every other
  `Parser*.cpp`/`Codegen*.cpp` file) also `#include "Codegen.h"`, which
  itself pulls in `llvm/IR/IRBuilder.h`, `llvm/IR/Constants.h`,
  `llvm/IR/Function.h`, and `llvm/IR/Module.h` — the same full LLVM IR type
  hierarchy `SymbolTable.h` used to pull in directly, arriving by a second,
  independent path this fix does not touch. **The fix is still correct and
  still worth having** — it just does not pay off for the specific example
  TU the spec picked. It *does* pay off, measured live, for every TU that
  includes `SymbolTable.h` but not `Codegen.h`: the ten `Resolver*.cpp`/
  `TypeChecker*.cpp` files, plus `AliasAnalysis.{h,cpp}`, `Analysis.{h,cpp}`,
  `Sandbox.h`, `ValueRange.h`, and `CompileBuffer.cpp` (confirmed via grep —
  16 of the 28 `SymbolTable.h`-including files). Measured on
  `ResolverDecl.cpp`/`TypeCheckerDecl.cpp` (both real 143,170/143,123 lines
  before, 115,124/115,077 after — a genuine **~19.6% / ~28,046-line cut**
  each, and `ResolverDecl.cpp`'s `-fsyntax-only` wall time dropped from
  2.135s to 1.685s, ~21% faster). A future session should cite these numbers
  for Item 1, not §3.4's original ParserDecl.cpp figures, which describe a
  TU this fix does not actually help.
- **"`ExprAST` has a way to get an arbitrary statement's source location."**
  It does not — every concrete AST node class defines its own `getLoc()`
  independently; there is no virtual base-class accessor. This is why
  `UnreachableBlockWarning` is anchored at `BB->getTerminatorLoc()` (a real
  position *inside* the unreachable block, since the terminator is one of
  its own statements) rather than the unreachable block's first statement:
  getting the first statement's own location would need either a new
  virtual `getLoc()` across ~42 node kinds (real architecture, out of HYG-001's
  XS scope) or an ad-hoc `dynamic_cast` dispatch chain built for this one
  call site (inconsistent with `StatementAfterTerminatorError`'s own,
  pre-existing precedent of anchoring at the terminator instead — see that
  class's raise site and `compiler_pipeline.md`'s description of it). This
  precedent, not a fresh design choice, is why `DeadBranchWarning` uses the
  same anchor.
- **"A `TurfWarning` subclass automatically gets a `[E0NN]` code once
  registered in `ErrorCodes.h`, the same as a `TurfError` subclass."** It did
  not, before this session — `TurfWarning::emit()` never called `getCode()`
  at all (see *Compiler architecture*). This was never exercised before
  because no warning class had ever been registered.

## Known pitfalls

- **The ParserDecl.cpp number in `ARCHITECTURE_OVERHAUL.md` §3.4/§8 no
  longer describes this fix's actual effect.** See *Removed assumptions*
  above. `docs/archive/ARCHITECTURE_OVERHAUL.md` itself is frozen and not
  edited by this record (§25 item 24) — a future reader who cites §3.4's
  number for *this specific TU* will be wrong; point them at this record's
  `ResolverDecl.cpp`/`TypeCheckerDecl.cpp` measurements instead.
- **A future TU that includes `SymbolTable.h` and dereferences `Alloca`
  (calls a method on it, not just stores/passes the pointer) will fail to
  compile** until it adds its own `#include "llvm/IR/Instructions.h"` — the
  forward declaration is only sufficient for pointer-only use. Confirmed
  live: `src/CodegenVar.cpp` does dereference it (`A->getAllocatedType()`)
  and compiles unchanged only because it already gets the complete type
  transitively via `Codegen.h`, not because of anything this fix added.
- **`BB->getTerminatorLoc()` as the unreachable-block anchor is a real
  position inside the block, but not necessarily its very first statement.**
  For a block whose terminator was itself set from a control-flow construct
  deeper in the block (not verified to be impossible), the caret could land
  later than a reader might expect. Not observed in either worked example
  tested this session (both anchored exactly at the block's own dead
  `return`/`if`), but worth knowing if a future bug report says the caret
  looks "off" for a more complex unreachable region.
- **`TurfWarning::getCode()` now exists and every other warning subclass is
  silently exempt from it** (returns `""`, same as before) purely because
  nothing else is registered in `ErrorCodes.h` yet — this is not a gate, it
  is just that nobody has added the other ~15 warning classes to the
  registry. A future session registering one of them gets a code "for free"
  the moment it's added, with zero further code changes needed.

## Unresolved questions

- **HYG-001's own completion criterion — "`llvm/IR/Instructions.h` no longer
  reaches any Parser TU" — does not hold, for all five `Parser*.cpp` files,
  and cannot be made to hold within this feature's stated scope.** Verified
  live with `c++ -H -fsyntax-only src/ParserDecl.cpp`: `llvm/IR/
  Instructions.h` is still reached. Root cause: every one of
  `ParserCore.cpp`/`ParserDecl.cpp`/`ParserLiteral.cpp`/`ParserModule.cpp`/
  `ParserStmt.cpp` independently `#include "Codegen.h"`, which pulls in
  `llvm/IR/IRBuilder.h`, `llvm/IR/Constants.h`, `llvm/IR/Function.h`, and
  `llvm/IR/Module.h` — the same LLVM IR type hierarchy `SymbolTable.h` used
  to pull in directly, arriving by a second, completely independent path
  this feature's "Relevant files" list (`include/SymbolTable.h`,
  `src/CFG.cpp`, `include/ErrorsFlow.h`) does not include and does not
  authorize touching. §3.4's own closing note anticipates the parser not
  becoming fully "LLVM-free" because of `llvm/ADT/SmallString.h`/
  `llvm/Support/FileSystem.h`/`llvm/Support/Path.h`, but does not mention
  `Codegen.h` at all — which turns out to be the actual reason the parser
  doesn't even become "LLVM-IR-free" as that note claims it would. Making
  the literal completion criterion true would mean decoupling `Codegen.h`'s
  own LLVM-IR includes from every parser TU that includes it — a real,
  separate architectural change (§1.3's layering question, not §3.4's
  narrower header-hygiene one), unambiguously outside HYG-001's XS
  complexity and named file list. **Not attempted here** — implementing it
  under this feature ID would be exactly the kind of scope creep §25 warns
  against. The fix as specified (forward-declare in `SymbolTable.h`, real
  include in `SymbolTable.cpp`) is implemented exactly as the spec's own
  concrete instruction says, and does deliver a real, measured win for
  every TU that does NOT separately include `Codegen.h` (see *Removed
  assumptions*) — the criterion's specific wording just doesn't hold for
  the parser TUs, and no scoped fix exists that would make it hold. Flagging
  this for whoever next touches parser/Codegen header layering rather than
  silently marking the criterion satisfied.
