**Commit 5 — `feat(cli): the turf front end: dispatch, compiler discovery, version handshake (@a2ys)`**

*Layout:*
- `cli/cmd/turf/main.go` is the dispatcher.
- `cli/cmd/turf/cmd_<name>.go` holds one file per command.
- `cli/internal/driver/` holds discovery, the handshake, and exec
  (`exec_unix.go` / `exec_other.go` with build tags).
- `cli/internal/version/version.go` has
  `var Version = "unknown"`, set by `-ldflags "-X github.com/turf-lang/turf-lang/cli/internal/version.Version=<v>"`.
- **Go standard library only, no `cobra`.** Design decision: nearly every
  command forwards its flags verbatim. With cobra that means
  `DisableFlagParsing` everywhere, which throws away the help and validation
  that are cobra's reason to exist, and zero dependencies keeps the release
  pipeline trivial. Stage 5 adds a TOML library; that will be the first
  dependency.

*Dispatch.* Classify `os.Args[1:]` exactly as §6.16 "Passthrough" says:

| First argument | Action |
|---|---|
| none | print help to stderr, exit 2 |
| `--version` / `version` | print `turf <Version>`, then the discovered compiler's `turfc --version` line 1 and its path; exit 0. If discovery or the handshake fails, print `turf <Version>` and then the error; exit 1 |
| `--help` / `-h` / `help [cmd]` | help (overall, or that command's) to stdout, exit 0 |
| a known subcommand | that command. Inside it, `-h`/`--help` appearing before any `--` shows the command's help |
| `install` | error: `` `turf install` is now `turf fetch` (LEC-001 stage 6) ``, exit 2 |
| starts with `-`, or ends in `.tr` | **passthrough**: exec `turfc` with every argument unchanged |
| anything else | `turf: unknown command 'X'`, plus `did you mean 'Y'?` when the nearest command name has edit distance ≤ 2; exit 2 |

*Commands.* All of these run the handshake first.

| Command | Runs | Notes |
|---|---|---|
| `compile <args…>` | `turfc <args…>` | all args verbatim, including unknown flags (§6.16). The CLI validates nothing; `turfc` does |
| `check <args…>` | `turfc --check <args…>` | |
| `dump <what> <args…>` | `turfc --check --dump-<flag> <args…>` | `<what>`: `ast`→`--dump-ast`, `resolved`→`--dump-resolved`, `typechecked`→`--dump-typechecked`, `modules`→`--dump-modules`, `symbols`→`--dump-resolver-symbols`, `instantiations`→`--dump-instantiations`. Unknown or missing `<what>`: error listing the six, with a suggestion, exit 2 |
| `explain <code>` | `turfc --explain <code>` | missing code: usage, exit 2 |
| `fmt [--write] <files…>` | `turfc --format [--write] <file>`, once per file | without `--write`, exactly one file (the output goes to stdout, and concatenating several would be ambiguous); with `--write`, any number. Project-wide `fmt` and `--check` are REL-002. Exit status: the first non-zero `turfc` status, after running every file |
| `migrate <name> [--write] <files…>` | `turfc --migrate=<name> [--write] <files…>` | missing `<name>`: usage naming `pub`, exit 2. An unknown name is left to `turfc`'s own error |
| `run <file.tr> [compiler flags…] [-- program args…]` | see below | |
| `new`, `init`, `build`, `test`, `clean`, `fetch`, `add`, `remove`, `update` | nothing | `turf: '<cmd>' is not implemented yet (LEC-001 stage N)`, naming the stage from the table above (`test` is REL-002); exit 2 |
| `publish` | nothing | `turf: the package registry is not part of TurfLang 2.0; publish a library by pushing a git tag (FUTURE F-7c)`, exit 1 |
| `run` with no `.tr` argument | nothing | `turf: project builds arrive in LEC-001 stage 5; use 'turf run <file.tr>'`, exit 2 |

*`turf run`:*
1. Make a temp directory with `os.MkdirTemp`.
2. Run `turfc <file> <flags> -o <tmp>/<stem>` (plus `.exe` on Windows),
   with stdio inherited. A compile failure exits with `turfc`'s status.
3. A user-supplied `-o` is an error:
   `turf run builds to a temporary file; use 'turf compile -o …'`, exit 2.
4. Success without the output file existing (e.g. `--emit-llvm`):
   `turf: the compiler produced no executable`, exit 1.
5. Run the program with the arguments after `--`, stdio inherited. Ignore
   SIGINT in `turf` while the child runs, so Ctrl-C reaches the child and
   `turf` still cleans up.
6. Remove the temp directory.
7. Exit with the child's status, or 128+signal number if it was killed by a
   signal (Unix).

*Discovery* (`internal/driver`, §6.16's order):
1. `$TURF_COMPILER`, if set and non-empty. It must exist, or error.
2. `filepath.EvalSymlinks(os.Executable())`'s directory + `turfc` (plus
   `.exe` on Windows).
3. `$TURF_HOME/bin/turfc`.
4. `exec.LookPath("turfc")`.

Not found:
```
turf: cannot find the compiler (turfc)
  looked in: <each place tried, one per line>
hint: set TURF_COMPILER to the turfc binary, or build it with `cmake --build build`
```
Exit 1.

*Handshake:*
- Run `<turfc> --version` and compare line 1 with `"turfc " + version.Version`.
- If `version.Version == "unknown"` (a plain `go build` without the stamp):
  error `turf was built without a version stamp; build it with 'cmake --build build --target turf-cli'`.
  No bypass, not even with `TURF_COMPILER` (§6.16).
- Mismatch:
  ```
  turf: compiler version mismatch
    turf  <v1>  (<path to turf>)
    turfc <v2>  (<path to turfc>)
  hint: turf and turfc must come from the same build; rebuild with `cmake --build build`, or point TURF_COMPILER at the matching turfc
  ```
  Exit 1. A `turfc` that fails to run or prints nothing reports its path and
  the error.

*Exec:*
- For `compile`, `check`, `dump`, `explain`, `migrate`, single-file `fmt`
  and passthrough, on Unix use `syscall.Exec`. This **replaces** the process,
  so stdout, stderr, exit status and signals are the compiler's by
  construction; that is what makes passthrough byte-identical.
- Elsewhere, and for multi-file `fmt` and `run`, use `os/exec` with inherited
  stdio and propagate the exit code.

*Exit codes for the CLI's own errors:* 2 for usage, 1 for everything else.
**Provisional**; REL-001 decides and may renumber.

*Help text:*
- Overall help lists the commands in three groups (*Any file*, *Project —
  not yet implemented*, *Other*) with a one-line description each, and
  shows `turf <file.tr> [flags]` as the passthrough form.
- `turf compile --help` lists every flag `parseArgs()` accepts today, one
  line each, copied from the compiler's usage text (plus `--check` and
  `--version`).
  - That duplication is accepted for stage 2. Leave a `// Drift:` comment
    saying REL-001's `turfc --help` should replace it, with `turf compile
    --help` then forwarding.

*CMake target:*
- Add `option(TURF_BUILD_CLI "Build the Go front end (cli/) as build/turf" ON)`.
- When it is ON and `PROJECT_IS_TOP_LEVEL` (so `turf-lsp`'s
  `add_subdirectory` never needs Go):
  - `find_program(TURF_GO go)`. If Go is not found, print
    `message(STATUS "Go not found: build/turf (the CLI) will not be built; build/turfc is unaffected")`
    and add no target.
  - Otherwise add
    `add_custom_target(turf-cli ALL COMMAND ${CMAKE_COMMAND} -E env CGO_ENABLED=0 ${TURF_GO} build -trimpath -ldflags "-X github.com/turf-lang/turf-lang/cli/internal/version.Version=${TURF_VERSION}" -o "${CMAKE_BINARY_DIR}/turf${CMAKE_EXECUTABLE_SUFFIX}" ./cmd/turf WORKING_DIRECTORY "${CMAKE_CURRENT_SOURCE_DIR}/cli" VERBATIM)`.
  - `ALL` is fine: Go's build cache makes a no-op rebuild take milliseconds.
- **Do not name the target `turf`.** Under Ninja a phony target with the

### Stage 3 — what landed

Single-file mode (the only mode until stage 4) now examines every search root
for `import m;`, and more than one distinct file is **E090
`AmbiguousModuleError`**.

- **`CollectModuleCandidates()`** (`src/ParserModule.cpp`) replaces the
  first-hit chain in both `ParseModuleImportByName()` and
  `ResolveModuleFile()`.
  - It returns every candidate in the old search order (stdlib → lib/usr →
    the importing file's directory → the cwd).
  - Candidates are deduplicated by canonical path, keeping each one's old
    spelling, because that string is `ResolvedPath`, the import-identity key.
  - `ResolveModuleFile()` returns `""` for an ambiguous name, as a real import
    of it is an error.
- **Two stdlib-only rules**, both needed so that examining every root does not
  manufacture errors:
  - **Imports written inside lib/std** (`ImportsResolveInStdlibOnly()`) resolve
    in the stdlib only. This follows F-PKG-2 with the stdlib as one package.
  - **The prelude** (`ParsePreludeImports()` → `StdlibOnly`) resolves in the
    stdlib only.
  - Without them, a user's local `list.tr` would have broken every program in
    its directory: `strings` (prelude) imports `list`.
  - Demonstrated: every `lib/std/**` file passes `turfc --check --module`
    when run from a directory containing a local `list.tr`.
- **E090 message** lists each candidate as `kind  path`. Paths are shown
  canonicalized, and as `./rel` when under the cwd.
  - The kinds are "standard library", "installed package (lib/usr)",
    "next to <importing file>" and "current directory".
  - The hint depends on what collided. Against the stdlib: rename your file
    (with an example name). Two user files: rename or delete one.
  - Candidates are in the message body, not `withRelated()` notes, because a
    related note renders as "(line, col)" with no file name.
  - `docs/errors/codes/E090.txt` is the `turf explain E090` page.

### Stage 4 — what landed

The compiler half of package builds. `turf` does not produce a graph until
stage 5, so everything here is driven with `turfc --package-graph` directly
and proven by `scripts/package_graph_smoke.sh`.

- **The seam's concrete form** (engineering judgement; §6.16 left it open):
  a JSON file, `turfc --package-graph <file>`. The format is documented in
  `include/PackageGraph.h`:
  ```json
  {"format": 1, "root": "myapp", "packages": {
    "myapp":    {"src": "myapp/src",    "deps": ["geometry"], "allow_unsafe": true},
    "geometry": {"src": "geometry/src", "deps": []}}}
  ```
  - **Why a file and not repeated flags:** each package has its *own*
    dependency list (direct-dependencies-only is per package), which flags
    express badly.
  - A file is what a driver writes anyway, and it gives tools one artifact
    to inspect.
  - Relative `src` paths are relative to the graph file.
  - LLVM's `llvm/Support/JSON.h` parses it, so there is no new dependency.
  - `turfc`'s driver interface goes 1.0 → **1.1** (additive).
    `version.Required` in the CLI stays 1.0 until stage 5 starts passing a
    graph.
- **Validation up front** (`LoadPackageGraph()`, `src/PackageGraph.cpp`).
  It checks, before anything is parsed:
  - the format;
  - unknown keys;
  - identifier names;
  - existing src directories;
  - dependencies that name packages in the graph, with no self-dependency
    and no duplicates;
  - that no dependency is named like a stdlib module;
  - that every depended-on package has its root module `src/<name>.tr`;
  - that the entry file is inside the root package.

  Each failure is one line naming the file and the problem, exit 1. The
  point: a bad graph must not surface as a "module not found" deep inside a
  dependency.
- **Resolution** (`CollectPackageModuleCandidates()`): from package P, an
  import may name one of three things, and lib/usr, the importing file's
  directory and the cwd are not searched:
  - (a) P's own `src/**/m.tr`, *all* matches, so two are E090;
  - (b) a direct dependency's root module;
  - (c) the stdlib.
  - E090 gains the candidate kinds "module of package 'P'" and "dependency
    'D'", and a "may not share its name with a dependency" hint.
  - **E091 `ModuleNotImportableError`** (`ExplainUnreachableModule()`)
    covers a module that exists but is out of reach. There are two
    messages:
    - a transitive dependency (naming the packages that do depend on it,
      with the hint "add it to [dependencies]");
    - another package's internal module (naming the file, with the hint
      "import the package and use its root module's `pub` items").
  - It is a separate code from E027 because the fix is different: the file
    exists. The `turf explain` page is `docs/errors/codes/E091.txt`.
- **Module identity** (INV-PKG-2). A dependency package's modules get the
  identity `<package>/<path under src/>`, for example `geometry/util` or
  `geometry/geometry`. Everything else keeps its name, so single-file mode,
  the stdlib and the root package are byte-for-byte unchanged, and the suite
  shows it.
  - **How:** the parser rewrites the spelling at read time.
    `ParseModuleImportByName()` records `util → geometry/util` in the current
    file's alias map (`CurrentFileModuleAliases`), and `ModuleKeyFor()` is
    applied at the three places a qualifier is read (`ParseType`'s `M::T`,
    `ParsePrimaryBase`'s `M::x`, the `M::Enum::Variant` chain).
  - The alias map is per file: `ParseFile()`'s `LexerStateGuard`
    saves/clears/restores it around each import, and `ParsePreludeImports()`
    clears it at the start of each top-level pass, in both drivers.
  - **Why at parse time:** the Resolver, TypeChecker, Monomorphizer and
    Codegen already treat a module *name* as an identity (`Modules_`,
    `TypeIdentity`, flat-import `SourceModule`, symbol names). Giving them an
    identity instead of a spelling fixes them all with no change. The
    alternative, an alias lookup at every `hasModule()`/type-identity site
    downstream (six Resolver sites alone), is the kind of change that misses
    one.
  - Demonstrated: two packages each declaring `util::Node` compile to two
    types and run correctly (result 21). A diamond loads its shared
    dependency once. A flat `import geometry::area;` works.
  - `--dump-modules` shows `geometry/util::Node` and `util::Node`.
- **Per-package unsafe** (F-PKG-4, `HasRawPointerCapability()`). In a package
  build the capability is the file's package's `allow_unsafe` bit (the
  install root stays unconditional). `--allow-unsafe-modules` is **not**
  consulted, because a global flag would grant every dependency at once,
  which is the consent the per-package rule makes explicit.
- **Display** (`DisplayModuleName()` / `DeclaringFileName()`,
  `include/ErrorsModule.h`):
  - A package's root module `geometry/geometry` reads as `geometry` in
    E088/E089.
  - Their "mark it `pub` in <file>" hint now names the declaration's own
    file, not `<module>.tr`. The file name was only right while a module's
    name was its file stem.
  - Other module-naming messages still show a dependency module's identity
    raw (see *Known pitfalls*).
- **Tests:** `scripts/package_graph_smoke.sh`, run in CI after
  `migrate_pub_smoke.sh`. It has 17 cases (about 45 checks); each checks the
  exit status and the error code or message it is about.
  - A mutation run (two expectations deliberately wrong) confirmed it
    reports failures.
  - Suite **876/876** unchanged, `turf-api-tests` passing.

### Stage 5 — what landed

`turf` reads projects. It finds the nearest `turf.toml`, resolves path
dependencies into a package graph, writes it to `build/package-graph.json`,
and drives `turfc --package-graph`. The compiler changed in one place only
(the E027 hint). `version.Required` is now **1.1**.

- **`internal/manifest`** (`manifest.go`, `edit.go`): `Load`/`Parse` with
  `github.com/BurntSushi/toml` v1.6.0, the CLI's first dependency. Every rule
  in the spec is a distinct message naming the file, with the line where it
  can be recovered.
  - `Parse` takes text so `add`/`remove` can validate what they are about to
    write.
  - `Manifest.DepOrder` keeps `[dependencies]` in file order, so the graph
    lists dependencies as declared.
  - The reserved-word list is copied from `src/Lexer.cpp` with a `// Drift:`
    comment; `project_smoke.sh` compares the two.
- **`internal/project`**: `FindRoot`, `Resolve(root)`, `Graph.JSON()`,
  `CheckStdlibNames`, `CheckCompilerVersion`. The package graph is a
  depth-first walk with paths relative to the *declaring* manifest,
  canonicalised with `EvalSymlinks` so a diamond reached through a symlink is
  one package.
- **`internal/stdlib`**: the stdlib module names, read from `lib/std` under
  the install root (`$TURF_HOME`, else `dirname(realpath(turfc))/..`, the rule
  of `TurfInstallRoot()`). Used by `turf build`, `turf add` and `turf new`. If
  no stdlib can be found the check is skipped, not failed, because `turfc`
  rejects the same names itself.
- **Commands.** `build`, `run`, `check` (no `.tr` argument), `clean`, `new`,
  `init`, `add`, `remove`. `fetch`, `update` and `test` remain stubs.
  - **`turfc` runs with its working directory set to the project root**
    (`driver.RunIn`), so `build/package-graph.json` and `src/main.tr` are
    relative and the invocation is identical wherever in the tree the user
    typed `turf build`. `turf run` still runs the *program* in the user's own
    cwd.
  - **The first failing `turfc` status stops the sequence**, for `build` and
    for `check`. When the program fails to compile, a second run over a library
    it imports would repeat the same diagnostics.
  - `-o`, `--package-graph` and `--package-graph=…` are exit 2 for
    `build`/`run`/`check` in a project.

### Stage 6 spec (for the implementing session)

Written by the design session. The **design decisions are made here**; the
implementing session builds them.
- `FREEZE.md` §6.16 F-PKG-3 is the authority: path and git sources only, the
  root's `turf.lock` pins commit and SHA-256, the hash is verified on every
  build, one version per name, `--offline`, `--locked`, and `turf update` is
  the only thing that moves a ref.
- If anything here contradicts it, or is impossible, **stop and report
  back**.

**Goal.**
- `jsonx = { git = "https://github.com/someone/jsonx", tag = "v1.2.0" }`
  works end to end: `turf build` fetches it once and pins it in `turf.lock`.
- Every later build uses the pinned, hash-verified tree with no network.
- `turf update` is the only thing that moves it.
- `--offline` and `--locked` do what they say.
- CI tests all of it against local bare repositories, with no network.

**Out of scope, do not do:**
- a registry or semver ranges (F-7c);
- a `subdir` key (a git dependency's repository root *is* the package);
- git dependencies of the compiler itself;
- `turf test` (REL-002);
- `examples/` or the reference page (stage 8);
- changes to `turfc`. The compiler is not touched in this stage; git
  dependencies reach it as ordinary directories in the graph.

#### The design (decided; do not reinterpret)

1. **Git is the system `git` binary**, run with `exec.Command`.
   - Always set `GIT_TERMINAL_PROMPT=0` in its environment. A private repo
     must fail with git's message, never hang on a password prompt.
   - `git` missing from `PATH`: `turf: git dependencies need the 'git'
     program, which is not on PATH ('<name>' in <file>)`, exit 1.
   - Any git URL git accepts is accepted: https, ssh, `file://`, and a local
     path. The tests use local bare repositories.
2. **The cache** is `$TURF_CACHE_DIR` if set (the tests use it), else
   `<os.UserCacheDir()>/turf`. Under it:
   - `git/<sha256(url) hex, first 16>/` holds a **bare mirror** of each URL:
     `git clone --mirror <url> <dir>` the first time, `git --git-dir=<dir>
     fetch --prune --tags origin` when refreshing.
   - `src/<name>-<full commit>/` holds the **extracted tree** of one commit.
     It is produced by `git --git-dir=<mirror> archive --format=tar <commit>`,
     read with Go's `archive/tar`, and written to a temp directory beside the
     target and renamed into place. It is atomic, so an interrupted fetch
     never leaves a half tree under the final name. It never contains
     `.git`, because `git archive` does not emit it.
   - The cache is disposable: deleting it costs only a re-fetch.
3. **Resolving a ref to a commit** (in the mirror, after a fetch when one is
   needed):
   - `tag = "v1.2.0"` → `git rev-parse --verify refs/tags/v1.2.0^{commit}`;
   - `branch = "main"` → `refs/heads/main^{commit}`;
   - `rev = "3f2a9c1"` → `<rev>^{commit}`, and the lockfile records the
     **full** 40-hex commit.

   An unknown ref is an error naming the URL and the ref.
4. **The tree hash**, version 1 (`internal/treehash`, a pure function over a
   directory). Walk the tree. For every regular file and every symlink,
   **skipping any path component named `.git`**, emit one line:
   ```
   <hex sha256 of the file's bytes, or of the symlink's target string> <f|l> <slash-separated path relative to the tree root>\n
   ```
   - Sort the lines by path (byte order) and take the SHA-256 of their
     concatenation.
   - Written `sha256:<hex>`.
   - Permissions, mtimes, ownership and empty directories do not count.
     That is FREEZE's "independent of mtimes and permissions".
   - A path containing `\n` is an error, since it could forge a line.
   - It is computed on the **extracted tree in the cache**. That tree, not
     the git objects, is what the compiler reads.
5. **`turf.lock`**: the root project's only; a dependency's own `turf.lock`
   is ignored (F-PKG-3). It is TOML, written by turf, deterministic
   (packages sorted by name, fixed key order), and always written, even for
   path-only projects, so that adding the first git dependency is a
   one-entry diff.
   ```toml
   # This file is generated by turf. Commit it; do not edit it.
   version = 1

   [[package]]
   name = "geometry"
   source = "path+../geometry"          # relative to the project root, forward slashes

   [[package]]
   name = "jsonx"
   source = "git+https://github.com/someone/jsonx"
   ref = "tag=v1.2.0"                  # tag= / branch= / rev=, exactly as the manifest asks
   commit = "3f2a9c1e..."              # full 40 hex
   hash = "sha256:…"
   ```
   - An unknown `version`, an unknown key, or a malformed entry is an error
     naming `turf.lock`, with the hint "delete it and run `turf build` to
     regenerate it".
6. **Which commit a build uses.** For each git dependency in the graph:
   - A lock entry with the **same name, same source URL and same `ref`
     string** → use its commit. There is no network if `src/<name>-<commit>`
     is in the cache. If the tree is missing, fetch the mirror (or use it, if
     it already has the commit) and extract.
   - No such entry (a new dependency, or its URL or ref changed in the
     manifest) → resolve the ref (fetch the mirror first), extract, and
     record the new entry.
   - So a tag that was re-pointed upstream, or a branch that moved, is
     **not** noticed by `build`, only by `update`. That is F-PKG-3's "turf
     update is the only command that moves" rule.
7. **Hash verification** runs on every build, for every git dependency,
   against the lock entry.
   - A mismatch is an error: `turf: the cached tree of '<name>' (<path>) does
     not match turf.lock (expected <h1>, found <h2>): it was modified or
     corrupted`.
   - Hint: `delete <path> and build again to re-extract it; if turf.lock
     itself is wrong, 'turf update <name>'`.
   - A freshly extracted tree is hashed and, for a new entry, the hash is
     recorded. For an existing entry it must match, or the same error
     applies: the upstream history was rewritten under the same commit id,
     which should be impossible, but is exactly what the hash is for.
8. **The graph with git dependencies.**
   - A git dependency's package directory is its extracted cache tree.
     `internal/project`'s walker then treats it like any directory:
     - its `turf.toml` is loaded, and the name/key and library checks apply;
     - the "same name from two different directories" conflict catches two
       different commits of one package. Its message must say which ref
       each requirer asked for.
   - A path dependency *inside* a git package (for example a monorepo's
     sibling package) is resolved relative to the extracted tree and must
     stay inside it. `path = "../x"` escaping the tree is an error: "a git
     dependency's path dependencies must stay inside its repository".
   - Git dependencies of git dependencies are fetched the same way.
9. **Flags** are turf's own, never forwarded to `turfc`, accepted by `build`,
   `run`, `check` and `fetch`:
   - **`--offline`**: no git network command at all (`clone`/`fetch`).
     Anything not already locked **and** cached, or locked but missing from
     both the tree cache and the mirror, is an error naming it: "needs the
     network; run without --offline". Offline resolution of an *unlocked*
     ref from a possibly stale mirror is deliberately refused: it could
     silently pin an old commit.
   - **`--locked`**: if the lock computed for this build differs from the
     file on disk in any way, it is an error, and nothing is written. The
     error names each added, removed or changed entry. A missing `turf.lock`
     is an error too.
10. **Commands:**
    - **`turf fetch [--offline] [--locked]`** does everything `build` does
      up to writing `turf.lock` (resolve, fetch, extract, verify) and does
      not compile. Printing one line per git dependency is fine.
    - **`turf update [name…]`** refreshes the mirror of each named git
      dependency (all of them with no names) and re-resolves its ref:
      - a tag re-resolves (a moved tag moves);
      - a branch moves to its tip;
      - a `rev` resolves to the same commit, so it is a no-op by nature.

      Then it extracts, hashes and writes the lock. It prints `<name>
      <old12> -> <new12>` for each change, and `<name> unchanged` otherwise.
      A named path dependency: "'x' is a path dependency; it is always used
      as it is on disk". An unknown name is an error. `--offline` with
      `update` is a usage error.
    - **`turf add <name> --git <url> (--tag T | --branch B | --rev R)`**:
      exactly one ref, else a usage error. It fetches and extracts first and
      checks the package's name and root module, like `add --path`, then
      writes one line: `<name> = { git = "<url>", tag = "<T>" }`. `add
      --git --offline` is a usage error.
    - **`turf remove`** of a git dependency: removes the line, as for a
      path. The next build drops its lock entry.
11. **Legacy code is deleted**:
    - `cmd/turf/{install,update,publish}.go` (the pre-2.0 registry model;
      `cmd_publish.go`'s F-7c stub stays);
    - `internal/{legacymanifest,resolver,lockfile,cache,config,archive,semver,checksum}`.

    It stays reachable in git history: the subtree import `350acd8` brought

## Why

The 2.0 question is how someone outside the project obtains, builds,
imports and distributes a non-trivial TurfLang project. Today:
- Module names are flat file stems, searched stdlib → `lib/usr` → source
  directory → cwd.
- A local `json.tr` is silently shadowed by the stdlib (audit F-19).
- Two files named `util.tr` in different directories cannot coexist.
- `turf-cli`, a separate Go tool last touched 2026-06, writes
  `turf.toml`/`turf.lock` and installs into `turf_modules/`, which the
  compiler never searches.

So there is no working way to depend on anyone else's code
(`ROADMAP_v2.0.0.md` LEC-001, Part IX).

**Why the roadmap's DEC-8 was overturned.** The roadmap recommended writing
the project tool inside the C++ driver and not shipping `turf-cli`. The
owner chose the Go CLI as the front end. Reasons recorded for this decision:
- The work LEC-001 adds is TOML, running `git`, hashing, caching and
  archives. Go's standard library and ecosystem handle all of it; in C++
  each would be written by hand or pulled from LLVM piecemeal.
- The roadmap's own objections are all met by the constraints F-PKG-1
  imposes:
  - *One version to ship:* same tree, same archive, exact version handshake.
  - *No Go in the release pipeline:* `CGO_ENABLED=0 go build` produces a
    static binary and cross-compiles without a C toolchain, which is cheaper
    than the C++ it replaces.
  - *No two programs called `turf`:* the compiler becomes `turfc`.
- The split is the proven Cargo/rustc one: the tool fetches and locks, the
  compiler is told where each package is.
- It stops `src/main.cpp` (1896 lines, already slated for splitting in the
  module-breakdown plan) from absorbing a package manager.

## Language semantics

### Old behaviour
- `import foo;` takes the **first** of `$TURF_HOME/lib/std/**/foo.tr`,
  `lib/usr/**/foo.tr`, `<source dir>/foo.tr`, `<cwd>/foo.tr`. A local
  `json.tr` beside `main.tr` is never loaded while the stdlib has a `json`;
  the program silently gets the stdlib's.
- There are no packages. `turf-cli`'s `turf install` copies packages into
  `turf_modules/`, which no import ever reaches.
- `turf` is the compiler: `turf file.tr [flags]`.

### New behaviour (as frozen; the toolchain split, single-file collisions and project mode with path dependencies are implemented; git dependencies and `turf.lock` are not)
- Single-file mode: the same four roots, but all are examined. A local
  `json.tr` plus `import json;` is a hard error naming both files.
- Project mode:
  - `import foo;` resolves to exactly one of the package's own `src/**/foo.tr`,
    a direct dependency named `foo`, or stdlib `foo`. More than one is an
    error.
  - Dependencies are `path`/`git` entries in `turf.toml`, pinned in
    `turf.lock`.
- `turf` is the Go CLI. `turf file.tr [flags]` still works because it is
  forwarded to `turfc` unchanged. `turf compile file.tr [flags]` is the
  spelled-out form, and the other compiler modes get subcommands (`check`,
  `fmt`, `explain`, `migrate`, `dump`).

### Is this breaking?
Yes, in two places:
- **The silent-shadow case becomes an error** (R1, safe: a program that hit
  it was already running code its author did not write). Migration: rename
  the local module.
- **Anything that invoked the compiler as `build/turf` or `bin/turf` by
  path** now finds the CLI there. The CLI forwards non-subcommand
  invocations unchanged, so the old command lines keep working. Scripts in
  this repository are pointed at `turfc` directly in stage 2, so the test
  suite does not depend on the CLI.

## Compiler architecture
Stage 1 changes no compiler code. Planned, per the freeze:
- **Driver:**
  - Target renamed `turfc`; `--version`.
  - The package-graph input (stage 4): repeated flags or a plan file. LLVM's
    `llvm/Support/JSON.h` is available if it is a file.
- **Parser module resolution** (`ParseModuleImportByName`, `IndexModuleDir`):
  - Examine every root and collect candidates by canonical path (stage 3).
  - Resolve against the package graph when one is given (stage 4).
- **Resolver:** module identity gains the package where two packages' module
  names coincide (F-TYPE-1's module component).
- **Capability check:** `HasRawPointerCapability()` becomes per-package
  (stage 4): honored if the file is under the install root, or its package's
  allow bit is set, or (single-file mode) `--allow-unsafe-modules` was
  given.
- **Diagnostics:** new typed errors for module ambiguity, internal-module
  access and unknown dependency. Codes are assigned when implemented. No new
  `SLM::ErrorCategory` (F-DIAG-3).

## Runtime changes
None. `libturfrt` stays statically linked into every executable (RT-001);
LEC-001's distribution story relies on that and does not change it.

## Standard-library changes
None planned. Consequence of F-PKG-2: a library package may not be named
after a stdlib module, and a new stdlib module can make an existing user
module name ambiguous (see *Unresolved questions*).

## New invariants
Added to `INVARIANTS.md` (*Packages and module resolution*) by stage 4:
- **INV-PKG-1**: every `import m;` resolves to exactly one file or is an
  error (E090 / E091), with no precedence between roots. It is enforced by
  the candidate collection itself.
- **INV-PKG-2**: a module's identity is (package, path). Every pass after the
  parser sees identities only.

## Removed assumptions
- **"`build/turf` is the compiler."** After stage 2 it is the CLI, and the
  compiler is `build/turfc`.
  - Scripts, CI, `turf-lsp`, the editors, and the `homebrew-turf`/
    `scoop-turf` recipes all assume the old name. 28 files in this
    repository alone reference `build/turf`.
  - `TURF_COMPILER` keeps meaning "the compiler binary"; it must now point
    at `turfc`.
- **"Search order resolves conflicts."** In both modes, a name found in two
  roots is an error, never "first root wins". Code that relied on ordering
  (for example, a test fixture shadowing a stdlib module on purpose) breaks
  loudly.
- **"The project tool and the compiler are one version because they are one
  binary."** They are one version because they are built from one tree and
  checked at run time. A hand-assembled pair from different builds is
  refused by the handshake, not silently tolerated.
- **"`lib/usr` is where packages go."** It never received any. Project mode
  ignores it, and REL-003 retires it.

## Known pitfalls
- **Stage 5: building the compiler tree now needs the Go module proxy the
  first time**, not just a Go toolchain. `turf-cli` is an `ALL` CMake target
  and `cli/` has its first dependency (`github.com/BurntSushi/toml`), so on a
  machine with Go but no network (verified with `GOPROXY=off` and an empty
  module cache: `module lookup disabled by GOPROXY=off`) the target fails, and
  with it `cmake --build`. When that failure lands first under a parallel
  make, `build/turfc` is not linked at all: the first build of this session
  ended exactly that way, from a Go compile error rather than a download, but
  it is the same mechanism. AGENTS.md's "Go is optional" covers Go being
  *absent*, not Go being unable to fetch.
  - **Resolved at merge by vendoring:** `cli/vendor/` (172 KB, from
    `go mod vendor`) is committed, and Go builds from it automatically.
  - Verified: with `GOPROXY=off` and an empty `GOMODCACHE`, `go build
    ./cmd/turf` and `go test ./...` both succeed.
  - The rule for the future: adding or upgrading a Go dependency means
    re-running `go mod vendor` in `cli/` and committing the result. A
    `go.mod` change without it fails the build, because Go refuses an
    inconsistent vendor directory.
  - A Go *compile* error still fails `cmake --build`, which is correct: it
    is a broken tree, not a missing network.
- **Stage 5: BurntSushi/toml keeps no key positions**, so a manifest error's
  line number is recovered by re-scanning the text for the key
  (`parser.lineOf`). A key spelled with dots, or a dependency declared as a
  `[dependencies.x]` table, may get no line; the message then names the file
  only, which is the honest answer.
- **Stage 5: `add` then `remove` is byte-identical only when
  `[dependencies]` already existed.** When `add` has to append the table,
  `remove` deletes the entry and leaves the header and a blank line. A file
  with no final newline gets one on the line `add` inserts after. Both are
  cosmetic; a test pins the first.
- **Stage 5: `remove` only searches `[dependencies]`.** The spec's
  `^\s*<name>\s*=` over the whole file deletes `name = "app"` from `[package]`
  when the dependency is called `name` or `version` (both valid package
  names). A regression test covers it.
- **Stage 5: `turf add` resolves the whole graph, so any dependency that does
  not resolve blocks every `add`**, including a git dependency until stage 6
  makes those resolvable. That is the price of "add never writes what build
  rejects"; the error says "cannot add 'x' (nothing was written)" and names the
  real problem.
- **Stage 5: `turfc` runs with its cwd set to the project root, and the
  compiler path must be absolute for that.** Go resolves a *relative* executable
  path against `cmd.Dir`, so a relative `TURF_COMPILER` would silently point at
  the wrong file; `withProject` makes it absolute first. The user's program
  still runs in the user's own cwd.
- **Stage 5: diagnostics name imported files but not the entry file.**
  Verified: an error in a dependency's root module prints `in file
  /abs/path/geometry/src/geometry.tr` (absolute, because the graph's `src`
  paths are), while an error in `src/main.tr`, or in the library file `turf
  build` checks directly, prints only line and column. Pre-existing compiler
  behaviour; LEC-005 (diagnostics) owns it. Do not "fix" it in the CLI: turf
  never rewrites a diagnostic.
- **Stage 5: `turf check` with no file used to forward to the compiler and now
  means the project.** A script that ran `turf check --module` with no file
  gets the "not inside a TurfLang project" usage error (exit 2) instead of the
  compiler's missing-input error. Nothing in the repository did.
- **Stage 5: every `turf build` recompiles**, since `turfc` has no incremental
  mode, and prints turfc's own "Compiled to …" lines, since the CLI never
  rewrites compiler output.
- **Stage 5: a `project_smoke.sh` setup step can be legitimately refused.**
  `turf add` rejects a name conflict or a cycle, so a test *for* the conflict
  or cycle has to write the offending line by hand; the script does, and also
  asserts that `add` refuses.
- **Stage 5: the project commands are untested on Windows.** The smoke script is
  bash, the graph carries absolute paths with backslashes there, and the CI
  Windows job does not run it. The manifest stores dependency paths with forward
  slashes, so a manifest is portable; a build on Windows is unverified.
- **Stage 4: a new place that reads a module qualifier must call
  `ModuleKeyFor()`.** Identities reach the later passes only because the
  parser rewrites every qualifier it reads. A future syntax that spells a
  module name (a qualified extension-method receiver, a new import form)
  and skips the rewrite would work in single-file mode, where the key is
  the name, and silently resolve to the wrong module in a package build,
  where it is not.
- **Stage 4: dependency identities leak into some messages.** E088/E089 go
  through `DisplayModuleName()`. Every other message that names a module
  (ambiguous flat import, "declared in module X, use `X::T`", E031
  suggestions, `--dump-*`) prints `geometry/util` raw. Worse, a hint that
  suggests the spelling `X::T` suggests `geometry/util::T`, which does not
  parse. Route those through `DisplayModuleName()` (LEC-005, diagnostics),
  and for a suggested *spelling* use the importing file's own spelling of
  the module.
- **Stage 4: `IndexPackageSources()` caches per src root for the process.**
  That is right for one compile, and the same as `IndexModuleDir()`'s
  lib/std cache. A long-lived embedder (an LSP re-analysing an edited
  project) would not see a new or deleted module file. Before REL-002
  rebuilds the LSP on package builds, make the cache resettable through the
  SMP-001 facade.
- **Stage 4: the SLM Sandbox re-analyses a fix in-process.** In a package
  build its snippet's path is in no package, so its imports resolve
  stdlib-only and a suggestion touching a dependency is discarded as not
  compiling. It is safe (nothing wrong is shown), just less helpful. It
  needs the facade to carry the graph (REL-002).
- **Stage 4: a duplicated warning in a dependency shows the wrong
  snippet.** Seen while testing the unsafe bit: an unused variable in a
  dependency was reported twice, once without its file and with the main
  file's line text. This is the known duplicate-warning problem (roadmap
  N8, LEC-005), not package-specific.
- **Stage 3: a new resolution path must decide who is importing.** Any future
  caller of `CollectModuleCandidates()` or `ParseModuleImportByName()` has to
  say whether the import comes from inside lib/std, or is synthetic like the
  prelude. Otherwise it reintroduces the "a user's local `list.tr` breaks the
  stdlib" failure: `strings` imports `list`, and every program gets
  `strings`. Stage 4's package graph generalises this (the stdlib is a
  package that imports only itself), so it must keep the rule, not replace
  it.
- **Stage 3: an ambiguous import cascades.** Each later `m::f()` also reports
  E031 "isn't a known module", exactly as after E027 "module not found". The
  E090 is the real error, and the E031s are noise. Fixing it belongs to
  LEC-005 (diagnostic cascades), not to module resolution.
- **Stage 3: `--resolve` on a module file exits 1** ("No entry point found")
  because it goes on to link. This is pre-existing. For a real check that a
  module resolves and type-checks, use `turfc --check --module`; a loop over
  `--resolve` exit codes reports every module as failing.
- **`TURF_COMPILER`, not a new variable.** The CLI's override reuses the
  name `scripts/test_runner.sh` and CI already use, so there is one knob
  meaning "which compiler". Do not add `TURFC`.
- **The test suite must not depend on Go.** After stage 2,
  `scripts/test_runner.sh` and the other scripts invoke `build/turfc`
  directly. A contributor without Go must still be able to build and test
  the compiler: the CLI's CMake target is conditional on Go being found.
- **Canonicalise before counting candidates** (stage 3). When the source
  directory is the cwd, the same file is found twice; counting paths
  instead of canonical paths turns every local import into a false
  ambiguity.
- **`turf add`/`remove` must not rewrite `turf.toml` wholesale.** Go's TOML
  libraries do not round-trip comments or layout. Edit the
  `[dependencies]` table in place; a user's comments surviving `turf add`
  is a test case.
- **`TurfInstallRoot()` strips the executable's file name** to find
  `<bin>/..`. It does not care what the binary is called, so the rename is
  safe there. Confirm it rather than assuming it, and keep `lib/` discovery
  working for `build/turfc` with no `TURF_HOME`.
- **The pre-2.0 CLI's hand-rolled manifest reader** (line-by-line
  `key = "value"`) cannot parse inline tables. Stage 5 replaces it; do not
  extend it.

Found during stage 2, each verified live:
- **`TURF_HOME` in a developer's shell decides which checkout's `lib/` a build
  uses.** In the authoring environment it pointed at the main checkout, so a
  worktree's `build/turfc` silently used the main checkout's `lib/std` and
  `lib/libturfrt.a`, and `turfc --resolve lib/std/core/char.tr` reported a false
  `Ambiguous UFCS call` (observed with `TURF_HOME` set, gone with it unset; the
  cause is inferred, not traced: the worktree's file is not the path the
  prelude resolved under the other root, so the self-import skip in
  `ParsePreludeImports()` would not fire). Run every check with
  `TURF_HOME` unset; `scripts/cli_smoke.sh` unsets it itself. A build directory
  outside the repository (the DoD's `/tmp/.../nogo`) has its install root at
  `<build>/..`, which holds no `lib/`, so that suite run needs `TURF_HOME`
  pointing at the checkout, in addition to `TURF_COMPILER`.
- **`turf run` must not `signal.Ignore` SIGINT.** An ignored disposition is
  inherited across `exec`, so the program itself would ignore Ctrl-C.
  `signal.Notify` with a buffered channel discards the signal in `turf` while
  the child gets the default. Checked: SIGINT to the process group during a
  `while (true)` program exits 130 and leaves no `turf-run-*` directory.
- **A successful `turfc` compile prints `Compiled to <name>` on stdout**, so
  any byte-identity comparison between two invocations must use the same `-o`.
- **An unanchored `.gitignore` entry named `turf` ignores `cli/cmd/turf/`.**
  Files already tracked (the subtree import) are unaffected, which is why
  commit 2 worked and only new files in commit 5 would have been dropped.
- **The Windows release job is unverified.** `actions/setup-go` puts Go on the
  Windows `PATH`; `msys2 {0}` steps see a minimal one, so CMake may not find
  `go` there and skip `build/turf.exe`.
- **Under CMake, `find_program` searches `/usr/bin` and `/usr/sbin` regardless
  of `PATH`**, so hiding Go for the "Go not found" check took
  `-DCMAKE_IGNORE_PATH`, not just a stripped `PATH`.

## Unresolved questions
1. **Stdlib growth vs. user module names.** Under F-PKG-2, adding a stdlib
   module `foo` in a 2.x minor release makes every existing user module or
   dependency named `foo` an import ambiguity: the module-level version of
   the problem FDN-003 fixed for types. 2.0 accepts this (a loud error, not
   silent shadowing). The additive fix is an explicit spelling, e.g.
   `import std::foo;`, and a matching one for the own-package case. Not
   frozen.
   - **Owner plan (2026-09-30): GitHub issue #264**, "Module resolution now
     also should have library resolution in module ambiguity, critical before
     2.0.0". Before 2.0.0 the ambiguity error will list candidates as
     `stdlib::list`, `<dependency>::list`, `src::list`, and `import std::list;`
     will pick the stdlib's, searching the stdlib's flattened module index.
   - Explicitly not for now. Stage 3 ships the error only, with a "rename your
     file" hint.
   - Constraints for whoever implements it:
     - `import std::list;` today parses as a *symbol import* of `list` from a
       module named `std`. `std` must become a reserved package qualifier,
       never a module name. Freezing that needs a `FREEZE.md` amendment
       (§6.16's non-goals currently exclude path-qualified imports).
     - The E090 hint becomes "write `import std::list;`" once that exists.
     - E090's candidate kinds are already the natural labels for it
       (standard library / dependency / own module).
2. **How the LSP learns the package graph.** `turf-lsp` analyses files
   in-process through the SMP-001 facade and needs the same graph `turfc`
   gets. Options: a `turf metadata` command (the `cargo metadata` pattern)
   that the LSP runs, or the LSP reading the manifest itself (which would
   break F-PKG-1's "only the CLI reads the manifest"). Recommendation:
   `turf metadata`. REL-002 decides.
3. **Root package's own `unsafe module;` without listing** (F-PKG-4) is a
   decision made in this freeze beyond the roadmap's text. Recorded here so
   the owner can revisit it before stage 4 implements it.
4. **Diagnostic hints still spell the compiler as `turf --…`** (E088's
   `turf --migrate=pub --write`, `--explain`'s `turf --explain E0NN`). They
   stay correct through passthrough, so stage 2 leaves them alone.
   - Whether they should say `turf migrate pub` / `turf explain`, or `turfc
     --…`, is a wording decision for LEC-005 (diagnostics).
   - Changing them means updating `tests/api/analysis_test.cpp`'s
     hint-fragment assertions too.
   - Stage 2 also left every `turf ...` command in `showcase/*.tr` header
     comments, `src/ParserModule.cpp` comments and the wording of `turfc`'s own
     `Unknown error code` hint alone, for the same reason.
5. **The Windows release job's Go discovery** (see *Known pitfalls*). If the
   added check step fires, the fix is `path-type: inherit` on `Setup MSYS2` or
   a separate `go build` step; the first real tag build will show which.
6. **`docs/reference/cli_and_diagnostics.md` still describes the compiler as
   `turf`** everywhere except one `Usage:` line. That is the user-facing
   reference the handbook queue owns; it should be rewritten around
   `turf`/`turfc` when stage 8 writes `docs/reference/projects_and_packages.md`.
7. **Resolved after stage 2: `--check` and the entry point.** As landed,
   `--check` skipped the entry-point check, so `turf check` passed a file that
   `turf compile` rejects. The owner asked for a program's missing `main` to be
   an error.
   - Nothing in a file says whether it is a program or a module: a module is
     only "a file someone imports". So the caller says which:
     - `turfc --check x.tr` checks `x.tr` as a program, and the missing `main`
       error is the same as a compile's, plus a hint naming `--module`.
     - `turfc --check --module x.tr` checks it as a module.
   - `--module` without `--check` is an error, because a module cannot be
     linked.
   - `turf dump` always passes `--module`: a dump is an inspection, not a
     verdict.
   - Covered by `scripts/cli_smoke.sh`.
   - In a package build (stage 4) the package graph answers the question
     instead: only `src/main.tr` is an entry point.
8. **Owner plan: leave the monorepo before the public release** (2026-09-30:
   "before release, I will try to make this not a monorepo, but for now,
   it's fine").
   - **Unblocked by the same-day amendment to F-PKG-1.** The owner decided
     the two programs are independently versioned: "turflang and turf-cli can
     grow independently as long as they work together … Turflang being in
     2.0.0 and CLI being at 1.0.0 will display both versions separately".
   - The version-equality handshake became a `major.minor` **driver
     interface** check: `turfc --version` line 2 is `interface M.m`, and the
     CLI declares the interface it needs. Nothing in the rule depends on one
     tree any more.
   - What moves when the repo splits: `cli/`'s Go module path
     (`github.com/turf-lang/turf-lang/cli`), the CMake `turf-cli` target, and
     `scripts/cli_smoke.sh`. The smoke script is the compatibility test and
     then runs in the CLI's CI against a released `turfc`.
   - Same decision: `turf` is the user's tool and `turfc` the tooling
     interface. User-facing docs and hints say `turf`, and users are never
     asked to type `turfc`.
   - Suggested for REL-003, not decided: install `turfc` under
     `libexec/turf/` instead of `bin/`, the way git keeps its helpers off
     `PATH`. Discovery would then need a
     `<turf dir>/../libexec/turf/turfc` step.
