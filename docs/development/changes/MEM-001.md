## Why

A collector can only collect what it allocated. Before this group, every
"managed" allocation — a string returned by concatenation, a `List<T>`'s
growing backing buffer — was a bare `malloc`/`calloc`/`realloc` call
indistinguishable, at the source level, from a programmer's own manual
allocation via `mem::alloc`. `docs/architecture/memory_model.md` §1.7
(pre-this-group) stated it plainly: "Turflang has no automatic memory
management today... every heap allocation... is freed only if some line of
code explicitly calls `free`/`mem::free` on it." MEM-002 (the actual
collector) needs a single, closed answer to "what am I allowed to trace and
reclaim" — this group is what builds that answer, by routing every
language-owned allocation through `libturfrt`'s `turf_rt_alloc` family
instead of a bare `malloc`, with **zero observable behaviour change**: doing
the rerouting as its own group means the large, mechanical part (which
`malloc` call site is GC-heap vs. manual-heap) is reviewed separately from
the small, subtle, risky part (the collector itself, MEM-002).

## Language semantics

### Old behaviour

No previously-visible language-level behaviour changes at all — every
`.tr` program's stdout/exit code is byte-identical before and after this
group (verified: full 737→738-test suite unchanged in outcome, the one new
test is this group's own; `scripts/opt_levels_smoke.sh`/
`scripts/debuginfo_smoke.sh` both still clean). What's new is a Turf-level
**capability**: three bare language intrinsics, `gc_alloc(n)`,
`gc_alloc_zeroed(n)`, and `gc_realloc(p, n)` (`include/Intrinsics.h`
category 1, dispatched in `FuncCallExprAST::codegen()` exactly alongside
`typeof`), each evaluating to a raw `void*` — the identical "untyped
result, caller casts" contract `mem::alloc()`/`mem::realloc()` already
have. Like `sizeof`/`typeof`, these are callable with no module qualifier
and no import; like any other raw-pointer-producing expression, binding the
result to a local still requires `unsafe { }` outside a module that
declares the `unsafe module;` capability (LANG-002's existing gate,
unmodified by this group).

### New behaviour

```turf
unsafe module;
fn demo(): void {
    mut p: void* = gc_alloc(16);          // libturfrt's turf_rt_alloc(16, NULL)
    mut z: void* = gc_alloc_zeroed(16);   // turf_rt_alloc_zeroed(16, NULL) -- zero-filled
    mut r: void* = gc_realloc(p, 32);     // turf_rt_realloc(p, 32, NULL)
}
```

Every one of the GC-heap call sites classified below (see *Removed
assumptions*) now uses these instead of a bare `malloc`/`calloc`/`realloc`
or `mem::malloc`/`mem::realloc`. The allocated bytes, their contents, and
every existing program's observable behaviour are unchanged — `turf_rt_alloc`
is, as of RT-001, still a thin `malloc` wrapper under the hood (MEM-002 is
what gives it a real heap), so this group changes *which function is
called*, not *what memory comes back*.

### Is this breaking?

No. Verified live: the full suite (737 tests before this group, 738 after —
the one new test is this group's own `tests/05_arrays_pointers_ffi/
21_gc_alloc_intrinsics.tr`) passes identically; `lib/std/**` and
`showcase/**` both compile clean directly; `showcase/http_server.tr` +
`curl`, and `showcase/kv_store_server.tr` + `showcase/kv_store_client.tr`,
were smoke-tested live end to end (real socket I/O through the rerouted
`net::TcpConnection.read()`, real `Map<string,string>` growth through the
rerouted `map.tr`) with correct output. The only new *capability* is
additive (three new bare intrinsics no existing program could have been
using, since they didn't exist).

## Compiler architecture

- **Builtins** (`src/Builtins.cpp`) — `gc_alloc`/`gc_alloc_zeroed`/
  `gc_realloc` registered in `g_builtins` (arity 1, 1, 2) alongside `typeof`.
- **Resolver** (`src/ResolverCall.cpp`) — added to the `BareIntrinsics` set
  so a bare, unqualified call to one of these three names skips the
  "unresolved function" error path, exactly like `typeof`.
- **TypeChecker** (`src/TypeCheckerCall.cpp`) — all three short-circuit to
  `void*` (`std::make_shared<TurfPointerType>(TurfVoid())`), the same
  minimal-validation convention `typeof` already uses (arity checked
  generically above this branch; no argument *type* validation — a
  non-`int` byte count would simply codegen with whatever LLVM width its
  own expression produces, both runtime parameters already being 64-bit
  `size_t`/matching Turf's 64-bit `int`).
- **Codegen** (`src/CodegenCore.cpp`'s `getExprType()`, `src/CodegenFunc.cpp`'s
  `FuncCallExprAST::codegen()`) — `getExprType()` gets an explicit `void*`
  case for the same reason `typeof` does (these are bare intrinsics with no
  `ResolvedCallTarget`/`FuncReturnTypes` entry; falling through to the
  mangled-name reconstruction path would just fail to find one).
  `FuncCallExprAST::codegen()` dispatches all three, alongside `typeof`,
  before the "Issue #9: Codegen trusts the Resolver" path that assumes a
  real `MangledName` exists — get-or-declares the matching `turf_rt_*` LLVM
  function prototype (mirroring `CodegenPanic()`'s existing pattern for
  `turf_rt_panic`) and emits the call, with `desc` always a literal null
  pointer (see *Removed assumptions* for why no real `TurfTypeDesc` is ever
  passed here).
- No Lexer/AST/Parser/CFG changes — these are dispatched exactly like
  `typeof`, an existing bare-call-expression shape, not new grammar.

## Runtime changes

`runtime/turfrt.h`/`runtime/turfrt_alloc.c` gain:
- `turf_rt_alloc_zeroed(bytes, desc)` — a `calloc(1, bytes)`-backed
  zero-filling counterpart to RT-001's `turf_rt_alloc`.
- `turf_rt_realloc(p, new_size, desc)` — a `realloc()`-backed resize,
  needed so collection growth keeps realloc's in-place-extend behaviour
  instead of degrading to always-allocate-fresh-and-copy (a real, if
  currently unobservable, peak-memory regression the naive "just call
  `gc_alloc` again and memcpy" approach would have introduced).
- `TurfRtStats`/`turf_rt_stats()` — the allocation-accounting hook stage 3
  of this group's roadmap entry calls for, explicitly built to become
  MEM-002's own regression harness (a future collector test can diff
  `turf_rt_stats()` before/after a collection to prove it reclaimed
  something). Three monotonically-increasing counters (`alloc_count`,
  `realloc_count`, `bytes_requested` — a cumulative *request* total, not a
  live-byte count, since nothing collects yet so there is no "live" to
  measure), incremented inside all three alloc functions. Not reachable
  from Turf source under any name (Rule B2/B3) — read directly from C
  (`scripts/mem_smoke.sh`, linked straight against `lib/libturfrt.a`) or
  via `turf_rt_shutdown()`'s new opt-in stderr dump, gated on the
  `TURF_RT_STATS_DUMP` environment variable being set to anything
  non-empty, specifically so it changes NO existing compiled program's
  default output (verified live: `scripts/mem_smoke.sh` check 3 confirms
  silence with the variable unset).

## Standard-library changes

Every `malloc`/`calloc`/`realloc`/`mem::malloc`/`mem::realloc` call site in
`lib/std` was enumerated and classified into exactly one of two heaps
(**Rule: a value the LANGUAGE is responsible for returning to the caller —
string results, collection backing buffers — is GC-heap; a value the
PROGRAMMER explicitly owns, or that is transient scratch memory paired with
an explicit `free`, is manual-heap**, per F-MEM-3):

**Rerouted to the GC heap** (`gc_alloc`/`gc_alloc_zeroed`/`gc_realloc`):

| File | Site | Old | New | Why GC-heap |
|---|---|---|---|---|
| `lib/std/core/strings.tr` | `operator +` | `malloc(n)` | `gc_alloc(n)` | returns a `string` result |
| " | `substring` | `malloc(len+1)` | `gc_alloc(len+1)` | returns a `string` result |
| " | `replace`'s `chbuf` | `malloc(2)` | `gc_alloc(2)` | feeds into a `string` result via `+` |
| " | `to_upper` | `malloc(n+1)` | `gc_alloc(n+1)` | returns a `string` result |
| " | `to_lower` | `malloc(n+1)` | `gc_alloc(n+1)` | returns a `string` result |
| " | `pad_left` | `malloc(target_len+1)` | `gc_alloc(target_len+1)` | returns a `string` result |
| " | `pad_right` | `malloc(target_len+1)` | `gc_alloc(target_len+1)` | returns a `string` result |
| `lib/std/io/io.tr` | `input()` | `calloc(4096, 1)` | `gc_alloc_zeroed(4096)` | returns a `string` result; zero-reliant (see below) |
| " | `read_to_string()` | `calloc(size+1, 1)` | `gc_alloc_zeroed(size+1)` | returns a `string` result; zero-reliant (documented: the byte past the last one read is the NUL terminator) |
| `lib/std/io/net.tr` | `TcpConnection.read()` | `mem::alloc_zeroed(1, maxBytes+1)` | `gc_alloc_zeroed(maxBytes+1)` | returns a `string` result; zero-reliant (recv() may write fewer than maxBytes bytes) |
| `lib/std/collections/list.tr` | `List.push` growth | `mem::malloc`/`mem::realloc` | `gc_alloc`/`gc_realloc` | collection backing buffer |
| `lib/std/collections/stack.tr` | `Stack.push` growth | " | " | collection backing buffer |
| `lib/std/collections/queue.tr` | `Queue.enqueue` growth | " | " | collection backing buffer |
| `lib/std/collections/set.tr` | `Set.add` growth | " | " | collection backing buffer |
| `lib/std/collections/map.tr` | `Map.put` growth (both `keys` and `values` arrays) | " | " | collection backing buffer (×2) |

**Deliberately left on the manual heap** (F-MEM-3 — a programmer-owned
value, or scratch memory paired with an explicit `free`):

| File | Site | Why manual-heap |
|---|---|---|
| `lib/std/mem/mem.tr` | `alloc`/`alloc_zeroed`/`grow`/`dup`/`alloc_aligned` (all of `mem.tr`) | this **is** the manual heap's own implementation — F-MEM-3 names it explicitly |
| " | `Pool<T>.track`'s `items` backing array | `Pool<T>` exists to batch-free a set of manual-heap allocations; its own bookkeeping array must stay freeable the ordinary way (`free_pool()` calls `free(pool.items)` directly) — putting it on the GC heap would make that a cross-heap free, the exact hazard F-MEM-3 forbids |
| `lib/std/io/net.tr` | `buildSockAddr()`'s 16-byte sockaddr image | transient C-struct scratch memory, explicitly `mem::free`d at every call site (`connect()`, `bind()`) immediately after use |
| " | `TcpListener.bind()`'s `optVal` (setsockopt scratch) | same — explicitly `mem::free`d right after `setsockopt()` |

`lib/std/json/json.tr` and `lib/std/http/http.tr` were checked directly
(`grep -n "malloc\|calloc\|realloc"`) and contain no allocation call sites
of their own — both build entirely on `strings`/`list`/`map`, already
covered above.

**Import cleanup, a direct consequence of the reroute, not a separate
pass**: `import mem;` removed from `list.tr`/`stack.tr`/`queue.tr`/
`set.tr`/`map.tr` (each imported it *solely* for `mem::malloc`/
`mem::realloc`, verified by grep before removal — no other `mem::` symbol
was used in any of the five). `extern fn malloc` removed from
`strings.tr` (its own comment used to say "malloc is declared directly
here to avoid inter-stdlib import issues" — now dead, since every call
site uses the bare `gc_alloc` intrinsic instead). `extern fn calloc`
removed from `io.tr` for the identical reason. `net.tr` keeps `import mem;`
(still used by the two manual-heap sites above).

## New invariants

None added to `INVARIANTS.md`. This group deliberately does not introduce
a NEW checkable invariant of its own — "every GC-heap allocation goes
through `turf_rt_alloc`" is not yet independently *enforceable* (there is
no static or dynamic check that would catch a future stdlib change quietly
reverting to a bare `malloc`; `scripts/mem_smoke.sh`'s allocation-count
assertion is regression coverage for the CURRENT set of call sites, not a
structural guarantee). MEM-002 is positioned to add the real invariant
("every reachable GC-heap object is traced and reclaimed") once there is
something to enforce it.

## Removed assumptions

- **"A `string`'s pointer-identical representation to `ptr`/`void*` means a
  leaked buffer can, in principle, be freed manually via `mem::free` once
  cast."** This was true, harmlessly, before this group (nothing on either
  side of that cast belonged to a distinct heap). It is no longer true in
  the same harmless way: a `string` returned by concatenation or a stdlib
  string function now lives on the GC heap, and `mem::free`ing a GC-heap
  pointer is exactly the cross-heap mistake F-MEM-3 forbids ("the two heaps
  do not merge" — this group's own "Must NOT reinterpret" entry). Nothing
  diagnoses this yet (MEM-002 is what gives the GC heap a block table to
  check a pointer against), so it is merely *unsupported* today rather than
  *rejected* — but a future session reading the pre-this-group version of
  `docs/architecture/memory_model.md` §1.4 (which stated the claim as
  fully true) would be relying on something this group specifically made
  false. Updated in place; see that document's current §1.4/§2.4/§2.6.
- **"Every collection's backing buffer grows via `mem::malloc`/
  `mem::realloc`, the identical mechanism `mem::alloc`/`mem::grow`
  themselves use."** True before this group (verified: `grep -n "mem::"
  lib/std/collections/*.tr` before this session's changes showed exactly
  this). False after: `List<T>`/`Stack<T>`/`Queue<T>`/`Set<T>`/`Map<K,V>`
  now allocate via `gc_alloc`/`gc_realloc` (the GC heap); only `mem.tr`'s
  own `Pool<T>` still uses `mem::malloc`/`mem::realloc` directly. A future
  session assuming "any `T*` field on a stdlib struct came from `mem::`"
  (e.g. when writing a debugger extension, or a leak-tracking tool) would
  be wrong for five of the six generic containers in the standard library.
- **"`turf_rt_alloc`'s `desc` parameter is always eventually populated with
  a real `TurfTypeDesc` once something actually calls it."** RT-001's own
  change record speculated this direction without committing to it (`desc`
  "may be NULL... callers that always have one should still pass it"). This
  group is the first real caller, and the honest answer turned out to be
  "never, structurally, not just contingently": none of the GC-heap call
  sites classified above are allocating ONE INSTANCE of a monomorphized
  aggregate the way `EmitAllTurfTypeDescs()`'s per-struct descriptors
  describe — a string is a raw byte run with no struct type at all; a
  `List<T>` backing buffer is N elements of `T`, and no descriptor shape
  for "N of T" exists yet (RT-001's own `pointer_word_bitmap` doc comment
  already flagged an array-shaped descriptor as MEM-002 territory, not
  something to invent speculatively here). Every one of MEM-001's
  `turf_rt_alloc`/`turf_rt_alloc_zeroed`/`turf_rt_realloc` call sites passes
  a literal `NULL`. A future session should not assume this changes without
  MEM-002 first deciding what an array-of-T descriptor even looks like.

## Known pitfalls

- **`gc_alloc`/`gc_alloc_zeroed`/`gc_realloc` are bare intrinsics reachable
  from ANY `.tr` file, not just `lib/std`.** Unlike `turf_rt_alloc` itself
  (never reachable from Turf source under any name — Rule B2/B3), these
  three ARE part of the ordinary language surface, exactly like `sizeof`/
  `typeof`. This is intentional (MEM-001's own roadmap text explicitly
  names `@gc_alloc(T, n)`-shaped syntax as the expected mechanism), but a
  future session tightening capability boundaries elsewhere should not
  assume these need the SAME gate `unsafe module;`/`--allow-unsafe-modules`
  applies to raw pointer SIGNATURES — a `void*` result from `gc_alloc` is
  gated the ordinary way (binding it to a local needs `unsafe { }`, exactly
  like binding any other raw pointer expression), but the bare CALL itself
  needs no capability at all, matching `typeof`'s own unrestricted bare-call
  status.
- **`turf_rt_realloc`/`gc_realloc` exist specifically to avoid a
  peak-memory regression, not because the simpler "always allocate fresh +
  copy" approach would have been incorrect.** It would have been
  behaviour-*observably*-identical in every test this group's suite can
  see (nothing measures peak RSS), but it would have thrown away realloc's
  in-place-extend fast path on every single collection growth in every Turf
  program that exists, silently. A future session simplifying the runtime's
  API surface should not fold `turf_rt_realloc` back into "just call
  `turf_rt_alloc` again" without first checking whether peak memory matters
  to whoever is asking.
- **`desc` is `NULL` at every one of this group's call sites, and that is
  not a placeholder waiting to be filled in — see *Removed assumptions*
  above.** A future session should not treat "pass the real TurfTypeDesc"
  as leftover MEM-001 cleanup; it requires MEM-002 (or later) to first
  define what a descriptor for an N-element array of `T` even looks like,
  which does not exist today in any form.
- **The `TURF_RT_STATS_DUMP` stderr dump is a `mem_smoke.sh`-only
  diagnostic, not a documented CLI feature.** It intentionally has no flag,
  no `--help` entry, and no `docs/reference/` mention — it exists solely so
  a C-level smoke test can observe `libturfrt`'s internal counters without
  modifying `.tr` source. Do not point end users at it; if allocation stats
  ever need to be genuinely user-facing (a `turf --mem-stats` flag, say),
  that is new scope requiring its own design, not a promotion of this hook.
- **`mem::Pool<T>`'s own `items` backing array staying on the manual heap
  is a deliberate exception to "collections are GC-heap", not an
  oversight.** A future session doing a mechanical sweep for "any stdlib
  struct with a `T*`/`K*`/`V*` field should allocate via `gc_alloc`" would
  wrongly reroute `Pool<T>` too — its own `free_pool()` calls `free()` on
  that array directly, which would become a cross-heap free (a GC pointer
  handed to the manual `free`) exactly like the string/`mem::free` hazard
  in *Removed assumptions* above. `Pool<T>` is manual-heap bookkeeping FOR
  the manual heap; it is not a "collection" in the sense this group's
  reroute rule applies to.
