## Why

TYPE-002's own change record disclosed, but classified as "a coverage gap,
not a live correctness bug", that a by-value cycle closing only through a
concrete generic instantiation escaped `checkStructLayoutAcyclicityForClone()`
entirely:

```turf
struct A<T> { val: T }
struct B { back: A<B> }
fn main(): int { mut x: A<B> = A::default(); return 0; }   // turf: exit 139, no output
```

`A<T>` alone is not cyclic (its own field is the still-open parameter `T`)
and `B` alone is not cyclic (its own field is the still-uninstantiated
generic type `A<B>`) — the cycle `A<B> -> B -> A<B>` exists only once `T` is
substituted with the concrete `B`, and only the monomorphizer ever produces
that substitution. `checkStructLayoutAcyclicityForClone()` (TYPE-002 S13a)
runs per freshly-substituted clone specifically to catch this class of case,
but its shared DFS core resolved a `GenericType` field to its TEMPLATE's own
base name, not to the concrete clone actually being checked — so it never
saw the closing edge. The 2026-09-26 closure audit re-verified the crash
live and reclassified it: this is a live segfault (INV-LAYOUT-1 violation,
§23 DoD item 1), not a documented limitation.

## Language semantics

### Old behaviour
The reproducer above compiled with no diagnostic and crashed the compiler
itself (SIGSEGV, exit 139, no output) before ever reaching a running
program.

### New behaviour
Rejected at compile time with `StructLayoutCycleError` (E069), naming the
real cycle through the concrete instantiation:

```
error at line 1, col 1 [E069]
struct 'A_gen1_B' cannot contain itself by value.
cycle: A_gen1_B -> B -> A_gen1_B
Note: field 'A_gen1_B::val' has type 'B'
Note: field 'B::back' has type 'A<B>'
```

The same struct pair with the cyclic field made a pointer/nullable
reference (`back: A<B>*` / `back: &?A<B>`) is unaffected — it compiles and
runs exactly as it did before, since pointer-shaped fields were never edges
in this graph.

### Is this breaking?
No. The old "behaviour" was an uncontrolled compiler crash, not a program
any user could have been relying on; every input this change newly rejects
previously produced no output at all.

## Compiler architecture

- **Resolver.** `byValueEdgeTarget()` (`src/ResolverCore.cpp`, the shared
  helper both `checkStructLayoutAcyclicity()` (Pass 1, templates) and
  `checkStructLayoutAcyclicityForClone()` (TYPE-002 S13a, one clone) feed
  into the same `detectStructLayoutCycles()` DFS core) now tries a
  `GenericType` field's CONCRETE instantiation name first —
  `Monomorphize::instantiatedDeclName(GT->getBaseName(), GT->getTypeArgs())`
  — the exact mangled name `drainStructRequests()` (`Monomorphize.cpp`)
  already gives the clone before registering it into the same
  `KnownStructs` map (`Clone->getName()`, pre-existing code, unchanged).
  If that mangled name is a known struct, it is the edge target; otherwise
  the walker falls back to the original base-name behaviour verbatim. The
  fallback path is exercised, unchanged, by every Pass-1 template-only call
  (no clone has ever been registered at that point, so the mangled lookup
  always misses) and is what keeps the existing `Box<T> { inner: Box<T> }`
  template-level self-cycle test green.
- No change to `Monomorphize.cpp`, `checkStructLayoutAcyclicityForClone()`,
  or `detectStructLayoutCycles()` — the fix is entirely inside the one
  function that decides "does this field type contribute a graph edge, and
  to which node."

generics, until now.

## Removed assumptions

- **"A `GenericType` field's base name is an adequate proxy for its
  concrete instantiation, for acyclicity purposes" was never actually true
  once monomorphization existed** — it happened to be harmless for every
  case exercised before this fix because those cases either weren't
  cyclic at all, or were cyclic already at the TEMPLATE level (caught by
  the base-name match itself, e.g. `Box<T> { inner: Box<T> }`). The
  moment a cycle depended on which CONCRETE type argument was supplied
  (`A<B>` cyclic, some other `A<SomethingElse>` not), the base-name
  approximation silently walked into the template's own still-open `T`
  placeholder instead of the real clone, found no further edges, and
  missed the cycle. Any future by-value graph walk over generic fields
  needs to resolve to the concrete instantiation the same way, not repeat
  the base-name shortcut.

## Tests

Added, all under `tests/38_monomorphization/`:
- `fail_generic_instantiation_by_value_cycle.tr` — the reproducer above,
  rejected at compile time with E069 naming the `A_gen1_B -> B -> A_gen1_B`
  cycle.
- `fail_generic_instantiation_by_value_cycle_two_params.tr` — the same
  shape through the SECOND type parameter of a two-parameter generic
  struct (`struct P<X, Y> { x: X, y: Y }`, `struct Q { p: P<int, Q> }`),
  proving the fix doesn't depend on which parameter position carries the
  cyclic argument. Rejected with E069 naming `P_gen2_int_Q -> Q ->
  P_gen2_int_Q`.
- `29_generic_instantiation_cycle_via_reference.tr` — the positive twin:
  the identical `A<T>`/`B` pair with `back: &?A<B>` instead of `back: A<B>`
  compiles and runs, proving the fix rejects only the genuinely
  infinite-size shape, not every generic self-reference.

Full suite: 778/778 (775 + these 3) at default and `-O0`. `lib/std/**` and
`showcase/**` compiled directly — no new errors or warnings; the only
non-clean output anywhere in either sweep is the pre-existing,
already-documented set (`list.tr`'s own E034 self-import, OVH-011's
business; the `NeverReturnsErrorWarning`/unused-variable/unreachable-code
warnings on `io`/`json`/`http`, OVH-012's business) — unaffected by this
item, reproduced identically before and after the fix.

## Known pitfalls

- **The mangled-name lookup must use `KnownStructs` (the SAME map the DFS
  walks), not a separate registry.** `checkStructLayoutAcyclicityForClone()`
  already puts exactly one clone — the one currently being checked — into
  that map under its own mangled name, before the DFS starts. That single,
  pre-existing line is the entire "registration" this fix depends on; no
  new state was added anywhere. A future session tempted to also thread in
  every OTHER already-drained clone (for a hypothetical multi-clone
  indirect cycle) should first check whether any such chain can actually
  arise without ALSO closing back through the clone under test — every
  cycle this item's tests exercise is a "self" edge in exactly this sense
  by construction (F-INIT-3 requires the initial containment to originate
  from somewhere, and that somewhere is always the newly-registered
  instantiation).
- **`instantiatedDeclName()`'s mangled string must be computed the same way
  regardless of which AST occurrence of the `GenericType` produced it.** It
  is — the function depends only on each type argument's own
  `getMangledName()`, a structural property, never node identity — but this
  is exactly the kind of assumption worth re-verifying live (`AGENTS.md`'s
  own rule) rather than trusting by inspection, which is why both the
  direct reproducer and the two-parameter variant were compiled and their
  exact error text inspected, not merely "compiles to an error."
