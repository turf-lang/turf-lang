## Why

LANG-001's completion criterion "`List<T>[i]` works" was true only for
`T = int`. `operator` declarations could not take a type-parameter list, so
`list.tr` declared `operator [](l: List<int>, ...)`, `map.tr` declared
`Map<string, int>`'s, `set.tr` `Set<int>`'s. Everything else was a dead end:

```turflang
mut ss: List<string> = List::default();
ss.push("a");
mut s: string = ss[0];      // no operator[] matches List<string>
```

A language whose indexing works for `List<int>` and not for `List<string>` is
incoherent (R5). OVH-003 added `get`/`set`, so it was never a safety problem;
this makes the operator form uniform.

Two further defects sat directly behind it and are fixed here because the
feature cannot work without them (see *Removed assumptions*): a struct element
read through `operator[]` crashed the compiler on a field access (`bs[1].c`), and
the monomorphizer could not tell two overloads of one name apart.

## Language semantics

### Old behaviour

```turflang
operator<T> [](l: List<T>, i: int): T { ... }   // parse error: expected an overloadable operator
```

and `ss[0]` for `List<string>` was a type error ("No operator[] overload").

### New behaviour

An `operator` declaration may carry a `<...>` type-parameter list straight after
the keyword — `operator<T> [](l: List<T>, i: int): T`, `operator<K, V>
[]=(m: &Map<K, V>, key: K, value: V): void` — on every overloadable operator. The
type parameters are inferred from the operands; each declared operand type is then
substituted and must match its operand **exactly** (F-OP-1 is untouched — a generic
operator adds inference and nothing else). `l[i]`, `l[i] = v`, `m[k]` and `s[i]`
now work for every `List<T>`, `Map<K, V>` and `Set<T>`, including a 24-byte struct
element and nested containers (`m["k"][1]` on `Map<string, List<int>>`).

`l[i].field` and `l[i].method()` work for any element type. `x[i]` is a **value, not
a place**: a write into a field of it, or a method that assigns to its `self`, would
only change a copy, so each is a compile error, **E098** — `bs[0].a = v`,
`bs[0].a += 1`, `bs[0].a++`, `bs[0].bump()`, `outer[0].push(v)`, and `mm["a"]["b"] = v`
(a `[]=` whose container is `&T`, applied to another `[]`'s result). Not rejected,
because the write reaches real storage: `grid[i][j] = v` on a `List<List<T>>` (the
inner `[]=` takes the header by value and stores through the shared buffer), a write
through a `&T`/`T*` element, and the read-modify-write the hint recommends.

Two declaration rules, both **E097**: every type parameter must appear in an
operand; at least one operand must be a type the declaring module owns (a bare `T`
operand would match every type).

### Is this breaking?

No. Additive: a program that compiled before still does. The stdlib's three
concrete operator sets were replaced by generic ones, which accept everything the
concrete ones did (`12_stdlib_list_index`, `13_stdlib_map_index`,
`14_stdlib_set_index` pass unchanged). `Set<T>` still has no `operator[]=`.

## Compiler architecture

- **Lexer** — none.
- **Parser** (`ParseOperatorDecl`, `ParserDecl.cpp`) — after `operator`, `<`
  followed by an identifier opens a type-parameter list; `<` followed by `(` is the
  less-than operator. One token decides, no lookahead buffer. The list is
  registered in a `SymbolScopeGuard` exactly as `ParseFuncDef` does, so `T` parses
  as a `TurfGenericParamType`. The result is an ordinary `FuncDefExprAST` with
  non-empty `TypeParams`.
- **Resolver** (`validateOperatorDecl`, `ResolverCore.cpp`) — for a generic
  operator, E097 for a type parameter no operand mentions, and a **non-vacuous**
  orphan rule: an operand owned by this module must exist, found through `&`/`*` and
  a `GenericType`'s base name. The concrete path is unchanged (including its vacuous
  pass when no operand is a declared type, which `strings.tr` relies on).
  `buildFunctionSymbol` records `Sym.Decl`, the declaration it came from.
- **TypeChecker** — one helper, `TypeChecker::matchOperatorOverload`
  (`TypeCheckerCall.cpp`), replaces the inline `sameTypeExact` comparisons at all
  seven resolution sites: binary, the desugared `!x`, unary, compound assignment,
  `++`/`--`, `operator[]`, `operator[]=`. A concrete candidate behaves as before. A
  generic one: `unify` each operand → every parameter bound → substitute → `sameTypeExact`
  (or `operatorSelfOperandMatches` for the `[]`/`[]=` self operand, unifying the
  pointee of a `&Map<K,V>` parameter) → result type is the substituted return type →
  record a FreeFunction request at the operator node, only if fully concrete.
- **Monomorphizer** (`Monomorphize.cpp/.h`) — an operator is a FreeFunction-kind
  request whose sites are operator nodes. `retargetOperatorSite` points each node
  kind at its clone (`DeclKey` separates `a[i]`'s read from its write, and `!x` from
  `!=`). `InstantiationRequest::Decl` carries the exact template; the drain uses it
  instead of the `(module, name)` registry. The clone name uses
  `sanitizeSymbolName`, so no `[]`/`=` reaches an LLVM symbol. An operator whose first
  operand is named `self` is not mistaken for a method by either drain.
- **Codegen** (`CodegenArray.cpp`, `CodegenVar.cpp`) —
  `ArrayAccessExprAST::codegenLValue()` returns null for an operator read ("no
  address"), the contract `FieldAccessExprAST` and `MethodCallExprAST` already use
  to fall back to an r-value spill. A by-reference self whose base has no address
  (`outer[a][b]` read) is spilled to a temporary. The spill is only sound for a read,
  so the TypeChecker rejects every write into it (next bullet); the Codegen
  `LogErrorAt` for the nested `[]=` shape is an unreachable backstop.
- **TypeChecker, write side (E098)** — `operatorIndexTemporaryRoot()` /
  `rejectOperatorTemporaryWrite()` (`TypeCheckerExpr.cpp`) walk a write target or
  receiver down field accesses and builtin indexing, stopping at a pointer/reference
  base, and report when they reach the by-value result of an `operator[]` read. Called
  from `visitAssignment` (field target, and a by-reference `[]=` container),
  `visitCompoundAssignment`, `visitPostfixExpr`, and `visitMethodCall` when the method
  `MutatesSelf`. This was added in a follow-up the same day: the first version only
  caught the nested by-reference `[]=` and let `bs[0].a = 50`, `bs[0].bump()` and
  `outer[0].push(5)` compile and silently lose the write (see *Removed assumptions*).
- **Types, AST, CFG/analysis, Optimization** — none. Diagnostics: E097
  `GenericOperatorError` and E098 `OperatorTemporaryWriteError` in
  `ErrorCodes.h`/`ErrorsModule.h`.

## Runtime changes

None.

## Standard-library changes

`list.tr`: `operator<T> [](List<T>, int): T`, `operator<T> []=`. `map.tr`:
`operator<K, V> [](Map<K, V>, K): V`, `operator<K, V> []=(&Map<K, V>, K, V)`.
`set.tr`: `operator<T> [](Set<T>, int): T`. The concrete versions are deleted
(keeping both would be an ambiguity at every `List<int>` use). Comments rewritten:
they said operators "can't be generic".

## New invariants

Added to `INVARIANTS.md`: **INV-OP-5** (an `operator[]` result is a value, never written
into — E098), plus **INV-OP-3** (a generic operator never widens an operand —
the substituted signature is re-checked exactly — and its orphan rule is not vacuous)
and **INV-OP-4** (a monomorphizer request names its exact template declaration, so
overloads are never merged — free functions, operators, methods and constructors).
INV-OP-1 and INV-OP-2 are unchanged.

## Removed assumptions

- **"`operator` declarations are non-generic."** Written into four comments in the
  stdlib, `ParseOperatorDecl`'s doc comment, LIMITATIONS.md item 4 and two reference
  pages. All updated.
- **"A generic template is identified by (module, name)."** Untrue as soon as there
  are overloads, and operators are *all* overloads (unary/binary `-`, `+` per right
  operand). It had always been untrue for ordinary generic functions too: on the
  pre-LEC-006 compiler, `fn<T> f(x: T)` plus `fn<T> f(x: T, y: T)` instantiated one
  clone for both and failed in codegen with "Incorrect number of arguments passed to
  called function". Found live by `19_generic_operator_user_struct_forms.tr`; fixed
  for free functions, operators, methods and constructors via `Decl` (regression test
  `38_monomorphization/31_overloaded_generic_free_functions.tr`).
- **"`List<T>[i]` crashes for T ≠ int because no overload exists."** FDN-001's record
  says so and sends it here. Half true: a concrete `operator[]` returning a struct
  crashed too — `bag[1].c` hit `ArrayAccessExprAST::codegenLValue`'s "Base is not an
  array or pointer" fatal error, because field access asks its base for an address
  and an operator read has none. Reproduced with a plain non-generic operator and
  struct first, then fixed (`17_...` and the `Bag` shape both pass).
- **"Spilling an operator result to a temporary is harmless."** It was, for a read. My
  first Codegen fix for `bs[1].c` made `codegenLValue()` answer "no address" and the
  field-access/method-call fallbacks spilled the copy — which turned the old loud crash
  on `bs[0].a = 50`, `bs[0].bump()` and `outer[0].push(5)` into a SILENT lost write. I
  first diagnosed only the nested by-reference `[]=` shape and described the rule as
  "rejected when the write would be lost", which was untrue until the follow-up added the
  other writes (E098). Found by being asked whether the rule was uniform and testing it.
- **"The orphan rule is vacuous when no operand is a declared type."** True for a
  concrete operator (`strings.tr`), a hole for a generic one: `operator<T> +(a: T, b:
  T)` would match every type. Generic declarations get the non-vacuous form.
- **Test-file naming.** A test named `*_across_module.tr` is silently skipped by the
  runner (`_module.tr` substring). Caught by the sweep in AGENTS.md; the test is
  `20_generic_operator_from_another_file.tr`.

## Known pitfalls

- **Overloaded generic *methods* and constructors had the same bug — fixed in a
  follow-up the same day.** `fn<T> Box.put(x: T)` plus `fn<T> Box.put(x: T, y: T)`, called
  as `b.put(1)` / `b.put(1, 2)`, failed in codegen with "Incorrect number of arguments".
  Not reachable from an operator (none is a method), so it was first left open, then fixed
  with the same mechanism: `visitMethodCall`'s two `record()` sites pass `Best->Decl`
  (`visitFuncCall` already did, which covers `Box::new(v)` / `Box::new(v, w)`), and
  `drainMethodRequests` / `drainConstructorRequests` instantiate `Decl` before consulting
  the name registry. Regression test
  `38_monomorphization/32_overloaded_generic_methods_and_constructors.tr` (generic struct,
  non-generic struct with a method-level `<U>`, overloaded constructors). Verified the test
  guards the constructor path by temporarily disabling it: the compiler crashed.
- **`Decl` is a raw pointer** to an AST node. Safe because the pre-pass AST list
  outlives monomorphization, and symbol copies name the same node. A future change that
  rebuilds or moves those nodes between hoisting and the drain would dangle it.
- **`matchOperatorOverload` records before the ambiguity check.** Two matching candidates
  both record a request, then the call is rejected. Harmless (the error stops the compile),
  but do not add a path that continues after the ambiguity error.
- **TypeArgs order is the declaration's `<T, U>` order**, not first-appearance order in the
  operands. The drain pairs them positionally with `Template->getTypeParams()`; do not
  "simplify" to `collectParamOrder`.
- **Do not widen an operand to make a generic candidate fit.** `unify` skips a mismatch
  silently; the substituted `sameTypeExact` is the only thing rejecting
  `Cell<int> == Cell<string>`.
- **`m[k] += 1`, `l[i]++` through an index operator** are still unsupported (§6.7); the
  message names the explicit form.
- **"Mutates self" is now transitive over `self.m()` calls — and still direct-only
  everywhere else.** E098 and the immutable-variable check ask two things: does the method's
  own body assign to `self.<field>` (the `MutatesSelf` flag), and does a chain of `self.m()`
  calls reach such a method (`ResolverSymbolTable::mutatesSelfTransitively`, added in a
  follow-up the same day). The closure is built in the Resolver's Pass 2 (the only walker that
  sees every expression) and queried lazily by the TypeChecker, because candidate symbols are
  copied during Pass 2 and a flag written back afterwards would never reach them. A call
  counts only if EVERY same-name, same-arity method it could mean mutates (overloads differing
  only by parameter type cannot be told apart in the Resolver), so the check cannot reject a
  call over an overload that does not mutate. Measured on the stdlib: exactly three methods
  become newly mutating (`json::Parser.parse_value`, `map::Map.bucketMaybeGrow`,
  `set::Set.bucketMaybeGrow`), all private and all genuinely mutating; nothing in the
  stdlib, showcase or test suite changes behaviour.
  **The direct scan was widened in the same follow-up.** It used to recognise only
  `self.<field> = …` and to recurse only through blocks, `if`, `while`, `for`, `for each`, so
  `self.arr[0] = v`, `self.inner.f = v`, and an assignment inside a `compare` arm or a `defer`
  all compiled on an `immut` variable (verified live before the change). It now walks every
  statement kind that holds a body (adds `do/while`, `unsafe`, `defer`, `compare`) and treats
  an assignment as a mutation of self when its place chain is rooted at `self` and stays in
  self's own value storage, using the declared field types: a value struct or fixed array
  continues the walk, a pointer or reference ends it (`self.data[i] = v` on a `T*` writes the
  pointee, so `List.set` is NOT a mutation of the list value — flagging it would reject
  `grid[i].set(j, v)`, which works, pinned by `06_structs/28_…`), and a type it cannot
  resolve ends it in the under-flagging direction. Measured on the stdlib, showcase, examples
  and the whole suite: nothing changes behaviour.
  **Still missed (verified live):** a mutating call on a value FIELD (`self.inner.bump()`),
  and aliasing (`&self.x` passed on). Catching the first needs call edges keyed by the field's
  struct, not just `self`; it is the one known gap left in "mutates self".
- **E098 stops at a pointer/reference.** `nodes[0].v = 1` for `List<&Node>` is legal and
  must stay so; a future change that makes the walk look through pointers would reject
  working code. `22_index_result_writes_that_land.tr` pins it.
- **Reading is unaffected.** `bs[0].a` as an r-value, `&bs[0]` (already "non-addressable")
  and passing `bs[0]` to a function are all copies and fine.
- A `List<T>` element dead-store/`x += 1` warning noise (`19_...` prints one on a
  `mut p`) is the known false-positive class LEC-005 owns.
