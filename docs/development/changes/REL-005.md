## Language semantics
### Old behaviour
`Map`/`Set` hashed a key's raw bytes (`hashing.tr`'s generic overload). Keys
that `==` called equal could hash apart: a struct's padding holds leftover
bytes (at -O0, 1999 of 2000 equal padded-struct keys were not found again; at
-O2, none, an answer that depended on the optimization level), `-0.0` and
`0.0` differ in their sign bit, and a struct whose `operator ==` compares
string fields by content was hashed by the string pointers.
### New behaviour
`hash_of(expr): int`, a new bare intrinsic, hashes a value from its static
type, agreeing with field-by-field `==`: a string by its text, a double with
`-0.0` taken as `0.0`, a struct field by field (never its padding), a fixed
array or `T[]` element by element, a reference or pointer by its address.
Both `hashing::hash` overloads call it, so every `Map`/`Set` key does.
### Is this breaking?
No program's meaning changes except where it was wrong: a struct or `double`
key that used to be missed is now found. Iteration order of a `Map`/`Set` is
insertion order (dense arrays), unaffected by the hash. `hash_of` is a new
name: a user's own function `hash_of` still wins over the intrinsic, as for
every bare intrinsic.

## Compiler architecture
- `include/Intrinsics.h` / `src/Builtins.cpp`: `BareIntrinsic::HashOf`,
  `hash_of`, arity 1 (F-STD-2: the list stays closed and enumerated).
- `src/TypeCheckerCall.cpp`: `hash_of(x)` is `int`; `void` is E-VoidValue.
- `src/CodegenCore.cpp`: `EmitStructuralHash()` walks the static type and
  folds each part into a 64-bit state (multiply, xor, splitmix64's finalizer
  so `hash & (bcap - 1)` sees mixed low bits), plain wrapping arithmetic (a
  hash never traps). Strings go through one emitted helper per module,
  `__turf_hash_cstr` (FNV-1a, internal linkage; a null string hashes as "").
  Arrays loop; structs `extractvalue` field by field.
- `src/CodegenStruct.cpp`: the UFCS branch of `MethodCallExprAST::codegen()`
  now appends a `@caller_location` callee's hidden argument, as the
  struct-method branch always did; `s.substring(1, 3)` asserted (f602b94).

## Runtime changes
`runtime/turfrt_gc.c` (91c6a1d): `turf_gc_reregister_block`, run on every
`gc_realloc`, found its block with a linear scan of `g_pending` (every block
allocated since the last collection) or removed it from the sorted `g_blocks`
with a `memmove` of the tail: O(heap) per realloc. Now:
- `g_pidx`, a hash index (open addressing, Fibonacci hashing, keys 0/1 as
  empty/deleted) from a pending block's start to its position in `g_pending`,
  kept in step by `pending_remove()` (swap-with-last), rebuilt when live plus
  deleted keys pass 70%, emptied when a collection merges pending.
- A `g_blocks` entry a realloc moves away from is marked `dead`, not removed.
  Exact lookups and `gc_find_containing` treat it as absent; `gc_rebuild_index`
  drops dead entries (order-preserving) before merging, so no collection's
  mark or sweep sees one, and a new block at a dead entry's address never
  shares its start in the sorted array.
The ABI is unchanged (`turf_rt_abi_2_0`).

## Standard-library changes
- `lib/std/collections/map.tr`, `set.tr` (c7f231c): a `tombs` count in the
  header; the rebuild check counts tombstones, and rebuilds at the same size
  (clearing them) unless live entries alone fill more than 35%.
- `lib/std/json/json.tr` (7003042): the parser reads through `Parser.at()`
  (`byte_at_unchecked` after the caller's `pos < len`) and copies through
  `Parser.copy_into()` instead of `strings::substring()` on the whole document;
  `parse_string` copies runs of plain bytes; `stringify_array`/`_object` use a
  `StringBuilder`.
- `lib/std/collections/hashing.tr` (321dc58): both overloads return
  `hash_of(x)`; the header's wrong claim that the byte hash satisfied
  `a == b ⇒ hash(a) == hash(b)` for plain data is replaced.
No `pub` item was added or removed (`stdlib_surface_check.sh`: 310, all locked).

## New invariants
- REL-005 gate: on the baseline machine, `scripts/bench.py --compare` against

  regression is explained in `BENCHMARKS.md`. Checked per release candidate

- `hash_of(a) == hash_of(b)` whenever `a` and `b` are equal field by field

## Removed assumptions
- "Benchmarks are machine-dependent, so none belong in the repository."
  Programs, runner and per-machine numbers are committed; only numbers from
  the same machine and build type are compared.
- "LLVM hoists the `strlen` of `s[i]` out of a loop at -O2" (FDN-004). Not
  when `s` is read through `self` in a loop that writes another field of
  `self` (the JSON parser): the check stayed per byte, quadratic.
- "Tombstones only need to be reused, not counted." Under steady churn they
  fill every empty slot.
- "The byte hash meets `a == b ⇒ hash(a) == hash(b)` for every plain-data type"
  (old `hashing.tr` header). False for padded structs and signed zeros.
- "`g_pending` is small in practice" (old `turfrt_gc.c` comment on the linear
  scans). Collections are rare by design (heap doubling), so it holds every
  block allocated since the last one: hundreds of thousands.
- "Wall-clock medians are stable enough for a 20% gate." Not on a hybrid
  laptop CPU under WSL: up to 30% between back-to-back runs of one commit.

## Known pitfalls
- A test whose cost is allocations × live heap (a big JSON round trip) is fine
  normally and takes over 700 s under `TURF_GC_STRESS=1` (a collection per
  allocation): keep correctness tests small and leave size to `bench/`.
- Naming a file `bench/json.tr` makes the `json` module ambiguous (E090);
  `step` and `run` are reserved words (a loop variable `step`, a `run` local
  in `json.tr` both failed).
- An array a loop fills needs a write the definite-assignment pass can see
  first (`ps[0] = …;`), as in `bench/structs.tr` (F-INIT-1).
- `bench.py` must time programs through GNU `time`, not `os.wait4()`: a child
  forked from Python inherits Python's peak RSS across `exec`.
- Pinning matters more than run count on a hybrid CPU: interleave and pin
  before adding rounds. Compare minimums.
- `strings::substring(s, a, b)` measures all of `s`; in a loop over a long
  `s` it is quadratic. So is `s[i]` read through `self`.

## Unresolved questions
- **NaN keys.** NaN never equals anything, itself included, so a NaN `Map`
  key is never found again and a `Set` can hold several. Documented, not
  decided (Python finds it by identity; Java treats NaNs as equal).
- **JSON exponents — resolved 2026-10-13.** `json::parse("[3e2]")` failed
  entirely (so did reading back `1e+21`, which `stringify` writes);
  `strings::parse_double` now validates an optional exponent and converts with
  `s to double` (correctly rounded), and the JSON header is corrected.
  Tests: `tests/34_http_and_json/08_json_numbers_with_exponents.tr`,
  `tests/13_string_stdlib/22_str_parse_double.tr` (now exact `==`).
  `json_roundtrip` against the baseline: −2.7%.
- **Generator coverage — resolved 2026-10-13** (turf-fuzz faa2d4e): `double`
  and padded-struct (`Kp`) Map/Set keys, with a bulk fill past 128 slots;
  against a compiler built at 91c6a1d (before `hash_of`) it reports a wrong
  answer (seed 352) and a -O0/-O2 difference (seed 381). The re-run that
  followed (turf-fuzz lock 9c576a0) found one more, unrelated crash: a
  `compare` with only `otherwise` on a struct subject (fixed 91e784a).
- **Other machines.** The only baseline is the WSL laptop above; a Windows-
  native or macOS baseline needs its own entry, measured on that machine.
- **F-24.** `structs` measures 1.06x C here, but it is a reconstruction, not
  D24's program; F-24's question (range proofs vs an opt-in wrapping
  construct) is unchanged.
