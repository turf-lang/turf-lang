## Why

`docs/planning/OVERHAUL_REMAINING_WORK.md` OVH-009 (reproduced live,
2026-09-26): a nested generic type written with no space between its
closing angle brackets failed to parse.

```turf
mut ll: List<List<string>> = List::default();
// error: Expected '>' or ',' in generic type
// (plus a misleading cascade: "Statements are not allowed outside of a function")
```

The lexer's maximal munch (`src/Lexer.cpp`, uniform, `INV-LEX-1`) reads
`>>` as one `TOK_RSHIFT` token and `>>=` as one `TOK_RSHIFT_ASSIGN` token
regardless of context — correct and necessary for the real bitwise-shift
and shift-assignment operators, but `ParseType()`'s generic-argument-list
closing check (`src/ParserCore.cpp`) only ever recognized a literal `'>'`
token, so a nested generic's inner `ParseType()` call returned with
`CurTok == TOK_RSHIFT` sitting where it expected `'>'`, one level short of
what it needed. Existing code (`tests/38_monomorphization/
16_nested_generic_struct_field.tr`) worked around this with an explicit
space (`List<List<Big> >`) rather than fixing the parser.

## Language semantics

### Old behaviour
`List<List<int>>` (and any other nested generic closing with no space) was
a syntax error. `List<List<Big> >` (with a space) was the only way to
write it. `List<T>= value;`/`Map<K, List<V>>= value;` (a generic type
annotation immediately followed by `=`, no space) were also syntax errors
for the identical reason, one level lower.

### New behaviour
`>>` closes two nested generic argument lists, and `>>=` closes two and
continues as the assignment operator `=` — the same treatment C++11 and
Java give this ambiguity. `List<List<int>>`, `Map<string, List<int>>`,
`List<List<List<int>>>` (three closers, `>>` then `>>` — actually lexed as
`TOK_RSHIFT` then a plain `'>'`, since there is no dedicated triple-`>`
token), and `Map<string, List<int>>= Map::default();` (`TOK_RSHIFT_ASSIGN`)
all parse. The spaced form continues to work unchanged — both spellings
are legal now, and the existing spaced test
(`16_nested_generic_struct_field.tr`) was left untouched to prove it.

### Is this breaking?
No. This only makes previously-rejected input compile; no program that
compiled before this fix parses any differently now (a real `>>`/`>>=`/`>=`
binary-operator use in an EXPRESSION is untouched — `ParseExpression()` is
a completely different function from `ParseType()`, never affected by this
change; verified live, see *Tests*).

## Compiler architecture

- **Parser only — the lexer is untouched.** `ParseType()`'s generic
  argument loop (`src/ParserCore.cpp`, the `if (CurTok == '<') { ... }`
  branch) gains three more branches alongside its existing `CurTok == '>'`
  check, each **replacing `CurTok` in place and `break`ing, without ever
  calling `getNextToken()`**:
  - `TOK_RSHIFT` (`>>`) → `CurTok = '>'` — one `'>'` is logically consumed
    by closing THIS level; the other is left in `CurTok` for whichever
    enclosing generic-argument list (or ordinary caller) parses next.
  - `TOK_RSHIFT_ASSIGN` (`>>=`) → `CurTok = TOK_GEQ` — one `'>'` consumed,
    `>=` left over.
  - `TOK_GEQ` (`>=`) → `CurTok = TOK_ASSIGN` — one `'>'` consumed, `=` left
    over. Reached either directly (a single-level generic immediately
    followed by `=`, `List<int>=`) or as the second split of a `>>=`
    bubbling up from a nested level.
  Not calling `getNextToken()` in any of the three new branches is the
  entire mechanism: the lexer already advanced PAST the whole fused token
  in one `gettok()` call when it first produced `TOK_RSHIFT`/
  `TOK_RSHIFT_ASSIGN`/`TOK_GEQ`, so nothing needs to be re-read from the
  source — only the ALREADY-read remainder needs to be handed to the next
  consumer. The ordinary `CurTok == '>'` branch (unchanged) is what
  eventually calls the real `getNextToken()`, once every `'>'` a given
  fused token represented has been logically consumed by some level of
  nesting — at that point the lexer's actual stream position is exactly
  where it needs to be to read whatever comes after the original fused
  token.
  A triple-`>` close (`List<List<List<int>>>`) needs no special handling
  beyond the above: the lexer has no dedicated 3-character token, so
  `>>>` lexes as `TOK_RSHIFT` (`>>`) followed by a real, separately-lexed
  `'>'` — the innermost level's `TOK_RSHIFT` split hands a synthetic `'>'`
  to the middle level, whose OWN `CurTok == '>'` branch calls the real
  `getNextToken()`, which reads the third `'>'` fresh from the source
  (exactly where the lexer left off) for the outermost level to close.

## Removed assumptions

- **"`ParseType()`'s generic-argument-list closing check only ever sees a
  literal `'>'` token" was never true once the lexer could produce
  `TOK_RSHIFT`/`TOK_RSHIFT_ASSIGN`/`TOK_GEQ`** — it happened to hold for
  every SPACED nested generic, which is why the bug went unnoticed long
  enough to need an explicit spaced workaround in
  `16_nested_generic_struct_field.tr` rather than being fixed outright.
  Any future addition to `ParseType()`'s closing logic (a new bracket kind,
  say) should check whether the lexer's OWN maximal munch could fuse its
  closing character with an adjacent one first, rather than assuming a
  single-character token is the only shape that ever arrives.

## Known pitfalls

- **Do not call `getNextToken()` in any of the three new split branches.**
  It is tempting to "normalize" by calling it after setting `CurTok`, the
  way the pre-existing `'>'` branch does — but the whole point of the
  split is that the lexer has ALREADY produced the one token covering
  every character in the fused spelling; calling `getNextToken()` again
  here would silently discard the just-synthesized remainder and skip a
  real token from the source instead (e.g., for `Map<string,
  List<int>>= Map::default();`, it would skip straight to `Map::default()`
  itself, dropping the entire `=`).
- **`TOK_GEQ` reached by this closing check is not always a "synthetic"
  intermediate from splitting `TOK_RSHIFT_ASSIGN`.** A single-level generic
  immediately followed by `=` with no space (`List<int>=`) produces a
  GENUINE, directly-lexed `TOK_GEQ` (`>=`) the very first time this check
  ever sees it — treated identically to the synthesized case, which is
  correct (both mean "one `'>'` closes this level, `'='` is what's left"),
  but worth knowing if a future reader is tracing where a given `TOK_GEQ`
  value actually came from.
