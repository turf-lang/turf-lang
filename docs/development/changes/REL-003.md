## Why
Three things stood between "it builds" and "someone else can install it":

1. **`--target` failed with the host linker's words.** `turfc prog.tr
   --target=aarch64-unknown-linux-gnu` emitted a correct AArch64 object and
   then ran the host `cc`, which answered `file in wrong format` plus a
   `-lturfrt` command line. Nothing said that cross-linking does not exist
   (D20).
2. **The release archive had the wrong shape.** `turfc` sat at the archive's top
   level, but it derives its install root from `<bin>/..`; it only worked from
   inside the archive by accident of where `lib/` was, and nothing in CI ever
   unpacked an archive and used it.
3. **There was no installer, no checksum check and no recipes**, and the
   version came from three places (REL-001's deferred single-sourcing item).

Stages 1, 2 and 4 of the roadmap entry are done as far as this machine can
prove (Linux x86-64, no Docker daemon, no macOS or Windows). Stage 3 (macOS
port) and the "unzip and nothing else" promise are **REL-008**, which supersedes
them (DEC-2, DEC-14).

## Language semantics
### Old behaviour
```
$ turfc hello.tr --target=aarch64-unknown-linux-gnu -o h
/usr/bin/ld: h.o: Relocations in generic ELF (EM: 183)
/usr/bin/ld: h.o: error adding symbols: file in wrong format
Linking failed (exit code 1)
Command was: cc h.o -o h -L.../lib -lturfrt -lm -lm
```
### New behaviour
```
$ turfc hello.tr --target=aarch64-unknown-linux-gnu -o h
Compiled to h.o
Error: cannot link a program for 'aarch64-unknown-linux-gnu': cross-linking is
not supported in 2.0; the runtime (libturfrt) is built for x86_64-pc-linux-gnu.
  The object file for 'aarch64-unknown-linux-gnu' was kept as h.o. Link it with
  a toolchain and a runtime built for that target, or compile for this machine
  by leaving --target out.
```
Exit 1; `h.o` is real AArch64 code (`e_machine` 183) and is kept. The host's own
triple in any vendor spelling (`x86_64-linux-gnu`, `-unknown-`, `-pc-`) links
as before.
### Is this breaking?
No. The only change in observable behaviour is the message and that the object
is no longer deleted when the link is impossible.

## Compiler architecture
- **Driver (`src/main.cpp`)**: `isForeignTarget()` compares architecture, OS and
  ABI environment of the normalised requested triple against the host's; it is
  checked right after `emitObjectFile()` and before `linkObject()`. The
  environment is compared on purpose (`x86_64-linux-musl` on glibc is foreign:
  `libturfrt` is built against the host libc). **REL-008 stage 4 is the one
  change that must revisit this**, when the archive carries a musl runtime.
- Nothing else in the compiler. The driver interface is unchanged (no new flag).

## Removed assumptions
- **"An unpacked archive works."** It worked only from the right directory. The
  new layout is what `turfc`'s root rule and `turf`'s `turfc` lookup expect, and
  `release_smoke.sh` runs `turf` from the installed tree with `TURF_HOME` unset.
- **"`--target` is a flag that mostly works."** Only the object half does. The
  user now gets that said.
- **"The checkout's `lib/` is the archive's `lib/`."** The archive has
  `libturfrt.a` only; the checkout also has `libturfrt_asan.a`.
- **"`ls` the archive to see its name."** The name is `turf-v<VERSION>-…`, and
  packaging refuses a tag that is not `v<VERSION>`.

## Tests
- **Added `scripts/cross_target_smoke.sh`** (CI, `test.yml`): a foreign target
  exits 1 with the TurfLang message and *without* any host-linker text, the
  object is kept and is AArch64, no executable exists; four host spellings
  link and run; `x86_64-linux-musl` is foreign; a plain build is unchanged. It
  was run against the pre-change behaviour's output (above) to know the
  "no host-linker text" check can fail.
- **Added `scripts/release_smoke.sh`** (CI on every push, and in `release.yml`
  against the archive about to be published, Linux and macOS): archive layout
  (nine required paths in, no `libturfrt_asan`, no binary at top level); a tag that
  disagrees with `VERSION` is refused; a truncated archive is refused by the
  checksum and installs and edits nothing; the PATH block appears once after
  two installs and the user's own lines survive; the default (latest) lookup
  and `--no-modify-path`; a *new* bash and zsh resolve `turf` to the installed
  one; `turf version` shows the prefix as the root and no PATH note;
  `turf new hello` / `run` / `build`; a path dependency (the bundled
  `examples/plotter`); `turf explain` reads the installed docs; uninstall
  restores the start-up file byte for byte, leaves the package cache, and fails
  loudly when run twice; recipes carry the archive's hash. 34 checks, all pass
  on Linux x86-64.
- **`install.sh` shows progress (owner report, 2026-10-07):** numbered steps
  `[1/4]`..`[4/4]`, and the tool's own progress bar for the archive download
  (`curl -#`, or `wget --show-progress`) when stderr is a terminal. Not a
  terminal (a CI log), no bar, steps only. Checked on a real pty against a local
  HTTP server and without one; the wget branch was not run (no wget here).
- **Added `scripts/package_release.sh`, `install.sh`, `scripts/gen_recipes.sh`.**
  The release workflow's packaging is now this script (the composite action
  calls it), so CI publishes what a developer can build and open.
- **Found and fixed on the way: `gc_hardening_asan` has failed on every run
  since #263.** Not part of REL-003 proper, reported by the owner mid-session.
  Three tests failed under ASan, for three different reasons:
  - `tests/12_string_ops/fail_string_index_negative_write_runtime.tr` was a
    **real over-read**: it called `strlen()` (a negative-index write does) on a
    `gc_alloc(4)` buffer, which is plain `malloc`, assuming its bytes were zero.
    ASan: `heap-buffer-overflow … READ of size 5 … 0 bytes after 4-byte region`.
    The test now uses `gc_alloc_zeroed`.
  - `fail_oom_huge_direct_allocation.tr`: ASan's `malloc` aborts on 2^63-1 bytes
    with its own report, so `turf_rt_alloc`'s "out of memory" path never ran. The
    ASan steps set `allocator_may_return_null=1`.
  - `fail_stack_overflow_deep_recursion.tr`: an ASan build installs no SIGSEGV
    handler by design (`runtime/turfrt_signal.c`, INV-RT-5's FDN-005 exception;
    `handle_segv=0` / `allow_user_segv_handler=1` were tried and give a bare 139).
    Skipped in the ASan steps through the new `TURF_TEST_EXTRA_EXCLUDE` (the
    wrapper's own repository policy, like its `--exclude custom`).
  They began failing when #263 made `EXPECT-RUNTIME` binding (before it, an abort
  of any text passed). Locally, with a fresh `build_asan/`: the ASan suite at the
  default level and at `-O0` is 1156/1156; the two `TURF_GC_STRESS` ASan steps
  (700 s each) were **not** re-run here.

## Known pitfalls
- **None of this makes a release self-contained.** The archive's `turfc` links
  LLVM dynamically and linking a program runs the system `cc`. `release_smoke.sh`
  therefore leaves `cc` on `PATH`, and says so. The clean-machine proof
  (no `cc`, no LLVM, in a container) is REL-008 stage 8; **no Docker daemon was
  available**, so no container run exists for any of this.
- **Unverified here, written to be correct:** macOS (the smoke's `Darwin`
  branches: `.bash_profile`, a login `bash -li`, BSD `sed`/`tar`/`mktemp`,
  `shasum`), the Windows zip path of `package_release.sh` (`7z`/`zip`, `.exe`),
  `install.sh` under a strict POSIX `sh` (only run with bash as `sh`; no
  `dash`/busybox available), the Homebrew formula (no Ruby; Scoop's JSON and the
  PKGBUILD *were* parsed with `jq` and `makepkg --printsrcinfo`), and the
  `release.yml` edits (YAML parses; never run).
- `install.sh` finds the archive through `checksums.txt`, whose lines name
  `turf-v<ver>-<platform>.tar.gz`; the release job builds that file with
  `cat *.sha256`, so a `.sha256` with a path in it (not a bare name) would break
  the lookup. `package_release.sh` writes bare names.
- `--target` is checked *after* emitting the object, so a typo'd triple fails in
  LLVM's target lookup (`could not create a target machine`), not here.
- An uninstall cannot remove the one newline `install.sh` adds to a start-up
  file whose last line had none; it does remove the blank line it added.
- The recipes are correct only for self-contained archives (REL-008): until then
  a Homebrew/Scoop package from today's archive would need the matching LLVM
  installed and says nothing about it.
- A negative-index string write calls `strlen()` on its target. Any such write
  into a buffer that is not NUL-terminated reads past it (found via the test
  above, fixed there, **not** in the language). Left as is: it is the `#256`
  semantics, and the check cannot be made without a length.
