## Why

Three independent, live bugs around `int32`, all verified against
`refactor/architecture` @ `cde1d30` by the 2026-09-26 closure audit:

1. **`++`/`--` on an `int32` lvalue is an internal compiler error, not a
   diagnostic.**
   ```turf
   fn main(): int { mut c: int32 = 5 to int32; c++; return c to int; }
   // Internal compiler error: generated LLVM IR is invalid.
   //   call { i64, i1 } @llvm.sadd.with.overflow.i64(i32 %postfix.load, i64 1)
   ```
   `PostfixExprAST::codegen()` (`CodegenVar.cpp`) unconditionally builds its
   overflow-checked-add path assuming an i64 operand; a genuinely i32-typed
   `OldVal` produces a call with mismatched operand widths — invalid LLVM IR,
   caught only by the verifier, not by any TurfLang-level diagnostic. `c--`
   and prefix `++c`/`--c` reproduce identically.

2. **An untyped integer literal is wrongly rejected as `int -> int32`
   narrowing.**
   ```turf
   fn main(): int { mut n: int32 = 5; return 0; }
   // error [E066]: Cannot initialise 'int32' variable 'n' with value of type 'int'.
   ```
   `c += 1` (compound assignment) hits the same root cause, but surfaces as a
   *type* error instead of an ICE (`inferArithmeticType()` promotes the
   result to `int`, then the same narrowing check rejects it) — a real bug,
   but a different shape from item 1.

3. **A representability test passed for the wrong reason.**
   `tests/36_numeric_semantics/fail_int32_literal_out_of_range.tr`
   (`mut x: int32 = 99999999999;`) is meant to exercise `E076` (out of
   `int32`'s representable range) but, before this fix, was rejected by bug 2
   instead — an ordinary `E066` type mismatch that would have fired for
   *any* literal value, not just an out-of-range one. The test runner only
   checks "compilation failed," so this went unnoticed.

Root cause for 2 and 3: `TypeChecker::visitNumber()` (`TypeCheckerExpr.cpp`)
always types an integer literal `int`, with no way to record "this is still
an untyped literal" in the `TurfTypePtr` it returns. Every type-fixing call
site (`VarDecl` init, assignment, call argument, return) then runs
`typesCompatible(int, int32)`, which correctly rejects that pairing for a
*genuinely* `int`-typed value (FREEZE.md §6.2 row 4) — but wrongly rejects it
for a literal that was never actually typed `int` to begin with and should
instead acquire `int32` directly, exactly like it already acquires `int` or
`double` at every other destination. `checkLiteralRepresentable()`, the
function meant to check exactly this, was never reached at all for an
`int32` destination, because `typesCompatible()` had already raised an error
first.

## Language semantics

### Old behaviour
- `mut n: int32 = 5;` → `E066` (type mismatch), unconditionally, regardless
  of the literal's value.
- `mut x: int32 = 99999999999;` → also `E066`, for the same reason — never
  reached the `E076` representability check its own test comment claimed.
- `c++`/`c--`/`++c`/`--c` on an `int32` local → internal compiler error
  (invalid LLVM IR), no TurfLang-level diagnostic at all.
- `c += 1` on an `int32` local → `E066`, with the generic message "Cannot
  assign value of type 'int' to variable of type 'int32'."

### New behaviour
- `mut n: int32 = 5;` compiles; `n` holds `5`.
- `mut x: int32 = 99999999999;` → `E076` ("Integer literal is not
  representable in type 'int32'"), citing the exact value and `int32`'s
  range — the test now genuinely exercises what it claims to.
- The same acquisition applies at every type-fixing site: plain assignment
  (`n = 5;`), a call argument (`takesInt32(5)`), and a return value
  (`return 5;` from a function declared `int32`, including the success type
  of a `!int32`).
- `c++`/`c--`/`++c`/`--c` on an `int32` local → a clean compile error:
  ```
  error [E066]
  postfix '++' is not supported on 'int32' -- int32 is never itself an
  arithmetic result type.
  Hint: Write 'c = (c + 1) to int32;' explicitly instead.
  ```
  No ICE is reachable from any input.
- `c += 1` on an `int32` local → a clean, DEDICATED compile error naming the
  actual reason, instead of the generic type-mismatch message:
  ```
  error [E066]
  Compound assignment '+=' is not supported on 'int32' -- int32 is never
  itself an arithmetic result type.
  Hint: Write 'c = (c + int) to int32;' explicitly instead.
  ```
- **Unchanged, by design:** a genuinely `int`-TYPED value still cannot
  narrow to `int32` implicitly. `mut existing: int = 5; mut n: int32 =
  existing;` is still `E066`, exactly as before — this fix is scoped to
  UNTYPED literals only (FREEZE.md §6.2 row 4's "typed `int → int32` stays
  an error" is unaffected).

### Is this breaking?
No. Every changed case either (a) newly ACCEPTS a program that used to be
rejected with no loss of safety (an untyped literal's value is still checked
against `int32`'s range via `checkLiteralRepresentable()`, exactly as it
already is for `int`/`double`), or (b) newly REJECTS, with a diagnosable
error, a program that used to either crash the compiler outright (`++`/`--`)
or fail with a confusing, wrong-cause message (`+=`). No program that
compiled and ran correctly before this fix behaves differently after it.

## Compiler architecture

- **TypeChecker** (`TypeCheckerCore.cpp`). New helper
  `TypeChecker::untypedLiteralAcquiresInt32(const ExprAST *Val, const
  TurfType *Dest)`: true when `Dest->isInt32()` and `Val` is exactly the
  kind of untyped-literal-only expression `tryFoldUntypedIntConstant()`
  already folds (a bare literal, or `+`/`-`/`*` of pure literals) — reusing
  that existing fold as a pure "is this still untyped?" detector
  (`IsTopLevel=true`, which is also the branch that never raises on its own).
  Consulted, alongside the existing `typesCompatible()` check, at every
  type-fixing site:
  - `visitVarDecl()` (`TypeCheckerDecl.cpp`) — initializer.
  - `visitAssignment()` (`TypeCheckerExpr.cpp`) — RHS.
  - `visitReturn()` (`TypeCheckerStmt.cpp`) — both the plain-return and the
    `!T` success-type branches.
  - The four candidate-matching loops that gate a
    `checkCallArgsRepresentable()` call (`TypeCheckerCall.cpp`): the ordinary
    free-function/`extern fn` path (`visitFuncCall()`), the UFCS fallback
    (`tryUFCSFallback()`), the module-qualified method-call path, and the
    struct-method path (both inside `visitMethodCall()`) — all five reachable
    call shapes, not just the plain-function case the test file exercises
    directly, since `int32` exists specifically to describe `extern fn`
    parameters and any of these shapes could legitimately declare one.
  - When `Dest` is `int32`. When the mismatch would otherwise be reported,
    the helper's `true` result is treated as "compatible after all," and
    `checkLiteralRepresentable()`/`checkCallArgsRepresentable()` runs exactly
    as it already does for the `int`/`double` destinations — no new
    representability logic, only a new way to REACH the existing one.
  - **`visitPostfixExpr()`** (`TypeCheckerExpr.cpp`): a new check, before the
    existing generic `!OpTy->isNumeric()` rejection (which `int32` already
    passes, silently, since it IS numeric) — `OpTy->isInt32()` is now a
    dedicated error naming the reason and suggesting the rewrite, returning
    early so Codegen is never reached for this input at all.
  - **`visitCompoundAssignment()`** (`TypeCheckerExpr.cpp`): a new branch,
    `else if (LhsTy && RhsTy && LhsTy->isInt32())`, taken BEFORE
    `inferArithmeticType()` runs at all (which would otherwise promote to
    `int` and produce the generic, misleading "Cannot assign value of type
    'int' to variable of type 'int32'" message) — a dedicated error with the
    same "int32 is never itself an arithmetic result type" wording and a
    concrete rewrite hint.
- **Codegen** (`CodegenVar.cpp`). `PostfixExprAST::codegen()` gains a debug
  assertion, right after computing `isDouble`: `assert(isDouble ||
  OpTy->isNamed("int"))`. Not the fix itself (the TypeChecker gate above is)
  — this exists so that if a FUTURE numeric type is ever added without
  updating that gate, the failure is a loud, immediate assertion here
  instead of silently re-emitting invalid LLVM IR the way `int32` did before
  this session.
- No change to `inferArithmeticType()`, `typesCompatible()`, or
  `checkLiteralRepresentable()` itself — every fix is either a new call site
  consulting an existing check, or a new check placed BEFORE an existing one
  that would otherwise fire with the wrong message (or not at all, for the
  ICE case).

## Removed assumptions

- **"A destination check that already exists for `int`/`double` also
  applies uniformly to `int32`" was false, silently, for exactly one
  reason: `int32`'s implicit-conversion rule (FREEZE.md §6.2 row 4, "int32
  widens, int narrows") is the ONE destination among the three
  `checkLiteralRepresentable()` covers where a genuinely-typed source value
  and an untyped literal are NOT treated the same by `typesCompatible()`.**
  For `int`/`double`, any `int`-typed value (literal-derived or not) is
  already compatible with the destination, so the representability check
  was always reached regardless of whether the source started life as a
  literal. For `int32`, a typed `int` value is NOT compatible — so the
  literal-vs-typed distinction, which every other destination could ignore,
  suddenly matters, and nothing in `typesCompatible()`'s type-only signature
  could ever make that distinction on its own. Any FUTURE destination type
  with an asymmetric implicit-conversion rule (widens one way, not the
  other) will have the identical gap unless it also gets its own
  `untypedLiteralAcquiresXXX()`-shaped exception at every type-fixing site —
  this is not a general mechanism, it is five call sites each explicitly
  patched for this one case.
- **"`int32` reaching `PostfixExprAST::codegen()`'s non-double branch is
  impossible" was never actually enforced anywhere** — it happened to be
  true only because no test ever tried `int32++`. The moment one did, the
  function's own hardcoded i64 assumption (`ConstantInt::get(*TheContext,
  APInt(64, 1, true))`, and `EmitCheckedIntArith()`'s own i64-width
  intrinsic) produced invalid IR with no TurfLang-level diagnostic anywhere
  in the pipeline. The new TypeChecker gate is the actual fix; the new
  Codegen assertion is what makes the NEXT such gap loud instead of silent.

## Known pitfalls

- **`untypedLiteralAcquiresInt32()` must be checked in ADDITION to
  `typesCompatible()`, never as a replacement for it, and only ever makes a
  `false` result true — never the reverse.** It is structured everywhere as
  `!typesCompatible(...) && !untypedLiteralAcquiresInt32(...)` (or the
  equivalent `... || untypedLiteralAcquiresInt32(...)` on the "is this
  compatible" side) specifically so a call site that is ALREADY compatible
  by the ordinary rule (e.g. a genuine `int32 → int32` exact match) never
  even evaluates the helper, and a call site that is incompatible for a
  DIFFERENT reason (e.g. `string` to `int32`) still gets the ordinary
  rejection, since `tryFoldUntypedIntConstant()` returns `std::nullopt` for
  anything that isn't a pure untyped-literal-arithmetic tree.
- **The four call-argument matching loops needed the identical exception
  independently — there is no single shared "is this call's argument list
  compatible" function to patch once.** `TypeCheckerCall.cpp` re-implements
  essentially the same arity/type-filter loop four times (plain function,
  UFCS, module-qualified method, struct method), each with its own
  `ArgTypes`/`Cand->Params` indexing convention (some offset by a receiver
  slot, some substituted through a generic `Subst` map first). A session
  that only patches the first one it finds (the plain-function path, which
  is what the one test file in this item happens to exercise) will silently
  leave the other three shapes broken for any `int32`-typed parameter they
  declare — verified live by reading, not assuming, all five
  `typesCompatible(ArgTy, ParamTy)` call sites in that file before deciding
  the fix was complete.
- **The Codegen assertion in `PostfixExprAST::codegen()` is NOT the fix for
  bug 1 — the TypeChecker gate in `visitPostfixExpr()` is.** The assertion
  is compiled out in a release (`NDEBUG`) build; it exists purely as a
  loud-failure tripwire for a FUTURE regression of the same shape (a new
  numeric type reaching this function's non-double branch without the
  TypeChecker having rejected it first), not as runtime protection in a
  shipped binary. Do not mistake it for defense-in-depth that makes the
  TypeChecker check optional.
- **`visitCompoundAssignment()`'s new `int32` branch must run BEFORE
  `inferArithmeticType()` is called at all, not after inspecting its
  result.** `inferArithmeticType()` has a side effect on failure (it calls
  `reportError()` itself, for the "cannot apply operator to these types"
  case) — calling it first and only conditionally using its result would
  either double-report or require suppressing its own error path, both
  worse than simply not calling it for this one destination.
