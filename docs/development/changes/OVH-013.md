## Why

`docs/planning/OVERHAUL_REMAINING_WORK.md` OVH-013 (verified live, 2026-09-27,
before this fix): `.github/workflows/release.yml` builds and ships four
platforms — `linux-x86_64`, `linux-arch-x86_64`, `macos-arm64`,
`windows-x86_64` — but `runtime/turfrt_gc.c`'s conservative-GC root-scanning
code only ever implemented x86-64 System V:

- `#if !defined(__x86_64__) #error ...` unconditionally failed the build on
  any non-x86-64 target — **macOS arm64 could not build `libturfrt` at
  all**, meaning the `macos-arm64` release job would only pass today because
  nothing in it actually ran the resulting binary's GC path.
- `gc_capture_callee_saved()` spilled only `rbx`/`rbp`/`r12`-`r15` — the
  System V callee-saved set. Win64's own calling convention additionally
  treats `rdi`/`rsi` as callee-saved (volatile under System V) and the full
  128 bits of `xmm6`-`xmm15` as callee-saved (System V has no callee-saved
  XMM registers at all) — **the `windows-x86_64` release job built a binary
  whose conservative register scan was unsound**: a GC pointer live only in
  `rdi`/`rsi`/an `xmm` register at a collection point would not be found as
  a root, a genuine use-after-free the release build shipped silently.
- `turf_gc_record_stack_base()` found the thread's real stack bounds via
  Linux's `/proc/self/maps`, with no equivalent on macOS or Windows — on
  either platform it silently fell through to the call-depth-dependent
  local-variable fallback the function's own comment documents as strictly
  worse (a stack-scan lower bound that depends on how deep `turf_rt_init()`
  happened to be called from, not the thread's actual stack base).

Given a choice between narrowing the release matrix to what the runtime
already supports (Option A, small) and porting the runtime to match the
matrix it already ships (Option B, roadmap-sized), the user chose Option B.

## Runtime changes

`runtime/turfrt_gc.c` gains a compile-time platform dispatch, resolved once
near the top of the file (right after the standard includes) into two
independent sets of macros used by name everywhere else in the file:

- `TURF_GC_REGCAP_SYSV64` / `TURF_GC_REGCAP_WIN64` / `TURF_GC_REGCAP_AAPCS64`
  — which register set `gc_capture_callee_saved()` spills, and
  `TURF_GC_REGCAP_WORDS` — how many `uintptr_t` words it produces (6, 28, and
  19 respectively).
- `TURF_GC_STACKBASE_PROCFS` / `TURF_GC_STACKBASE_APPLE` /
  `TURF_GC_STACKBASE_WIN32` — which OS API `turf_gc_record_stack_base()`
  calls.

Dispatch logic: `_WIN32` selects Win64 (x86-64 only; any other Windows
architecture is an `#error`) and `<windows.h>` (with `_WIN32_WINNT` bumped to
`0x0602` if not already higher, since `GetCurrentThreadStackLimits` is a
Windows-8-and-later API). `__APPLE__` selects the Apple stack-bounds query
and requires `__aarch64__` (Intel Mac releases were already dropped from
`release.yml` before this item — see that file's own comment — so no x86-64
macOS branch was added). Anything else falls through to the original
`/proc/self/maps` query, gated on `__x86_64__` (System V) or `__aarch64__`
(AAPCS64, e.g. Linux arm64 — not a release target today, but the identical
AAPCS64 register set macOS arm64 needs, so it falls out for free). A target
matching none of these is a hard `#error` naming this change record — an
unported architecture must fail to **build**, never build and silently
under-scan (OVH-001's own failure mode).

`gc_capture_callee_saved()` grows three bodies behind `#if
defined(TURF_GC_REGCAP_*)`:

- **SysV64** (unchanged): `rbx`/`rbp`/`r12`-`r15` via `movq`.
- **Win64**: the SysV64 set plus `rdi`/`rsi` (one `movq` block, 8 GPRs), plus
  `xmm6`-`xmm15`'s full 128 bits each, extracted as two 64-bit halves via
  `movq` (low 64) and `movhps` (high 64) — both baseline SSE1/SSE2
  instructions guaranteed present on any x86-64 CPU, chosen over SSE4.1's
  `pextrq` specifically so this does not silently require a newer CPU
  feature than Win64 itself already mandates.
- **AAPCS64**: `x19`-`x28` and the frame-pointer register `x29` via `str`
  (11 words), plus the low 64 bits of `d8`-`d15` via `str` (8 words) — AAPCS64
  only requires the bottom half of `v8`-`v15` preserved, not the full
  128-bit `q`/`v` view, so only that half is captured.

The Win64 XMM capture is ten independent two-operand `asm` statements (one
per register), not one statement with all 20 outputs — found live via a
`mingw-w64-gcc` cross-compile (see *Tests*/*Known pitfalls*): a single
statement with 20 memory output operands failed to assemble at `-O0`
("`asm` operand has impossible constraints or there are not enough
registers"), because GCC could not simultaneously solve the address
computation for all 20 operands with `-O0`'s reduced register-allocator
freedom. It built fine at `-O2` — this would have been a debug-build-only
compile failure on Windows, invisible to this project's own Release-only
CI (`cmake_build.sh --release`) and to a session with no way to actually
run a Windows compile at all. Splitting into ten statements removes the
register pressure; verified clean at every `-O0`-`-O3`/`-Os` level.

`turf_gc_record_stack_base()` grows two new branches: `pthread_get_stackaddr_np(pthread_self())`
on Apple (its own documented "highest address of this thread's stack,"
exactly `g_stack_base`'s existing semantics), and `GetCurrentThreadStackLimits()`'s
`HighLimit` output parameter on Windows (MSDN's own name for "the stack's
base," again the same semantics). The Linux `/proc/self/maps` branch, and the
call-depth-dependent last-resort fallback for when a platform's query finds
nothing, are both unchanged.

`gc_mark()`'s two call sites (`uintptr_t regs[6]` and the `for (i = 0; i < 6;
...)` loop) are widened to `uintptr_t regs[TURF_GC_REGCAP_WORDS]` /
`i < TURF_GC_REGCAP_WORDS` — the only change outside `gc_capture_callee_saved()`
and `turf_gc_record_stack_base()` themselves.

`turfrt_alloc.c`/`turfrt_panic.c`/`turfrt_types.c` — audited, unchanged: none
of the three includes anything beyond `<stdio.h>`/`<stdlib.h>`/`"turfrt.h"`,
so they were already fully portable C11 with no platform-specific code at
all. `CMakeLists.txt`'s `turfrt` target needed no change (no new link
dependency: `pthread_get_stackaddr_np` is part of macOS's always-linked
`libSystem`, `GetCurrentThreadStackLimits` is part of Windows' always-linked
`kernel32`).

## New invariants

**INV-RT-4** (`docs/development/INVARIANTS.md`, Runtime section): the
register-scanning root set matches the compiled target's own ABI's
callee-saved list exactly, for each of the three implemented ABIs; an
unported target fails to build rather than silently under-scanning. Recorded
`holds` for Linux x86-64 (verified live — see *Tests* below); Win64 and
AAPCS64 are cross-compile-verified (a real assembler accepted the emitted
instructions at every `-O` level, for both the register capture and, for
Win64, the full `libturfrt.a` link) but explicitly **not verified by
executing a binary** on either platform (see *Known pitfalls*) — the row
distinguishes "assembles correctly" from "runs correctly" rather than
implying the stronger claim.

## Removed assumptions

- **"`turfrt_gc.c` is Linux/x86-64-only, and every future porting session
  will need to decide how to structure that from scratch."** No longer
  true — the `TURF_GC_REGCAP_*`/`TURF_GC_STACKBASE_*` dispatch is now the
  place a fourth ABI's branch goes; a future session porting to, say, RISC-V
  or 32-bit ARM adds one more `#elif` pair rather than redesigning the file.
- **"A release job that builds successfully means that platform's binaries
  are sound."** False before this item (the Windows release job built a
  binary with an unsound register scan and nothing caught it) and — see
  *Known pitfalls* — still only partially addressed: `release.yml` builds
  all four platforms but runs no test/smoke script on any of them, so
  "builds" and "the GC is verified correct on this platform" remain two
  different claims even after this fix.
- **"An inline-asm block with N memory output operands either assembles or
  it doesn't, independent of optimization level."** False, found live: the
  original 20-operand Win64 XMM-capture statement (see *Runtime changes*)
  failed to assemble at `-O0` specifically, while `-O2` built it without
  complaint. A future reader adding a wide multi-register inline-asm
  capture to this file (a fifth ABI, say) should test `-O0` explicitly, not
  assume a `-O2`-only smoke build is representative — this project's own
  test convention (`test_runner.sh -O0`) exists for exactly this class of
  optimization-level-dependent failure, and it applies to `libturfrt`'s own
  C sources just as much as to compiled Turf programs.

## Tests

- `./scripts/test_runner.sh` (default level): 792/792, unchanged from before
  this session — this item touches only `gc_capture_callee_saved()`/
  `turf_gc_record_stack_base()`, both dead code on the compile target this
  repository's test suite actually runs on except for the (unchanged)
  `TURF_GC_REGCAP_SYSV64`/`TURF_GC_STACKBASE_PROCFS` branch.
- `./scripts/test_runner.sh -O0`: 792/792 — the harder case per this
  project's own convention (conservative stack scanning can pass at `-O2`
  "by register luck" and fail at `-O0`; both levels green here).
- `scripts/gc_smoke.sh`, `scripts/gc_rss_smoke.sh`, `scripts/runtime_smoke.sh`,
  `scripts/mem_smoke.sh`, `scripts/opt_levels_smoke.sh`: all clean, all
  unchanged output from a pre-session baseline run (compared explicitly, not
  assumed).
- **Cross-compile verification** (a follow-up round in this same session,
  after the user installed `mingw-w64-gcc`/`aarch64-linux-gnu-gcc`):
  `x86_64-w64-mingw32-gcc -std=c11 -Wall -Wextra` compiles `turfrt_gc.c`
  clean at `-O0`/`-O1`/`-O2`/`-O3`/`-Os`, and the full `libturfrt.a`
  (all four `runtime/*.c` files) links, with `nm` confirming
  `turf_rt_init`/`turf_rt_collect`/`turf_gc_record_stack_base` present in
  the archive. `aarch64-linux-gnu-gcc` compiles the same file clean at all
  five `-O` levels (this exercises the AAPCS64 register-capture assembly
  under a real ARM64 assembler, via the Linux target — it does NOT exercise
  `TURF_GC_STACKBASE_APPLE`, which needs `__APPLE__`, undefined for a Linux
  cross-compile). This round is what caught the register-pressure `asm`
  bug described in *Removed assumptions* and *Runtime changes* — the
  Win64 branch did NOT compile clean before that fix.
- **Not run: any test that executes a binary on macOS or Windows.** No such
  machine was available to this session — cross-compilation proves the code
  *assembles*, not that a running binary's GC behaves correctly. See
  *Known pitfalls* for exactly what remains unverified and how a future
  session (or CI, on an actual tagged release) should close that gap.

## Known pitfalls

- **This change record cannot claim "verified live" (execution) for two of
  the three ABIs it implements, and does not pretend otherwise.** The
  Win64 and AAPCS64 branches were written directly against each ABI's own
  published callee-saved register list (Microsoft's x64 calling convention
  documentation; ARM's AAPCS64) and each OS's own documented stack-bounds
  API. This session's shell had no `sudo`, so the cross-compilers needed to
  even check these paths *compile* were installed by the user, on request,
  partway through the session (`mingw-w64-gcc`, `aarch64-linux-gnu-gcc`) —
  see *Tests* above for what that verified, and it was not merely
  precautionary: it caught a real bug (the Win64 XMM-capture `asm`
  register-pressure failure at `-O0`, now fixed — *Removed assumptions*).
  What cross-compilation still CANNOT check: `aarch64-linux-gnu-gcc`
  targets Linux, not Darwin, so `pthread_get_stackaddr_np` (Apple-only, no
  glibc equivalent) is never exercised by it; and neither cross-compiler
  can *run* the resulting code, so whether the captured register set
  actually retains a live GC pointer through a real collection on either
  platform remains unproven. Before shipping a tagged release built from
  this change, run `scripts/gc_smoke.sh` and `scripts/runtime_smoke.sh`
  (both fully portable bash+`cc`, no Linux-specific tooling beyond `nm`,
  which exists on both macOS and MinGW) on an actual `macos-arm64` and
  `windows-x86_64` build first.
- **`release.yml`/`test.yml` still run no test or smoke script on macOS or
  Windows** — building successfully on those runners (which `release.yml`
  already did before this session, `#error`s and all correctness gaps
  notwithstanding, since nothing there ever ran the resulting binary) is
  not the same claim as "the GC is sound there." Wiring `gc_smoke.sh`/
  `runtime_smoke.sh`/`mem_smoke.sh` (or the full `test_runner.sh`, a much
  larger CI-time/cost decision) into either workflow for the two non-Linux
  platforms is a natural, currently-unscoped follow-up — not done here to
  avoid silently expanding a runtime-portability fix into a CI-cost
  decision nobody was asked about. `mem_smoke.sh`/`runtime_smoke.sh` also
  hardcode the binary path `./build/turf`; Windows produces `build/turf.exe`,
  so those two scripts (not `gc_smoke.sh`, which never references the
  compiled binary) would need a small path fix before they could even run
  unmodified in the Windows job — flagged here, not fixed, since fixing it
  blind with no Windows machine to test the fix against would be exactly
  the kind of unverified claim this section exists to avoid making.
- **`lib/std/mem/mem.tr`'s `malloc_usable_size`/`posix_memalign` `extern fn`
  bindings have no equivalent on macOS (`malloc_size`, different name) or
  MinGW (neither exists) — a genuinely separate platform-support gap from
  this item's own scope (CI/runtime/README, per OVH-013's own subsystem
  line), found while auditing `runtime/`'s own platform assumptions but
  deliberately not touched here.** A Turf program that never calls
  `mem::usable_size()` is unaffected (an unreferenced `extern fn` costs
  nothing at link time); one that does would fail to link on macOS/Windows.
  Not reproduced live (no machine to link against either libc), not fixed,
  recorded so a future session doesn't have to rediscover it from scratch.
- **`gc_capture_callee_saved()`'s technique — read a callee-saved register's
  CURRENT value, on the strength of the calling convention's own spill
  obligation — is not re-derived from first principles for Win64/AAPCS64
  here.** It is the same technique this file already used for SysV64,
  applied to two more register lists; if a future reader doubts its
  correctness for a specific ABI, the argument to check is this file's own
  top comment (the "Why a value found in a register/stack word... survives
  correctly" paragraph), which is ABI-agnostic by construction — it only
  depends on "an intervening call obligates the callee to spill anything of
  the caller's it clobbers," true of every ABI implemented here.
