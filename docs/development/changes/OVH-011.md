## Why

`docs/planning/OVERHAUL_REMAINING_WORK.md` OVH-011 (reproduced live,
2026-09-27, before this fix): `turf --resolve lib/std/collections/list.tr`
failed with `[E034] A struct named 'List' is already declared`, and the
identical failure for `lib/std/mem/mem.tr`. The prelude module `strings`
(one of the 6 modules injected into *every* top-level compile,
`ParsePreludeImports()`) does `import list::List;` — so compiling
`list.tr` directly as the entry file makes the ALWAYS-INJECTED prelude
chain transitively re-import the exact file already being compiled, fully
re-parsing and re-declaring its own `struct List` a second time.
§23 DoD item 26 requires `lib/std` to "compile clean directly";
`scripts/session_postflight.sh` special-cased "E034 and nothing else" for
these two files as a workaround, and three separate change records
(ARCH-001, TYPE-001, OPT-002) each independently re-discovered this exact
bug without fixing its root cause.

```
$ turf --resolve lib/std/collections/list.tr
── error [E034]
  A struct named 'List' is already declared.
```

Root cause (found live, tracing `ParseFile()`/`main.cpp`): the entry
file's own top-level declarations are parsed by `main.cpp`'s own
token-consuming loop, directly against the global lexer state — **never**
through `ParseFile()` at all. `ParseFile()`'s `ImportedFiles`/`ImportStack`
machinery (the exact mechanism that lets two ordinary user files both
`import list;` without duplicating anything) therefore has **no entry for
the file currently being compiled as the entry point**, no matter how it's
reached. When `strings.tr`'s own `import list::List;` — parsed transitively
during prelude injection, entirely *before* `main.cpp`'s own top-level loop
starts reading the entry file's tokens — resolves to the exact same
physical path, `ParseFile()` has genuinely never seen that path before and
parses it for real, a second, fully independent time.

## Language semantics

### Old behaviour
`turf --resolve lib/std/collections/list.tr` (and `mem.tr`) failed with
`E034`, for a reason having nothing to do with either file's own content —
purely an artifact of the prelude chain reaching back to whichever file
happens to be the entry point. `scripts/session_postflight.sh`'s stdlib
sweep exempted exactly these two paths, checking only "no error other than
this specific known one."

### New behaviour
`turf --resolve lib/std/collections/list.tr` (or any other `lib/std`
module) reports nothing but `Error: No entry point found` — the same,
entirely expected message a pure library file with no `main()` always
produces. No per-file exemption remains anywhere.

### Is this breaking?
No. This only makes previously-rejected input (a direct compile of a
self-referencing `lib/std` module) succeed; no program that compiled
before this fix is affected — the fix only activates when a transitive
import's resolved path exactly matches the entry file's own path, which
was unconditionally an error (or, for an ordinary user program, simply
never happened) before this change.

## Compiler architecture

- **Parser** (`src/ParserModule.cpp`): new function `ClaimEntryFileImportSlot(EntryPath)`,
  exported via `include/Parser.h`. Called once per parse pass (both
  `main.cpp`'s pre-pass and its separate mandatory pass — `ImportedFiles`
  is cleared between them by `ClearParsedTopLevelASTs()`, so each pass
  needs its own claim), immediately after that pass's own
  `ParsePreludeImports()` call and *before* the entry file's own top-level
  declaration loop starts. Two outcomes:
  - The entry path (or its stdlib/usr-index alias — see below) is *already*
    in `ImportedFiles`: a transitive import during **this pass's** prelude
    injection already reached it and parsed it for real, exactly like any
    ordinary first-time import (nothing about that parse changes — it is
    still the one, authoritative parse, correctly registering everything
    under the real module name, e.g. `"list"`). Returns `true` — the
    caller must skip its own top-level loop entirely: every declaration
    this file has is already present; re-parsing would only duplicate it.
  - The entry path is *not yet* in `ImportedFiles` (the ordinary case: an
    arbitrary user program, or a `lib/std` module whose prelude chain never
    happens to reach it). Registers it *now*, before the caller's own
    top-level loop runs, so a *later* self-reference introduced by one of
    the entry file's own `import` statements (a companion module importing
    the entry back — not merely a prelude-triggered one) becomes an
    ordinary already-imported cache hit too. Returns `false` — the caller
    proceeds normally.
  - Also registers the same physical file's stdlib/usr-index alias (e.g.
    `StdIndex["list"]`) when one exists and matches by `real_path()` — a
    transitive import reaches this file through the *module search path*,
    not by repeating the entry's own command-line spelling, so the two
    strings essentially never match as plain text without this
    canonicalization (mirrors `ParsePreludeImports()`'s own, narrower,
    pre-existing self-check, which needs the identical technique for the
    identical reason).
- **`main.cpp`**: both copies of the entry file's own top-level parsing
  loop (the pre-pass's `while (CurTok != TOK_EOF) { ... }` and the
  mandatory pass's `while (true) { ... }`) are now wrapped in
  `if (!ClaimEntryFileImportSlot(SourceFilename)) { <loop> }`, placed
  immediately after that pass's own `ParsePreludeImports()` call.

## New invariants

**INV-STD-3** (`docs/development/INVARIANTS.md`, "Capabilities and the
standard library" section): any import (direct or transitive, prelude or
not) whose resolved path is the exact file currently being compiled as the
entry point binds to that entry's own already-parsed content instead of
re-parsing and re-hoisting it a second time. Recorded as narrower than its
own name suggests — see *Known pitfalls* below for the one disclosed gap.

## Removed assumptions

- **"The entry file's own declarations are parsed exactly once per pass,
  no matter what" was never actually true once a prelude module could
  transitively reach the same physical path** — it happened to hold for
  every `lib/std` module *except* the two whose transitive prelude chain
  reaches back to themselves (`list.tr`, `mem.tr`), which is exactly why
  this bug survived three separate change records re-discovering it rather
  than being fixed outright. Any future addition to the prelude list, or
  to what a prelude module itself imports, should check whether it could
  newly create a self-referencing chain back to some other `lib/std`
  module — this fix makes the CONSEQUENCE (duplicate declarations)
  impossible, but does not prevent new self-referencing chains from
  forming.
- **"Only `ParseFile()` ever needs to consult `ImportedFiles`/`ImportStack`"
  is no longer true.** `main.cpp`'s own entry-file parsing loops now also
  read (and, in the general case, write) `ImportedFiles` directly — a
  future refactor of the import-cache data structures must account for
  this second, non-`ParseFile()` caller.

## Known pitfalls

- **The general fix (`ClaimEntryFileImportSlot`) only proves a *bare*
  (`import X;`, no `::`) back-reference is safe — an on-demand/qualified
  one is a disclosed, unfixed gap.** When the entry-path claim triggers the
  "register now, before parsing" branch (the general, non-prelude case), a
  transitive re-import gets an EMPTY cache-hit body — correct for avoiding
  a duplicate declaration, but it means the entry file's own declarations
  (registered under `hoistTopLevel()`'s `""`/"current file" context, never
  under whatever module name a transitive importer used) are **not**
  visible to that importer's `import entry::Something;`-style on-demand
  request (`registerOnDemandImports()`'s `RegisterTypeIfOwned`/
  `RegisterFunctionIfPresent` checks `getTypeOwningModule(Name) ==
  SourceModule`, which is `""`, not the importer's own name for this file)
  — that request would fail with `UnknownModuleSymbolError`. This is why
  `entry_file_reimported_transitively_module.tr` deliberately imports the
  entry back in **bare** mode only. The CONCRETE bug this item fixes
  (`list.tr`/`mem.tr`) does **not** hit this gap: there, the transitive
  import (`strings.tr`'s `import list::List;`) happens entirely *before*
  the entry's own top-level loop even starts (during prelude injection),
  so `ClaimEntryFileImportSlot()` takes the *other* branch (`true`, "skip
  my own re-parse") and the transitive parse is the one, real,
  correctly-`"list"`-tagged parse — the qualifier mismatch never arises.
  Reproduced live while investigating this: naively pre-registering the
  entry path *before* prelude injection (rather than checking-then-
  conditionally-registering *after* it, as implemented) makes the
  transitive `strings.tr` import ALSO get an empty body, which genuinely
  breaks `strings::split()`/`strings::join()`'s own use of `List` —
  confirmed by temporarily reordering the two calls and recompiling:
  `import list::List;` (`strings.tr:32`) then fails with
  `[E030] Module 'list' has nothing named 'List'`. Closing this gap fully
  would need the
  entry file's own top-level declarations to be registered under BOTH the
  `""` context AND whatever module name(s) it's independently reachable
  as — a Resolver-level change (`hoistTopLevel()` currently hardcodes `""`
  for structs, never consulting `currentModuleName()`), out of this item's
  Parser-scoped size (S–M) and not attempted here.
- **The naming sweep's plain-text grep can false-positive on a comment.**
  `tests/22_prelude/entry_file_reimported_transitively_module.tr`'s first
  draft included the literal phrase "declares no `fn main()`" in its own
  top comment, explaining why the file has no entry point — `find tests
  -name "*_module.tr" | xargs grep -lE '\bfn\s+(int\s+)?main\s*\('`
  (AGENTS.md's own mandated sweep) matched that COMMENT text as if it were
  a real declaration, flagging a file that has no `main()` at all as one
  that supposedly does. Reworded to avoid the literal `fn ... main(`
  substring in prose; a future test file's own doc comments should avoid
  spelling out that exact pattern for the same reason.
- **Order matters: check-then-register must run *after* `ParsePreludeImports()`,
  never before.** The whole fix depends on the transitive prelude-triggered
  import being allowed to run for real (a genuine, non-cache-hit parse)
  before the entry's own claim registers anything — reversing the order
  (registering the entry path *before* calling `ParsePreludeImports()`)
  reproduces the exact `UnknownModuleSymbolError` regression described in
  the first pitfall above, for every `lib/std` module the prelude chain
  transitively touches, not just the two this item names.
