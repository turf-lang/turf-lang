## Why

`docs/development/OVERHAUL_CLOSURE_AUDIT.md` §3 finding F-01 (reproduced
live, 2026-09-26): `TurfTypeDesc.pointer_word_bitmap` (`runtime/turfrt.h`)
was a single inline `uint64_t`, so `turf_rt_typedesc_is_pointer_word()`
(`runtime/turfrt_types.c`) returned 0 for any `word_index >= 64`, and
`gc_scan_block_precise()`'s mark loop (`runtime/turfrt_gc.c`) capped
`max_word` at 64. RT-001 shipped this as a disclosed limitation ("a future
session must widen it first," nothing read the bitmap yet). MEM-002 then
built a real collector on top of it without widening it first, which
turned the disclosed limitation into a live use-after-free: any struct, or
collection element type, whose alloc size exceeds 512 bytes and has a
pointer-shaped field past byte 512 was silently untraced. A GC-heap object
that field pointed at could be freed by the collector while the containing
struct was still reachable — the worst possible collector failure mode for
a design whose whole premise (F-MEM-1) is precise heap tracing.

Reproduced live (matching the audit's own reproducer shape): a struct with
70 `int` fields followed by a `string` field (`name`, landing at word 70)
compiled and ran fine right up until a collection swept the string out
from under a still-reachable `List<Big>` element — `test::assert` failure,
exit 134. A control struct with only 60 `int` fields (61 words, entirely
within the old cap) passed.

## Language semantics

### Old behaviour

No Turf-level language change of any kind — this is a compiler↔runtime
internal fix. A compiled program's *correct* observable behaviour is
unchanged; what changes is that a program using a struct/collection element
type over 512 bytes with a pointer field past that point, which previously
corrupted memory nondeterministically after a collection, now behaves
correctly instead.

### New behaviour

Identical from a Turf source perspective. Internally, every pointer-shaped
word of every descriptor-described type is traced by the collector, at any
type size — no fixed cap, no silent truncation.

### Is this breaking?

No Turf-level breakage. It IS a breaking change to the compiler↔runtime C
ABI (`TurfTypeDesc`'s layout changed field-for-field), but `libturfrt` is
versioned lock-step with the compiler (F-MEM-4) and never distributed or
linked independently — every existing compiled Turf binary is naturally
recompiled against the matching pair, so there is no external consumer to
migrate.

## Compiler architecture

- **Codegen** (`src/CodegenStruct.cpp`):
  - `getOrCreateTurfTypeDescType()` now builds `{i64, ptr, i64, ptr}`
    (`size, name, word_count, pointer_words`) instead of the old
    `{i64, ptr, i64}` (`size, name, pointer_word_bitmap`).
  - `collectPointerWordBits()` now fills a `std::vector<uint64_t>&`
    (one entry per 64 traced words) instead of ORing bits into a single
    `uint64_t&`, with an `assert` that a computed word index never falls
    outside the vector it was given (a defensive bound — the caller sizes
    the vector to cover the type's own full alloc size first, so this
    should be unreachable, but a future caller that gets the sizing wrong
    now fails loudly rather than truncating silently).
  - New shared helper `buildTurfTypeDescInit()` computes
    `word_count = ceil(size / 8)`, builds a `[N x i64]` constant array
    global (`N = ceil(word_count / 64)`) for the bitmap, and assembles the
    full `TurfTypeDesc` constant — used by BOTH `emitTurfTypeDesc()` (one
    per whole struct instance) and `getOrCreateElementTurfTypeDesc()` (one
    per collection element type). These two call sites duplicated the
    old inline-bitmap logic independently before this fix, which is
    exactly why the 64-word cap needed fixing in two places instead of
    one — factoring the wide-bitmap logic into one function removes that
    failure mode going forward.
  - A hard `assert(word_count * 8 >= size)` plus `assert(bitmap vector
    length == computed word count)` at emission — a future reintroduction
    of any fixed cap now fails loudly in a debug build instead of silently
    truncating again.

## Runtime changes

- `runtime/turfrt.h`: `TurfTypeDesc.pointer_word_bitmap` (`uint64_t`) →
  `word_count` (`uint64_t`) + `pointer_words` (`const uint64_t *`, a
  `ceil(word_count / 64)`-element static array).
- `runtime/turfrt_types.c`: `turf_rt_typedesc_is_pointer_word()` bounds-checks
  against `desc->word_count` (the type's real word count) instead of a
  fixed `64`, and reads `desc->pointer_words[word_index / 64]` bit
  `word_index % 64` instead of shifting a single inline field.
- `runtime/turfrt_gc.c`: `gc_scan_block_precise()`'s mark loop now iterates
  `w < b->desc->word_count` with no `if (max_word > 64) max_word = 64;` cap
  at all.

## Standard-library changes

None. No `lib/std` file references `pointer_word_bitmap`/`TurfTypeDesc`
directly (Rule B2/B3 — this is compiler/runtime-internal, never surfaced to
Turf source).

## New invariants

Added to `INVARIANTS.md`:
- **INV-MEM-2**: "Every pointer-shaped word of every descriptor-described
  object is traced, at any size — no fixed cap, no silent truncation."
  Enforced by the variable-length bitmap plus the emitter's own length
  assertion; verified live by reproducing the original bug (temporarily
  reintroducing the 64-word cap crashed both new regression tests with the
  exact corruption the missing trace causes) and confirming both pass
  cleanly with the cap removed.

Updated: **INV-RT-3**'s wording (`pointer_word_bitmap` → `pointer_words`,
no other change — the ordering guarantee it describes is untouched by this
fix).

## Removed assumptions

- **"A `TurfTypeDesc`'s bitmap only needs to cover 64 words/512 bytes
  because no TurfLang struct in `tests/`/`lib/std/`/`showcase/` is anywhere
  near that size."** This was RT-001's own stated justification for
  deferring the widening. It was true when written (nothing read the
  bitmap yet) and became false the moment MEM-002 built a real collector
  on top of it — the assumption was never re-checked against the new
  consumer's actual requirements. The bitmap now has no size limit at all;
  no future struct size can silently exceed it again.
- **"The per-element descriptor path (`getOrCreateElementTurfTypeDesc()`)
  and the per-struct path (`emitTurfTypeDesc()`) can each own their own
  copy of the bitmap-building logic."** They can't, safely — see
  *Compiler architecture* above. Any future change to how the bitmap is
  computed must go through `buildTurfTypeDescInit()`, not be duplicated
  again at either call site.

## Known pitfalls

- The two descriptor-building call sites (`emitTurfTypeDesc()`,
  `getOrCreateElementTurfTypeDesc()`) used to each hand-roll the same
  name-global/GEP idiom independently. `buildTurfTypeDescInit()` now owns
  the WHOLE constant (size, name pointer, word count, bitmap pointer) —
  a future change to any of the four fields' construction belongs there,
  not back at either call site. `emitTurfTypeDesc()`/
  `getOrCreateElementTurfTypeDesc()` now only choose the two global names
  (matching their own pre-existing naming so `scripts/runtime_smoke.sh`'s
  `--emit-llvm` greps keep matching) and wrap the shared constant in their
  own `GlobalVariable`.
- `word_count` is computed as `ceil(size / 8)`, not `size / 8` — a type
  whose alloc size is not a multiple of 8 (possible for a struct with no
  8-byte-aligned field, though none of the language's own primitives
  currently produce one smaller than a whole word) still gets a word count
  that covers its last partial word, satisfying the `word_count * 8 >=
  size` assertion. This matters if a future language change ever adds a
  sub-8-byte-aligned aggregate type.
- LLVM's IR printer collapses an all-zero constant array to the
  `zeroinitializer` sigil rather than spelling out `[i64 0]` — the smoke
  script's own `check_desc()` has to special-case this (see the script's
  comment) or it reports a false failure on every pointer-free type
  (`Plain`, in particular).
- The `if (auto *ST = llvm::dyn_cast<...>)` / `assert(!ST->isOpaque())`
  pattern in `getOrCreateElementTurfTypeDesc()` produces an "unused
  variable" warning in a release (`NDEBUG`) build, where `assert()` is a
  no-op — this is pre-existing (unrelated to this fix, same pattern
  existed before under the old bitmap field) and not addressed here.
