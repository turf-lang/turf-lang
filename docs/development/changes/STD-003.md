## Why

TYPE-002 (monomorphization) deliberately landed with the standard library
*unchanged*, leaving a set of workarounds in `lib/std` that existed only
because of the erasure model TYPE-002 replaced — each documented in
`LIMITATIONS.md` or a source comment as "works around a compiler gap." This
group's job was to consume those now-available capabilities: real
per-instantiation `sizeof(T)`, real per-`T` operator dispatch, and (new,
made possible by both) a real generic `hash(T)`.

This group ended up going further than that: THREE independent, genuine,
user-reachable compiler bugs were found while doing the stdlib work (none
was what the group set out to fix), and the user asked for all three to be
fixed directly once each was understood to be a real language-level
defect rather than an inconvenience specific to this group's own ticket.
See *Session log* items 3, 7, and 10, and all three *Known pitfalls*
entries.

## Language semantics

No frozen decision was reinterpreted. Two genuine compiler-behavior
CORRECTIONS (not semantic changes — neither changes what any
previously-compiling program means, both below) were made.

### Fix 1 — Old behaviour (the self-call compiler bug)

```turf
struct Box<T> { v: T }
fn<T> Box.bar(x: int): int { return 0; }
fn<T> Box.foo(x: int): int { return self.bar(x); }
fn main(): int {
    mut b: Box<int> = Box::default();
    return b.foo(1);
}
```

Failed to compile: `Internal error: LLVM function 'turf_Box.bar_Box_ptr'
not found after successful name resolution. This is a compiler bug.` — a
real, user-reachable failure with no workaround available in Turf source
(see *Known pitfalls* for the precise trigger condition).

### Fix 1 — New behaviour

Same program compiles and runs correctly, returning `0`.

### Fix 2 — Old behaviour (the FuncType substitution gap)

```turf
fn<T> List.sort(cmp: fn(T, T): int): void { /* ... */ }
fn cmpInt(a: int, b: int): int { return a - b; }
fn main(): int {
    mut l: List<int> = List::default();
    l.push(3); l.push(1);
    l.sort(cmpInt);
    return 0;
}
```

Failed to compile at the DEFINITION site with `No overload of 'List.sort'
matches argument types (fn(int, int): int)` — the comparator parameter's
own `T` never resolved against the caller's concrete argument type.

### Fix 2 — New behaviour

Same program compiles and runs correctly, sorting `l` in place.

### Fix 3 — Old behaviour (the cast-legality gap)

```turf
fn<T> castToInt(x: T): int {
    return x to int;
}
fn main(): int {
    return castToInt(42);
}
```

Failed to compile at the DEFINITION site (`fn<T> castToInt`'s own
declaration, checked once, unconditionally, regardless of whether it is
ever called) with `Cannot explicitly cast 'T' to 'int'` — even though the
only real call site instantiates `T = int`, a cast the same legality
whitelist already permits once concrete (`SrcName == DstName`).

### Fix 3 — New behaviour

Same program compiles and runs correctly, returning `42`.

### Is any of the three breaking?

No, for all three. Nothing that previously compiled successfully is
affected — each fix only makes a previously-rejected program (one with an
internal codegen error and no diagnostic recourse, two with an ordinary
but incorrect type-checker rejection) now succeed. No migration needed for
any of them.

## Compiler architecture

- **Fix 1** — TypeChecker (`src/TypeCheckerCall.cpp`,
  `TypeChecker::visitMethodCall`) only. See *Known pitfalls* for the root
  cause and fix.
- **Fix 3** — TypeChecker (`src/TypeCheckerExpr.cpp`,
  `TypeChecker::visitCast`) only — one bypass, mirroring
  `typesCompatible()`'s own Rule 1: either side being a bare
  `TurfGenericParamType` skips the whole legality whitelist at the
  TEMPLATE's own check, deferring the real check to the per-instantiation
  clone's own re-typecheck (which re-runs this same function with the
  generic parameter already substituted to something concrete). See
  *Known pitfalls* for the full repro and the narrower, still-open gap
  this fix does NOT reach (a generic struct's own field access via
  `self`).
- **Fix 2** — five call sites, the identical missing case (a `FuncType`
  branch) added everywhere the existing pointer/array/`GenericType` cases
  already lived:
  - **Resolver** (`src/ResolverCore.cpp`, `substituteTypeParams()`) — a
    generic declaration's own `NamedType` occurrences inside a `FuncType`
    parameter/return type now become `TurfGenericParamType`, same as a
    bare parameter already did.
  - **Types** (`src/Types.cpp`, `typesCompatible()`) — candidate matching:
    two `FuncType`s are now compatible when they have equal arity and
    each parameter/return position is itself `typesCompatible()`
    (recursively — this is what lets a still-generic `fn(T, T): int`
    match a concrete `fn(int, int): int` candidate).
  - **TypeChecker** (`src/TypeCheckerCall.cpp`,
    `collectGenericSubstitution()`/`collectGenericParamNameOrder()`) —
    building the `Subst` map (and its canonical name ordering) from a
    call site now recurses into a `FuncType` argument's own parameter/
    return types.
  - **Monomorphizer** (`src/Monomorphize.cpp`,
    `substituteConcreteTypes()`) — a monomorphized clone's own `FuncType`
    parameter now gets its inner `TurfGenericParamType`s replaced with
    the concrete instantiation's types, same as every other wrapper shape
    already did; without this, a clone would still trip the existing
    `INV-GEN-1` assert at `finishInstantiation()`'s own completion check.

## Removed assumptions

- **`LIMITATIONS.md` item 2's own framing was wrong, and had been for a
  while.** It said TYPE-002 unblocked the underlying generic-comparator
  mechanism, leaving only the stdlib conversion as this group's job. That
  turned out to be false, discovered only by actually attempting the
  conversion (not from re-reading the document, which is exactly the
  "verify claims live" pitfall `AGENTS.md` warns about generally, now
  demonstrated concretely). A future session should not trust a prior
  session's "should be straightforward now" note without independently
  re-confirming it, even when that note itself sounds confident.
- **"Compiler changes: None" (this group's own original scope line) is a
  default, not an absolute.** It correctly kept this group from freelancing
  on unrelated compiler work for its own convenience — but it is not a
  reason to leave a genuine, independently-reproducible, user-reachable
  language defect unfixed once discovered, if the user asks for it to be
  fixed with that tradeoff explicit. Two such fixes landed in this single
  session (the self-call bug, the `FuncType` substitution gap), both
  outside the group's original scope line, both because a real person
  writing ordinary Turf code would hit them with no workaround available.
  A future session should read a scope-limiting line like this one as
  "don't go looking for unrelated compiler work," not as "never fix
  anything outside the ticket regardless of what's found or who asks."
- **A generic struct method whose own parameter list references the
  struct's type parameter is not the only shape monomorphization
  supports** — it's the only shape that happened to be EXERCISED before
  this group. `bucketRehash(newCap: int)`'s need for a parameter wholly
  unrelated to `K`/`V` is what surfaced the compiler bug below; nothing
  about `Map`/`Set`'s pre-existing methods (`indexOf(key: K)`,
  `contains(key: K)`, etc.) ever needed this shape, so it went
  undiscovered through TYPE-002's own 8 sessions and every test written
  since.
- **A collection module's storage field being `T*` vs. a safe `&T` is not
  independent of what `T` can legally be instantiated with.** It's
  tempting to read LANG-002 (nullable references / declared capabilities)
  as making item 8 a purely mechanical `T* -> &T` field-type swap. It
  isn't: `T`/`K`/`V` are unconstrained generic parameters, a caller can
  legally instantiate any of these five modules with a raw pointer type
  argument (`List<SomeStruct*>`, still explicitly supported per item 2),
  and once that happens the collection's OWN method parameters (`item:
  T`, `key: K`, `hashing::hash`'s own `x: T`) substitute to raw-pointer
  types that need the DECLARING FILE's raw-pointer capability regardless
  of what the backing-array field's own type is. A scoped `unsafe { }`
  block around just the allocation calls cannot satisfy this, because
  `checkNoRawPointersInSignature` checks the function's DECLARED
  SIGNATURE, not how its body is written.
- **Removing `unsafe module;` from a generic-over-`T` stdlib file is not
  safe to validate with only `int`/`string`-instantiated test cases.**
  Every test written for this group's own hash-index work used `int`/
  `string` keys/elements exclusively (matching every actual use of
  `Map`/`Set` anywhere in this codebase) — the item-8 regression
  (`List<Point*>`, `Map<Point*, int>`) was only found by deliberately
  testing a pointer-typed instantiation specifically BECAUSE item 2's own
  "not removed, still supported" claim demanded it. A future session
  touching any of these five files' capability declarations must test a
  pointer-typed instantiation, not just the types the current stdlib
  happens to use internally.
- **`typesCompatible()`'s existing wrapper-shape coverage (pointer/array/
  `GenericType`) was never exhaustive, and nothing signaled that it
  wasn't.** `FuncType` is a perfectly ordinary wrapper shape — a value
  containing other typed positions, the same category as a pointer's
  pointee or an array's element — and had simply never been exercised
  generically before this group, in this entire codebase, across every
  compiler-development session since generics landed. There is no
  mechanical way to know a wrapper-type case is missing until something
  needs it; a future session adding a new wrapper-shaped type (another
  compound type carrying its own nested `TurfTypePtr` positions) should
  assume it needs the identical treatment in all five places this fix
  touched, not just the ones that happen to come up first.
- **A single build/rebuild cycle during fast iteration is not enough to
  trust an unexpected pass OR an unexpected failure.** While developing
  Fix 3, `cmake --build` followed immediately by a single failing test run
  appeared to show the fix breaking an unrelated, previously-passing test
  (`list_sort`) — investigated as a real regression for several steps
  before a from-scratch rebuild plus a full suite re-run showed it was
  never real (the exact same test, same binary invocation, passed cleanly
  moments later with no source change in between). The likely cause was an
  incremental-build/linking race, not anything about the fix's own logic.
  A future session hitting a result that contradicts recent, confident
  testing should rebuild clean and re-run before spending time
  root-causing what might not exist.

## Known pitfalls

### Fix 1 — the self-call compiler bug (not STD-003's own scope, fixed on explicit instruction)

**Trigger.** Inside a generic struct's method, calling ANOTHER method of
the same struct via `self.` fails at codegen with `Internal error: LLVM
function '...' not found after successful name resolution` whenever the
CALLEE's own parameter list contains no occurrence of the struct's type
parameter(s) — independent of the caller's own signature, independent of
argument count, independent of return type.

**Minimal repro:**
```turf
struct Box<T> { v: T }
fn<T> Box.bar(x: int): int { return 0; }         // no T anywhere
fn<T> Box.foo(x: int): int { return self.bar(x); }  // <- E011 here
```
Change `bar`'s parameter to `x: T` and it works — this is the entire
difference. Confirmed absent for a non-generic struct
(`lib/std/json/json.tr`'s `Parser.skip_ws()`, called the identical way
from a sibling method).

**Root cause** (`src/TypeCheckerCall.cpp::visitMethodCall`): recovering
the struct's own generic-parameter substitution (`Subst`, used to know
e.g. `T=int` for a given call site) used to re-derive the receiver's type
via a FRESH `getType(Node.getBase())` call, instead of reusing the
ALREADY pointer-unwrapped `BaseTy` local computed a little earlier in the
same function (`BaseTy = PtrTy->getPointee()`, for the `self`-is-a-
pointer-to-struct case). `self`'s own registered type is always
`TurfPointerType(GenericType(StructName, Args))` — never itself a bare
`GenericType` — so `dynamic_cast<GenericType*>` on that fresh, still-
wrapped fetch always failed, and `Subst` came back permanently empty for
every `self.method(...)` call. This stayed invisible whenever the
CALLEE's own parameters happened to independently reference the struct's
type parameter, because a SECOND, independent substitution source
(`MethodOwnSubst`, built by matching the callee's declared param types
against the caller's already-concrete arguments) filled the same map
entries through an unrelated path. It only broke — silently, all the way
through to a codegen-time internal error with no earlier diagnostic — when
NEITHER source had anything to contribute.

**Fix.** Capture the pointer-unwrapped `BaseTy` into its own variable
(`UnwrappedGenericBaseTy`) right after the unwrap, BEFORE it gets
overwritten by the bare-name `GenericType -> TurfStructType` lookup a few
lines later, and reuse that snapshot at both of the two places that used
to independently re-fetch `getType(Node.getBase())` (the `Subst` scan
itself, and the Method-kind instantiation-request recording just after
it — a second, independent instance of the identical bug, found by
re-testing after the first fix alone turned out to be insufficient).

**Why this matters beyond STD-003.** This is not an obscure internal
compiler-development pattern — `self.otherMethod(concreteArg)` inside a
generic struct's method, where the callee doesn't happen to redeclare the
struct's type parameter in its own signature, is an entirely ordinary
thing for anyone writing Turf to write. STD-003 hit it because
`bucketRehash(newCap: int)` needed a growth-size argument unrelated to
`K`/`V` — the first time this stdlib needed that shape at all, in 8
sessions of TYPE-002 plus everything built since. A user would have hit
it with no warning and no workaround in Turf source. Fixed on the user's
explicit instruction once this was explained, rather than left as a
"report it" item per STD-003's own "Compiler changes: None" scope
guidance — that guidance is about not treating STD-003 as license to
freelance on unrelated compiler work, not about leaving a genuinely
user-facing landmine in place because fixing it happens to fall slightly
outside one session's original ticket.

### Fix 2 — the FuncType substitution gap (not STD-003's own scope, fixed on explicit instruction)

**Trigger.** Any generic method with a callback-typed parameter that
mentions the struct's/function's own type parameter inside the callback's
signature — `cmp: fn(T, T): int`, `predicate: fn(T): bool`, or the return-
type-only shape `fn(): T` — failed to type-check at the CALL SITE with "No
overload ... matches argument types," even though the argument's own
concrete function type (`fn(int, int): int`) was exactly what the
declaration meant. Unlike Fix 1 (a codegen-time internal error with no
earlier diagnostic), this failed at an ordinary, correctly-worded
diagnostic point — but for a call that should have succeeded.

**Minimal repro:**
```turf
fn<T> identity_cmp(cmp: fn(T, T): int): int { return cmp(1, 1); }
fn cmpInt(a: int, b: int): int { return a - b; }
fn main(): int { return identity_cmp(cmpInt); }  // <- "No matching overload"
```

**Root cause.** Five separate functions, spread across the Resolver/
TypeChecker/Monomorphizer, each walk a declared type recursively to handle
every "wrapper" shape it might take — a pointer's pointee, an array's
element, a `GenericType`'s own type-argument list — so that a generic
parameter buried inside one of those shapes is still found and substituted
correctly. None of the five had ever been given an equivalent case for
`FuncType` (a function type's own parameter list and return type are
exactly the same kind of "nested typed position" a pointer's pointee is),
because nothing in this codebase's entire generics history — TYPE-002's 8
sessions, every stdlib file, every test — had ever declared a generic
callback parameter until this group tried to. `list.tr`'s own pre-fix
comment documented the resulting failure mode in detail (four different
workaround shapes tried, each blocked by the same underlying gap
manifesting differently) without diagnosing the actual missing case.

**Fix.** A `FuncType` branch added to each of the five functions,
structurally identical to (and inserted alongside) each function's
existing pointer/array/`GenericType` branch: recurse into every parameter
position plus the return type. See *Compiler architecture* above for the
full list and what each one specifically does.

**Why this matters beyond STD-003.** A generic function/method taking a
callback parameter is an entirely ordinary, commonly-reached-for pattern
(`sort`/`filter`/`map`-style APIs, event handlers, comparators) — not
something specific to `List<T>.sort()`. Any Turf program defining its own
generic higher-order function would have hit this with no workaround.
Fixed on the user's explicit instruction, for the identical reasoning as
Fix 1.

### Fix 3 — the cast-legality gap (not STD-003's own scope, fixed on explicit instruction)

**Trigger.** An explicit `to`-cast where either the source or destination
type is a bare generic type parameter (`x: T`, cast as `x to int`) was
rejected unconditionally, at the enclosing generic function/method's own
TEMPLATE type-check — the ordinary, whole-program pass every declaration
goes through once, generically, regardless of whether it is ever called —
with a correctly-worded but wrong-timed `Cannot explicitly cast 'T' to
'...'`. Unlike Fix 1 (an internal codegen error) or Fix 2 (a wrong
rejection at the CALL site), this one rejected the DEFINITION itself,
before any instantiation ever got a chance.

**Minimal repro:**
```turf
fn<T> castToInt(x: T): int { return x to int; }
fn main(): int { return castToInt(42); }  // <- fails at castToInt's OWN declaration
```

**Root cause** (`src/TypeCheckerExpr.cpp::visitCast`). Every other type-
checking path that can legitimately encounter a bare generic parameter
during a template's own check — `typesCompatible()`'s Rule 1 (equality,
argument matching), `collectGenericSubstitution()`, field access — has an
explicit `dynamic_cast<TurfGenericParamType*>` bypass: "this is a still-
open generic parameter, treat it as compatible with anything, and let the
REAL check happen once a per-instantiation clone re-runs this same code
with the parameter substituted to something concrete." `visitCast`'s own
cast-legality whitelist (`Legal = SrcName == DstName || ...`, a fixed list
of exact source/destination type-name pairs) never had this bypass —
`SrcName`/`DstName` would literally be `"T"` during the template check,
matching none of the whitelist's pairs, so the diagnostic fired
unconditionally, before monomorphization ever ran.

**Fix.** One bypass, mirroring the existing pattern: if either
`OperandTy` or `DestTy` is a `TurfGenericParamType`, skip the whitelist
entirely (the cast is provisionally legal at the template level), and let
the clone's own re-typecheck — which re-runs `visitCast` with the
parameter already concrete — apply the real whitelist then. Verified this
safety net still works: a genuinely illegal cast for a REAL instantiation
(`fn<T> badCast(x: T): bool { return x to bool; }` called as
`badCast(42)`, i.e. `int to bool`) is still correctly rejected, just at
the instantiation site instead of the (wrong) definition site.

**What this fix does NOT reach.** The motivating case — converting
`mem::Pool<T>`'s `free_pool` into a genuine `fn<T> Pool.free_all(): void`
method — still doesn't work, for a DIFFERENT reason this fix doesn't
touch: written the natural way (`free(self.items[i])`, no explicit cast,
since `free(p: void*)`'s own ordinary argument-compatibility check already
has the ordinary Rule-1 bypass), it fails with `No overload of 'free'
matches argument types (T)`, NOT a cast error. `self.items`'s type, for a
generic struct field accessed through `self` in a template check, resolves
through `GlobalSymbolTable`'s own registered `TurfStructType` for the
struct — a SEPARATE, stale copy of the struct's fields, permanently stuck
as `NamedType("T")` rather than `TurfGenericParamType("T")`, per
`TypeCheckerCall.cpp`'s own `visitMethodCall` doc comment (the same
NamedType-vs-TurfGenericParamType distinction that function `Subst`
recovery already has to special-case around). Adding an EXPLICIT cast
(`self.items[i] to void*`) does not help either — confirmed live: that
specific `NamedType("T")` operand also fails to match this fix's
`TurfGenericParamType`-only bypass, for the identical underlying reason.
Fixing this would mean the field-type resolution itself, a larger and
less-contained change than this fix (which is one dynamic_cast bypass in
one function) — not pursued, on a judgment call that the practical payoff
is low (`Pool<T>` is always instantiated at a pointer type in this
codebase, so a generic `free_all()` would never be called with anything
the existing concrete `free_pool(pool: Pool<void*>)` doesn't already
handle) versus a real, if probably modest, risk of touching field-type
resolution more broadly. Reported to the user rather than decided
unilaterally.

**Why this matters beyond STD-003.** An explicit conversion inside a
generic function/method (`x to SomeType`) is ordinary code, not specific
to `mem::Pool<T>` or this group's own work — any Turf program with its own
generic function needing to convert its type parameter to something
concrete would have hit this with no workaround. Fixed on the user's
explicit instruction, for the identical reasoning as Fix 1 and Fix 2.

### Item 8 (dropping the raw-pointer capability from collections) — investigated, not done

Making `List`/`Stack`/`Queue`/`Map`/`Set`'s backing-array field(s) a safe
`&T` instead of `T*`, and dropping each file's `unsafe module;` pragma in
favor of a scoped `unsafe { }` block around just the `gc_alloc`/
`gc_realloc` calls, compiles and passes every existing test — UNTIL a
caller instantiates the collection with a raw-pointer type argument
(`List<Point*>`, `Map<Point*, int>`), which is a real, explicitly-still-
supported pattern (item 2). At that point `push(item: T)`/`put(key: K,
...)`/`hashing::hash`'s own `x: T` all substitute to a raw-pointer-typed
PARAMETER, and `checkNoRawPointersInSignature` (`TypeCheckerCore.cpp`)
requires the DECLARING FILE to hold the raw-pointer capability for that —
a requirement a scoped `unsafe { }` block around the function BODY cannot
satisfy, because the check runs against the function's declared signature,
not its body. Confirmed live (both for `List<Point*>.push` and, separately,
for `hashing::hash`'s own generic fallback via `Map<Point*, int>`), then
reverted in all files touched (`list.tr`, `hashing.tr`) — `map.tr`/
`set.tr`/`stack.tr`/`queue.tr` were never actually changed for this item,
only investigated via the two files that were. Each file now carries a
short note explaining why `unsafe module;` stays.
