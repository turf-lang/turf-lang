## Why

A struct field whose own declared type is ANOTHER generic instantiation
could not be used as the base of a further field access. Verified live
against `refactor/architecture` (the 2026-09-26 closure audit):

```turf
struct Pair<A, B> { a: A, b: B }
struct Box<T> { inner: Pair<T, T> }
fn main(): int { mut b: Box<int> = Box::default(); b.inner.a = 3; return b.inner.a - 3; }
// error: Cannot access field on non-struct type
```

Going through a local (`mut p: Pair<int, int> = b.inner; p.a = 3;`) already
worked — the bug was specifically in resolving the type of `b.inner` when
it is itself used as the base of another field access, for both reads and
writes.

**Root cause.** Per the plan's own strategy, `--dump-typechecked`/direct
inspection confirmed the TypeChecker was never the problem: `TypeChecker::
visitFieldAccess()`'s (`TypeCheckerCall.cpp`) own `Scan`/`substituteReturnType()`
pair already recurses into a field whose declared type is itself a
`GenericType` (the "NestedGT" case added by TYPE-002 S15/D4) and correctly
resolves `b.inner`'s type to the concrete `GenericType("Pair", [int, int])`.

Codegen has its own, independent, structurally separate type-inference
function, `getExprType()` (`CodegenCore.cpp` — see
`docs/architecture/compiler_pipeline.md` §4's own note on this duality).
Its `FieldAccessExprAST` case has the identical Subst-recovery `Scan`/
`Apply` pair TypeChecker's does, for the identical reason (`GlobalSymbolTable`'s
per-instantiation clones don't help here — this is about recovering a
STRUCT DECLARATION's own type-parameter names from its TEMPLATE'S field
shapes) — but neither `Scan` nor `Apply` had a case for a field whose own
type is a `GenericType`. `Scan` never recovered `T -> int` from `Box<T>`'s
`inner: Pair<T, T>` field at all (none of its branches — bare
`TurfGenericParamType`, `NamedType`, pointer, array — match a bare
`GenericType`), and even had it, `Apply` had no case to REBUILD a
substituted `GenericType` either. The net effect: `getExprType(b.inner)`
returned the literal, still-open `Pair<T, T>` (`T` a live
`TurfGenericParamType`) instead of `Pair<int, int>`.

`FieldAccessExprAST::codegenLValue()` (also `CodegenStruct.cpp`) was
**already correct** for the next step — it resolves a `GenericType` base to
its real, per-instantiation registered clone via `Monomorphize::
instantiatedDeclName(GT->getBaseName(), GT->getTypeArgs())` (a TYPE-002 S13b
fix). But fed the UNSUBSTITUTED `Pair<T, T>` by `getExprType()`, it built
the mangled name from the literal, open `T, T` type arguments — a name the
monomorphizer never registered anything under (it genuinely does register
`Pair<int, int>`, confirmed via `--dump-instantiations`: `[struct] Pair<int, int>`
appears in the census with 2 call sites). The lookup failed, `BaseType`
was never resolved to a real `TurfStructType`, and the fallback
`"Cannot access field on non-struct type"` fired.

## Language semantics

### Old behaviour
`b.inner.a` (read or write), where `inner`'s declared type is itself a
generic instantiation of another type parameter (`Pair<T, T>` on `Box<T>`),
failed to compile with `"Cannot access field on non-struct type"` — even
though the equivalent access through an explicit local variable
(`mut p: Pair<int, int> = b.inner; p.a`) already worked.

### New behaviour
Arbitrary chains of field access through a generic struct field whose own
type is another generic instantiation work for reads, writes, and compound
assignment, at any nesting depth, including through a struct method's own
`self`.

### Is this breaking?
No. Only removes a false rejection; no previously-accepted program is
affected.

## Compiler architecture

- **Codegen** — `getExprType()`'s `FieldAccessExprAST` case
  (`CodegenCore.cpp`): the `Scan` lambda gained a `GenericType` branch that
  recurses into the field's own type-argument list (mirroring
  `TypeCheckerCall.cpp`'s S15/D4 "NestedGT" fix); the `Apply` lambda gained
  a matching `GenericType` branch that rebuilds a new, substituted
  `GenericType` from the recursively-`Apply`'d argument list, cached in the
  same static `FieldSubstCache` map the existing pointer-wrapper case
  already uses (keyed by mangled name), for the same reason that map exists
  at all: `getExprType()` returns a raw `const TurfType *`, so a
  freshly-constructed type must be kept alive for the rest of the process,
  not just this call.
- **Resolver, TypeChecker** — no changes; both were already correct for
  this shape (verified live, see *Why*).
- **`codegenLValue()`** (`CodegenStruct.cpp`) — no changes; its own
  mangled-instantiation-name lookup was already correct once handed a
  properly-substituted `GenericType`.

## Removed assumptions
- **"`getExprType()`'s field-type Subst-recovery only ever needs to handle
  a scalar/pointer/array-shaped type parameter occurrence."** Its `Scan`/
  `Apply` pair was written before a generic struct field's own type could
  itself be another generic instantiation was a live, tested shape — the
  gap silently persisted because nothing exercised it until OVH-007's own
  reproducer. `TypeCheckerCall.cpp`'s equivalent pair already carries this
  exact fix (TYPE-002 S15/D4); `getExprType()`'s pair did not, despite
  being a structural duplicate of the same logic (the duality
  `compiler_pipeline.md` §4 names directly).
- **"A `GenericType` reaching `codegenLValue()`'s base-type resolution is
  always already concrete."** True for a variable's own declared type, but
  not for the result of `getExprType()` on an intermediate FIELD access —
  this item's fix is what makes that assumption actually hold at the point
  `codegenLValue()` relies on it.

## Tests

- `tests/38_monomorphization/nested_generic_field_chain.tr` (new): the
  exact reproducer (read, write to the other field, compound-assign),
  three levels deep (`Wrap<int> -> Box<int> -> Pair<int,int> -> int`), and
  through a method's own `self` (both a generic-method read via
  `self.inner.a` and a generic-method write via `self.inner.a = v`).
  Compound-assignment *inside* a generic method body directly on the
  struct's own still-open type parameter (`self.inner.a += 1` inside
  `fn<T> Box.bump()`) was tried and found to be a SEPARATE, pre-existing,
  unrelated restriction — confirmed live with a non-nested, single-level
  reproduction (`struct Box<T> { val: T } fn<T> Box.bump(): void { self.val
  += 1; }` fails identically, with no nesting involved at all): `+=`
  desugars to `+`, and `+` needs an exact type match (F-OP-1) that a bare,
  still-open `T` can never satisfy during the TEMPLATE's own type-check.
  Out of this item's scope; the test instead exercises compound-assignment
  from the CONCRETE call site (`b.inner.a += 10;` in `main()`, where `T` is
  already `int`) and a plain (non-compound) write through `self`.
- Full suite (`./scripts/test_runner.sh`) green at default and every
  `-O0`..`-O3`/`-Os` level (785/785, including the new test). Every
  `lib/std/**/*.tr` and `showcase/*.tr` file compiled directly — no new
  errors.

## Known pitfalls

- **`getExprType()` and `TypeChecker::visitFieldAccess()`'s Subst-recovery
  logic are independent, hand-duplicated implementations of the same
  idea**, not a shared helper — this is exactly the architectural wrinkle
  `docs/architecture/compiler_pipeline.md` §4 names ("a 'what type is this'
  answer inside `Codegen*.cpp` almost never comes from the TypeChecker's
  own `NodeTypes_` table"). A future fix to one's Subst-recovery shape
  (e.g. a THIRD level of field-of-field-of-field generic nesting, or a
  struct with more than two type parameters whose fields don't mention
  every parameter in declaration order — the existing "not fully general"
  caveat both copies already carry) must be applied to **both** copies
  independently, or Codegen and the TypeChecker will silently disagree
  again the same way this item's own bug did.
- **This is genuinely a two-level nesting fix, not an N-level one by
  induction.** `Scan`'s new `GenericType` branch recurses into a NESTED
  generic's type arguments looking for the OUTER struct's OWN type
  parameter (T appearing inside `Pair<T, T>`); it does not need to go any
  deeper than that, because `Apply`'s matching branch rebuilds the nested
  `GenericType` by recursively calling `Apply` on each of ITS OWN type
  arguments — which is what actually gives this arbitrary depth (confirmed
  live via the three-level `Wrap<int> -> Box<int> -> Pair<int,int>` test
  case, not merely asserted).
- **Compound assignment directly on an open generic parameter, inside a
  generic function/method's own template body, is rejected regardless of
  nesting** (see *Tests* above) — this is `F-OP-1`'s exact-match
  requirement doing its job correctly (an open `TurfGenericParamType`
  cannot exact-match a concrete `int` for operator resolution), not a bug
  this item introduces or was asked to fix. Do not conflate the two if
  revisiting this file.
