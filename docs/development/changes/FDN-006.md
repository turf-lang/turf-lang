## Why
Every runtime failure a user can hit must end in a documented message and
exit code, and a binary must never silently run against the wrong runtime.
Before this group:

- A stack overflow was a bare `SIGSEGV` — exit 139, no message (the
  Overhaul closure audit's own F-20 finding).
- RT-001 already put the fail-fast OOM policy "in one place"
  (`turf_rt_alloc`/`turf_rt_alloc_zeroed`/`turf_rt_realloc`), but it was
  never actually verified with a test — the audit's own attempt to reach it
  spun forever inside `strings::repeat()`'s quadratic loop instead of ever
  triggering a real allocation failure.
- Nothing stopped a freshly compiled object from linking against a stale or
  incompatible `libturfrt.a`; a missing runtime library surfaced only as
  `cc`'s own generic `-lturfrt: No such file` error, with no mention of
  TurfLang or `TURF_HOME`.

## Language semantics
### Old behaviour
```turf
fn recurse(n: int): int {
    return recurse(n + 1) + n; // unbounded, non-tail recursion
}
fn main(): int { return recurse(0); }
```
crashed with a bare `SIGSEGV`, exit 139 (128+11), no message. A direct huge
`gc_alloc()` call already fail-fast panicked (RT-001's own code path), but
had never been exercised by a test. A missing/mismatched `libturfrt.a`
either produced a generic linker error or (for a stale-but-present archive)
could link successfully and misbehave at run time.

### New behaviour
The same recursion now prints `panic: stack overflow: the call stack
exceeded its limit -- check for unbounded or missing-base-case recursion
(<runtime>:0)` and aborts (`SIGABRT`, exit 134) — the same terminal shape
every other panic already has. Any OTHER `SIGSEGV` (a real memory-safety bug
in `unsafe` code, or in the compiler/runtime itself) now prints `panic:
segmentation fault (this is a bug in unsafe code or in TurfLang) at address
<addr>` and also aborts (134), rather than crashing silently. A direct huge
allocation panics `out of memory` — unchanged behaviour, now with real test
coverage. Every compiled binary's `main` wrapper calls a new, do-nothing
runtime symbol, `turf_rt_abi_2_0()`; a `libturfrt.a` that predates this
symbol (or a hypothetical future ABI-breaking runtime that renamed it)
fails to **link**, with that name in the linker's own error, instead of
linking and misbehaving at run time. A missing `libturfrt.a` at the
resolved install root is now a TurfLang diagnostic naming the exact path
checked, reported before `cc`/`gcc` is even invoked.

### Is this breaking?
No (R3/R5) — every one of these was previously either undefined/
undocumented behaviour (a bare `SIGSEGV`, an unverified-but-already-fail-fast
OOM path, a silently-possible ABI mismatch) or already a hard failure
(a missing runtime library). No program that compiled and ran correctly
before this group is affected; the observable change is strictly additive
(better diagnostics on paths that were previously silent or generic).

## Compiler architecture
- **Codegen** (`src/CodegenFunc.cpp`) — `WrapMainWithRuntimeBootstrap()`
  declares (or reuses) a `turf_rt_abi_2_0` prototype and calls it in the
  `main` wrapper's entry block, alongside `turf_rt_init()`. No other Codegen
  file touched.
- **Driver** (`src/main.cpp`) — `linkObject()` now checks
  `llvm::sys::fs::exists(<TurfInstallRoot()>/lib/libturfrt.a)` and returns a
  TurfLang-diagnostic failure (exit 1, no `cc`/`gcc` invocation attempted)
  before building the link command line, if the archive is missing.
- No Lexer/Parser/AST/Resolver/TypeChecker/CFG/diagnostics changes.

## Runtime changes
- New `runtime/turfrt_signal.c` — `turf_rt_install_segv_handler()`, a
  `sigaltstack`-backed `SIGSEGV` handler (POSIX only; a documented no-op on
  `_WIN32` — Windows is FUTURE per `ROADMAP_v2.0.0.md` DEC-2, and a Windows
  stack overflow is a Structured Exception, not `SIGSEGV`, a wholly
  different mechanism). Classifies a fault as a stack overflow by comparing
  the fault address against a window computed from `getrlimit(RLIMIT_STACK)`
  and the stack base `turfrt_gc.c` already records for conservative
  scanning; degrades to the generic message whenever it can't verify that
  (an unqueryable/unlimited `RLIMIT_STACK`, or a fault outside the window) —
  never a false positive misattributing a real memory-safety bug to
  recursion.
- New `runtime/turfrt_abi.c` — `turf_rt_abi_2_0(void)`, an intentionally
  empty function; its only purpose is to exist as a link-time contract (see
  *Language semantics* above).
- `runtime/turfrt_gc.c` — new `turf_gc_get_stack_base()` accessor (exposes
  the existing `g_stack_base` static to `turfrt_signal.c` without a second,
  independently-tracked copy).
- `runtime/turfrt_internal.h` — prototypes for both of the above.
- `runtime/turfrt.h` — `turf_rt_abi_2_0`'s public declaration.
- `runtime/turfrt_alloc.c` — `turf_rt_init()` now also calls
  `turf_rt_install_segv_handler()`, after `turf_gc_record_stack_base()`
  (ordering matters: the handler reads the stack base).
- `CMakeLists.txt` — `turfrt_abi.c`/`turfrt_signal.c` added to the `turfrt`
  static-library target's sources.
- `include/Intrinsics.h` — `turf_rt_abi_2_0` added to the closed,
  enumerated runtime-symbol list (F-STD-2).

## Standard-library changes
None. `mem::alloc`'s own OOM path (`lib/std/mem/mem.tr`, `sys::panic()`)
is untouched and remains independently implemented from the GC-heap OOM
path (F-MEM-3) — verified live: `git diff --stat -- lib/std` for this
branch is empty.

## New invariants
Added to `INVARIANTS.md`'s "## Runtime" section:
- **INV-RT-5** — a stack overflow is classified and reported as `panic:
  stack overflow`, distinct from a generic `SIGSEGV`, both terminating via
  `SIGABRT`/134, never a bare 139 crash. POSIX only; documented
  false-negative-leaning gap (never a false positive) for an unqueryable
  `RLIMIT_STACK` or an out-of-window fault address.
- **INV-RT-6** — every compiled binary references `libturfrt`'s versioned
  ABI stamp (`turf_rt_abi_2_0`); a runtime lacking it fails to link, never
  silently misbehaves at run time.
- **INV-RT-7** — a missing `libturfrt.a` is reported as a TurfLang
  diagnostic naming the exact path checked, before `cc`/`gcc` is ever
  invoked.

## Removed assumptions
- **"RT-001's fail-fast OOM policy, once code-reviewed, doesn't need its own
  test."** It already worked (verified by reading `turfrt_alloc.c` — every
  one of `turf_rt_alloc`/`turf_rt_alloc_zeroed`/`turf_rt_realloc` already
  panicked on a `NULL` return), but nothing had ever actually exercised the
  path — the Overhaul closure audit's own attempt (`strings::repeat()` in a
  loop) never reached it, since a quadratic string-doubling loop exhausts
  CPU time (or gets killed by an external limit) long before it exhausts
  address space on a modern 64-bit machine with overcommit. A single
  `gc_alloc(9223372036854775807)` call reaches the real failure
  immediately and deterministically — "test the policy against a direct
  large allocation," per this milestone's own stage 2 instruction, rather
  than trying to get there by attrition.
- **"A signal handler for a stack-exhaustion fault needs to be strictly
  POSIX async-signal-safe to be worth installing at all."** Rejected as the
  standard here: `turf_rt_panic()`/`fprintf` are not on the async-signal-safe
  list (only `abort()` itself is), but the alternative — a hand-rolled
  `write(2)`-only formatter with its own pointer-to-hex/integer-to-decimal
  code, duplicated from nothing — was judged not worth it for a path where
  the process is terminating either way. The one accepted, disclosed risk:
  a fault arriving while the crashing thread already held stdio's own
  internal lock could make the handler's own `fprintf`/`turf_rt_panic` call
  deadlock rather than print — the process still terminates in that case
  (via the OS's own subsequent handling, or simply hangs until an external
  timeout/signal), it just loses the diagnostic message on that specific
  interleaving. See *Known pitfalls* below.
- **"Referencing a new runtime function from Codegen is enough to make a
  link fail if the symbol is missing — no need to actually CALL it."**
  Checked, and it is NOT enough on its own for every linker/toolchain
  configuration: an unreferenced `Function::Create(..., ExternalLinkage,
  ...)` declaration with no actual `call` instruction anywhere in kept code
  can be dead-stripped before the linker ever needs to resolve it. The ABI
  stamp is therefore an actual `CreateCall`, not just a declaration, inside
  the `main` wrapper — which OPT-001's own Internalize must-preserve set
  (`{"main"}`) guarantees is never itself eliminated.

## Known pitfalls
- **The stack-overflow classification window is a heuristic, not an exact
  boundary — don't "tighten" it without re-testing across frame sizes.**
  `TURF_STACK_GUARD_WINDOW` (`runtime/turfrt_signal.c`, 256 KiB either side
  of the computed `RLIMIT_STACK` boundary) exists because a single stack
  frame that pushes far past the limit in one instruction (a large local
  array, aggressive inlining) can fault meaningfully beyond the exact
  computed address. Narrowing this window risks misclassifying a real
  overflow as a generic `SIGSEGV`; the direction that's safe to adjust
  without re-verification is widening it, not narrowing it.
- **An unqueryable or unlimited `RLIMIT_STACK` silently disables overflow
  classification, not silently claims every `SIGSEGV` is one.** Verify this
  before "fixing" it the other way: reporting every fault as "stack
  overflow" when there's no address to compare against would misdiagnose a
  real memory-safety bug at least as badly as the status quo ante (a bare
  crash) — the chosen degradation (always generic in that case) is
  deliberate, matching this project's own EscapePass/FDN-002 precedent
  ("never a false positive at the cost of a real, honest false-negative
  gap").
- **Calling `turf_rt_panic()`/`fprintf` from inside a signal handler is not
  strictly async-signal-safe — this is disclosed, not accidental.** See
  *Removed assumptions* above. Do not "fix" this by rewriting the handler
  around `write(2)` without checking whether the resulting formatter
  actually needs to reproduce `turf_rt_panic()`'s pointer/message
  formatting from scratch — that tradeoff was made deliberately once
  already.
- **The ABI stamp must be an actual call, not just a declared-but-unused
  external function.** See *Removed assumptions* above — a future session
  adding a second versioned symbol for some other purpose should confirm
  it is genuinely referenced from kept code (e.g. also called from the
  `main` wrapper, or from some other function OPT-001's Internalize pass
  cannot eliminate), not merely declared.
- **Bumping the ABI suffix (`_2_0` → `_2_1`) is a two-file, atomic change.**
  Both `runtime/turfrt_abi.c`'s definition and
  `WrapMainWithRuntimeBootstrap()`'s (`src/CodegenFunc.cpp`) reference must
  be renamed together — a mismatch between them defeats the entire
  mechanism (the compiler would reference a symbol its own bundled runtime
  doesn't define, which is a self-inflicted version of exactly the failure
  this stamp exists to catch in OTHERS).
- **The `libturfrt.a`-existence check only runs inside `linkObject()`,
  after a successful compile.** A `TURF_HOME` pointing at a tree with no
  `lib/std` at all fails much earlier (module resolution, before this check
  is ever reached) with a different, pre-existing error — this check is
  specifically for "compiled fine, but the runtime library itself is
  missing," not a general TURF_HOME-misconfiguration diagnostic.
