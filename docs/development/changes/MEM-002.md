## Why

Before this group, `docs/architecture/memory_model.md` stated it plainly:
*"there is no automatic memory management of any kind today."* MEM-001 routed
every language-owned allocation (`string` results, collection backing
buffers) through `turf_rt_alloc`, but nothing collected — both heaps still
leaked identically to before. This group is what actually reclaims that
memory: a non-moving, mark-sweep collector, precise on the GC heap via
compiler-emitted per-type/per-element pointer bitmaps, conservative on the
stack and callee-saved registers, stop-the-world, single-threaded, no
finalizers (`defer` is the answer — LANG-003 already landed).

It is the single highest-risk, least-reversible item in the whole
architecture-overhaul roadmap (`ARCHITECTURE_OVERHAUL.md` §14.10 says so
explicitly), and it found a real, reproducible heap-use-after-free during
its own development — see *Removed assumptions* below.

## Language semantics

### Old behaviour

```turf
import list::List;

fn main(): int {
    mut l: List<int> = List::default();
    l.push(1);
    l.push(2);
    return l.length();
}
```

Every `gc_alloc`/`gc_alloc_zeroed`/`gc_realloc` call (MEM-001) reached
`turf_rt_alloc`/`turf_rt_alloc_zeroed`/`turf_rt_realloc`, which were thin
`malloc`/`calloc`/`realloc` wrappers that recorded nothing. Every GC-heap
allocation, for the life of the process, leaked — identically to a program
with no collector at all.

### New behaviour

Same program, same output — this group is observably invisible to a program
that never runs long enough or allocates enough to notice. What changed:
every `turf_rt_alloc`/`turf_rt_alloc_zeroed`/`turf_rt_realloc` call now
registers its block with a real collector (`runtime/turfrt_gc.c`, new), and
`turf_rt_collect()` (explicit, or automatically on allocation pressure — a
heap-doubling heuristic) reclaims anything unreachable from the stack,
callee-saved registers, or a registered global root. Three new bare
intrinsics reach the collector directly from Turf source, the same
mechanism `gc_alloc` already used:

```turf
gc_collect();                 // force one mark-sweep cycle
mut managed: bool = gc_is_managed(p);   // true iff p is a live GC-heap block's own start address
```

And `mem::free()`'s signature/usage is unchanged, but its behaviour is not:

```turf
import mem;
import strings;

mut s: string = strings::repeat("x", 10);
mem::free(s to void*);   // used to be undiagnosed corruption risk; now panics
```

### Is this breaking?

Only in the one way MEM-002's own roadmap entry names explicitly: a program
that `mem::free()`s something it got from `strings::*` or a collection
(always undefined/corrupting behaviour before this group, since nothing
tracked which heap a pointer belonged to) now gets a diagnosable runtime
panic instead. Swept `tests/`, `lib/std/`, and `showcase/` for this pattern
— none exists. Every other observable behaviour is unchanged: full suite
green (744/744, 738 baseline + 6 new), `lib/std/**` and `showcase/**` both
swept directly with no regressions, and `showcase/http_server.tr` + `curl`,
`showcase/kv_store_server.tr` + `showcase/kv_store_client.tr`, and the three
directly-runnable showcase programs were all smoke-tested live end to end
under the new collector with correct output.

## Compiler architecture

- **Builtins** (`src/Builtins.cpp`) — `gc_collect`/`gc_is_managed`/
  `gc_checked_free` registered in `g_builtins` (arity 0, 1, 1), alongside
  MEM-001's `gc_alloc` family.
- **Resolver** (`src/ResolverCall.cpp`) — the three new names added to the
  `BareIntrinsics` set, identical mechanism to `gc_alloc`.
- **TypeChecker** (`src/TypeCheckerCall.cpp`) — `gc_collect()`→`void`,
  `gc_is_managed(p)`→`bool`, `gc_checked_free(p)`→`void`. Same
  minimal-validation convention as `gc_alloc`'s own branch.
- **Codegen**:
  - `src/CodegenCore.cpp`'s `getExprType()` gets a `bool` case for
    `gc_is_managed` (same reason `gc_alloc`'s own `void*` case exists —
    these are bare intrinsics with no `ResolvedCallTarget`/`FuncReturnTypes`
    entry).
  - `src/CodegenFunc.cpp`'s `FuncCallExprAST::codegen()` dispatches all
    three new intrinsics (declares/calls the matching `turf_rt_*` LLVM
    prototype, mirroring `gc_alloc`'s own pattern exactly), and the
    existing `gc_alloc`/`gc_alloc_zeroed`/`gc_realloc` branch now passes
    `PendingGCAllocDescOverride` instead of a literal null pointer when one
    is set.
  - `src/CodegenExpr.cpp`'s `CastExprAST::codegen()` — the one genuinely new
    piece of Codegen logic. Recognizes a `gc_alloc(...)`/
    `gc_alloc_zeroed(...)`/`gc_realloc(...)` operand being cast `to T*`
    (every collection-growth call site in list/stack/queue/set/map.tr is
    written exactly this way) and, BEFORE generating the inner call, sets
    `PendingGCAllocDescOverride` to a real per-element `TurfTypeDesc` for
    the concrete `T` — determined from the cast's own destination type,
    which is concrete because this call site is always inside a
    monomorphized clone (TYPE-002).
  - `src/CodegenStruct.cpp` — `getOrCreateElementTurfTypeDesc(ElemTy)`
    (new), sharing RT-001's existing `collectPointerWordBits()`/
    `getOrCreateTurfTypeDescType()` helpers to build a descriptor for ONE
    element of an arbitrary LLVM type (not just a whole struct instance),
    memoized by raw `llvm::Type*` identity.
  - `src/CodegenInternal.h` — declares `getOrCreateElementTurfTypeDesc()`
    and the file-scope `PendingGCAllocDescOverride` hand-off (a `Value*`,
    the same "can't change a virtual `codegen()` signature for one caller"
    pattern `SetDebugLoc()`'s `CurrentDebugScope` already uses), reset to
    `nullptr` at the top of `InitializeModule()`.
- **No Lexer/Parser/AST/CFG changes.** Every new intrinsic is dispatched
  exactly like `typeof`/`gc_alloc` — an existing bare-call-expression shape,
  not new grammar. No Codegen change for global-root registration (see
  *Removed assumptions* below for why).

## Runtime changes

All of it, per §14.4–§14.8. `runtime/turfrt_gc.c` (new):

- **Block table.** `GcBlock {start, size, desc, marked}`. Two arrays: an
  unsorted, append-only `g_pending` (O(1) amortized insert — the hot path
  every `turf_rt_alloc` call takes) merged into a sorted-by-`start`
  `g_blocks` exactly once per collection (`gc_rebuild_index`). A
  block-CONTAINING-address query (`gc_find_containing`, binary search) only
  ever runs during a collection, against the just-rebuilt sorted array.
- **Root discovery**, exactly matching §14.6:
  1. Callee-saved registers (x86-64 System V: `rbx`/`rbp`/`r12`–`r15`) —
     spilled via **inline assembly**, not `setjmp()`. Verified against
     glibc's own `jmp_buf` implementation before choosing this: glibc
     XOR-obfuscates saved pointer values with a per-process secret
     (`PTR_MANGLE`) since glibc 2.4, which would make every register's
     saved bit pattern fail to resemble a real heap address — Boehm GC's
     own `GC_push_regs` avoids the identical trap the same way, on the
     same platform, for the same reason.
  2. The stack range `[current SP, stack base)`, scanned conservatively,
     word by word.
  3. Registered global roots (`turf_rt_add_global_root`), dereferenced
     precisely.
  4. A worklist (explicit array, not recursion — a long linked structure
     must not blow the C stack) traces each newly-marked block's own
     declared pointer words precisely, via its `TurfTypeDesc`.
- **Allocation-pressure heuristic.** Heap-doubling: collect once cumulative
  bytes requested since the last collection cross a threshold (1 MiB floor),
  then set the next threshold to `2 × post-sweep live bytes`.
- **`TurfTypeDesc` reuse for arrays**, not a new C field (`turfrt.h`'s own
  doc comment has the full reasoning): the mark phase repeats a descriptor's
  `pointer_word_bitmap` across a block's REAL allocated length in
  `size`-byte strides. A single-instance struct allocation is the
  degenerate case where the block's length exactly equals `size` — one
  stride, no code-path difference needed.
- **`TurfRtStats` extended** with `collect_count`/`live_count`/
  `live_bytes`/`freed_count` (point-in-time as of the most recent
  collection, not cumulative) — exactly the "before/after a collection"
  comparison MEM-001's own doc comment on this struct predicted this hook
  would need.
- **New public API** (`runtime/turfrt.h`): `turf_rt_collect()`,
  `turf_rt_add_global_root`/`turf_rt_remove_global_root`,
  `turf_rt_is_gc_pointer`, `turf_rt_checked_free`.
- **`turf_rt_init()`** now calls `turf_gc_record_stack_base()` — see
  *Removed assumptions* for why this is NOT simply "the address of a local
  variable inside `turf_rt_init()`'s own frame" (the obvious, and wrong,
  first implementation).

## Standard-library changes

`lib/std/mem/mem.tr`'s plain `extern fn free(p: void*): void;` is gone.
Turf's `extern fn` binds a declared name directly to an identically-named C
symbol with no alias syntax (verified against `ExternFuncDeclExprAST`,
`include/ASTDecl.h` — exactly one `Name_` field, used for both), so a
checked wrapper could not itself be named `free` in the same file without
colliding with that extern declaration (the same class of conflict
`tests/21_extern_conflict/` exists to catch). Fixed by moving the actual
libc `free()` call into `libturfrt` itself
(`turf_rt_checked_free`/`gc_checked_free`, above) and giving `mem.tr` a
genuine, ordinary `fn free(p: void*): void { gc_checked_free(p); }` —
`mem::free(p)`'s public name and signature are unchanged for every existing
caller (`free_pool()`'s own two internal call sites now go through this
same checked path too, for free). `alloc_aligned()`'s scratch-buffer free
(never anything but its own `malloc(8)`) also now goes through
`gc_checked_free` for the same reason — one fewer raw-`free`-shaped call
site to keep track of, at the cost of one always-false `gc_is_managed`
lookup on a hot-ish path that isn't actually hot (called once per
`alloc_aligned()` invocation).

## New invariants

**INV-MEM-1** (`INVARIANTS.md`) — `mem::free()` never silently corrupts
state when handed a GC-heap pointer; it panics with a named diagnostic
instead (`gc_checked_free`/`turf_rt_checked_free` checking every pointer
against the block table before delegating to libc `free()`). Deliberately
narrower than "the collector always reclaims everything unreachable" or "no
root is ever missed" — those are real properties this group's tests give
strong empirical evidence for, but neither has a single, nameable
enforcement MECHANISM the way `INVARIANTS.md`'s own bar requires (they are
emergent properties of the whole mark-sweep design, not a single assertion
or checked call site) — a future session with a precise, testable framing
for either is welcome to add it, but this record does not manufacture one
just to have more rows.

## Removed assumptions

- **"The address of a local variable inside `turf_rt_init()`'s own frame is
  a safe upper bound for conservative stack scanning."** This was the
  FIRST implementation, and it is wrong: `turf_rt_init()` is a real function
  call that RETURNS before the user's actual `main()` body starts running
  (`WrapMainWithRuntimeBootstrap()` calls it, gets the return, THEN calls
  the renamed user `main` — a SIBLING call at the wrapper's own depth, not
  a nested one). Once `turf_rt_init()` returns, its frame is popped, and the
  subsequent call to user `main()` reuses that exact address range (or
  deeper) for ITS OWN frame — meaning a local captured inside
  `turf_rt_init()` is not guaranteed to sit above every frame the program
  will ever push. **Found live**, via a genuine heap-use-after-free, on
  `tests/13_string_stdlib/17_stress_10k_concat.tr` (confirmed with an
  AddressSanitizer rebuild of `libturfrt`: `strcpy.part.0` reading a
  1447-byte string region that `gc_sweep` had already `free()`d one
  allocation earlier — a real, silent stack-scan gap, not a theoretical
  one). Fixed by reading `/proc/self/maps`'s `[stack]` region instead — a
  value fixed at thread-creation time, independent of call depth. A future
  session must NOT revert to the local-variable-capture idiom for this
  specific value, even though it is the more obvious "no Codegen changes
  needed" technique and is exactly what this file's own top comment
  correctly still uses for the CURRENT-SP half of scanning (captured fresh
  on every collection, so it has no stale-capture hazard — only the
  ONE-TIME `stack_base` capture did).
- **"A pointer held only in C-heap (`malloc`'d) memory is found by
  conservative scanning the same way a stack-held one is."** False, and
  deliberately so (F-MEM-3/§14.3's own documented "a GC pointer stored only
  in manual memory is not a root" unsoundness) — verified live while
  measuring this group's own pause-time benchmark: an early version stored
  a "live set" tracking array via `malloc()` instead of on the C stack, and
  every one of the 20,000 blocks it referenced was (correctly, per the
  frozen design) swept as unreachable, even though nothing else in the
  program had touched them. A future session writing a test or benchmark
  against `libturfrt` directly must keep the "live set" it wants retained
  on the STACK (or reachable via a registered global root) — a plain C
  heap array of pointers is not a root, exactly like `mem::alloc`'d memory
  holding a GC pointer isn't in a real Turf program.
- **"`MEM-001`'s always-NULL `desc` argument is a permanent, structural fact
  about `gc_alloc`'s call sites, not a placeholder."** MEM-001's own change
  record said exactly this ("never, structurally, not just contingently") —
  correct as of that group, wrong now: `CastExprAST::codegen()`'s new
  special case means every `gc_alloc(...) to T*`/`gc_realloc(...) to T*`
  site (every collection's growth call) now passes a real, per-instantiation
  element descriptor. Only `strings.tr`/`io.tr`/`net.tr`'s raw-byte-buffer
  sites (`to string`, never `to T*`) still pass NULL — which this group
  DEFINES as "opaque, no pointer words traced," a decision, not a leftover
  gap (see `turf_rt_alloc`'s own updated doc comment in `runtime/turfrt.h`).
- **"TurfLang's memory model has no automatic memory management."**
  `docs/architecture/memory_model.md`'s own one-sentence summary, verbatim,
  before this group — now false, and the document is rewritten accordingly
  (see *Handbook impact*).

## Performance

MEM-002's own completion criterion requires "a documented, measured
pause-time and throughput number" — measured directly against
`lib/libturfrt.a` (no Turf compiler involved), `-O2`, this machine, three
runs each:

- **Throughput**: 2,000,000 sequential `turf_rt_alloc(32, NULL)` calls
  (immediately discarded, no live set retained) completed in 328–370 ms
  across three runs — **5.4–6.1 million allocations/second**, with 61
  collections triggered along the way (the 1 MiB-floor heap-doubling
  heuristic against a near-empty live set after each sweep).
- **Pause time**: one explicit `turf_rt_collect()` call over a genuinely
  live working set of 20,000 blocks (held on the C stack, each written to
  and read back to defeat `-O2` dead-store elimination — see *Removed
  assumptions*), with ~220,000 additional already-dead blocks from
  intervening churn also present in the block table at collection time,
  took **7.2–10.1 ms** across three runs (rebuild-index sort + conservative
  root scan + precise worklist trace + sweep, all included).

**What these numbers do and do not claim.** They establish that the design
is not pathologically slow for a block table on the order of 10^5–10^6
entries — nothing more. No comparison against another language's collector,
no claim about behavior at 10^7+ live objects (this group's own sorted-array
block table is `O(n log n)` per collection in the number of live blocks,
via `qsort` at `gc_rebuild_index` — see *Known pitfalls* for why this was a
deliberate simplicity-over-throughput choice, not an oversight), and no
claim about pause time under a workload this group's own test suite doesn't
exercise (a large fraction of the live set being interior-pointer-reachable
rather than start-address-reachable would cost more per pointer checked,
for instance). Reproduce with the benchmark described above — it is not
checked into the repo as a script (unlike `gc_rss_smoke.sh`), since it
measures a machine-dependent absolute number rather than a bounded
pass/fail property; a future session wanting to track this over time should
decide deliberately whether to promote it into one.

## Known pitfalls

- **Conservative scanning means a stale copy of a dead pointer left behind
  on the stack (in memory the current call depth never overwrote) is a
  real, accepted false-positive source, not a bug.** Every regression test
  this group adds that wants to prove something is genuinely reclaimed
  (`scripts/gc_smoke.sh`'s check 1, and to a lesser extent check 2)
  deliberately churns the stack with several levels of recursive calls
  writing real data into a local buffer BEFORE asserting a low live count —
  without that churn, a test could pass "by accident" (stale garbage that
  happens to still be a valid address) without the collector actually
  doing anything. A future session writing a similar test that skips the
  churn step will get a flaky-in-the-wrong-direction test: one that looks
  green but proves nothing.
- **The block table is a sorted array, rebuilt with `qsort` once per
  collection (`O(n log n)` in the live-block count), not a tree or hash
  table.** A deliberate simplicity choice, not an oversight: allocation
  itself stays `O(1)` amortized (append-only `g_pending`, merged in only at
  the next collection), and `O(n log n)` per collection is what this
  group's own performance numbers above were measured against — fine at
  the 10^5–10^6-live-block scale this repository's tests exercise, not
  necessarily fine far beyond it. A future session hitting real collection
  pause times at a much larger live-set size should look here first, not
  assume the bottleneck is elsewhere.
- **A pointer to a GC-heap block, if it exists ONLY inside manually-managed
  (`malloc`'d) memory, is not a root — by design, not oversight.** See
  *Removed assumptions* above for how this was rediscovered live while
  writing this group's own pause-time benchmark. `mem::root()`/
  `mem::unroot()` (§14.3's own named escape hatch for this exact case) is
  NOT built by this group — nothing in MEM-002's roadmap entry or
  completion criteria calls for it, and no test/showcase/stdlib code in
  this repository currently needs it (every GC pointer that needs to
  survive is always reachable from the stack, a register, or — someday — a
  registered global root). A future session adding closures, or any other
  feature that stores a GC pointer inside a manually-allocated structure
  long-term, will need to design and add this API, not assume it already
  exists.
- **`turf_rt_add_global_root`/`turf_rt_remove_global_root` have no Codegen
  call site, and that is deliberate, not an oversight to "finish."**
  Verified live: TurfLang has no mutable global/static storage of any kind
  today (`export immut` constants are inlined literal values with no
  storage — already documented in `memory_model.md` before this group; a
  repo-wide grep for `new llvm::GlobalVariable`/`new GlobalVariable` in
  `src/*.cpp` turns up only RT-001's constant `TurfTypeDesc` globals and
  the compiler's own `argv`/`argc` plumbing, neither of which is a
  Turf-level mutable pointer slot). The API is genuine, tested runtime
  surface (`scripts/gc_smoke.sh` check 2) built now specifically so a
  FUTURE feature that adds real global storage (closures' captured
  environments is the one named in the roadmap, §22 D1) needs no second
  runtime change to plug into it — but a future session should not go
  looking for a missing Codegen hook here; there is nothing to call it
  from yet.
- **The register-scanning path (`gc_capture_callee_saved`, `turfrt_gc.c`)
  is x86-64 System V ONLY**, gated with a hard `#error` on any other
  target. `ARCHITECTURE_OVERHAUL.md` §14 itself calls the register-spill
  technique "platform-specific." Porting to another architecture means
  writing that architecture's own equivalent inline-asm register-capture
  (its own callee-saved register set, per its own ABI) — not a
  configuration flag, a real per-platform implementation.
- **`gc_rss_smoke.sh`'s 20MB bound is generous on purpose, not tuned
  tight.** Measured peak RSS at landing time was 2,688 KB — the bound has
  roughly 7× headroom above that measurement specifically so ordinary
  platform/allocator/loader variance (a different libc, a different page
  size, ASLR-related mapping overhead) doesn't make this script flaky in
  CI, while staying far enough below the ~80MB an actual regression (the
  collector silently no longer collecting) would produce that the signal
  stays meaningful. A future session should not "tighten" this bound
  toward the measured figure without first confirming it's stable across
  more than one machine.
- **This landed in one session against a three-session (S20–S22) roadmap
  estimate.** See *Unresolved questions* below for what that compresses,
  honestly, rather than silently.

## Unresolved questions

**This group landed in one session against the roadmap's own three-session
(S20–S22) estimate for MEM-002's Complexity: XL rating — stated honestly,
not silently compressed.** What actually happened: the core design (block
table, conservative root scanning via inline-asm register capture rather
than `setjmp`, precise per-element tracing via a reused `TurfTypeDesc`, the
allocation-pressure heuristic) came together as one coherent piece of work,
and a real bug (the stack-base capture ordering hazard) was found and fixed
live via an ASan repro during the SAME session rather than surfacing later.
Two things a future session should treat as genuinely open, not merely
"could be nice later":

1. **Real-world exercise is still narrow.** This group's own test suite
   (five `tests/41_gc/` files, two smoke scripts, one stress test) and the
   `showcase/` sweep (config_and_dice, text_toolkit, the LLVM FFI demo, and
   a live http_server/kv_store client-server pair) are the full extent of
   what has actually run under this collector. Nothing resembling a
   long-running server process, a program with a genuinely large/complex
   object graph (deep linked structures, many interacting collections), or
   sustained multi-hour operation has been tried. §14.10's own "honest
   alternative" framing (stopping after MEM-001 + `defer` + an arena type)
   was written with exactly this kind of risk in mind — this group's
   choice to proceed past that point rests on the test coverage above, not
   on a broader empirical track record.
2. **The register-scanning technique (inline asm, not `setjmp`) has not
   been cross-validated against an independent conservative-GC
   implementation on this exact toolchain/kernel combination.** It is
   modeled directly on Boehm GC's own documented technique and reasoning
   (see *Runtime changes* above), and this group's own tests pass, but
   "modeled on a technique known to be correct elsewhere" is not the same
   claim as "independently verified correct here" for a mechanism this
   subtle. A future session with more time/scrutiny budget specifically
   for this piece — not a general re-review of the whole group — would be
   time well spent before this collector is exercised under load nobody
   related to this project's own test suite has generated yet.

If a future reader is deciding whether to trust this collector for
something higher-stakes than this repository's own test suite currently
exercises, these two points are the honest place to start, not this
record's own "landed" status line.
