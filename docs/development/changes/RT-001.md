## Why

TurfLang had no runtime at all before this group (`docs/architecture/memory_model.md`
§1.7: "no automatic memory management of any kind"). Every panic was an
inline `fprintf`+`abort()` built per call site directly in Codegen;
allocation was libc `malloc` reached through an ordinary `extern fn`; the
linker line was `cc obj -o out -lm`. The entire memory track (MEM-001,
MEM-002) needs a real, process-wide place for the heap, the collector, and
consistent panic/OOM behaviour to live (Rule B2) — and precise heap tracing
specifically needs a per-type pointer bitmap, which needs a real,
per-instantiation struct layout to compute from, which is exactly what
TYPE-002 just delivered. This group is the scaffolding: a real C library,
linked into every compiled binary, with the two pieces that don't need a
heap yet (panic, a thin allocator wrapper) built for real, and the
type-descriptor infrastructure the collector will need built now, while
TYPE-002's layouts are fresh.

## Language semantics

### Old behaviour

No language-level change of any kind. A compiled program's observable
behaviour (stdout, exit code, timing characteristics) is unaffected by this
group — verified live via `scripts/opt_levels_smoke.sh` (unchanged, still
byte-identical across `-O0`..`-O3`/`-Os`) and the full 736-test suite
(unchanged pass count, before and after).

### New behaviour

The only user-visible difference is a panic's exact printed message: what
used to be a bare `<message>\n` (e.g. `Division by zero`) is now
`panic: runtime check: <message> (<file>:<line>)\n` — the same `abort()`
(SIGABRT, exit 134) either way. No test asserted the old exact wording (all
of them, correctly, only check exit code / "aborted"), so this is not a
breaking change to anything in the test suite, but it IS a real, visible
change to what a user watching stderr sees.

A TurfLang installation now ships a library, not just a binary —
`build/turf` alone is no longer sufficient; `<install-root>/lib/libturfrt.a`
must exist alongside it (see *Removed assumptions*).

### Is this breaking?

No, for compiled Turf programs (identical behaviour, byte-identical output
at every optimization level). Marginally yes, for anything that greps a
panic's exact stderr text, and for any out-of-tree tooling that copies just
`build/turf` around without the sibling `lib/` directory (was already true
for `lib/std/`; now also true for `lib/libturfrt.a`).

## Compiler architecture

- **Codegen** — `CodegenPanic()` (`src/Builtins.cpp`) rewritten to call
  `turf_rt_panic()` instead of building `fprintf`+`abort()` IR inline; new
  `WrapMainWithRuntimeBootstrap()` (`src/CodegenFunc.cpp`) and
  `EmitAllTurfTypeDescs()`/`emitTurfTypeDesc()`/`collectPointerWordBits()`
  (`src/CodegenStruct.cpp`).
- **Driver** (`src/main.cpp`) — `linkObject()` now passes
  `-L<TurfInstallRoot()>/lib -lturfrt` ahead of every other link flag;
  `runCompilerMain()` calls `WrapMainWithRuntimeBootstrap()` right after the
  entry-point check, and `EmitAllTurfTypeDescs()` right before
  `verifyModule()`.
- **Parser** (`src/ParserModule.cpp`, `include/Parser.h`) — `TurfInstallRoot()`
  exported (was file-local) so the driver can anchor `-lturfrt`'s search
  path at the same root `import` already resolves `lib/std` against,
  without a second, independently-maintained copy of the `TURF_HOME`/
  fallback logic.
- No Lexer/AST/Resolver/TypeChecker/CFG/diagnostics changes.

## Runtime changes

Everything in this group. New `runtime/` directory:
`runtime/turfrt.h` (the complete public API — `turf_rt_init`,
`turf_rt_shutdown`, `turf_rt_alloc`, `turf_rt_panic`,
`turf_rt_typedesc_is_pointer_word`, and the `TurfTypeDesc` struct),
`runtime/turfrt_alloc.c` (bootstrap no-ops + the fail-fast `malloc`
wrapper), `runtime/turfrt_panic.c` (the panic formatter), `runtime/turfrt_types.c`
(the one descriptor accessor). Built as a new CMake static-library target,
`turfrt`, with no dependency on `turfcore`/LLVM — not linked into the `turf`
compiler binary itself, only into compiled Turf programs. See
`docs/architecture/runtime.md` for the full design writeup (why static not
shared, why the build output lands in `lib/`, the exact `main`-wrapping
mechanism, and §4's full account of a real crash this group found and fixed
in its own type-descriptor emission).

## Standard-library changes

None. `lib/std/mem/mem.tr`'s `malloc`/`free`/`mem::alloc`/etc. bindings are
byte-for-byte unchanged — the manual heap stays manual (F-MEM-3); nothing
in `lib/std` calls `turf_rt_alloc` (that is MEM-001's job). Verified live:
`git diff --stat -- lib/std` for this branch is empty.

## New invariants

Added to `INVARIANTS.md`, new "## Runtime" section:
- **INV-RT-1** — every compiled binary links `libturfrt`; `turf_rt_init`/
  `turf_rt_shutdown` run around every path through `main`.
- **INV-RT-2** — every one of the compiler's own inline safety-check panics
  goes through `turf_rt_panic()`, never an ad-hoc sequence.
- **INV-RT-3** — a `TurfTypeDesc` is only ever built from a struct whose
  `setBody()` has already run (an ordering guarantee, not an assertion —
  see *Removed assumptions* below for the crash that made this necessary).

## Removed assumptions

- **"A struct's own `DataLayout` size/layout can be queried the moment its
  `setBody()` runs, during `StructDeclExprAST::codegen()` itself."** This
  was the first implementation of type-descriptor emission (inline, per
  struct, right after `ST->setBody(...)`), and it is FALSE in general once a
  struct can embed a monomorphized generic instantiation by value
  (`struct Holder { items: List<int> }`). `main.cpp`'s struct pre-pass
  codegens structs in `PrePassASTs` order, and a monomorphized clone
  (`List_gen1_int`) is *appended* to that list — so `Holder`, declared
  earlier in the source, codegens BEFORE `List<int>`'s own clone gives it a
  real body. Querying `Holder`'s own `DataLayout::getTypeAllocSize()` at
  that point forces LLVM to also compute — and **permanently cache, keyed
  by `StructType*`, with no invalidation hook** — a zero-element
  `StructLayout` for the still-opaque `List<int>` field. When `List<int>`'s
  own clone is codegenned moments later and given its real fields,
  `DataLayout::getStructLayout()` on that exact `StructType*` returns the
  SAME stale, zero-element cached object — `StructLayout::getElementOffset(0)`
  then asserts. Confirmed live: crashed exactly this way on
  `tests/38_monomorphization/04_method_on_generic_struct.tr`,
  `06_generic_struct_over_8_bytes.tr`, `15_generic_struct_field_only.tr`,
  `16_nested_generic_struct_field.tr`, `21_nested_generic_struct_same_t.tr` —
  every test in that folder that embeds a generic instantiation by value.
  Fixed by making descriptor emission a single, separate pass
  (`EmitAllTurfTypeDescs()`) run once, from `main.cpp`, after EVERY struct
  in the module is guaranteed fully built (see `docs/architecture/runtime.md`
  §4.1 for the complete mechanism). A future session adding ANY new
  per-struct codegen-time logic that queries `DataLayout` should read this
  entry first — the same hazard is fully general, not specific to type
  descriptors.
- **"`turf --resolve <file>` failing with `E034` (`A struct named 'X' is
  already declared`) on `lib/std/collections/list.tr` and
  `lib/std/mem/mem.tr` is something this group broke."** It is not —
  confirmed live via `git stash` against the pre-RT-001 commit (`90cb8c2`):
  both files fail identically, byte-for-byte, without any of this group's
  changes applied. Neither file is one of the six prelude modules
  AGENTS.md's direct-compile check covers (`int`/`double`/`bool`/`char`/
  `strings`/`array`, all under `lib/std/core/`); this is a separate,
  pre-existing, unrelated quirk of compiling those two specific files
  directly as an entry point, out of this group's scope to fix.
- **"`turf --resolve` alone is enough to sanity-check a library module with
  no `main()`."** It is not, and was never claimed to be by AGENTS.md
  either — `--resolve` still runs the FULL pipeline through the
  entry-point check; every non-prelude `lib/std/**` file legitimately ends
  in "Error: No entry point found" (expected — they're libraries, not
  programs). The signal worth watching for is reaching THAT message
  cleanly, not avoiding it.
- **A pre-existing, unrelated `_module.tr` naming-sweep finding, surfaced
  by AGENTS.md's own sweep procedure while adding this group's new test
  file**: `tests/07_functions_modules/export_qualified_cross_module.tr`
  ends in the literal substring `_module.tr` (`..._cross_module.tr`) and is
  therefore silently excluded by `scripts/test_runner.sh`'s `grep -v
  "_module.tr"` filter today, even though it declares `fn main()` and is a
  genuine standalone test. Confirmed live: `git log` shows it was added in
  an earlier, unrelated commit (`847128c`, the `export`/`Map<K,V>` group),
  and `test_runner.sh`'s own output never mentions it. Not fixed here —
  renaming it or narrowing the filter is a change to the test runner or an
  unrelated test file, out of RT-001's scope (§25's "don't drive-by-fix a
  neighbouring problem" applies exactly as much to the test infrastructure
  as to the compiler). Recorded here so it isn't independently
  "discovered" again as if it were new.

## Known pitfalls

- **Do not move type-descriptor emission back to being inline in
  `StructDeclExprAST::codegen()`.** It looks like the natural place (right
  after `setBody()`), and it crashes — see *Removed assumptions* above for
  the exact mechanism. If a future session needs per-struct information at
  declaration time for some OTHER reason, that information must not include
  anything that makes LLVM compute (and therefore permanently cache) a
  `DataLayout`-derived size/layout for the struct being declared, unless
  every field type it might embed by value is already guaranteed non-opaque
  — which is not true in general during the struct pre-pass.
- **`WrapMainWithRuntimeBootstrap()` must run before
  `runOptimizationPipeline()`, not after.** OPT-001's `Internalize` pass
  treats `{"main"}` as its entire must-preserve set. If the wrapper ran
  after optimization, the ORIGINAL user-body function (still literally
  named `"main"` at that point) would be the one preserved, and the
  freshly-created wrapper function would itself be an ordinary, unreferenced
  internal symbol — `GlobalDCE` would delete it, and the binary would never
  call `turf_rt_init`/`turf_rt_shutdown` at all. This was caught in design,
  not live, but is exactly the kind of one-line-reorder mistake a later
  refactor could reintroduce silently (nothing crashes — the binary still
  links and runs, just without the bootstrap calls).
- **A `TurfTypeDesc`'s `pointer_word_bitmap` is a SOUND OVER-approximation,
  not a precise one, and this is easy to misread as a bug later.** It marks
  every pointer-SHAPED word (any `T*`/`&T`/`&?T`/`string`/embedded-struct-
  containing-a-pointer field), not only words proven to point into the GC
  heap specifically — nothing before MEM-001/MEM-002 tags a pointer field
  with which heap it points into, so there is no way to be more precise yet.
  MEM-002's collector must treat this as "may be a pointer, verify against
  the block table before trusting it," never as "is definitely a live GC
  reference."
- **`pointer_word_bitmap` only covers the first 64 words (512 bytes) of a
  type's layout.** A struct at or beyond that size silently loses bits 64+
  with no diagnostic. No struct in `tests/`, `lib/std/`, or `showcase/`
  approaches this size today, but a future session adding one (or MEM-002
  itself, if it ever needs to trace something larger) must widen
  `TurfTypeDesc` first, not assume the field is already general.
- **The `List<T*>` >8-byte workaround documented in
  `docs/reference/stdlib/collections.md` is unaffected by this group** —
  it was already obsolete-but-harmless after TYPE-002; RT-001 neither
  needed nor made any stdlib change here. Don't conflate "this group
  touched struct layout code" with "this group changed what stdlib code
  needs to look like."
