## Why
`&T`/`&?T` are the language's safe references, but nothing stopped `return
&local;`, storing `&local` into a struct that outlives this frame, pushing it
into a collection, or boxing it with `heap()` — each silently produces a
dangling pointer once the frame pops. Confirmed live (the audit's F-16):

```turf
fn make(): &Node {
    mut n: Node = Node::default();
    return &n; // compiled before this change; n's storage is gone on return
}
```

D23 (`ROADMAP_v2.0.0.md` §27) is the same hazard for an unsized `T[]`
parameter converted to `ptr` and returned — the cast discards the type
system's only memory of where the pointer aliases.

## Language semantics
### Old behaviour
`return &local;`, `param.field = &local;` (param/heap-owned), pushing a local
reference into a `List`/`Map`/`Set`/`Stack`/`Queue`, and `heap(&local)`
compiled without complaint and produced a reference whose target no longer
exists by the time anything reads it.

### New behaviour
Each of those is now a compile-time `DanglingReferenceEscapeError` (E086).
Returning `&param.field` (a reference reached through an already-reference-
typed parameter, including `self`) and returning `heap(local)` (a fresh
GC-heap copy) both continue to compile — the pass never flags a `Param`- or
`Heap`-provenance value, only `Stack`.

### Is this breaking?
Yes (R1) — a program that previously compiled into a dangling reference now
fails to compile. Every such program was already producing a wrong answer or
undefined behaviour, so there is no correct program this rejects; the
"migration" is fixing the underlying bug (usually: `heap()` the value before
returning/storing it, or return a parameter's own reference instead of a
local's).

## Compiler architecture
- **CFG/analysis**: new `EscapePass` (include/Analysis.h, src/Analysis.cpp),
  run immediately after `NullabilityPass` in `FuncDefExprAST::codegen()`
  (src/CodegenFunc.cpp). Forward, intraprocedural dataflow over the existing
  CFG, one instance per function, tracking a `Stack`/`Param`/`Heap`
  provenance for every reference-typed (`&T`/`&?T`/raw pointer incl. `self`)
  or unsized-array (`T[]`) parameter/local. Absence from the per-block map is
  the permissive fourth state, `Unknown` — never flagged.
- **Diagnostics**: new `DanglingReferenceEscapeError` (E086,
  `MEMORY_ERROR` category — the same category `UseAfterFreeError`/
  `PossibleNullDereferenceError` already use, per F-DIAG-3's "ordinary
  category, no new SLM category" rule).

## New invariants
**INV-MEM-3** (`docs/development/INVARIANTS.md`): a reference-typed value
whose provenance this pass can PROVE points into the current function's own
stack frame can never reach a `return`, a field of a `Param`/`Heap`-owned
object, a `List`/`Map`/`Set`/`Stack`/`Queue` mutator argument, a real
`operator[]=` dispatch, or `heap()`'s own operand. Enforced by `EscapePass`
(`EscapePass::runOnCFG`, `src/Analysis.cpp`). Residual gap, by design:
anything the pass cannot classify (a field read two levels deep through a
handle, a value returned from another call, a struct copied by value whose
OWN fields hold a dangling reference) is `Unknown` and is silently allowed —
this pass is intraprocedural and flow-local only, never a false positive at
the cost of a real, documented false-negative gap. No lifetime annotations,
no borrow checker, no interprocedural summaries (Overhaul §0.6, and this
milestone's own Non-goals).

## Removed assumptions
- A program that compiles no longer implies its references are all valid —
  before this pass, "does this compile" and "is this memory-safe" were the
  same question only for the cases OVH-001..003/FDN-001 already covered
  (heap objects, array bounds, nullability). A local's address escaping the
  frame was compilable and simply wrong. That gap is now closed for the
  syntactic shapes above; it is **not** closed for a reference smuggled out
  inside a by-value struct copy, or through an intermediate function call —
  see INV-MEM-3's residual gap.
- `heap(expr)`'s own operand was documented (FDN-001) as "FDN-002's rule
  applies to the operand" but unenforced until now — a caller boxing an
  already-locally-dangling reference (`heap(&local)`, `local` itself being a
  reference type, not a struct) is now rejected at the `heap()` call, not
  silently accepted.

## Known pitfalls
- **A new expression kind defaults to `Unknown`, not a crash — verify that's
  intentional, don't "fix" it into a false positive.** `classifyProvenance()`
  and `classifyAddressOfProvenance()` (src/Analysis.cpp) `dynamic_cast`
  through a fixed list of node kinds and fall through to `std::nullopt`
  (Unknown) for anything else. Adding a new reference-producing expression
  form later (e.g. a ternary, a closure capture) needs an explicit case here
  or it is silently permissive for that shape — which is correct *only* if
  nobody has proven it dangerous yet. Grep for `classifyProvenance` before
  trusting this pass covers a new construct.
- **A new collection method needs adding to the sink list by hand.** The
  collection-mutator sink is a fixed name+module allowlist
  (`isCollectionMutatorCall()`), not a general "any struct method" rule —
  deliberately, to avoid flagging an unrelated user method that happens to
  be named `push`/`set`. A sixth stdlib collection, or a new mutator on an
  existing one, needs its own entry or this pass silently won't check it.
- **Field/array-access chains longer than one hop are not tracked.**
  `p.next.field = &local` is not caught (`p.next`'s own provenance is
  `Unknown`, not derived from `p`'s) — only the immediate base of a field
  assignment is classified. This is the INV-MEM-3 residual, not a bug to
  "fix" by adding deep struct-field taint tracking (that's explicitly a
  Non-goal here; it would need per-field provenance, which is
  interprocedural-adjacent).
- **A future mutable global variable feature must add its own sink.** The
  roadmap's fifth sink ("a global root") has no test and no enforcement here
  because no mutable top-level variable exists yet (`export mut` is
  rejected at parse time) — there is nothing to assign into. Whoever adds
  real mutable globals must add the "Stack value assigned into a global"
  check to `EscapePass` at that time; it does not fall out of anything built
  here automatically.
