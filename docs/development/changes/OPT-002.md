## Why

`ValueRangePass` (`src/ValueRange.cpp`) already runs a constant-propagation
dataflow over every function body and uses it to raise a compile-time
`ArrayBoundsError` for a provably-out-of-range constant index — but nothing
ever used the SAME analysis to skip the corresponding *runtime* check when
the index is provably **in** range. `DESIGN_NOTES.md` §1 ("Bounds Check
Elimination") named this directly: Codegen always injects
`EmitRuntimeBoundsCheck`, the data needed to skip it is already computed,
and it is simply unused. The roadmap (§8, OPT-002) extended the same idea to
`SEM-002`'s checked-overflow arithmetic (`EmitCheckedIntArith`/
`EmitCheckedIntNegate`/`EmitCheckedShl`) — this is explicitly what recovers
F-NUM-3's cost, and §27.2 item D24 has a **measured** number for why it
matters: the checked-overflow branch alone was confirmed (2026-09-20,
`refactor/architecture`, post-OPT-001) to block LLVM's auto-vectorizer on a
hot numeric loop, closing a 53%-slower-than-`clang -O3` gap down to parity
once that one branch was removed by hand.

Also in scope per §8's own text: `CallGraphPass::runGlobal()` was a literal
stub (`std::lock_guard` then a comment) while `AddCallEdge()` populated a
`caller → set<callee>` map nothing ever read back — "either use it or delete
it."

**A load-bearing fact discovered before writing any code, worth stating
plainly because it decided the whole architecture below:** `ValueRangePass`'s
existing invocation (`FuncDefExprAST::codegen()`, `CodegenFunc.cpp`) runs
strictly **after** `Body->codegen()` has already emitted every runtime
check's LLVM IR. Its results have always arrived one compile too late to
suppress anything — they were only ever usable for the compile-time
diagnostic, never for elision. Confirmed live with a small probe program
and `--emit-llvm`: at `-O0`, a `mut i: int = 3; arr[i] = 42;` access
unconditionally got the full `idx_neg`/`idx_toobig`/`arr_oob` branch
structure, with no path for any later pass to remove it without either
re-running Codegen or patching already-emitted IR.

## Language semantics

### Old behaviour

Every array access whose index Codegen could not fold to an LLVM
`ConstantInt` at emission time got a runtime bounds check
(`EmitRuntimeBoundsCheck`), and every `int` `+`/`-`/`*`/`<<`/unary-`-` got a
checked-overflow branch (`EmitCheckedIntArith`/`EmitCheckedShl`/
`EmitCheckedIntNegate`), regardless of whether the operands were provably
safe by any means short of literal constant-folding at the AST level. A
`mut` local assigned once from a literal and never reassigned — provably
constant to a human, and already provably constant to `ValueRangePass`'s own
dataflow — still got the full runtime check.

### New behaviour

A NEW pass, `ValueRangePass::markElidableChecks()`, runs on a **second,
throwaway CFG** built from the same (not-yet-codegenned) function body
**before** `Body->codegen()` (`CodegenFunc.cpp`, right after parameter
allocas and Lint, before the body is walked). It performs the identical
constant-propagation dataflow `runOnCFG()` already does, but instead of
raising a diagnostic for the out-of-range case, it marks the in-range/
no-overflow case: `ArrayAccessExprAST::ProvenInBounds`,
`{Binary,Unary,CompoundAssignment,Postfix}ExprAST::ProvenNoOverflow`. Codegen
(`CodegenArray.cpp`/`CodegenExpr.cpp`/`CodegenVar.cpp`) checks these flags
before emitting the corresponding check, and skips straight to the
unchecked operation (`nsw` arithmetic, or a plain GEP with no branch) when
set.

This is a **frontend, proof-driven** transformation, not an
optimization-level-gated one (F-OPT-2 — "removal by proof only, never by
flag") — it fires identically at every `-O` level including `-O0`, unlike
LLVM's own generic dead-branch folding (confirmed live: at `-O2`/`-O3`,
LLVM's own `PassBuilder` pipeline from OPT-001 *already* folds away every
check in a fully-constant-foldable function via SCCP/InstCombine — the new
value here is specifically the cases that are constant PROVABLY, but not
foldable to an LLVM constant at emission time, and doing it uniformly
regardless of `-O` level).

**Safety-critical addition beyond DESIGN_NOTES.md's own sketch:**
`markElidableChecks()` also computes a whole-function "address taken" set
(`collectAddressTaken()`) and refuses to trust a tracked constant for any
symbol whose address is ever taken (`&x`) anywhere in the function, at all,
regardless of the dataflow's own local answer. `runOnCFG()`'s existing
diagnostic pass has no such guard, and doesn't need one — a missed
compile-time diagnostic there just means the runtime check still catches
the bug live, same as before this group existed. Eliding a check has no
such fallback: an unsound proof here is a genuine out-of-bounds memory
write with **no** check at all, not merely a missed diagnostic. `&x` lets
that reference be widened to `T*` and mutated through it inside an
`unsafe { }` block (real, expressible pathway — `p to int*` then
`raw[0] = 99`), which the local, non-aliasing-aware dataflow has no way to
see. Confirmed live (see Tests) that this guard is load-bearing, not
theoretical: without it, `tests/43_check_elision/
fail_address_taken_index_not_elided.tr` would have been wrongly elided and
would have missed a real out-of-bounds write.

### Is this breaking?

No. Every provably-safe elision computes the bit-identical result the
checked path would have computed (that's what "provably safe" means here);
every case the pass cannot prove safe is unaffected and still checked,
exactly as before. Full suite (763/763, including 5 new tests), `lib/std`
direct-compile sweep, and all 7 `showcase/*.tr` programs (compiled and, for
three of them, also run) are unchanged in observable behaviour.

## Compiler architecture

- **AST** (`include/ASTAccess.h`, `include/ASTExpr.h`): new boolean fields —
  `ArrayAccessExprAST::ProvenInBounds`; `BinaryExprAST`/`UnaryExprAST`/
  `CompoundAssignmentExprAST`/`PostfixExprAST::ProvenNoOverflow`. Not copied
  by `clone()`, same contract as every other Resolver/TypeChecker-set
  "resolved" field on these classes — a cloned (monomorphized) tree is
  re-analyzed by its own, independent `FuncDefExprAST::codegen()` call.
- **CFG/analysis** (`src/ValueRange.cpp`, `include/ValueRange.h`): new
  `ValueRangePass::markElidableChecks()`, plus its supporting static
  functions (`arithProvablySafe`, `shlProvablySafe`, `negProvablySafe`,
  `evalConstExprElidable`, `collectAddressTaken`, `applyTransfer`,
  `markNode`). `runOnCFG()` itself is **completely unmodified** — same
  function body, same diagnostic behaviour, same call site.
- **Codegen**:
  - `CodegenFunc.cpp`: `FuncDefExprAST::codegen()` builds a second,
    throwaway `CFGBuilder().buildCFG(...)` and calls
    `ValueRangePass().markElidableChecks(...)` right before
    `Body->codegen()`. The EXISTING CFG build + full analysis suite
    (`runOnCFG()` included) a few dozen lines later, after
    `Body->codegen()`, is untouched.
  - `CodegenArray.cpp`: both `EmitRuntimeBoundsCheck` call sites
    (`codegenLValue()`, `codegen()`'s R-value fallback) gate on
    `!ProvenInBounds`.
  - `CodegenExpr.cpp`: `BinaryExprAST::codegen()`'s `+`/`-`/`*`/`TOK_LSHIFT`
    cases and `UnaryExprAST::codegen()`'s unary `-` case emit plain `nsw`
    arithmetic (`CreateNSWAdd`/`CreateNSWSub`/`CreateNSWMul`/`CreateShl`/
    `CreateNSWNeg`) instead of calling the checked helper when
    `ProvenNoOverflow` is set.
  - `CodegenVar.cpp`: `CompoundAssignmentExprAST::codegen()`'s `+`/`-`/`*`/
    `TOK_LSHIFT` cases and `PostfixExprAST::codegen()`'s `+`/`-` cases, same
    pattern.
- **Deleted**: `src/CallGraph.cpp`, `include/CallGraph.h`,
  `CMakeLists.txt`'s reference to the former, `CodegenFunc.cpp`'s
  `scanCalls` block that populated the now-gone edge map, the
  `#include "CallGraph.h"` line from all eight files that had it, and
  `main.cpp`'s `ClearCallGraph()`/`CallGraphPass::runGlobal()` call sites.
  Chosen over "wire up a consumer": nothing in the roadmap (§8, §17, §27)
  names a planned use for a whole-program call graph, and inventing one
  would be exactly the kind of unscoped feature addition `ARCHITECTURE_
  OVERHAUL.md` §25 warns against doing "while implementing something else."

## Runtime changes

None. `libturfrt` is untouched.

None directly. `lib/std/**` compiles clean via direct sweep (unchanged

## New invariants

- **INV-OPT-2**: Array-bounds and checked-overflow-arithmetic elision only
  ever happens when `ValueRangePass::markElidableChecks()` proves it safe,
  independent of `-O` level, and never for a symbol whose address is taken
  anywhere in the enclosing function. Enforced by: `markElidableChecks()`
  running unconditionally (not gated on any `-O` flag) before
  `Body->codegen()`, and `collectAddressTaken()`'s whole-function,
  conservative exclusion set. `holds` — verified live via `--emit-llvm -O0`
  on three probes: (1) a provably-safe bounds+overflow case has the check
  genuinely absent from the emitted IR, not just optimized away later; (2)
  an unprovable case (a value read from a function-call return) keeps its
  check; (3) an address-taken case that a naive (non-aliasing-aware)
  dataflow would wrongly treat as constant correctly keeps its check and
  traps at runtime (`tests/43_check_elision/
  fail_address_taken_index_not_elided.tr`).

## Removed assumptions

- **It used to be safe to assume `ValueRangePass`'s results were only ever
  consumed once, after `Body->codegen()`.** That is no longer true — a
  SECOND, independent invocation now runs before `Body->codegen()`, on a
  throwaway CFG, for elision purposes only. A future session extending
  `ValueRangePass`'s dataflow (e.g. real interval ranges, not just exact
  constants) must keep both invocations correct: the diagnostic one
  (`runOnCFG()`, still raises `ArrayBoundsError`) and the elision one
  (`markElidableChecks()`, never raises anything, and MUST stay
  conservative — a diagnostic false-negative just misses a compile-time
  error with the runtime check as a fallback; an elision false-positive is
  a genuine memory-safety bug).
- **It used to be safe to assume a "known constant" from this pass's
  dataflow could never be invalidated except by an ordinary
  `VarDeclExprAST`/plain-variable `AssignmentExprAST`.** `applyTransfer()`
  (the transfer function `markElidableChecks()` uses, deliberately NOT
  shared with `runOnCFG()`'s own inline transfer) additionally invalidates
  a tracked variable on `CompoundAssignmentExprAST`/`PostfixExprAST` — a gap
  `runOnCFG()` itself still has (see Known pitfalls), left unfixed there
  since it only costs that pass a missed diagnostic, not a memory-safety
  bug.
- **It used to be safe to assume a scalar local's value can't change except
  through a directly-visible assignment in the same function.** `&x`
  (`AddressOfExprAST`) plus an `unsafe { }` raw-pointer write through the
  resulting `T*` is a real, expressible way to mutate a variable with no
  assignment statement anywhere naming it. Any FUTURE pass reasoning about
  "this variable's value" from AST-local inspection alone needs the same
  address-taken guard this group added, or an equivalent one — it is not
  automatically safe just because `ValueRangePass`'s existing diagnostic
  pass got away without it.
- **`CallGraph.h`/`AddCallEdge`/`CallGraphPass` no longer exist.** Any
  future whole-program call-graph analysis starts from zero, not from this
  scaffold — the removed code was never wired to anything, so nothing is
  lost by its removal beyond the (nonexistent) print statement its stub
  never had.

## Known pitfalls

- **`runOnCFG()`'s own transfer function still doesn't account for
  `CompoundAssignmentExprAST`/`PostfixExprAST` mutating a tracked
  variable.** This group's `applyTransfer()` (used only by
  `markElidableChecks()`) fixes this for elision purposes, but deliberately
  does NOT touch `runOnCFG()` itself — out of scope, and it only costs that
  pass a missed compile-time diagnostic (e.g. `mut i=5; i += 1; arr[i]`
  against a too-small `arr` won't be caught at compile time), never a
  memory-safety issue, since the runtime check remains in place there
  regardless. A future session improving `ValueRangePass`'s diagnostic
  precision should port this fix over, but that's a distinct, small,
  separately-motivated change.
- **The address-taken guard is coarse, not flow-sensitive.** Once `&x`
  appears anywhere in the function, `x` is excluded from elision for the
  ENTIRE function, even in a block that provably runs before the
  address-of expression. This trades away some elision opportunities for a
  simple, obviously-sound rule; a flow-sensitive version (only excluding
  program points reachable from the `&x`) is a real, separate future
  improvement, not attempted here.
- **`markElidableChecks()` duplicates CFG construction and the
  constant-propagation fixed-point per function** (once before
  `Body->codegen()` for elision, once after for diagnostics). This is a
  compile-time cost, not a correctness one — deliberately accepted rather
  than reordering the existing, working post-codegen analysis suite ahead
  of `Body->codegen()` (a much larger, riskier restructuring touching
  `DefiniteAssignmentPass`/`AliasAnalysisPass`/`NullabilityPass`/
  `LivenessAnalysisPass`/`ConstructorFieldAssignmentPass`/infinite-loop/
  infinite-recursion detection, none of which this group's scope covers).
  Not measured against the compile-time baseline (`hello-world ~0.3s` per
  §17.4) — no test in this session's own scope required it, and OPT-002's
  roadmap text does not name compile-time cost as a completion criterion.
- **A pre-existing, unrelated finding surfaced by the mandatory `lib/std`
  direct-compile sweep, NOT caused by this group:** `turf --resolve
  lib/std/collections/list.tr` reports `E034` ("A struct named 'List' is
  already declared") when `list.tr` is compiled directly as its own entry
  point. Confirmed by code-path isolation, not just inference, that this
  group cannot be the cause — nothing here touches Resolver name
  resolution, import indexing, or struct declaration handling at all (this
  group's diff is confined to `ValueRange.cpp`, three `Codegen*.cpp` files'
  checked-op call sites, and the `CallGraph` deletion). `io.tr`/`http.tr`/
  `json.tr` show a pre-existing, unrelated, non-fatal warning
  (`read_lines`'s fallible-but-never-fails return type) before the same
  ordinary "No entry point found" every non-`main()` `lib/std` file
  produces under `--resolve` — also unrelated. Flagged here rather than
  silently left for the next session to rediscover (§25's spirit, mirroring
  SEM-002's own disclosed `export_qualified_cross_module.tr` finding).
