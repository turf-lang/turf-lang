## Why

LANG-002 replaced the path-based raw-pointer privilege (`IsPathUnderLibStd()`)
with a declared-in-source capability, and RT-001 introduced
`include/Intrinsics.h` as the closed, enumerated list of every
compiler-known symbol. Neither group closed the loop on the three specific
claims `ARCHITECTURE_OVERHAUL.md` §8's STD-001 entry names: (1) that the
closed intrinsic list actually covers everything, rather than being
accurate today by luck and silently drifting tomorrow; (2) that
`PreludeModuleNames` (`src/ParserModule.cpp`) — a bare hardcoded six-name
C++ array with no written rationale — is an intentional specification
rather than an arbitrary historical accident; and (3) that
`AGENTS.md`'s "No compiler special-casing; ordinary `.tr` files" claim is
*tested*, not merely believed. All three were true in substance before
this session (confirmed live, see *Removed assumptions*) but none were
mechanically checked — exactly the gap between "a design rule stated as
settled fact" and "a fresh test that actually tries to break it"
`AGENTS.md` itself warns about.

## Removed assumptions

- **"The closed intrinsic list (`include/Intrinsics.h`) covers literally
  every compiler-known name in the compiler."** False as a blanket claim,
  and it was worth finding out live rather than writing the enforcement
  script to assume it. `src/CodegenCore.cpp`'s `getExprType()` — Codegen's
  own independent, duplicate type-inference helper
  (`ARCHITECTURE_OVERHAUL.md` §25 item 4's "two type-inference engines"
  wart, explicitly protected from unrelated refactors) — has a last-resort
  fallback:
  ```cpp
  // Fallback for intrinsic path: malloc/realloc return ptr, free returns void
  if (CalleeName == "malloc" || CalleeName == "realloc")
    return TurfPtr().get();
  if (CalleeName == "free")
    return TurfVoid().get();
  ```
  reached only after every other lookup in that function fails. It is not
  itself a language-level intrinsic (it grants no capability and changes no
  legality — the TypeChecker has already accepted or rejected the call by
  the time Codegen runs), and touching it means touching the exact code
  §25 item 4 says not to unify as a drive-by fix. Left alone, deliberately,
  and documented instead — `docs/architecture/boundary.md` §2 "One
  documented exception", and `scripts/check_boundary.sh`'s own comment
  explains why its check 3 does not (and structurally cannot, via a simple
  grep) catch this class of fallback. A future session should not
  "discover" this as new; it should read this entry and `boundary.md` §2
  first.
- **"`PreludeModuleNames` being exactly `lib/std/core/`'s contents is a
  coincidence worth leaving undocumented."** It was already true before
  this session (`find lib/std/core -name '*.tr'` returns exactly `int`,
  `double`, `bool`, `char`, `strings`, `array`) but nothing tied the two
  together, tested the correspondence, or explained why `core/`
  specifically (as opposed to any other `lib/std` subfolder) is special.
  `ARCHITECTURE_OVERHAUL.md` §3.2's diagram already labels that layer
  `core (prelude)` — this session made the correspondence a written,
  enforced specification rather than an implicit fact only the diagram
  happened to already state.
- **A stale doc line, found and fixed alongside this work**:
  `docs/architecture/pointers_and_references.md` §2.5.1 item 3 still
  described `isUnsafeGateExempt()`'s third exemption as "the declaring
  file is under `lib/std` (`IsPathUnderLibStd(Loc.Filename)`)" — the
  pre-LANG-002 mechanism. The function itself has called
  `HasRawPointerCapability(Loc.Filename)` since LANG-002 landed
  (2026-09-23); that document's own §2.8 summary already said so
  correctly, but §2.5.1's earlier paragraph was never updated to match,
  the exact "verify claims live" failure mode `AGENTS.md`/
  `SESSION_PROTOCOL.md` name. Fixed by re-reading the actual current
  `TypeCheckerCore.cpp` source (`grep -rn "HasRawPointerCapability"
  src/TypeCheckerCore.cpp` — confirmed both call sites use the new
  function, not the old one) rather than trusting the existing doc's own
  internal consistency.

## Known pitfalls

- **`scripts/check_boundary.sh` check 1's grep deliberately excludes
  comment-only mentions of `IsPathUnderLibStd`.** Several doc comments in
  `src/ParserModule.cpp`/`include/Parser.h` still name it, on purpose,
  explaining what it was replaced with and why (this project's "doc
  comments explain WHY" convention). A naive `grep -rn IsPathUnderLibStd`
  would flag those every time and become exactly the kind of "red on
  arrival, so people learn to ignore it" check `SESSION_PROTOCOL.md`
  warns about for the `_module.tr` sweep. If a future session adds another
  historical comment mentioning the old name, this check stays green —
  only a live definition or call site (a line not starting with `//`/`*`
  before the match) fails it.
- **Check 2's `PreludeModuleNames` extraction is a textual `awk` scrape of
  `src/ParserModule.cpp`, not a compiler-driven check.** It will silently
  stop working (report a false empty-list failure, not a false pass) if a
  future refactor reformats the array declaration across more lines or
  renames it — this is deliberately a low-tech, readable check rather than
  building actual tooling to introspect the compiler's own C++ source. If
  this check ever fails with "could not find PreludeModuleNames[]", check
  whether the array was renamed or reformatted before assuming drift.
- **Do not extend check 3 to catch every `CalleeName == "..."` comparison
  in the compiler.** It is tempting — the malloc/realloc/free fallback in
  *Removed assumptions* looks exactly like what such a broader check would
  catch — but doing so would immediately and permanently fail on that
  known, deliberately-left-alone exception, becoming the "red on arrival"
  problem the previous pitfall already warns about, for a check with no
  real fix available (per §25 item 4). If a future session wants stronger
  coverage here, it must first decide what to do about that specific
  fallback (fix it as part of a deliberate, scoped
  duplicate-type-inference cleanup — not this group, not a drive-by).
- **`PreludeModuleNames` is intentionally NOT derived from `lib/std/core/`
  at compile time**, even though check 2 makes the two provably identical
  today. See `boundary.md` §4 for the full reasoning (keeping the
  correspondence *checked* rather than *generated* is what keeps `core/`
  from secretly becoming load-bearing the way no other `lib/std` subfolder
  is). A future session should not "simplify" this into a directory scan
  as a drive-by — that is a real behavior change (what happens when a
  *new* file lands in `core/`?) requiring its own explicit decision, not
  an obvious cleanup.
