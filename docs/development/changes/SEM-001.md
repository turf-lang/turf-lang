## Why

`strtoll`/`strtod`, unchecked for `errno`, destroyed a literal's real value
before the parser ever saw it:

```turf
mut x: int = 999999999999999999999999999999999999999999999999;  // 48 digits
// compiled with ZERO diagnostics, silently became 9223372036854775807
mut d: double = <1 followed by 400 zeros>.0;
// compiled with ZERO diagnostics, silently became inf
```

`NumberExprAST` stored a `double Val` copy even for integers (dead weight,
never read that way), and the lexer supported only bare decimal digits and
a single `.` — no hex/binary/octal, no `_` digit separators, no exponent.
`-9223372036854775808` was unwritable (`9223372036854775808` clamps to
`INT64_MAX` first, then negation runs, landing one short). `ValueRange.cpp`'s
`evalConstExpr` performed `lv + rv` on plain `long long` — signed-overflow
UB in the compiler's own C++, not just a user-facing gap.

Everything SEM-002 (representability) and SEM-003 (`guess` inference) need
is defined in terms of an *exact* literal value. That value didn't exist
anywhere in the compiler before this group.

## Language semantics

### Old behaviour

```turf
mut x: int = 999999999999999999999999999999999999999999999999;
// compiles, x == 9223372036854775807 at runtime
mut y = 0755;
// y == 493 (legacy octal) -- wait, no: today's lexer has NO radix support
// at all, so 0755 was already decimal 755 even before this group. Radix
// prefixes (0x/0b/0o), '_' separators, and any exponent form all failed
// to lex at all -- 0xFF was tokenized as identifier "xFF" preceded by an
// orphan integer "0", and 1e6 as integer "1" followed by identifier "e6".
```

### New behaviour

```turf
mut x: int = 999999999999999999999999999999999999999999999999;
// still compiles (representability is SEM-002's job) -- but the AST node
// now carries the value EXACTLY: --dump-ast prints
// NumberExpr(int:999999999999999999999999999999999999999999999999)
mut a: int = 0xFF;       // 255
mut b: int = 0b1010;     // 10
mut c: int = 0o17;       // 15
mut d: int = 1_000_000;  // separators anywhere between two digits
mut e: double = 1e6;     // dotless exponent (new -- see "Unresolved questions")
mut f: double = 1.5e-3;  // dotted exponent
mut g: int = 0755;       // still decimal 755, never octal (F-NUM-5)
```

Four new lexical errors, all raised directly by the Lexer with a real
E0NN code: `E070` (bare radix prefix, `0x` with nothing after it), `E071`
(a digit that's wrong for the literal's radix, `0b012`), `E072` (a digit
run starting or ending with `_`), `E073` (an exponent marker with no
exponent after it, `1.5e`).

### Is this breaking?

No, for every literal that compiled to a *correct* value before. Yes,
narrowly, for two shapes that used to compile to a *silently wrong* value:
a literal magnitude too large for its destination type (still compiles in
this group — SEM-002 turns it into a hard error) and a `5.`-shaped bare
trailing dot (now rejected by a pre-existing, unrelated parser diagnostic,
"Expected a method name after '.'" — `.` is left as its own token once the
lexer no longer commits to a fractional part with nothing after it). No
test in `tests/`, `lib/std/`, or `showcase/` used either shape (confirmed
by the full sweep both stayed green through). No migration needed for any
existing correct program.

## Compiler architecture

- **Lexer** (`src/Lexer.cpp`, `include/Lexer.h`) — the number-scanning
  branch of `gettokScan()` is a full rewrite: radix-prefix dispatch (hex/
  binary/octal), a shared `ScanDigitRun()` helper enforcing "no leading/
  trailing `_`" per digit run, a dotted-float path that only commits to
  `.` when a digit immediately follows it, and an exponent path shared by
  both the dotted and dotless forms. Deliberately still LLVM-free: the
  three new globals (`NumLitSpelling`/`NumLitClean`/`NumLitRadix`,
  replacing `NumVal`/`IntVal`) are plain strings/ints, not
  `llvm::APSInt`/`APFloat` — see Lexer.h's own comment on why. Four new
  `TurfError` subclasses raised directly from here (`include/ErrorsLex.h`)
  — the one place in the whole compiler where `Lexer.cpp` includes a
  `TurfError` header at all (see that file's own top comment for why this
  is architecturally clean, not circular).
- **Parser** (`src/ParserLiteral.cpp`) — `ParseNumberExpr()` is where the
  actual `llvm::APSInt`/`APFloat` gets built, from the lexer's raw
  `NumLitClean`/`NumLitRadix`. Bit width via `APInt::getBitsNeeded()` plus
  a round-trip safety check (construct, and if the sign bit is set, redo
  one bit wider) rather than trusting that function's exact rounding
  convention. Float overflow-to-inf detected via `APFloat::
  convertFromString()`'s returned `opStatus`. `ParserCore.cpp`'s two
  array-size sites (`T[N]`) and `ParserModule.cpp`'s lexer-state save/
  restore guard updated to the renamed globals — neither goes through
  `NumberExprAST` at all (array size is a compile-time-only dimension, not
  a value-position literal).
- **AST** (`include/ASTExpr.h`) — `NumberExprAST` reshaped into a genuine
  tagged union: `APSInt IntVal_` xor `APFloat FloatVal_`, plus
  `IsUntyped_` (real source literal vs. compiler-synthesized), `Overflowed_`
  (float rounding hit inf), `Spelling_`, and `Loc_` (new — this node had no
  location at all before). One private full-fidelity constructor every
  other constructor (and `clone()`) delegates to, so a clone can never
  silently reset `IsUntyped_` to the wrong value for whichever shape it
  started as (a bug in an earlier draft of this same change, caught before
  landing — see *Known pitfalls*). `getIntVal()`/`getDoubleVal()` kept as
  narrow, safely-truncating convenience accessors for the many low-stakes
  consumers that never needed exactness; `getIntValExact()`/
  `getFloatValExact()` added for the ones that do.
- **TypeChecker** (`src/TypeCheckerExpr.cpp`) — `compare` arm duplicate-
  pattern detection now fingerprints an integer literal by its exact value
  (`getIntValExact()`), not the truncated `getIntVal()`, so two distinct
  wide literals can no longer collide into a false "duplicate arm".
- **Resolver** (`src/ResolverCore.cpp`, `include/ResolverSymbolBase.h`) —
  `hoistExportedConstant()` captures an `export immut` integer constant's
  exact decimal string (`ResolverConstantSymbol::IntVal`, now `std::string`
  not `long long` — this header is explicitly, deliberately LLVM/AST-free,
  same constraint as Lexer.h, so it cannot hold an `APSInt` directly; see
  the field's own doc comment).
- **Codegen** (`src/CodegenExpr.cpp`, `src/CodegenCore.cpp`) —
  `NumberExprAST::codegen()` builds the LLVM constant directly from
  `getIntValExact()`/`getFloatValExact()` (extended/truncated to the fixed
  64-bit `int` LLVM type explicitly, never implicitly). `CodegenConstantValue()`
  (the `export immut` inliner) reconstructs an `APInt` from
  `ResolverConstantSymbol::IntVal`'s decimal string, same
  `getBitsNeeded()`-then-truncate pattern.
- **CFG/analysis** (`src/ValueRange.cpp`) — `evalConstExpr`'s binary-op
  folding replaced with checked 65-bit `APInt` arithmetic
  (`sadd_ov`/`ssub_ov`/`smul_ov`/`sdiv_ov`), removing the confirmed
  signed-overflow UB. See *New invariants* (INV-CONST-1) for why 65 bits,
  not literal arbitrary precision, is the correct scope here.
- **Diagnostics** — `E070`–`E073` (`include/ErrorCodes.h`,
  `docs/errors/codes/E07{0,1,2,3}.txt`, `docs/slm/codes/E07{0,1,2,3}.txt`),
  all routed to the existing `SYNTAX_ERROR` category per §8's explicit
  instruction not to add a new `SLM::ErrorCategory`.
- Ripple fixes not central to the reshape but needed to keep it honest:
  `Lint.cpp`'s branch-fingerprinting, `ASTDiff.h`'s sandbox-diff comparison,
  and `ASTPrinter.h`'s `--dump-ast` output all moved from the narrow
  `getIntVal()` to the exact accessor (see each file's own comment for the
  specific correctness gap this closes). `CompileBuffer.cpp`'s
  `LocationExtractorVisitor` gained a `visitNumber` case now that
  `NumberExprAST` has a real location — closing a documented, pre-existing
  "NumberExprAST has no SourceLocation field" comment that SEM-001's own
  reshape made stale.

## New invariants

- **INV-CONST-1** (already named in `INVARIANTS.md` as `planned` before
  this session): all compile-time arithmetic uses checked operations.
  Moved to `holds` — `evalConstExpr`'s UB is gone, replaced by checked
  65-bit `APInt` ops. See `INVARIANTS.md`'s own updated row for why 65
  bits (not unbounded) is the right scope for this specific pass.
- **INV-NUM-2** (already named as `planned — SEM-001/002`): partially
  satisfied. The "value never lost between the lexer and the AST" half is
  done and verified live (48-digit literal round-trips exactly through
  `--dump-ast`). Stays `planned`, now scoped to `SEM-002` alone (the
  "and the type check" half — representability enforcement — still owed).

## Removed assumptions

- **A `NumberExprAST`'s value could always be read as a plain `long long`/
  `double` with no loss.** It still can, via `getIntVal()`/`getDoubleVal()`
  — but those are now explicitly NARROW, TRUNCATING accessors, not the
  node's source of truth. Any future consumer that needs the literal's
  real, possibly-wider-than-64-bit value must reach for
  `getIntValExact()`/`getFloatValExact()` instead; reaching for the narrow
  ones by habit silently reintroduces the exact class of bug this group
  fixed (confirmed necessary via the Lint.cpp/TypeCheckerExpr.cpp/
  ASTDiff.h fingerprinting fixes — the narrow accessor was ALREADY capable
  of causing a false "these two are the same" collision at 3 separate call
  sites before this pass).
- **Every `NumberExprAST` was compiler-`IsUntyped_`-agnostic (the concept
  didn't exist).** It now does, and `clone()` must preserve it correctly
  regardless of which public constructor originally built the node — see
  *Known pitfalls* for the specific bug this assumption's absence almost
  caused.
- **`ResolverConstantSymbol::IntVal` was a plain machine integer.** It's a
  decimal string now (`ResolverSymbolBase.h` is deliberately LLVM/AST-free
  and cannot hold an `APSInt`) — any future code reading this field
  directly as a number needs to parse it first (see
  `CodegenConstantValue()` for the established pattern:
  `APInt::getBitsNeeded()` then construct then truncate).
- **A radix prefix, `_` separator, and exponent were simply not part of
  this language's numeric grammar.** They are now, and FREEZE.md §6.2 row
  1 is the settled definition — a future session should not "simplify" the
  lexer's number branch back toward the old bare-decimal-plus-dot form
  without re-reading that row first.
- **Lexer.cpp never constructed a coded `TurfError`.** It does now, for
  exactly these four classes (`ErrorsLex.h`'s own top comment explains
  why this doesn't create a header cycle) — a future session adding a
  fifth lexer-level diagnostic that needs a code has established precedent
  to follow, not a new pattern to invent.

## Known pitfalls

- **A leading-underscore identifier is completely broken on this
  compiler, unrelated to this group.** `mut _x: int = 5;` fails to parse
  (`isalpha(LastChar)` is the sole identifier-start condition in
  `Lexer.cpp`, and does not include `_`) — confirmed live on the
  pre-SEM-001 baseline (`62b2434`), so this predates this session entirely
  and is out of scope for it (identifier lexing, not numeric literals).
  This directly contradicts several of this compiler's OWN lint hint
  strings ("prefix its name with '_' by convention" for an unused
  variable). It also means a bare leading-`_` numeric literal (`_5`) can
  never reach the number-lexing branch at all — `fail_leading_separator.tr`
  uses `0x_5` instead (a reachable leading-separator position) and says so
  in its own comment. A future session touching identifier lexing should
  know this exists before assuming `_`-prefixed names already work.
- **`clone()` almost silently reset `IsUntyped_` for every clone,
  regardless of the original node's own value.** An early version of this
  change gave `clone()` a shortcut through the "real source literal"
  public constructors (which hardcode `IsUntyped_ = true`), which would
  have turned every clone of a compiler-SYNTHESIZED node (e.g. the
  desugared `1` in `x++`) into a false "real source literal" — caught
  before landing by tracing the constructor delegation chain, not by a
  test (nothing in the current suite distinguishes `IsUntyped_` yet; a
  future session relying on it for a real diagnostic should add one that
  exercises `clone()` specifically, e.g. via the Sandbox path). Fixed with
  one private, full-fidelity constructor every public one (and `clone()`)
  delegates to — see ASTExpr.h's own comment on `NumberExprAST`.
- **`APSInt`'s "overflow-checked" arithmetic methods
  (`sadd_ov`/`ssub_ov`/`smul_ov`) are inherited from `APInt` and return a
  plain `APInt`, not an `APSInt`.** Assigning the result directly to an
  `APSInt` variable does not compile (`APSInt`'s `APInt`-taking
  constructor is `explicit`) — this is why `ValueRange.cpp`'s fix uses
  plain `APInt` throughout rather than `APSInt`; nothing in that function
  actually needed `APSInt`'s extra "remembers if signed" bit, since every
  operation there is explicitly the signed (`s`-prefixed) variant already.
- **`llvm::APInt`/`APSInt` have no `std::string`-returning `toString()`.**
  Every call site in this change that needed a decimal string
  (`ResolverCore.cpp`, `ASTPrinter.h`, `Lint.cpp`, `TypeCheckerExpr.cpp`)
  goes through `llvm::SmallString<32>` first, then `.str().str()` (the
  first `.str()` is `SmallString::str()` → `StringRef`, the second is
  `StringRef::str()` → `std::string`) — easy to write `toString()`
  expecting a `std::string` return and get a compile error instead; this
  is the correct, established pattern, not a workaround to eventually
  clean up.
- **A bare trailing dot (`5.`) is a real, deliberate boundary decision
  that does NOT raise one of the four new lexical errors.** The lexer only
  commits to `.` as a literal's decimal point when a digit immediately
  follows it; `5.` is not scanned as float syntax at all, so `5` is
  returned as a plain int and `.` is left for the next token, which then
  fails with a pre-existing, generic "Expected a method name after '.'"
  parser diagnostic instead. This is intentional (see
  `fail_bare_trailing_dot.tr`'s own comment) — do not "fix" this into a
  fifth lexical-error class; the existing rejection is correct and
  sufficiently clear.

### Examples that became invalid

None — no handbook/reference example relied on a bare-trailing-dot float
or an out-of-range literal's old silently-clamped value.

### Examples that should be added

`0xFF`/`0b1010`/`0o17`/`1_000_000` alongside the existing plain-decimal
examples; `1e6` next to `1.5e-3` to show both exponent forms; `0755 == 755`
as its own explicit callout (the one place a C-background reader will
guess wrong).

### Sections that must NOT change

Anything describing `int`/`double`'s *type* semantics (range, `int32`
conversion, `bool`/`char` isolation) is untouched by this group — only the
LEXICAL description of how a literal is written changes, not what the
resulting typed value means.

## Unresolved questions

**Resolved during this session, recorded here for the record.** FREEZE.md
§6.2 row 1's original grammar (`[0-9_]*.[0-9_]+([eE][+-]?[0-9]+)?` as the
ONLY float form) made a bare exponent (`1e6`, no decimal point) lexically
invalid — directly contradicting this same group's own §8 testing-scope
text, which lists `1e6` alongside `1.5e-3`/`1E+10` as forms that must
work. Per `docs/development/FREEZE.md`'s own "stop and ask" rule for a
frozen decision that looks wrong, this was raised to the user rather than
resolved unilaterally. Decision: accept `1e6` (dotless-exponent form is a
second, independent alternative, unioned onto the dotted-float grammar,
not a replacement for it) — matches every mainstream language's float
grammar and SEM-001's own testing scope as written. FREEZE.md §6.2 row 1
was corrected in place (not left self-contradictory) to state both
alternatives; see that row's own inline note for the full history.
