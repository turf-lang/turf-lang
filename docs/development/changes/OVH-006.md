## Why

A user struct declared with the same name as a stdlib generic's own type
parameter (`T`, `K`, `V`, `U` — the exact letters `List<T>`, `Map<K, V>`, a
free `fn<U> ...`, etc. use) broke every generic in the program that used
that letter, not just the one the user happened to collide with. Verified
live against `refactor/architecture` @ `cde1d30` (the 2026-09-26 closure
audit, `OVERHAUL_CLOSURE_AUDIT.md`):

```turf
import list::List;
struct T { x: int }
fn main(): int { mut l: List<int> = List::default(); l.push(5); return l.pop() - 5; }
// error at line 106, col 3 [E066], in file lib/std/collections/list.tr
//   Return type mismatch: function declares 'int' but returns 'T'.
```

The same shape broke `Map<K, V>` the moment a user declared `struct V` (or
`struct K`), and independently explains why STD-003
(`docs/development/changes/STD-003.md`, *"What this fix does NOT reach"*)
found `fn<T> Pool.free_all(): void { free(self.items[i]); }` rejected with
"No overload of 'free' matches argument types (T)" and gave up rather than
touch what it correctly identified as "the field-type resolution itself."

**Root cause.** A generic struct's fields exist in TWO places, which used
to disagree:

1. The `StructDeclExprAST` AST node's own field list, which
   `Resolver::visitStructDecl()` rewrites in place — `NamedType("T")` →
   `TurfGenericParamType("T")` — for every field naming one of the struct's
   own type parameters (`substituteTypeParams()`, `ResolverCore.cpp`).
2. `GlobalSymbolTable`'s registered `TurfStructType` for the same struct
   name, built once at **parse** time (`ParseStructDecl()`,
   `ParserDecl.cpp`), directly from the as-parsed fields — before that
   substitution ever ran, and never updated afterward.

Every consumer that resolves a field's type by looking the struct back up
via `GlobalSymbolTable->LookupType(Name)` — `TypeCheckerCall.cpp`'s
`visitFieldAccess`/`visitMethodCall`, and their Codegen mirrors in
`CodegenCore.cpp` — therefore saw the stale, unsubstituted `NamedType("T")`
forever, never the real `TurfGenericParamType("T")` the AST node itself
carries. Because a bare `NamedType` can *also* legitimately name an
ordinary registered type, every one of those consumers had to tell "this
`NamedType` is actually this struct's own open type parameter" apart from
"this `NamedType` names some other real type" with a name-lookup
heuristic: *"if `GlobalSymbolTable->LookupType(name)` finds nothing, it
must be the type parameter."* That heuristic is exactly what `isOrWrapsGenericParam()`
(`TypeCheckerDecl.cpp`) and the `KnownElsewhere` checks inside the
Subst-recovery `Scan` lambdas (`TypeCheckerCall.cpp` × 2,
`CodegenCore.cpp` × 3) all independently implemented — and it silently
inverted the moment a real, unrelated struct existed under that exact
name: `GlobalSymbolTable->LookupType("T")` then found the user's own
`struct T`, and every one of those call sites substituted (or resolved)
the collision struct in place of the real type argument.

## Language semantics

### Old behaviour
- `struct T { x: int }` declared anywhere in a program that also uses
  `List<T>`'s namesake type parameter (i.e. any `List<...>` at all, since
  the parameter is spelled `T`) made `List<int>.pop()`'s return type
  resolve to the user's own struct `T`, not `int` — a `Type mismatch!`
  compile error on a program that has nothing wrong with it.
- The identical collision applied to `Map<K, V>` (structs named `K`/`V`),
  `Set<T>`/`Stack<T>`/`Queue<T>` (struct `T`), and any user-defined generic
  struct or free function using those same single-letter names.
- `fn<T> Pool.free_all(): void { free(self.items[i]); }` (STD-003's
  motivating case) was rejected even with **no** colliding struct present,
  because the stale `NamedType("T")` reaching `free`'s argument-type check
  never got the chance to hit `typesCompatible()`'s Rule 1
  (`TurfGenericParamType` matches anything) — it wasn't one.

### New behaviour
- A user struct may be named `T`, `K`, `V`, `U`, or anything else, without
  affecting any unrelated generic's own use of that same letter as a type
  parameter. `List<int>`, `Map<string, int>`, `Set<int>`, `Stack<int>`,
  `Queue<int>`, a user-defined generic free function, and a user-defined
  generic struct/method all continue to work correctly in the same program
  as colliding structs named after every one of those parameters.
- `self.<field>` of a generic struct, read inside its own generic method's
  template body, has type `TurfGenericParamType` — the real thing, not a
  stand-in `NamedType` that happens to usually behave the same way. The
  `fn<T> Pool.free_all()` shape now compiles (see the new
  `pool_free_all_generic.tr` test).

### Is this breaking?
No. Every previously-accepted program still compiles identically — this
only removes a false rejection (and one wrong-type acceptance path) that
depended on a struct name never colliding with a type-parameter letter,
which was never a documented restriction anywhere.

## Compiler architecture

- **Resolver** — `Resolver::visitStructDecl()` (`ResolverDecl.cpp`) now
  re-registers the struct's `GlobalSymbolTable` entry with a fresh
  `TurfStructType` built from the just-substituted field list (the same
  list it writes onto the AST node), immediately after the substitution
  loop. One representation, not two: `GlobalSymbolTable->LookupType(Name)`
  and the AST node's own `getFields()` can never disagree again for a
  generic struct's field types.
- **TypeChecker** — no logic changes. `isOrWrapsGenericParam()`
  (`TypeCheckerDecl.cpp`) and the `Scan` lambdas in `visitMethodCall()`/
  `visitFieldAccess()` (`TypeCheckerCall.cpp`) are unchanged code, but their
  `TurfGenericParamType` branch is now what actually fires for an ordinary
  generic struct field; their `NamedType`/`KnownElsewhere` branch becomes a
  defensive fallback instead of the common path. Doc comments at both sites
  updated to say so (see *Removed assumptions*).
- **Codegen** — unaffected directly; `CodegenCore.cpp`'s own `KnownElsewhere`
  Scan mirrors (×3) benefit from the same fix for the identical reason, with
  no code change needed there either.

## Removed assumptions
- **"A generic struct's field types can be told apart from an ordinary
  registered type by whether the name is registered."** This was the
  load-bearing (and wrong) assumption behind `isOrWrapsGenericParam()`'s
  `NamedType` branch and every `KnownElsewhere` Subst-recovery heuristic.
  It happened to hold in practice only because nothing in this codebase's
  own test suite or stdlib had ever declared a struct named `T`/`K`/`V`/`U`
  alongside the matching generic. It does not hold in general, and user
  code has no reason to avoid those names.
- **"GlobalSymbolTable's registered struct type and the AST node's own
  field list are two independent things that happen to usually agree."**
  They are the same struct's field types and must always agree; keeping
  them as two separately-mutated copies was the actual defect, not a
  tolerable implementation detail. `TypeCheckerDecl.cpp`'s and
  `TypeCheckerCall.cpp`'s own doc comments used to state the disagreement
  as a permanent fact ("permanently stuck," "never updated afterward") —
  both updated to describe the current, corrected state instead.

## Known pitfalls

- **The `NamedType`/`KnownElsewhere` heuristics were deliberately NOT
  deleted**, even though the fix makes them unreachable for every ordinary
  generic struct field. `isOrWrapsGenericParam()`'s `NamedType` branch,
  and the `KnownElsewhere` checks inside `TypeCheckerCall.cpp`'s two `Scan`
  lambdas and `CodegenCore.cpp`'s three mirrors, still run — they are just
  never the one that fires for a single-level generic struct field
  anymore. Two live paths still reach them with a genuine `NamedType`:
  (a) a **nested** generic struct field (`struct Outer<T> { inner:
  Inner<T> }`, OVH-007's own domain — explicitly listed as depending on
  this item), where the collision could plausibly resurface one level
  deeper; (b) a monomorphized clone whose concrete type argument happens
  to literally be a struct named the same as some OTHER struct's type
  parameter letter, which must still resolve correctly, not be misread as
  an open parameter. Deleting the fallback without independently verifying
  every such path is exactly the risk OVERHAUL_REMAINING_WORK.md's OVH-006
  entry flags without mandating removal ("if a NamedType still reaches it,
  that is a bug to fix at the source, not to classify by name" — read as
  "when it happens, fix it there," not "delete the safety net first and
  see what breaks"). Left in place, documented as defensive-only.
- **`self`'s declared type carries no type arguments of its own.** A
  struct method's implicit `self` parameter is a bare
  `TurfPointerType(NamedType(StructName))` (`ParserDecl.cpp`'s
  self-parameter construction) — never a `GenericType`. This is why the
  `Subst`-recovery `Scan` inside `visitFieldAccess()`/`visitMethodCall()`
  exists at all: there is nothing on `self`'s own type to unify against
  when checking a generic method's TEMPLATE body (only the struct's own,
  still-open type parameter, `TurfGenericParamType("T")`, which is exactly
  what should be seen there). This item does not change that shape — only
  makes the struct's *registered* field types agree with what
  `self.<field>` reads back as.
- **Re-verify `SEM-003`'s `fail_guess_uninstantiated_generic.tr` after any
  future change here.** `containsUninstantiatedGenericParam()`
  (`TypeCheckerDecl.cpp`) still depends on `isOrWrapsGenericParam()`'s
  behavior to reject `mut l = List::default();` — confirmed still correct
  (still `E066`, still "Nothing to infer!") after this fix, but this is
  exactly the kind of check a future session touching
  `isOrWrapsGenericParam()` again must re-run live, not assume.
- **A minimal repro of the STD-003 `Pool<T>.free_all()` shape needs
  `--allow-unsafe-modules`** if written outside `lib/std` (a file under the
  install root gets the raw-pointer capability unconditionally; any other
  file needs the flag or it fails on the *unrelated*, pre-existing
  raw-pointer-capability gate before ever reaching the bug this item
  fixes — cost real time to notice while writing this record's own repro).
