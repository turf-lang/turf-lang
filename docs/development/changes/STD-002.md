## Why

§15.6 of `ARCHITECTURE_OVERHAUL.md` named the standard library's real gap:
it had exactly two ways to report a problem (`sys::panic` with a bare
message and the STDLIB's OWN source line, or nothing), with no way to
attribute a runtime failure to its caller and no way for a `!T` failure to
carry any information beyond which variant occurred. Verified live before
this session: a failing `test::assert(1 == 2, "should never happen")`
printed only `"should never happen"` — no file, no line, nothing pointing
at which of possibly hundreds of test files actually failed. Three items
were in scope: (a) `@caller_location`, (b) instantiation-site error
reporting (already delivered by TYPE-002 per §15.6(b) — verified, not
rebuilt, see *Removed assumptions*), (c) a `message: string` payload on
error values.

Two genuine language-design forks came up mid-session and were put to the
user rather than decided unilaterally: how `@caller_location` should
propagate through a multi-hop call chain (single-hop-explicit-forwarding
vs. full Rust-`#[track_caller]`-style transitive propagation — the user
chose the latter, the bigger option), and whether to implement the error
payload at all given it required inventing a construction syntax (the user
chose yes, `ErrorType::Variant("msg")`).

## Language semantics

### Old behaviour

```turflang
fn fail(msg: string): void {
    sys::panic(msg);   // no file/line, ever
}

error MathError { DivisionByZero }
return MathError::DivisionByZero;        // fine
return MathError::DivisionByZero();      // ERROR: not callable, any arity
```

### New behaviour

```turflang
@caller_location
fn fail(msg: string): void {
    sys::panic(caller_location + ": " + msg);
}

error MathError { DivisionByZero }
return MathError::DivisionByZero;                          // unchanged, still fine
return MathError::DivisionByZero("division by zero at x");  // NEW: exactly one string arg
return MathError::DivisionByZero();                          // STILL an error (0 args)
return MathError::DivisionByZero("a", "b");                  // STILL an error (2+ args)

divide(10, 0) recover as err run {
    io::printline(err.message);   // NEW: "" for a bare variant, the attached string otherwise
};
```

`caller_location` (bare keyword, type `string`) is new syntax, legal only
inside a function declared `@caller_location`. `@` before `fn` is the first
(and only) legal decorator use in this language — every other `@word`
still gets the pre-existing "no decorator syntax" rejection.

### Is this breaking?

No new rejections for previously-valid programs. `ErrorType::Variant(...)`
was ALREADY rejected at every arity before this session; it is now accepted
at exactly one arity and still rejected at every other. `err`'s type
(`AnyErrorType`) gained its first-ever field (`.message`) — accessing any
OTHER field name on it is a new, clear rejection, but nothing could
previously access ANY field on `err` at all, so no program regresses.
`sys::panic`'s own printed message format is UNCHANGED (only
`test::assert`/`test::fail`'s messages gained a location prefix — see
*Removed assumptions* for why this was deliberately NOT extended to every
other `sys::panic()` call site in `lib/std`).

## Compiler architecture

Full pass-by-pass detail lives in the two new/updated architecture docs
this session wrote (see *Handbook impact*) rather than duplicated here.
Summary:

- **Lexer** — one new keyword, `TOK_CALLER_LOCATION`.
- **Parser** — `ParsePrimaryBase()`'s `TOK_AT` case (the sole legal `@`
  use); `ParseFuncDef()` gains a `HasCallerLocation` parameter; a new
  `CallerLocationExprAST` node for the bare-keyword read.
- **AST** — `FuncDefExprAST::HasCallerLocation` (deliberately NOT a
  `Params` entry); `ScopeAccessKind::ErrorVariantConstructWithMessage`
  (new).
- **Resolver** — `ResolverFunctionSymbol::HasCallerLocation` (populated,
  never validated — validation is TypeChecker's job entirely, mirroring the
  `unsafe {}` gate's own precedent); `visitFuncCall()`'s error-type branch
  now accepts exactly one arity as a real construction;
  `CollectReturnedErrorTypeNames()` updated to also recognize the new
  construction shape (a real bug found and fixed mid-session — see
  *Removed assumptions*).
- **TypeChecker** — `InCallerLocationFunc_` (mirrors `UnsafeDepth_`
  exactly); `visitCallerLocation()`; `visitFuncCall()`'s
  `ErrorVariantConstructWithMessage` short-circuit; `visitFieldAccess()`'s
  `AnyErrorType`/`.message` branch.
- **Codegen** — a `@caller_location` function's real LLVM signature gets
  one hidden trailing `i8*` parameter (never Turf-level-visible);
  `BuildCallerLocationValue()` is the entire forward-vs-stamp mechanism, in
  one function; the error-value runtime representation changed from a bare
  tag string to `TurfErrorValue{tag, message}` UNIFORMLY (bare and
  message-carrying variants alike) — see `errors_and_recover.md`'s own §2.8
  for the full "why not a discriminated union" reasoning.
- **Diagnostics** — new `CallerLocationOutsideMarkedFunctionError` (E084,
  `include/ErrorsFlow.h`/`ErrorCodes.h`).

## Removed assumptions

- **"§15.6(b)'s instantiation-site error reporting works as the roadmap
  prose describes."** Verified live rather than trusted: a generic function
  using an operation its concrete `T` doesn't support DOES produce a real
  compile error (confirmed: `fn<T> addThem(a: T, b: T): T { return a + b;
  }` called with a struct with no `operator+` fails cleanly) — but the
  diagnostic anchors at the GENERIC TEMPLATE's own line, not "the user's
  call site" §15.6(b)'s prose promises. This is not a gap STD-002
  introduces or is responsible for closing: `docs/development/changes/
  TYPE-002.md`'s own **D7** entry already discloses this exact scope
  decision ("the diagnostic must point at the instantiation site — is NOT
  met... fixing this properly needs a parent-request pointer on
  InstantiationRequest"). STD-002 consumes what TYPE-002 delivered, as its
  own §8 text says; it does not owe a fix for TYPE-002's own disclosed gap.
- **"`ErrorType::Variant(...)` never reaches Codegen at all."** A stale
  comment (`CodegenFunc.cpp`, pre-existing) said exactly this, correctly,
  for every arity before this session. Now false for exactly one arity —
  corrected in place alongside the new construction branch, not left for a
  future session to trip over.
- **"An error value's ENTIRE runtime representation is a bare tag string,
  an i8* like any other string."** True before this session, is the
  literal wording `errors_and_recover.md` §2.8 used, and is now false in
  general — every error value (bare or message-carrying) is now a pointer
  to a `TurfErrorValue{tag, message}` struct, uniformly. Every consumer of
  the OLD assumption was found and updated in the same session: equality
  (`GetErrorTagValue()`), the return-value construction dispatch
  (`IsErrorConstructionExpr()`), and the `NeverReturnsErrorWarning`
  structural scan (`CollectReturnedErrorTypeNames()` — see next entry).
  `errorPayload`'s own LLVM TYPE needed zero changes (still an opaque
  `i8*`/`ptr` either way) — only what it POINTS TO changed.
- **A real bug found and fixed mid-session, NOT anticipated by the original
  plan**: `CollectReturnedErrorTypeNames()` (the structural scan feeding
  `NeverReturnsErrorWarning`) only recognized a bare `ScopeAccessExprAST`
  return shape. A function that ONLY ever fails via the new
  `ErrorType::Variant("msg")` construction (never a bare reference) was
  wrongly flagged with `NeverReturnsErrorWarning` — confirmed live via a
  throwaway probe program before the fix, confirmed gone after. Fixed by
  also recognizing a returned `FuncCallExprAST` whose callee is a
  `ScopeAccessExprAST`, collecting `Left` the identical UNFILTERED way the
  bare branch already does (this scan runs during Pass 1 hoisting, before
  `ResolvedKind` is ever set — it can't yet tell an error-variant call
  apart from a struct constructor or module call by anything but shape;
  every consumer already re-filters through `isErrorTypeName()` later).
- **"Retrofitting `sys::panic()` itself with `@caller_location` is in
  scope."** Considered and deliberately rejected: `sys::panic()` is called
  from `mem.tr`, `net.tr`, `list.tr`, `map.tr`, `queue.tr`, `set.tr`,
  `stack.tr`, `strings.tr`, `http.tr`, `json.tr` — marking it (and changing
  its printed format) would be a much broader, riskier change than this
  group's own scope calls for. Instead, `test.tr`'s `fail()` builds the
  combined `"<loc>: <msg>"` string ITSELF and passes it to `sys::panic()`
  UNCHANGED — every other `sys::panic()` call site is completely
  unaffected. The mechanism (`@caller_location`) is fully general and ready
  for a future, broader sweep; this session's own scope is the one
  concretely-tested case, `test::assert`.

## Known pitfalls

- **`@caller_location`'s hidden parameter is intentionally invisible to
  `Params`.** A future session adding a NEW pass that iterates a function's
  "real" parameter list for some unrelated reason (a lint, a reflection
  API, …) will NOT see it there — by design. If that pass needs to know
  whether a function is caller-location-aware, it should read
  `FuncDefExprAST::hasCallerLocation()` / `ResolverFunctionSymbol::
  HasCallerLocation` directly, not infer it from `Params`.
- **Do not "simplify" the error-value representation back to a bare tag
  string for the message-less case "since it doesn't need a struct."** It
  was deliberately made uniform (see *Removed assumptions*) specifically so
  equality/`.message` never need to discriminate two runtime shapes. A
  discriminated union was considered and rejected — re-introducing one
  requires a real discriminant, not just "check if there's a NUL nearby."
- **`BuildCallerLocationValue()`'s forward branch trusts that
  `NamedValues["caller_location"]` is ALWAYS valid to read whenever it's
  present.** This is guaranteed by construction (TypeChecker's
  `InCallerLocationFunc_` gate ensures `CallerLocationExprAST` never even
  reaches Codegen unless the enclosing function is genuinely marked, and
  `FuncDefExprAST::codegen()` always populates the entry for a marked
  function before its body codegens) — but a future refactor of either
  side independently could silently break this coupling. If
  `caller_location` ever segfaults/reads garbage, check both halves stayed
  in sync.
- **The Resolver's new one-argument branch for error-type calls
  (`ResolverCall.cpp`) is checked BEFORE the unconditional "not callable"
  rejection, not instead of it.** A future session adding, say, a second
  legal arity must keep this ordering — the rejection path is still what
  every OTHER arity falls through to.
- **`err.message` is scoped to `AnyErrorType` only, deliberately NOT
  `TurfUserErrorType`.** Reading `.message` directly off a bare
  `ErrorType::Variant("msg")` construction (no `recover as err` involved)
  was considered and left out of scope — `err` inside `recover as err run`
  is the sole way a user gets a value to inspect today, matching the
  concrete example the roadmap/user approved. Extending this needs its own
  explicit decision, not a drive-by.
