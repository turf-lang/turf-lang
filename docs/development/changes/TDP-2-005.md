# LG-1, LG-2 — `List<int>::default()` and `f::<int>(...)`

| | |
|---|---|
| **Status** | landed |
| **Dates** | 2026-10-24 |
| **Commits** | (filled in at commit time) |
| **Sessions** | 1 of 1 |
| **Depends on** | TYPE-002's monomorphizer (`ConstructedType`, `GenericSubstitution`), `TypeWalk::unify()` |
| **Frozen decisions relied on** | F-GUESS-2 and F-GUESS-3 (`guess` is Model A, initializer-only; nothing here infers from a later statement), F-GEN-1/2 (one instance per type-argument list), F-6c (this is it) |

Issue #297.

## Why

A generic value could only be built where a declaration wrote its type
(`mut l: List<int> = List::default();`), and a generic function could only be
instantiated from its arguments or from a declared function type. `mut l =
List::default();` and `mut g = identity;` had nothing to infer from (E129,
E137), and the obvious spelling `List<int>::default()` parsed as `List < int`
(E110).

## Language semantics

- **LG-1.** After a name (or `module::Name`) in an expression, `<` begins a
  type-argument list when the list closes with `>` immediately followed by
  `::`. `Name<Args>::default()` and `Name<Args>::new(...)` build `Name<Args>`:
  the same instance, and the same IR, as the annotated declaration. Any other
  member after `Name<Args>::` is E148.
- **LG-2.** `::` followed by `<` writes a generic function's type arguments:
  `f::<int>(x)`, `module::f::<int>(x)`, and `f::<int>` as a value. One type per
  type parameter, in order; a size parameter is not written (an array argument
  or the target gives it, as before). The arguments must fit the written types
  with the usual implicit widening; nothing is inferred over them. A value with
  a declared function type too must agree with it (E066).
- E148 for the wrong number, for a function that is not generic, for a value,
  and for a bound method's call (`l.push::<int>(1)`).
- **LG-2 through UFCS** (owner decision, 2026-10-24). `x.f()` reaches a
  generic `f`: `tryUFCSFallback()` binds the type parameters from the written
  type arguments, then the receiver and the arguments (`TypeWalk::unify()`, as
  `visitFuncCall()` does), and matches the SUBSTITUTED parameters, the
  receiver exactly. The receiver is argument 1 for "Conflicting type
  arguments". The call is a FreeFunction instantiation request whose site is
  the `MethodCallExprAST`; `rewriteNewFuncCallSites()` points it at the clone.
  `x.f::<int>()` is E148 only when it resolves to a bound method. A generic
  struct's instance is a UFCS receiver as written (`Box<string>`), not as the
  bare struct `tryUFCSOnReceiver()` was handed; before, no function at all,
  generic or not, was reachable that way.

### Is this breaking?

No. Each new spelling was a syntax error: `x < y > ::z` (E103) and `f::<`
(E108), since `::` cannot begin an operand and must be followed by a name. One
2.0.0 test pinned the old rejection,
`tests/compat/2.0/01_syntax/fail_parse_error_generic_call_expression_hint.tr`,
and is listed in `tests/compat/2.0/RELAXED.txt`.

## Compiler architecture

- **Lexer** · a lookahead buffer: `peekToken(N)` lexes past `CurTok` without
  making the tokens current, and `getNextToken()` hands them out before calling
  `gettok()`. A buffered token carries everything `gettok()` sets. An import's
  parse saves and restores the buffer with the rest of the lexer state
  (`LexerStateGuard`), and `resetLexer()` empties it.
- **Parser** · `TypeArgsThenScopeAhead()` reads at most 64 type-shaped tokens
  from the `<` (an integer only after `[`) and answers whether the list closes
  with `>` then `::`. `ParseTypeArgList()` is the one parser of `<T1, ...>`,
  shared with type positions, so `>>`/`>=`/`>>=` split the same way.
  `ScopeAccessExprAST::LeftType` (LG-1) and `TypeArgs` on
  `VariableExprAST`/`ScopeAccessExprAST`/`MethodCallExprAST` (LG-2) are syntax
  and copied by `clone()`.
- **Resolver** · `resolveWrittenTypeArgs()` checks the written types with
  `validateNamedType()` (which rewrites spellings to identities) and makes a
  generic body's own parameters real, as for a declared type.
- **Monomorphizer** · `substituteTypesInBody()` substitutes the written types in
  a clone, so `List<T>::default()` and `identity::<T>(x)` in a generic body
  become concrete.
- **TypeChecker** · `visitFuncCall()` is `visitFuncCallImpl()` plus
  `applyWrittenConstructedType()`, which gives an LG-1 call the written type
  through `noteConstructed()` (the path a declaration's type takes). For LG-2,
  `writtenSubst()` binds the parameters before overload matching, which checks
  the substituted parameter types, and seeds the substitution the call records.
  `typeGenericFunctionValue()` builds the value's type from the written
  arguments when present.

Codegen is unchanged: it sees the same `ConstructedType` and instantiation the
annotated spellings produce.

## Runtime changes

None.

## Standard-library changes

None.

## New invariants

None frozen. Checked by `tests/56_use_site_type_arguments/`: the annotated and
written spellings of one program give the same IR at every `-O` level apart
from metadata (checked by hand for this record).

## Removed assumptions

- "The parser has one token of lookahead." It has as many as it asks for.
- "`<` after a name in an expression is always less-than" (the E110 hint). It
  is less-than unless `>` then `::` closes the list.

## Tests

`tests/56_use_site_type_arguments/`: the struct forms (plain, two arguments,
nested with `>>`, module-qualified, inside a generic body, as an operand), the
function forms (call, two arguments, widening, inside a generic body, value
with and without a declared type, as an argument, a size parameter from the
target), five shapes that stay comparisons, and seven `fail_*` tests for the
errors above. `tests/01_syntax/fail_parse_error_generic_call_expression_hint.tr`
is removed: it pinned the rejection LG-1 replaces. Through UFCS:
`04_ufcs_generic_function.tr` (inferred and written, two parameters, array,
generic-struct and reference receivers, inside a generic body, chained),
`05_ufcs_concrete_function_on_generic_struct.tr`, and four `fail_ufcs_*` tests
(wrong count, a function that is not generic, conflicting type arguments, a
written type that does not fit the receiver).

## Known pitfalls

- `obj.method::<T>(...)` is checked after resolution: through UFCS the written
  types bind the generic function's parameters; on a bound method they are
  E148, since a method of a generic struct takes its type arguments from the
  receiver. A `List<int>` value still does not reach `fn<T> f(l: &List<T>)`:
  the receiver matches exactly, and `&` is never added.
- A lexer error inside the lookahead window is reported when the token is
  lexed ahead, which is before the parser reaches it. Its text and location are
  the same.

# LG-7 — Hints that point at the written spellings

| | |
|---|---|
| **Status** | landed (compiler); the LSP half is with F-11 |
| **Dates** | 2026-10-24 |
| **Commits** | (filled in at commit time) |
| **Sessions** | 1 of 1 |
| **Depends on** | LG-1, LG-2 (above), TDP-2-001's compiler fixes |
| **Frozen decisions relied on** | none new |

Issue #298.

## Why

The spellings LG-1 and LG-2 add are only useful if the errors that need them
say so, and a beginner who writes `identity<int>(3)` should be shown the `::`.

## Language semantics

None. Diagnostics only.

- **E110** at `name<...>(`, when the list names a built-in type (`int`,
  `string`, ...): no operand can be one, so it is a generic function's type
  arguments without `::`. The fix inserts `::` after the name.
- **E129** at `mut b = Box::new(42);`: when the constructor's arguments bind
  every type parameter of the struct, that is the one candidate, and the fix
  writes it where the value is built (`Box<int>::new(42)`). With no candidate
  (`List::default()`) the hint shows both places a type argument goes and no
  fix is printed.
- **E137** at `mut g = identity;`: the hint shows `identity::<int>`.

## Compiler architecture

- **Parser** · `TypeArgListFollower()` generalises LG-1's lookahead: the token
  after a type-shaped list's `>`, and whether the list names a built-in type.
  `TypeArgsThenScopeAhead()` is that token being `::`.
- **TypeChecker** · `reportNothingToInferGeneric()` (`TypeCheckerDecl.cpp`)
  unifies the constructor's parameters with its argument types. The error
  handler forwards `DiagnosticHints::FixIts` and `FixReason` to the raised
  `TypeError`, which it did not before, so any type-checker raise site can carry
  a fix.

## Tests

`tests/55_compiler_fixes/`: `fail_fix_function_type_arguments_need_scope.tr`,
`fail_fix_struct_type_arguments_from_constructor.tr` (each pinned with
`EXPECT-FIX`) and `fail_fix_none_when_nothing_names_the_type_argument.tr` (no
fix). `slm_deterministic_fix_smoke.sh` passes.

## Known pitfalls

- `identity<Point>(p)` (a list of user types only) still parses as two
  comparisons and fails later as a type error: `Point` could be a variable.
- The E129 candidate needs every type parameter bound by an argument; a struct
  whose constructor leaves one unbound gets the hint only.

## LSP

Inlay hints for `guess`-inferred types belong to `turf-lsp`, which already
serves parameter-name inlay hints. The facade has what it needs:
`AnalysisResult::program()` reaches each `VarDeclExprAST`, and `typeOf()` gives
the inferred type. Roadmap LG-7 places the LSP half with F-11.
