Issue #297.

## Why

A generic value could only be built where a declaration wrote its type
(`mut l: List<int> = List::default();`), and a generic function could only be
instantiated from its arguments or from a declared function type. `mut l =
List::default();` and `mut g = identity;` had nothing to infer from (E129,
E137), and the obvious spelling `List<int>::default()` parsed as `List < int`
(E110).

## Language semantics

- **LG-1.** After a name (or `module::Name`) in an expression, `<` begins a
  type-argument list when the list closes with `>` immediately followed by
  `::`. `Name<Args>::default()` and `Name<Args>::new(...)` build `Name<Args>`:
  the same instance, and the same IR, as the annotated declaration. Any other
  member after `Name<Args>::` is E148.
- **LG-2.** `::` followed by `<` writes a generic function's type arguments:
  `f::<int>(x)`, `module::f::<int>(x)`, and `f::<int>` as a value. One type per
  type parameter, in order; a size parameter is not written (an array argument
  or the target gives it, as before). The arguments must fit the written types
  with the usual implicit widening; nothing is inferred over them. A value with
  a declared function type too must agree with it (E066).
- E148 for the wrong number, for a function that is not generic, for a value,
  and for a method call (`l.push::<int>(1)`).

### Is this breaking?

No. Each new spelling was a syntax error: `x < y > ::z` (E103) and `f::<`
(E108), since `::` cannot begin an operand and must be followed by a name. One
2.0.0 test pinned the old rejection,
`tests/compat/2.0/01_syntax/fail_parse_error_generic_call_expression_hint.tr`,
and is listed in `tests/compat/2.0/RELAXED.txt`.

## Compiler architecture

- **Lexer** · a lookahead buffer: `peekToken(N)` lexes past `CurTok` without
  making the tokens current, and `getNextToken()` hands them out before calling
  `gettok()`. A buffered token carries everything `gettok()` sets. An import's
  parse saves and restores the buffer with the rest of the lexer state
  (`LexerStateGuard`), and `resetLexer()` empties it.
- **Parser** · `TypeArgsThenScopeAhead()` reads at most 64 type-shaped tokens
  from the `<` (an integer only after `[`) and answers whether the list closes
  with `>` then `::`. `ParseTypeArgList()` is the one parser of `<T1, ...>`,
  shared with type positions, so `>>`/`>=`/`>>=` split the same way.
  `ScopeAccessExprAST::LeftType` (LG-1) and `TypeArgs` on
  `VariableExprAST`/`ScopeAccessExprAST`/`MethodCallExprAST` (LG-2) are syntax
  and copied by `clone()`.
- **Resolver** · `resolveWrittenTypeArgs()` checks the written types with
  `validateNamedType()` (which rewrites spellings to identities) and makes a
  generic body's own parameters real, as for a declared type.
- **Monomorphizer** · `substituteTypesInBody()` substitutes the written types in
  a clone, so `List<T>::default()` and `identity::<T>(x)` in a generic body
  become concrete.
- **TypeChecker** · `visitFuncCall()` is `visitFuncCallImpl()` plus
  `applyWrittenConstructedType()`, which gives an LG-1 call the written type
  through `noteConstructed()` (the path a declaration's type takes). For LG-2,
  `writtenSubst()` binds the parameters before overload matching, which checks
  the substituted parameter types, and seeds the substitution the call records.
  `typeGenericFunctionValue()` builds the value's type from the written
  arguments when present.

Codegen is unchanged: it sees the same `ConstructedType` and instantiation the
annotated spellings produce.

## Standard-library changes

None.

## New invariants

None frozen. Checked by `tests/56_use_site_type_arguments/`: the annotated and
written spellings of one program give the same IR at every `-O` level apart
from metadata (checked by hand for this record).

## Removed assumptions

- "The parser has one token of lookahead." It has as many as it asks for.
- "`<` after a name in an expression is always less-than" (the E110 hint). It
  is less-than unless `>` then `::` closes the list.

## Tests

`tests/56_use_site_type_arguments/`: the struct forms (plain, two arguments,
nested with `>>`, module-qualified, inside a generic body, as an operand), the
function forms (call, two arguments, widening, inside a generic body, value
with and without a declared type, as an argument, a size parameter from the
target), five shapes that stay comparisons, and seven `fail_*` tests for the
errors above. `tests/01_syntax/fail_parse_error_generic_call_expression_hint.tr`
is removed: it pinned the rejection LG-1 replaces.

## Known pitfalls

- `obj.method::<T>(...)` (LG-2's method form) parses and is E148. A method of a
  generic struct takes its type arguments from the receiver, and UFCS does not
  reach a generic free function today (`a.first(4)` with `fn<T> first(x: T, y:
  T)` is E056), so written ones have nothing to bind. When UFCS reaches generic
  functions, this is where they would be read.
- A lexer error inside the lookahead window is reported when the token is
  lexed ahead, which is before the parser reaches it. Its text and location are
  the same.
