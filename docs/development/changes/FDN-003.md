## Session sub-plan (written at session start, per ROADMAP §0.4 for an L item)

Baseline: `roadmap/update` @ `5fd1768`, `scripts/session_preflight.sh FDN-003`
clean, 798/798 tests.

Stage 1 decision — put to the owner as a question, answered 2026-09-27
"Roadmap design, stable typeof":

- A struct/enum/machine/error type is identified by *(owning module, name)*.
- Encoding: a type declared in an imported module `M` carries the internal
  name `M::Name`; a type declared in the main program file keeps its bare
  `Name`. DEC-13: the main file's module is `main`, never spelled.
- Spelling rules unchanged; the Resolver is the single spelling → identity
  step.
- `typeof()` and diagnostics print the identity — the same string wherever
  `typeof` is called. (The roadmap's recommendation was "qualified only when
  the type is not declared in the current file"; the owner chose the stable
  form, offered as the alternative, over it.)
- LLVM struct names, GC descriptor names, DWARF type names: `M.Name`.
- Cross-module `DuplicateTypeNameError` removed, same-module kept; a bare
  reference that could mean two visible types is an ambiguity error.

Stages as executed: (1) freeze entry + this record; (2) `TypeIdentity` and
resolved-identity marks; (3) Parser names declarations by module; (4)
Resolver: types first, declaration spellings in Pass 1, body spellings and
`Left::` in Pass 2, ambiguity error, registry keyed by identity; (5) Codegen
names; (6) tests, stdlib/showcase sweep, docs. All in one session.

## Why

Type identity was global by bare name (`modules_and_scope_resolution.md`
§2.6 before this change: *"two modules declaring the same struct name is a
genuine, permanent conflict regardless of import mode"*). Verified at the
baseline:

- A program with **no imports** could not declare `struct List`: the
  prelude's `strings` imports `list::List`. (Twice over, in fact — the Parser
  also rejected any bare `List` annotation by name, "Expected '<' after
  'list'".)
- `struct Parser` in any program importing `json` collided with `json`'s
  *internal* helper struct.
- Two unrelated modules each declaring `Point`
  (`tests/07_functions_modules/fail_duplicate_struct_across_modules.tr`) was
  a compile error.

With packages (LEC-001) and private types (LEC-002) that is unworkable: every
type name in every dependency, public or not, becomes reserved for the whole
program, and adding a struct to the stdlib in a minor release can break user
code. LEC-002 and LEC-001 both depend on this item (ROADMAP I.1).

## Language semantics

### Old behaviour

```turf
import json;
struct Parser { depth: int }   // error E034: A struct named 'Parser' is
                               // already declared. "struct/enum names are
                               // shared across your file and every module
                               // you import"
```

`typeof(x)` of any struct/enum was its bare name (`"JsonValue"`,
`"List<int>"`).

### New behaviour

```turf
import json;
struct Parser { depth: int }   // fine: this is `Parser`; json's is `json::Parser`

fn main(): int {
    mut p: Parser = Parser::default();
    mut v = json::parse("[1]") recover produce json::JsonValue::default();
    // typeof(p) == "Parser"          -- main-file type: bare
    // typeof(v) == "json::JsonValue" -- imported type: qualified
    return 0;
}
```

- Types belong to their declaring module. Two modules may each declare
  `Node`; the main file may declare its own too.
- Bare `Node` means the current file's/module's own type or one it
  on-demand-imported; if it could mean **both**, the use is rejected:
  `E085 AmbiguousTypeReferenceError`, naming both (no "local wins" — see
  FREEZE §6.11 for why). Two on-demand imports that bring in the same bare
  type name are rejected at the second import (`E024`, unchanged rule).
- `E034 DuplicateTypeNameError` now fires only for two declarations in the
  same file/module; its note says so.
- `typeof()` of a type declared in an imported module is qualified
  (`"list::List<string>"`, `"json::JsonValue"`); of a main-file type, bare.
- A generic struct named without type arguments in a type annotation
  (`mut b: Box = ...`) is a compile error ("Missing type arguments!",
  `TypeError`/E066) — previously an ICE for every generic except `List`,
  which the Parser special-cased by name (see *Removed assumptions*).

### Is this breaking?

Yes, narrowly (ROADMAP Part V row 12):

- **`typeof()` of an imported type** now carries its module. Code comparing
  `typeof(x) == "List<int>"` must say `"list::List<int>"`. No test, stdlib
  or showcase file did (all swept).
- **Programs that relied on the old E034** to reject a cross-module name
  now compile. Mechanical: nothing to do.
- **A file that declares `Node` AND on-demand-imports a `Node`** was
  already an error (E034); it is still an error, now E085 at each bare use
  instead of at the declaration.

## Compiler architecture

- **Types** (`include/Types.h`) — `namespace TypeIdentity`: `make()`,
  `owningModule()`, `bareName()`, `isModuleQualified()`, `llvmName()`. The
  identity is deliberately a *string* (`M::Name`, or bare for main) rather
  than a (module, name) struct: every name-keyed table in the compiler —
  the Resolver registry, `GlobalSymbolTable`, `LLVMTypeCache`, the
  `"Struct.method"` function keys, monomorphized clone names — became
  module-aware without changing its key type. `NamedType::resolveTo()` /
  `GenericType::resolveBaseTo()` rewrite a spelling to its identity in place
  and set a `Resolved` mark; `GenericType::withTypeArgs()` is now the one
  way to rebuild a GenericType (keeps the mark); `makeResolvedNamedType()`
  for types synthesized after resolution.
- **Parser** — `CurrentParseModule()` (`ParserModule.cpp`, the top
  `ImportStack` frame). `ParseStructDecl`/`ParseEnumDecl`/`ParseMachineDecl`/
  `ParseErrorDecl` name the node and register the type under
  `TypeIdentity::make(CurrentParseModule(), Name)`. The two best-effort
  "`X { ... }` is no longer valid syntax" hints look up the identity. The
  hardcoded bare-`List` parse error is deleted.
- **AST** — `ScopeAccessExprAST::resolveLeftTypeTo()` + `isLeftTypeIdentity()`
  (copied by `clone()`).
- **Resolver** — new `src/ResolverTypeIdentity.cpp`. `resolveAll()`'s Pass 1
  is now three steps: **1a** `hoistTypes()` registers every type declaration
  in every module under its identity, plus the type half of on-demand
  imports (`registerOnDemandTypeImports()`); **1b**
  `resolveDeclarationSpellings()` resolves, silently and in place, every
  declaration-level spelling — struct fields, function/extern signatures,
  and a method's receiver (`fn Pt.twice()` becomes `pt_module::Pt.twice`
  when `Pt` is an imported struct — a visibility lookup, since extension
  methods on imported structs are legal); **then** the old
  `hoistTopLevel()`/`hoistModuleBody()` (functions, externs, constants,
  imports — their type branches removed). Pass 2: `validateNamedType()`
  resolves as it validates (and a silent full walk catches positions it
  never descended into — `T**`, `!T`); `visitCast`/`visitSizeOf`/
  `visitArrayDecl` resolve silently (never validated before, still not);
  `resolveScopeLeftType()` handles the `Left` of every `Left::Right`
  (construction, static calls, enum/error variants) in `visitFuncCall`/
  `visitScopeAccess`. `buildFunctionSymbol()` maps the error-type names it
  collects from a body to identities. `GenericStructIdentities_` backs the
  "Missing type arguments!" check (`self` exempt).
- **Symbol tables** — `ResolverTypeRegistry` keyed by identity, with an
  always-on key check (`checkIdentityKey()`, INV-TYPE-3);
  `isKnownTypeIdentity()`, `identitiesWithBareName()`;
  `getModuleTypeNames()` now returns bare names.
  `ResolverSymbolTable::unqualifiedTypeCandidates()` (own + on-demand) and an
  identity-based `isTypeVisibleUnqualified()`;
  `ResolverModuleTable::lookupFlatTypeImport()`.
- **TypeChecker** — `Type::default()` and `Err::Variant(msg)` results are
  `makeResolvedNamedType`; Struct-kind instantiation requests record
  `TypeIdentity::owningModule()` of the resolved base instead of the use
  site's spelled qualifier.
- **Monomorphizer** — a clone's `self` GenericType is marked resolved; the
  struct-template registry comment rewritten (it is keyed by identity now,
  for free). `TypeWalk::substitute()` never substitutes a resolved NamedType
  (a real type is never a type parameter).
- **Codegen** — LLVM struct creation (three sites) and DWARF type names use
  `TypeIdentity::llvmName()`; GC descriptors inherit it from the LLVM name.
  Function symbols keep the identity verbatim
  (`turf_json_json::Parser.parse_...`) — legal in LLVM/ELF, collision-free.
- **Diagnostics** — `AmbiguousTypeReferenceError` (E085, DECLARATION —
  no new category); `DuplicateTypeNameError`'s note and doc comment
  narrowed; `docs/errors/codes/E085.txt` added, E034's human and SLM docs and
  four SLM grounding files corrected (they taught the old rule).

## New invariants

**INV-TYPE-3** — type identity is (module, name), keyed as
`TypeIdentity::make()`; a spelling becomes an identity only in the Resolver.
Enforced by `ResolverTypeRegistry::checkIdentityKey()` (always on).
Demonstrated: forcing `ParseStructDecl()` back to bare naming aborts the
first import of `list` with the INV-TYPE-3 internal error. See
`INVARIANTS.md` for its honest scope (the Resolver registry is checked;
`GlobalSymbolTable`/`LLVMTypeCache` agree by construction).

Deviation from the roadmap's wording, deliberate: FDN-003's completion line
says INV-TYPE-3 is "enforced by the registry's key type", and stage 2
suggested a display-only bare-name accessor guarded by a debug assertion.
Implemented instead as a *checked string key* — every registration verifies
the key is `TypeIdentity::make(module, name)` — with `TypeIdentity::bareName()`
documented as display-only (no assertion). A distinct C++ key type would have
had to thread through `GlobalSymbolTable`, `LLVMTypeCache`, the function-name
keys and the monomorphizer, none of which the registry owns; the string
encoding made all of them module-aware at once, and the check fires on the
exact failure the key type would have prevented at compile time (demonstrated
above). A debug-only assertion would not run in the release build the suite
uses.

## Removed assumptions

- **"A type's `getName()` is how the programmer spelled it."** It is the
  identity (`json::Parser`) everywhere after the Resolver — the TypeChecker,
  Monomorphizer and Codegen never see a module type's spelling. Code that
  builds a user-facing message from `getName()` shows `json::Parser`; if a
  message must show the spelling, `TypeIdentity::bareName()` it (the
  Resolver's own errors do).
- **"Type names are globally unique, so a bare-name key loses nothing."**
  Stated as the reason for bare keys in at least four places (Monomorphize's
  struct registry, `instantiatedDeclName()`'s doc, the registry header,
  `DuplicateTypeNameError`'s doc) — all rewritten.
- **"A Struct-kind instantiation request's `SourceModule` is the use site's
  spelled qualifier."** It is now the declaring module; `list::List<int>`
  and bare `List<int>` are one cache entry, not two.
- **"The parser rejects bare `List`."** A hardcoded
  `BaseName == "List"` parse error ("Expected '<' after 'list'") is gone. It
  existed only for that one spelling — `mut b: Box = Box::default();` for a
  user generic crashed the compiler ("generated LLVM IR is invalid:
  Cannot allocate unsized type") — and it made a user's own non-generic
  `struct List` unusable. Replaced by the Resolver's general "Missing type
  arguments!" rule (`fail_type_identity_generic_without_type_args.tr`,
  `fail_type_identity_stdlib_list_without_type_args.tr`).
- **"Every type declaration is hoisted alongside function signatures."**
  Types are hoisted first (1a) and declaration spellings resolved (1b)
  before any signature is captured; `hoistTopLevel()`/`hoistModuleBody()`
  no longer touch type declarations.
- **"Pass 2 is the first time a field type is looked at by name."** The
  layout cycle check (Pass 1) compares field types by name — which is why
  1b must run before it. Proven by
  `fail_type_identity_layout_cycle_inside_imported_file.tr`: without 1b a
  cycle declared inside a module would be keyed `Q` vs `cyc::Q`, miss, and
  reach Codegen.

## Known pitfalls

- **Never key anything by a spelling.** The whole design rests on "names
  that reach a table are identities". A new pass that reads a type NAME from
  source (a new `Type::thing` expression form, a new annotation position)
  must resolve it in the Resolver — through `validateNamedType()`,
  `resolveTypeSpellingsSilently()` or `resolveScopeLeftType()` — or it will
  silently work for main-file types (identity == spelling) and fail only
  for module types. Test new type-name positions with a MODULE-owned type.
- **A main-file type's identity is indistinguishable from a spelling by
  text.** That is what the `Resolved` marks are for. A type synthesized
  after the Resolver (`std::make_shared<NamedType>(...)`) should be
  `makeResolvedNamedType()`; a GenericType rebuilt from another must go
  through `withTypeArgs()`.
- **Clone resolution.** `resolveMonomorphizedClone()` re-resolves a clone in
  its template's module. A bare, unmarked name there is left alone (it can
  only be a type argument substituted in from the call site). No current
  path delivers such a name into a *module's* clone — the suite hits the
  rule only in main-file clones, where it is harmless — and
  `type_identity_generic_arg_shadows_module_type.tr` passes with the rule
  removed, because every type it substitutes arrives already marked. The
  rule is a guard for a future path that forgets a mark, not a tested
  behaviour.
- **`_module.tr` in a test name.** Two of this session's own tests were
  first named `..._same_module.tr` / `..._in_module.tr` and would have been
  silently skipped by the runner (AGENTS.md's trap); renamed before landing.
- **Rebuilding while a background suite runs** invalidates that run — this
  session did it once and re-ran.

## Unresolved questions

- **Pre-existing gaps found this session — fixed in follow-up commits
  the same day, at the owner's request** (each has its own regression
  test; see each commit message for the mechanism):
  1. An instance method with no type parameters on a generic struct
     (`fn List.extra()` on the imported `list::List`, or `fn Box.count()`
     in `Box`'s own file) crashed at its first call during
     monomorphization. Now rejected at the declaration, "Missing type
     parameters!", with the `fn<T> ...` fix in the hint — not inferred
     (`5b5742a`).
  2. Two functions in one file each declaring a local `struct P` shared
     one layout (and a local `P` could replace a top-level one). Now E034,
     consistent with §6.11's (module, name) identity (`cb8eeba`). Found
     alongside it and fixed: a local struct inside a GENERIC function
     crashed the compiler (registered into the function's temporary
     type-parameter scope — `7e3ec4f`), and a local `enum`/`machine`/
     `error` type was never registered at all (`d0bad34`).
  3. Under `-g`, a local initialized by `T::new`/`T::default()` had no
     DWARF variable, and any struct-typed local had an unspecified debug
     type; both fixed (`bf48e80`), and `debuginfo_smoke.sh` check 4 now
     asserts gdb prints such a local field by field.
  Still open, by design rather than as a bug: a local struct whose fields
  use the enclosing generic function's own `T` is rejected ("Unknown type
  'T'") — it would need a per-instantiation layout of its own.
- **Method subprogram names** in DWARF and function symbols keep the
  identity verbatim (`json::Parser.parse`), unlike type names (`json.Parser`).
  The approved decision covered type names; if the owner wants one spelling
  everywhere, it is a two-line change in `FuncDefExprAST::codegen()`'s
  mangling plus `ResolverFunctionSymbol::mangledName()` (both must agree).
- **`main::Name` as a spelling.** DEC-13 names the main module `main` but it
  can't be written — a module can't reach a main-file type anyway, and the
  main file itself uses bare names. LEC-001 (packages) should decide whether
  the main module's name becomes the package name.
