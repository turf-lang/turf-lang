## Stage 1 — release-shaped CI on every push

### Why
Until now the release was built only when a `v*` tag was pushed
(`release.yml`), and `test.yml` is Linux-only. Four dry-run tags in REL-003
found a build break on three of four platforms, a publish job that could not
find a script, and a missing Scoop manifest, all on release day. Stage 1 moves
that discovery to the commit that causes it, and adds the check that says
whether an archive is self-contained.

### What changed
- **`scripts/release_deps_check.sh`** (new): unpacks an archive and reads each
  `bin/` file's direct dependencies (`readelf -d`, `otool -L`, `objdump -p`;
  nothing is executed) against a per-platform allowlist of libraries the OS
  provides. Windows also reports any DLL bundled in `bin/`. An unreadable
  dependency list on Windows or macOS is a failure, never a pass.
- **`.github/workflows/build-archives.yml`** (the four release jobs, moved
  out of `release.yml`, now `on: workflow_call`), each ending with the
  dependency check. `release.yml` (tag: calls it, then publishes) and
  **`release-shaped-ci.yml`** (push/PR on master, dev, refactor/architecture,
  and manual dispatch: calls it, publishes nothing) share it, so CI cannot
  drift from the release.
- **`.github/actions/package-release`** passes `--expect-tag` only when the
  run is a tag (`GITHUB_REF_TYPE`); a branch run packages whatever `VERSION`
  says.

### Decisions to confirm (not in the roadmap text)
- **Enforcement.** The roadmap says the check fails today by design. The
  push CI therefore *enforces* it (red on all four platforms until stage 4),
  and the tag release runs it in *report* mode (`allowlist: report` in
  `release.yml`), so a publishing dry run is still possible. Flip `release.yml`
  to `enforce` when stage 4 lands. If a permanently red push CI is unwanted in
  the meantime, set `release-shaped-ci.yml` to `report`.
- **macOS allowlist** is `libSystem` **plus `libc++`/`libc++abi`** (the roadmap
  says libSystem only). Both ship with macOS, so statically linking an
  equivalent is not needed. One line each in `allowed()` to remove.
- **Windows allowlist** adds `ws2_32` (the `net` port, DEC-15) and `advapi32`,
  `kernelbase`, `ntdll` to the roadmap's `KERNEL32` and `UCRT`/`api-ms-win-*`.
  `msvcrt.dll` is not allowed: the release's MINGW64 MSYS2 environment links
  it, and the target is UCRT. Expect that to show up in the first Windows report.
- **Cost.** The jobs are the release's own, so each push builds with
  `--smart` ON (llama.cpp) on four runners. Stage 2 turns that off for the
  release configuration.

### Tests
- Run here: the script against this machine's real `turf-v2.0.0-dev-linux-x86_64.tar.gz`
  (exit 1: `libLLVM.so.22.1`, `libgomp.so.1`, `libstdc++.so.6`, `libgcc_s.so.1`
  not allowed; `libc`, `libm` ok; `turf` has no dynamic dependencies), against
  a control archive of binaries that need only libc (exit 0), and for Windows
  against a MinGW-built UCRT zip (exit 0) and the same zip with a DLL added
  (the bundled DLL reported, exit 1).
- **First real run (PR #262, run 37621789716).** Build, package, smoke and
  upload were green on all four platforms; the reusable-workflow call, the
  branch-run packaging (no tag check) and the MSYS2 step's archive path all
  worked. Only the dependency check was red, as designed. What it found:
  - **Linux (both):** `turf` is static; `turfc` needs `libLLVM.so.22.1`,
    `libgomp`, `libstdc++`, `libgcc_s` (libc and libm are fine).
  - **macOS:** `turfc` needs Homebrew's `libLLVM.dylib` (an absolute
    `/opt/homebrew/...` path, so the archive does not run on any other Mac) and
    the Accelerate, Metal, MetalKit, Foundation, CoreFoundation and `libobjc`
    frameworks, which are llama.cpp's (`--smart`; stage 2 turns it off).
  - **Windows:** `turfc.exe` needs `libLLVM-22.dll`, `libstdc++-6.dll`,
    `libgcc_s_seh-1.dll`, `libwinpthread-1.dll` and, as predicted, `msvcrt.dll`;
    ten DLLs are bundled in `bin/` (LLVM and its zlib/zstd/xml2/ffi/iconv chain).
  - **Two defects in the check, fixed after the run:** (1) GNU `objdump` cannot
    read the imports of a Go-built PE, so `turf.exe` was reported "could not be
    read" (the fail-closed rule worked); the Windows branch now uses
    `llvm-readobj --coff-imports` (present in the MSYS2 LLVM package), falling
    back to `objdump`; (2) `libresolv.9.dylib` (Go's `net` on darwin, in
    `turf`) was missing from the macOS allowlist, and `ole32`, `shell32` and
    `bcrypt` from the Windows one (a static LLVM still imports them; `version`
    and `psapi` were added for the same reason without being seen yet).
  - The fixed script was re-run here on the real Windows zip downloaded from
    CI: `turf.exe` now passes and the report lists only the items above. The
    fixed macOS allowlist is not re-run (no Mac); the change is one `case` line.

### Known pitfalls
- Nothing guards the allowlist against being widened to silence a stage's work;
  the header comment and `AGENTS.md` say not to.
- Linux archives are not checked for the glibc version they require, only the
  library names. A `turfc` built on `ubuntu-latest` may need a newer glibc than
  an older distribution has; stage 4's musl runtime and static link address it.

## Stage 2 — self-contained `turfc`

### Why
Stage 1's report said it: `turfc` needed LLVM, libstdc++, libgcc_s, libgomp
(Linux), Homebrew's `libLLVM.dylib` and the llama.cpp frameworks (macOS), and
LLVM plus the MinGW runtime as ten bundled DLLs (Windows). A user without that
exact set could not run it.

### What changed
- **`-DTURF_RELEASE_STATIC=ON`** (`CMakeLists.txt`; `scripts/cmake_build.sh
  --release-static` sets it with Release and `TURF_SMART=OFF`). It implies
  `TURF_STATIC_LLVM` (which already existed, for `turf-lsp`) and goes further:
  - **every LLVM target** is linked (`AllTargets*`), because `main.cpp` calls
    `InitializeAll*()` and `--target=aarch64-...` must keep producing a real
    object (`cross_target_smoke.sh`). `native` alone would have silently broken
    that. This is why the binary is large (below);
  - **`LLVMSupport`'s system-library list is replaced.** LLVM's exported
    interface carries what the machine that built LLVM linked it with; on
    Ubuntu that is `libz3.so` and a *shared* zlib and zstd, so a plain static
    link still needed them. We keep its LLVM entries and link static
    `libz.a`/`libzstd.a`/`libtinfo.a` (Linux), the same plus the Windows system
    libraries (Windows), or system `libz` and `curses` with a static `libzstd.a`
    (macOS, which has no static zlib in the SDK);
  - **static C++ runtime**: `-static-libstdc++ -static-libgcc` (Linux), `-static`
    (MinGW, which also removes `libwinpthread`); macOS links the system's libc++;
  - **configuration fails** (not a silent fallback) if `TURF_SMART=ON`, if an
    LLVM component is not a static library (Arch's LLVM ships none), or if a
    static archive is missing.
- **`build-archives.yml`**: all jobs build with `--release-static`; the
  llama.cpp submodule, its cache and OpenMP are gone from them; Ubuntu installs
  `zlib1g-dev libzstd-dev libncurses-dev` on every run (not covered by the LLVM
  cache), macOS `zstd`, MSYS2 `zlib zstd`. The Windows "collect the MinGW DLLs"
  step and `bin-extra` are removed: if a DLL comes back the check names it,
  where bundling it would have hidden it.
- **The Arch job is removed (decision for the owner).** It existed only because
  the Ubuntu archive's shared LLVM could not load on Arch; `install.sh` never
  selected it; Arch's LLVM has no static libraries so it could not be made
  self-contained. Revert is one `git show` of the old job.
- `release_deps_check.sh`: macOS allows `libz.1.dylib` and `libncurses.5.4.dylib`
  (what the static link uses there).
- `scripts/cross_target_smoke.sh` honours `TURFC=` (it hard-coded `build/turfc`),
  which is how it was run against this build.

### Tests (Linux, this machine)
This machine has no static LLVM (Arch), so the exact CI inputs were reproduced:
Ubuntu noble's `llvm-22-dev` 22.1.8 from apt.llvm.org plus its `zlib1g-dev`,
`libzstd-dev` and `libncurses-dev`, unpacked into a scratch directory.
- Configure, build and link first time on the second CMake revision (the first
  linked only the named components, not their transitive closure, and was
  replaced before building).
- `readelf -d turfc`: `NEEDED` is `libm.so.6`, `libc.so.6`, the loader. Nothing else.
- **The full suite with that static `turfc`: 1157/1157** (default level).
- `cross_target_smoke.sh` against it: all checks, including the real AArch64 object.
- Packaged with `package_release.sh` and checked: **`release_deps_check.sh` PASSES**
  on the Linux archive, and **`release_smoke.sh --archive` passes** on it.
- Size: 149 MB as linked, 131 MB stripped, **40 MB gzipped**. Not stripped in the
  build (a later choice; a smaller target list is the larger lever).
- Not run: `-O0`/GC-stress suites, the macOS and Windows configurations (no host
  here: the zlib/zstd/curses choices, `-static` on MinGW, `uuid`/`version` in the
  Windows list and MSYS2's LLVM exporting static component targets are all
  unproven until CI), and the dev (dylib) build was only reconfigured.

### Known pitfalls
- **No `--smart` in release archives** until REL-003's `--smart` row is decided.
  `turfc --smart` in a release build runs without the model (it was built
  with `SLMEngineDisabled.cpp`); the README says so.
- The compiled *programs* still link through the system `cc` and glibc (stages
  3 and 4); `release_smoke.sh` still leaves `cc` on PATH.
- A static glibc-linked `turfc` still needs a glibc at least as new as the build
  machine's for the symbols it uses (Ubuntu's CI image); a much older distribution
  may refuse it. Stage 4's musl runtime is the fix, not this stage.
- All LLVM targets make the binary ~130 MB. Restricting to X86, AArch64 would
  cut it a lot but needs `main.cpp` to initialize only those and `--target` to
  say which are supported; not done.

### Stage 2, first CI run (PR #262, run 37626186191)
- **Linux and macOS: green, and the stage 1 check PASSES on both.** Linux
  `turfc` needs libm, libc and the loader only. macOS `turfc` needs
  `libSystem`, `libc++`, `libz` and `libncurses` (all on the allowlist); `turf`
  needs `libSystem` and `libresolv`. The macOS install smoke (`turf new` /
  `run` / `build`, uninstall) ran against the static compiler and passed. The
  Linux build took 3.5 minutes and macOS 1.3, down from 6 and 2 (no llama.cpp).
- **Windows: failed at link**, not at configure (MSYS2's LLVM exports static
  component targets, and `libz.a`/`libzstd.a` were found). `ld` reported
  `multiple definition of std::__detail::_AnyMatcher<...>::operator()::__nul`
  and its guard variable, from `libLLVMMipsCodeGen.a` against `libstdc++.a`,
  and `duplicate section ... has different size` inside `libstdc++.a` itself.
  `turf-api-tests.exe` failed the same way, so the fix is on `turfcore`.
- **Reproduced locally** without a Windows machine: MSYS2's
  `mingw-w64-x86_64-llvm-22.1.8-3`, `zlib` and `zstd` unpacked, and a MinGW
  GCC 16.2.0 cross compiler (the same version CI has) building `turfc` against
  them. 20 messages, as on CI.
- **Fix:** `-Wl,--allow-multiple-definition` on `turfcore` for Windows release
  links (the clash is one inline std::regex static, defined by two objects from
  the same header, so the first definition is the right one; the cost is that
  `ld` stops reporting a genuine duplicate in these links), plus `-s` on
  `turfc.exe` (216 MB to 134 MB). Through CMake, `turfc.exe` and
  `turf-api-tests.exe` both link. `turfc.exe` imports only `KERNEL32`,
  `ADVAPI32`, `ole32`, `SHELL32`, `ntdll` and the C runtime's `api-ms-win-crt-*`;
  no libstdc++, winpthread or LLVM DLL. (The local cross compiler is UCRT, so
  this shows `api-ms-win-crt-*`; **the CI MINGW64 toolchain will show
  `msvcrt.dll`, which the check rejects until stage 4**.)
- **Not proven:** that this `turfc.exe` *runs* (no Windows, no wine here). CI
  now unpacks the zip and runs `turfc.exe --version` (required), and compiles and
  runs hello (informational: the Windows port is stage 5).
