## Stage 1 — release-shaped CI on every push

### Why
Until now the release was built only when a `v*` tag was pushed
(`release.yml`), and `test.yml` is Linux-only. Four dry-run tags in REL-003
found a build break on three of four platforms, a publish job that could not
find a script, and a missing Scoop manifest, all on release day. Stage 1 moves
that discovery to the commit that causes it, and adds the check that says
whether an archive is self-contained.

### What changed
- **`scripts/release_deps_check.sh`** (new): unpacks an archive and reads each
  `bin/` file's direct dependencies (`readelf -d`, `otool -L`, `objdump -p`;
  nothing is executed) against a per-platform allowlist of libraries the OS
  provides. Windows also reports any DLL bundled in `bin/`. An unreadable
  dependency list on Windows or macOS is a failure, never a pass.
- **`.github/workflows/build-archives.yml`** (the four release jobs, moved
  out of `release.yml`, now `on: workflow_call`), each ending with the
  dependency check. `release.yml` (tag: calls it, then publishes) and
  **`release-shaped-ci.yml`** (push/PR on master, dev, refactor/architecture,
  and manual dispatch: calls it, publishes nothing) share it, so CI cannot
  drift from the release.
- **`.github/actions/package-release`** passes `--expect-tag` only when the
  run is a tag (`GITHUB_REF_TYPE`); a branch run packages whatever `VERSION`
  says.

### Decisions to confirm (not in the roadmap text)
- **Enforcement.** The roadmap says the check fails today by design. The
  push CI therefore *enforces* it (red on all four platforms until stage 4),
  and the tag release runs it in *report* mode (`allowlist: report` in
  `release.yml`), so a publishing dry run is still possible. Flip `release.yml`
  to `enforce` when stage 4 lands. If a permanently red push CI is unwanted in
  the meantime, set `release-shaped-ci.yml` to `report`.
- **macOS allowlist** is `libSystem` **plus `libc++`/`libc++abi`** (the roadmap
  says libSystem only). Both ship with macOS, so statically linking an
  equivalent is not needed. One line each in `allowed()` to remove.
- **Windows allowlist** adds `ws2_32` (the `net` port, DEC-15) and `advapi32`,
  `kernelbase`, `ntdll` to the roadmap's `KERNEL32` and `UCRT`/`api-ms-win-*`.
  `msvcrt.dll` is not allowed: the release's MINGW64 MSYS2 environment links
  it, and the target is UCRT. Expect that to show up in the first Windows report.
- **Cost.** The jobs are the release's own, so each push builds with
  `--smart` ON (llama.cpp) on four runners. Stage 2 turns that off for the
  release configuration.

### Tests
- Run here: the script against this machine's real `turf-v2.0.0-dev-linux-x86_64.tar.gz`
  (exit 1: `libLLVM.so.22.1`, `libgomp.so.1`, `libstdc++.so.6`, `libgcc_s.so.1`
  not allowed; `libc`, `libm` ok; `turf` has no dynamic dependencies), against
  a control archive of binaries that need only libc (exit 0), and for Windows
  against a MinGW-built UCRT zip (exit 0) and the same zip with a DLL added
  (the bundled DLL reported, exit 1).
- **First real run (PR #262, run 37621789716).** Build, package, smoke and
  upload were green on all four platforms; the reusable-workflow call, the
  branch-run packaging (no tag check) and the MSYS2 step's archive path all
  worked. Only the dependency check was red, as designed. What it found:
  - **Linux (both):** `turf` is static; `turfc` needs `libLLVM.so.22.1`,
    `libgomp`, `libstdc++`, `libgcc_s` (libc and libm are fine).
  - **macOS:** `turfc` needs Homebrew's `libLLVM.dylib` (an absolute
    `/opt/homebrew/...` path, so the archive does not run on any other Mac) and

  - **Windows:** `turfc.exe` needs `libLLVM-22.dll`, `libstdc++-6.dll`,
    `libgcc_s_seh-1.dll`, `libwinpthread-1.dll` and, as predicted, `msvcrt.dll`;
    ten DLLs are bundled in `bin/` (LLVM and its zlib/zstd/xml2/ffi/iconv chain).
  - **Two defects in the check, fixed after the run:** (1) GNU `objdump` cannot
    read the imports of a Go-built PE, so `turf.exe` was reported "could not be

    `bcrypt` from the Windows one (a static LLVM still imports them; `version`
    and `psapi` were added for the same reason without being seen yet).
  - The fixed script was re-run here on the real Windows zip downloaded from
    CI: `turf.exe` now passes and the report lists only the items above. The
    fixed macOS allowlist is not re-run (no Mac); the change is one `case` line.

### Known pitfalls
- Nothing guards the allowlist against being widened to silence a stage's work;
  the header comment and `AGENTS.md` say not to.
- Linux archives are not checked for the glibc version they require, only the
  library names. A `turfc` built on `ubuntu-latest` may need a newer glibc than
  an older distribution has; stage 4's musl runtime and static link address it.

## Stage 2 — self-contained `turfc`

### Why
Stage 1's report said it: `turfc` needed LLVM, libstdc++, libgcc_s, libgomp
(Linux), Homebrew's `libLLVM.dylib` and the llama.cpp frameworks (macOS), and
LLVM plus the MinGW runtime as ten bundled DLLs (Windows). A user without that
exact set could not run it.

### What changed
- **`-DTURF_RELEASE_STATIC=ON`** (`CMakeLists.txt`; `scripts/cmake_build.sh
  --release-static` sets it with Release and `TURF_SMART=OFF`). It implies
  `TURF_STATIC_LLVM` (which already existed, for `turf-lsp`) and goes further:
  - **every LLVM target** is linked (`AllTargets*`), because `main.cpp` calls
    `InitializeAll*()` and `--target=aarch64-...` must keep producing a real
    object (`cross_target_smoke.sh`). `native` alone would have silently broken
    that. This is why the binary is large (below);
  - **`LLVMSupport`'s system-library list is replaced.** LLVM's exported
    interface carries what the machine that built LLVM linked it with; on
    Ubuntu that is `libz3.so` and a *shared* zlib and zstd, so a plain static
    link still needed them. We keep its LLVM entries and link static
    `libz.a`/`libzstd.a`/`libtinfo.a` (Linux), the same plus the Windows system
    libraries (Windows), or system `libz` and `curses` with a static `libzstd.a`
    (macOS, which has no static zlib in the SDK);
  - **static C++ runtime**: `-static-libstdc++ -static-libgcc` (Linux), `-static`
    (MinGW, which also removes `libwinpthread`); macOS links the system's libc++;
  - **configuration fails** (not a silent fallback) if `TURF_SMART=ON`, if an
    LLVM component is not a static library (Arch's LLVM ships none), or if a
    static archive is missing.
- **`build-archives.yml`**: all jobs build with `--release-static`; the
  llama.cpp submodule, its cache and OpenMP are gone from them; Ubuntu installs
  `zlib1g-dev libzstd-dev libncurses-dev` on every run (not covered by the LLVM
  cache), macOS `zstd`, MSYS2 `zlib zstd`. The Windows "collect the MinGW DLLs"
  step and `bin-extra` are removed: if a DLL comes back the check names it,
  where bundling it would have hidden it.
- **The Arch job is removed (decision for the owner).** It existed only because
  the Ubuntu archive's shared LLVM could not load on Arch; `install.sh` never
  selected it; Arch's LLVM has no static libraries so it could not be made
  self-contained. Revert is one `git show` of the old job.
- `release_deps_check.sh`: macOS allows `libz.1.dylib` and `libncurses.5.4.dylib`
  (what the static link uses there).
- `scripts/cross_target_smoke.sh` honours `TURFC=` (it hard-coded `build/turfc`),
  which is how it was run against this build.

### Known pitfalls
- **No `--smart` in release archives** until REL-003's `--smart` row is decided.
  `turfc --smart` in a release build runs without the model (it was built
  with `SLMEngineDisabled.cpp`); the README says so.
- The compiled *programs* still link through the system `cc` and glibc (stages
  3 and 4); `release_smoke.sh` still leaves `cc` on PATH.
- A static glibc-linked `turfc` still needs a glibc at least as new as the build
  machine's for the symbols it uses (Ubuntu's CI image); a much older distribution
  may refuse it. Stage 4's musl runtime is the fix, not this stage.
- All LLVM targets make the binary ~130 MB. Restricting to X86, AArch64 would
  cut it a lot but needs `main.cpp` to initialize only those and `--target` to
  say which are supported; not done.

## Stage 3 — embedded lld (Linux; Windows and macOS drivers wait for their runtimes)

### Why, and the scope this stage can honestly have
An in-process linker is half of "link with nothing installed"; the other half
is the C runtime it links against (`crt1.o`, `libc.a`, a compiler runtime), which
is stage 4. So stage 3 builds the **mechanism and its contract**, and proves it
on Linux against a stand-in runtime; it changes nothing for a user until stage 4
puts a runtime in `lib/rt/<platform>/`. The COFF/MinGW and Mach-O drivers are
not written: they need the Windows and macOS runtimes (CRT objects, `.tbd`
stubs) to be written against and tested, and a driver argument list written
blind is the kind of thing this milestone has been burned by. `TURF_EMBED_LLD`
refuses to configure on those hosts instead of silently doing nothing.

### What changed
- **`include/BundledLink.h`, `src/BundledLink.cpp`** (new). `BundledLink()`
  runs `lld::lldMain` with the ELF driver on an argument list built from the
  directory contract in the header (`crt1.o crti.o crtn.o libc.a` required;
  `crtbeginT.o crtend.o libm.a libgcc.a libgcc_eh.a` used when present; always
  static, libraries in a group). Without `TURF_EMBED_LLD` the same file
  compiles to "not available", so every other build is unchanged.
- **The hybrid rule in `linkObject()`** (`src/main.cpp`): in-process when the
  runtime directory is complete **and** every library the program names is
  part of the C runtime (`BundledRuntimeProvides`: `c m pthread dl rt util`);
  otherwise the system `cc`, exactly as before. A bundled link that fails
  returns an error that names the embedded linker and `TURF_LINKER=system`; it
  does **not** fall back by itself (a silent fallback would hide a broken
  runtime behind a machine that happens to have `cc`). Sanitizer builds always
  use `cc`.
  - *Found while testing:* the first version of the rule was "names no system
    library", and never fired, because the standard library's `math` module
    declares `extern from "m"` (14 declarations; the only library the stdlib
    names), so every program names one.
- **`--version`** gains `linker system-cc | embedded-lld` and, when usable,
  `bundled-runtime <dir>` (extra lines are interpreted by nothing, by design).
- **`-DTURF_EMBED_LLD=ON`** (needs `TURF_RELEASE_STATIC`; `cmake_build.sh
  --release-static --embed-lld`): links `lldELF`/`lldCommon` before the LLVM
  components (static archives resolve only forwards) plus the components lld's
  ELF driver needs (`lto dtlto object option binaryformat debuginfodwarf symbolize
  textapi bitreader bitwriter linker ipo`). Two more Debian/Ubuntu traps, both
  found by linking: lld's exported targets link the *shared* `LLVM` (overridden,
  as for `LLVMSupport`), and `LLVMLTO` drags in `LLVMExtensions` -> **Polly**, a
  separate package. The Polly edge is dropped and `getPollyPluginInfo()`, which
  LLVM's LTO calls for every extension LLVM was built with, is provided as a
  weak no-op in `BundledLink.cpp`.
- **`package_release.sh`** ships `lib/rt/` when it exists; `.gitignore` names it.
- **CI (Linux job only):** registers apt.llvm.org on every run and installs
  `llvm-22-dev liblld-22-dev` together (the LLVM cache restores files, not the
  repository, and a cached `llvm-22-dev` older than the repository's lld would
  fail LLDConfig's exact-version check); builds with `--embed-lld`; runs
  `scripts/bundled_link_smoke.sh`.
- **`scripts/bundled_link_smoke.sh`** (new): 17 checks against the real
  compiler with a **decoy `cc`** first on `PATH` that logs and fails, so "the
  system toolchain was not used" is observed: a runtime-only program links
  in-process and the result is a static ELF that runs; `TURF_LINKER=system`,
  `extern from "z"`, `--link z` and an incomplete runtime directory each reach
  the decoy; a present-but-broken runtime fails with the embedded-linker message
  and does not reach the decoy.

### Known pitfalls
- Until stage 4, nothing ships a `lib/rt/`, so a released archive still links
  with `cc`: the user-visible promise is not met yet.
- A static link cannot use `dlopen`/NSS-style features; musl's resolver avoids the
  worst of it, but `dl` is accepted by the rule while a static program cannot
  load shared objects at run time.
- The ELF argument list passes `-static`, no `--gc-sections`, no `-z relro`;
  hardening flags and size are stage 4's tuning with the real runtime.

## Stage 4 — the bundled C runtime (Linux verified here; Windows and macOS written, CI-only)

### What changed
- **`scripts/build_bundled_runtime.sh`** (new) builds `lib/rt/<platform>/` for each
  platform, so CI and a developer produce the same thing. Every directory also
  gets a `MANIFEST` and the licence texts the redistributed pieces need.
  - **linux-x86_64:** musl **1.2.6** from `musl.libc.org`, **pinned by SHA-256**
    (`d585fd3b…512a`; the tarball's PGP signature verified here against musl's
    published key, fingerprint 8364 8929 0BB6 B70F 99FF DA05 56BC DB59 3020 450F;
    CI checks the hash, so a change is deliberate), built static; `libturfrt.a`
    compiled **against that musl** with `musl-gcc` (the same sources and flags as
    the `turfrt` CMake target); gcc's `libgcc.a`; `COPYRIGHT.musl`. Takes 12 s.
    A tarball with the wrong hash is refused (checked).
  - **windows-x86_64:** the MinGW-w64 CRT of the running UCRT64 toolchain
    (`crt2.o`, `libmingw32.a`, `libmingwex.a`, `libucrt.a`, the Win32 import
    libraries, `libgcc.a`), `libturfrt.a` built with it. **It refuses a
    toolchain that does not target UCRT** (`_UCRT` undefined), because a
    program linked against an msvcrt CRT needs `msvcrt.dll`.
  - **macos-arm64:** a **stub `libSystem.tbd` written by the script** (the install
    name `/usr/lib/libSystem.B.dylib` and one symbol), and `libturfrt.a` built
    with the runner's clang for macOS 11. **No Apple file is copied or generated
    from the SDK**, so the roadmap's "confirm the stubs are redistributable"
    risk does not arise: there is nothing of Apple's to redistribute. The cost is
    in *Known pitfalls*.
- **`src/BundledLink.cpp`** now has three drivers, one per host: ELF (as in
  stage 3, with the runtime directory searched first so its musl-built
  `libturfrt.a` beats the glibc one in `lib/`), **MinGW/COFF** (`ld.lld -m
  i386pep`, which lld's GNU front end hands to its MinGW driver; the library
  order is gcc's) and **Mach-O** (`ld64.lld -platform_version macos 11.0.0
  11.0.0 -undefined dynamic_lookup`, libSystem through the stub; ad-hoc code
  signing is lld's default for arm64). `BundledRuntimeProvides` is per platform
  (Windows: the Win32 DLL import libraries and `m`; macOS: everything libSystem
  re-exports).
- **Windows needed two things MSYS2's packaging forces** (found by building
  `turfc.exe` with embedded lld against MSYS2's own packages, unpacked here, with
  a MinGW cross compiler): its static lld archives call libxml2 (16 functions,
  for manifest merging, which turfc never uses) and `llvm::demangle` through
  `__imp_` import-table slots a static link does not have. `src/
  BundledLinkWindowsShims.cpp` provides them (the xml ones as weak never-called
  stubs, `demangle` as a real forwarding slot), and the CMake overrides
  `LLVMWindowsManifest`'s link interface so `libxml2-16.dll` cannot come back. The
  turfc.exe so built imports only `KERNEL32`, `ADVAPI32`, `ole32`, `SHELL32`,
  `ntdll` and the UCRT `api-ms-win-crt-*`.
- **CI:** Linux, Windows and macOS all build with `--embed-lld`, build the
  runtime before packaging, and test the **archive's own** turfc and runtime
  with a **decoy compiler first on `PATH`** that records that it was run and
  fails (`cc` on Linux and macOS, `gcc.cmd` on Windows). Windows moves from
  MSYS2's MINGW64 to **UCRT64** (so `turfc.exe` itself no longer imports
  `msvcrt.dll`, the last item stage 1 reported), with `lld` added to its
  packages; macOS adds `lld@22`.
- `bundled_link_smoke.sh --archive` gains a macOS mode and a host-name lookup
  check (the DNS tests that static glibc could not pass).

### Known pitfalls
- **macOS `-undefined dynamic_lookup`:** a misspelled `extern fn` or a missing
  symbol no longer fails at link time; it fails when the call is first made
  ("symbol not found in flat namespace"). `TURF_LINKER=system` restores the
  link-time check. If a current macOS rejects flat lookups in an executable, the
  alternative is a stub generated from the SDK's `libSystem.tbd` (the
  redistribution question the stub design avoids).
- **Licences are for the owner to confirm:** musl (MIT), mingw-w64's runtime
  (ZPL/public domain, runtime exception) and `libgcc.a` (GPL-3.0 with the GCC
  Runtime Library Exception) are redistributed in the archive. The `MANIFEST`
  names them and Linux ships `COPYRIGHT.musl`; no combined `NOTICE` file or
  mingw-w64 licence text is shipped yet.
- Windows: the `net` module and the rest of the Windows port (Winsock names,
  `fs`, `time`, the test suite under Git Bash) are stage 5; a program that
  *links* is not a program that *works*.
- The Windows embedded driver passes no `--stack`: lld's MinGW default is
  smaller than GNU ld's, so deep recursion that works under gcc may overflow
  earlier. Stage 5's tests decide.
- `libgcc.a` comes from whatever gcc builds the archive (16.x here, the runner's
  in CI): not pinned, unlike musl.
- The glibc `libturfrt.a` in `lib/` is still shipped: it is what the system
  `cc` path (programs naming another C library) links.

## Stage 5 — the Windows port (suite green on a real Windows 11 machine; CI proof and macOS open)

### Method
Windows can only be exercised on the CI runner (a 15-minute round trip), so the
work is arranged to extract as much as possible without it:
- **Link-level gaps, measured here.** Every test (602 non-`fail_*` programs) is
  compiled with `--target=x86_64-w64-windows-gnu` (an object file; foreign targets
  stop before linking) and linked with `ld.lld -m i386pep` against the bundled
  MinGW runtime directory, with the argument list `BundledLink.cpp` builds. Result
  before this batch: **598 link, 4 fail**, on three symbols the Windows C runtime
  does not have: `posix_memalign`, `malloc_usable_size`, `setenv`. After: **602/602**.
  (Everything else the stdlib binds, including `opendir`, `usleep`, `mkdir` and
  the socket API, resolves.)
- **Behaviour gaps, read from the code**, listed below; **a CI run of the whole
  suite on the runner supplies the rest** (see the first item).

### What changed
- **`turfc --test` and `turf test` now run on Windows** (`src/TestRunner.cpp`; this
  was `unsupported platform`, REL-002's open item). A Win32 `RunProcess`:
  `CreateProcess` with an **explicit inherit-handle list** (otherwise two test
  processes started at once leak a pipe end to each other and one pipe never
  reaches end-of-file), stdin from `NUL`, stdout and stderr in one pipe, and a
  **Job Object** so a timeout or Ctrl-C kills the whole process tree. Exit codes
  are mapped into the runner's `128 + signal` vocabulary so the markers are
  unchanged: the C runtime's `abort()` exits 3 (-> 134), an access violation or
  stack overflow is an NTSTATUS (-> 139). The test binary is named `.exe`, there
  is no `mkdtemp`, and a console gets its colour escapes enabled. Syntax-checked
  with a MinGW cross compiler (`-Wall -Wextra`, clean) and on Linux; the POSIX path
  passes `test_cmd_smoke.sh`. **Not run on Windows.**
- **CI:** the Windows release job runs the whole suite after building the bundled
  runtime (so programs are linked by the embedded lld), informational, with
  `windows-suite.log` uploaded and the failure headlines printed, so one run lists
  everything that fails.
- **`runtime/turfrt_win32.c`** defines `posix_memalign`, `malloc_usable_size` and
  `setenv` for Windows under their POSIX names, so `lib/std` and its public API
  are unchanged. A block from `_aligned_malloc` is released through
  `_aligned_free` by `turf_rt_checked_free`. **Limitation:** `mem::grow` (realloc)
  of an over-aligned (> 16 byte) block is unsupported on Windows.
- **`runtime/turfrt_net.c`**, a portable socket layer used on every platform:
  `turfrt_net_startup` (WSAStartup, once), `turfrt_net_socket`, `turfrt_net_close`
  (`closesocket` on Windows), `turfrt_net_reuseaddr` (`SO_REUSEADDR` is 4 on Windows,
  2 on Linux) and `turfrt_net_sockaddr`, which builds the platform's own
  `struct sockaddr_in` (the byte image `net.tr` used to hand-assemble is wrong on
  BSD/macOS, where the first byte is a length, so this also covers stage 6's
  `sin_len`). `lib/std/io/net.tr` calls these; `resolve_hostname` starts Winsock
  first. `bind`, `listen`, `accept`, `connect`, `recv`, `send` and
  `gethostbyname` stay bound directly. The exported `SOL_SOCKET` / `SO_REUSEADDR`
  constants keep their Linux values (they are public API) and are documented as
  such. **Boundary note for the owner:** this puts a small platform-adaptation
  layer in the runtime (FREEZE.md 6.8, B2/B3). Its justification is that Turf has
  no conditional compilation and that Winsock start-up is genuinely process-wide
  state; a user program can bind the same symbols with `extern fn`.
- **Stack overflow:** the Windows stub in `runtime/turfrt_signal.c` is replaced by
  a **vectored exception handler** (`SetThreadStackGuarantee` for room to run,
  `SetErrorMode` and `_set_abort_behavior` so a crash does not open an error
  dialog nobody can click). It prints the same two messages as the POSIX handler,
  so `EXPECT-RUNTIME` text is the same on every platform.
- **Stack size:** lld's MinGW driver reserves 1 MB for the main thread (measured),
  GNU ld 2 MB, a Linux process 8 MB. Both Windows link paths now reserve 8 MB
  (`--stack=8388608`, `-Wl,--stack,8388608`), so a recursion depth that works on
  Linux works here. The `gcc` path also gains `-lws2_32`.
- Already right, checked: `lib/std/core/io.tr` opens files `"rb"`/`"wb"`, so
  Windows' text-mode CRLF translation does not touch file contents.

### Stage 5, second batch: the suite run on real Windows
GitHub Actions minutes ran out, so Windows was tested locally: WSL2 on the owner's
Windows 11 machine launches `.exe` files directly, so a MinGW-cross-built `turfc.exe`
(static LLVM, embedded lld, bundled UCRT runtime) was synced to `C:\turf-win` and the
suite run there. First run: **690/1157**. Final: **1191/1191** (the suite has grown),
also at `-O0`; `tests/41_gc` 18/18 under `TURF_GC_STRESS=1` and `TURF_GC_VALIDATE=1`;
`turf new`/`run`, and a git dependency (tag, `turf.lock` written, `--locked` and
`--locked --offline` rebuilds) with the real Windows `git`, all work.

What the run found and what fixed it:
1. **`longjmp` on Windows unwinds.** MinGW's `setjmp` records a frame, and the C
   runtime's `longjmp` unwinds to it with the OS, running GCC's SEH cleanup landing
   pads. `TurfError::raise()` relies on destructors NOT running. Symptom: an access
   violation inside ntdll before any diagnostic printed, behind 461 of 467 failures.
   Fix: `include/Lexer.h` defines `setjmp(buf)` as `_setjmp((buf), NULL)` on MinGW
   (no frame recorded, plain jump). A small isolated setjmp/longjmp program did NOT
   reproduce it; it was found with a temporary vectored-exception tracer, frames
   resolved with `nm`, and the disassembly of `raise()`.
2. **`malloc_usable_size` forwarded to `_msize`.** `_msize` on an `_aligned_malloc`
   block corrupts the heap (exit `0xC0000374`). The shim in `turfrt_win32.c` is the
   right implementation. The `@ffi` annotation work (`cef251d`) had already removed
   the compiler's name-keyed Windows rewrite, and `mem.tr` carries no Windows forward,
   so the shim is used; `17_mem_pool_and_aligned_alloc` passes. The old rewrite was
   keyed on the platform `turfc` was BUILT for, not the compile target, which is why
   the Linux-hosted cross compile hid it; `d413f6e` made forwarding follow `--target`.
3. **Stack.** `turfc.exe` linked by GNU ld had a 2 MB stack and crashed on
   `fail_deeply_nested_expression.tr` instead of reporting the nesting limit: the
   Windows `turfc` link now reserves 8 MB (`-Wl,--stack,8388608`).
4. **`time::clock_ticks()` and `random` assumed glibc.** Windows `clock()` is
   wall-clock MILLISECONDS (glibc: CPU microseconds); `RAND_MAX` is 32767 (glibc:
   2^31-1); `random.tr` reseeded `srand()` from the clock on every call, which only
   works with a microsecond clock. New `runtime/turfrt_sys.c`: `turfrt_clock_us()`
   (process CPU time in microseconds, every OS) and `turfrt_random_u31()` /
   `turfrt_random_reseed()` (one process-wide xorshift64* seeded once from OS entropy).
5. **Two tests were not portable.** `01_ffi_showcase.tr` used `/tmp/...` and text-mode
   files, and ran `system("echo 'test' > /dev/null")`, which `cmd.exe` rejects.
6. **Naming rule.** A stdlib function `random::reseed` mangles to `turf_random_reseed`,
   and an `extern fn` keeps its C name verbatim, so a runtime symbol named
   `turf_<module>_<name>` is the same LLVM symbol as the Turf function. The recursion
   check (correctly) rejected `reseed`. **Rule: runtime functions bound by Turf use the
   prefix `turfrt_`.** The socket layer was renamed to match (`turf_net_*` ->
   `turfrt_net_*`); `turf_rt_*` and `turf_gc_*` are not affected.

Facts for later: `lld`'s MinGW default stack is 1 MB. Windows `abort()` exits 3; an
access violation or stack overflow is `0xC0000005` / `0xC00000FD` (WSL shows only the
low byte). All network tests pass on real Windows (the `turfrt_net` Winsock layer).

**Decisions for the owner (made provisionally, not silently):**
- A small platform-adaptation layer now lives in the runtime (`turfrt_net`,
  `turfrt_win32`, `turfrt_sys`), justified by B2/B3 (FREEZE.md 6.8).
- `random.tr` behaviour changed: no per-call reseed; there is still no way to set a
  seed; `RAND_MAX` is now truthful (31 bits) on every platform; `reseed()` draws fresh
  OS entropy.
- `time::clock_ticks()` is now CPU time in microseconds everywhere (Windows resolution
  about 15.6 ms from `GetProcessTimes`).
- `mem::grow` (realloc) of an over-aligned (> 16 byte) block is unsupported on Windows.

### Stage 5, third batch: GC stress over the whole suite, and the smoke scripts
**The whole suite under `TURF_GC_STRESS=1` on Windows: 1191/1191.**

The bash smoke scripts were run under Git for Windows' `bash.exe` against the Windows

for Linux and macOS; of 17, **7 pass** (`package_graph`, `examples`, `pattern_warnings`,

because the SCRIPT assumes a POSIX host, not because the product is wrong:
`mktemp` returns an MSYS path (`/tmp/...`) that a native `.exe` cannot open, the fakes
in `cli_smoke` are shell scripts a Windows process cannot execute, symlinks need a
privilege, `abort()` is exit 3 not 134, `/usr/bin/time` and `bus.c` (SIGBUS) are POSIX,
`root /` is matched with a leading slash. With `git_deps_smoke`'s `url()` pointed at
`cygpath -m` (staged copy only), its failures fell to 5, all path SPELLING (`/tmp/...`
vs `C:/...` in messages). None of these is fixed, because the right fix is a decision:
port the scripts, or keep them POSIX-only and give Windows its own `.ps1` twins (stage 8
already plans one). **Real product findings the run produced (not fixed):**
1. **A program that returns 3 is reported as a crash.** The Windows runner maps exit
   status 3 to 134 (`abort()`'s status), so `fn main(): int { return 3; }` shows
   `RUNTIME FAILED (Exit code 134)`; `test_cmd_smoke.sh`'s `exit3` case caught it. The two
   cannot be told apart by status alone; a fix would make the runtime's abort path exit
   with a status ordinary programs do not use, or have it announce itself.
2. **`turfc.exe` writes CRLF on stdout** (text mode): `turfc --format f.tr`, `--version`
   and every diagnostic stream end lines with `\r\n`. `--format` output redirected to a
   file therefore differs from the file `--format` would write in place.
3. **Diagnostics use the native path separator on Windows** (`would reformat src\main.tr`,
   `skipped tests\lexbad.tr`), where the Linux and macOS output, and the docs, spell `/`.
4. `fmt_smoke.sh`'s corpus step fails with `Argument list too long` on Windows (a
   32 K command line; the script passes every file to one invocation).
