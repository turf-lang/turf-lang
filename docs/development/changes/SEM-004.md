## Why

Every declaration without an initializer went through one of two completely
different mechanisms, chosen by the variable's *type*, not by anything the
programmer wrote:

```turf
mut x: int;      // Mechanism A: statically unassigned, E008 if read before assignment
mut c: char;     // Mechanism B: eagerly zeroed, immediately readable
mut cfg: Config; // Mechanism B: every field recursively zeroed, immediately readable
```

`docs/reference/variables_and_types.md` called the split *"the single most
important gotcha in the type system"*; `SynthesizeDefault()`'s own
`isInt()/isDouble()/isBool()/isString()` branches were dead code on the path
that called it, because the caller had already excluded those exact types —
a small, telling sign the split was accreted, not designed.

## Language semantics

### Old behaviour

```turf
struct AllTypes { i: int, d: double, b: bool, s: string }
fn main(): int {
    mut a: AllTypes;                 // Mechanism B: immediately readable
    test::assert(a.i == 0, "...");   // passes, no assignment happened
    mut x: int;
    test::assert(x == 0, "...");     // E008: Mechanism A, x never assigned
    return 0;
}
```

### New behaviour

```turf
struct AllTypes { i: int, d: double, b: bool, s: string }
fn main(): int {
    mut a: AllTypes;
    test::assert(a.i == 0, "...");   // E008 now -- a never assigned
    mut a2: AllTypes = AllTypes::default();
    test::assert(a2.i == 0, "...");  // fine -- explicit opt-in
    return 0;
}
```

One rule, for every type, with no exception: a declaration without an
initializer leaves the variable statically unassigned; reading a
body-declared local before it is definitely assigned on every incoming path
is `DefiniteAssignmentError` (E008). Storage is still always zero-filled
underneath (F-INIT-2) — this is a purely static check, not a change to what
bits are actually there.

Two things frozen at a finer grain than "one rule":

- **Arrays get whole-array granularity, not per-element** (§12.6): a whole-
  array read with no prior element write or general initializer is E008, but
  a single element write (`arr[0] = 1`) counts as assigning the entire
  array. Elements are not tracked individually — the same granularity
  `ConstructorFieldAssignmentPass` already uses for `self.<field>`.
- **`T::default()` is the explicit opt-in**, and already existed before this
  group (`ScopeAccessKind::DefaultConstruct`, gated on the callee being a
  known struct) — no new syntax was added.

### Is this breaking?

Yes, intentionally, and per §8's own framing this is the most user-visible
source-compatibility break in the roadmap so far. The mechanical migration is
always the same shape: `mut c: Config;` → `mut c: Config = Config::default();`
(or, for a generic-typed local, the bare unqualified `List::default()` /
`Map::default()` — see *Known pitfalls*).

Swept `lib/std/**` and `showcase/**` by direct compile (`turf --resolve`,
AGENTS.md convention — neither is exercised by `test_runner.sh`) and migrated
every real hit:

- `lib/std/http/http.tr` — `parse_request()`'s `mut req: Request;` and
  `Server.listen()`'s `mut res: Response;` (two call sites).
- `lib/std/json/json.tr` — six `JsonValue` constructor helpers
  (`null_value`/`from_bool`/`from_number`/`from_string`/`new_array`/
  `new_object`), each `mut v: JsonValue;` then field writes, plus `parse()`'s
  `mut p: Parser;`.
- `showcase/kv_store_server.tr` — `mut store: List<Entry*>;`.

Also migrated in `tests/` (found by the full-suite run, not the `lib/std`/
`showcase` sweep, since these are ordinary test files, not stdlib):
`tests/07_functions_modules/09_stdlib_map.tr`,
`10_generic_double_erasure.tr`, `fail_map_get_missing_key.tr`;
`tests/25_errors/12_stdlib_map_tryget.tr`;
`tests/32_set_and_sort_stdlib/{01..04}` (List/Set locals);
`tests/34_http_and_json/{03,04}` (two more `http::Response`/`http::Server`
sites each, found only after fixing the first occurrence per file —
`grep`-swept the rest before re-running).

**Verified NOT a large migration** (§8's own stated risk was "the volume in
`lib/std` is the unknown, U-1") — 3 files in `lib/std`, 1 in `showcase`, ~9
test files, all one-line-per-declaration fixes. The deprecate → migrate →
remove split the risk section proposed as a fallback was not needed.

## Compiler architecture

- **Parser** (`src/ParserStmt.cpp`): `SynthesizeDefault()` deleted outright
  (was: return a `NumberExprAST`/`BoolExprAST`/`StringExprAST`/`NullExprAST`
  for the Mechanism-A-excluded types, or a `DefaultInitExprAST` for
  everything else). `ParseLetStatement()`'s type-exclusion condition around
  the call is deleted along with it — the no-`=` branch for a non-array
  declaration now unconditionally leaves `Init = nullptr`. Arrays were
  already on their own path (`ArrayDeclExprAST`, not `VarDeclExprAST`) and
  are untouched here; their granularity change is entirely in `Analysis.cpp`
  (see below).
- **AST** (`include/ASTExpr.h`): `DefaultInitExprAST` deleted. It was
  constructed in exactly one place (`SynthesizeDefault()`), so once that call
  is gone the node is unreachable dead code, not a "kept for compatibility"
  shim — removed outright, along with every visitor plumbing point that
  existed only to dispatch on it: `ASTVisitor::visitDefaultInit` (declaration
  + forward-decl, `include/ASTVisitor.h`), `Resolver::visitDefaultInit`
  (`include/Resolver.h`), `TypeChecker::visitDefaultInit` (declaration in
  `include/TypeChecker.h`, definition in `src/TypeCheckerExpr.cpp`),
  `ASTPrinter::visitDefaultInit` (`include/ASTPrinter.h`),
  `DefaultInitExprAST::codegen()` (`src/CodegenExpr.cpp`), its `TRY_LOC` entry
  (`src/CodegenCore.cpp`), its `TURF_EXTRACT_LOC` entry
  (`src/CompileBuffer.cpp`), and the no-op override in `Analysis.cpp`'s
  `AnalysisVisitor`.
- **CFG/analysis** (`src/Analysis.cpp`) — the actual behavior change:
  - `AnalysisVisitor::visitVarDecl` already only called `onDef()` when
    `Node.getInitializer()` was non-null (a pre-existing comment there
    explains this was already deliberate, for Mechanism A's primitives).
    With `SynthesizeDefault()` gone, every type now goes through this same
    branch uniformly — **no change needed here at all**, which is the
    cleanest possible confirmation that Mechanism A's tracking was already
    type-agnostic and only Mechanism B's *synthesis* was the special case.
  - `AnalysisVisitor::visitArrayDecl` changed from unconditionally calling
    `onDef()` ("arrays always get storage allocated — treat as defined
    immediately") to only calling it when `getInitList()` is non-empty or
    `getInitExpr()` is set — i.e., only when an actual initializer was
    given.
  - `AnalysisVisitor::visitAssignment` gained a new branch for
    `ArrayAccessExprAST` LHS (`arr[i] = v`): the index is visited as an
    ordinary read, and the base is treated as a **definition of the whole
    array**, but *only* when the base's resolved type is a concrete
    fixed-size `ArrayType` (`getSize() > 0`) — see *Known pitfalls* for why
    this guard is load-bearing, not incidental.
- **Diagnostics** (`include/ErrorsFlow.h`, `src/Analysis.cpp`):
  `DefiniteAssignmentError` gained two optional constructor parameters
  (`TypeName`, `SuggestDefault`, both defaulted so every pre-existing call
  site is unaffected) so the message names the variable's type and, only
  when that type is an actual `TurfStructType` (checked via `dynamic_cast`
  at the `Analysis.cpp` call site — enums/arrays/generics don't have a
  callable `::default()`, so suggesting one for them would name a construct
  that doesn't parse), suggests the exact mechanical migration in the hint
  text.
- **Resolver, TypeChecker, Codegen**: no other changes. `TypeCheckerDecl.cpp`'s
  ordinary (non-`guess`) `visitVarDecl` path already skips its whole
  initializer-compatibility block when `Node.getInitializer()` is null — a
  struct/enum/array/generic declaration with no initializer was always
  legal at the TypeChecker layer once Mechanism B stopped supplying one;
  nothing needed to change there.

## Runtime changes

None. Storage is still always zero-filled the same way it always was
(`ArrayDeclExprAST::codegen()`'s memset, `GetDefaultValue()`'s recursive
struct-field zeroing via `T::default()`) — this group only changes which
declarations the *static* check requires an assignment before reading.

## Standard-library changes

`lib/std/http/http.tr` and `lib/std/json/json.tr` migrated off Mechanism B —
see *Is this breaking?* above for the exact call sites. No behavioral change
to any of these functions: `T::default()` zero-inits identically to what
Mechanism B used to do eagerly, so `JsonValue.null_value()` etc. still
produce byte-identical results.

`INV-INIT-1` (`docs/development/INVARIANTS.md`) moved from `planned` to

## Removed assumptions

- **"A struct/enum/array/generic-typed local is readable immediately after
  declaration, with no assignment" is no longer true anywhere.** Every type
  now follows the same definite-assignment rule `int`/`double`/`bool`/
  `string`/pointers already had. Any code — including a future AI session
  working from a stale memory of this language, or a human who read an
  older copy of `docs/reference/variables_and_types.md` before it's
  rewritten (queued in `handbook-sync/PENDING.md`, not yet done) — that
  assumes `mut cfg: Config;` is immediately safe to read will now hit E008
  instead of silently getting zeros.
- **"An array variable is 'defined' the moment its `ArrayDeclExprAST` runs,
  regardless of contents" is no longer true.** It is defined only once an
  initializer or at least one element write has happened. This matters for
  anyone adding a new AST-walking pass that reasons about array liveness —
  see *Known pitfalls* for the specific representation trap this uncovered.
- **`DefaultInitExprAST` no longer exists.** Any future code (or session
  memory) that expects to find it in `include/ASTExpr.h`, or expects
  `SynthesizeDefault()` in `src/ParserStmt.cpp`, is working from a stale
  picture of the parser.

## Known pitfalls

- **The array-element-write-counts-as-assignment rule must NOT apply to a
  `string`/`ptr`/`T*`/unsized-`T[]` base, only to a genuine fixed-size
  `T[N]` local.** The first version of the `visitAssignment` change in
  `Analysis.cpp` special-cased *any* `ArrayAccessExprAST` LHS whose base was
  a plain `VariableExprAST`, unconditionally treating the base as a
  definition rather than a read. This broke `lib/std/core/strings.tr`
  immediately: `mut buf: string = malloc(n) to string; buf[i] = c;` writes
  through the pointer *stored in* `buf` — it genuinely reads `buf`'s current
  value to compute the write address, unlike a real `T[N]` local where the
  array's storage *is* the alloca and there is no separate pointer value to
  read at all. Treating it as pure "def, no read" silently made
  `LivenessAnalysisPass` (which shares the exact same `AnalysisVisitor` via
  `collectReadsAndDefs()`) flag the buffer's initial `malloc` assignment as
  a dead store in every `strings.tr` function that fills a buffer
  byte-by-byte (`to_upper`, `pad_left`, `pad_right`, ...) — confirmed live:
  running the full test suite with the unguarded version produced a wall of
  new, spurious `DeadStoreWarning`s across `lib/std/core/strings.tr` that
  weren't there before. The fix checks the base's resolved type is
  specifically a concrete `ArrayType` with `getSize() > 0` before treating
  the write as definition-only; anything else (including the unsized `T[]`
  parameter spelling, which is representationally a pointer too, per
  `docs/architecture/memory_model.md` §1.3) falls through to the ordinary
  read treatment. Anyone touching this branch again should re-run the full
  suite specifically looking for new dead-store/unused-variable warnings in
  `lib/std/**`, not just compile errors — a wrong guard here produces
  *warnings*, not failures, and the test runner doesn't fail on warnings.
- **§8's own text states "13 files depend on Mechanism B" in
  `tests/10_default_init/`; direct inspection found only 8.** `05` and `06`
  already called `Config::default()`/`Point::default()` explicitly (they
  were written to demonstrate the *replacement* mechanism, per their own
  header comments, predating this session), and `01`/`09`/`13` are
  pure-primitive tests that were always Mechanism A. Per AGENTS.md's "verify
  claims live" rule, this record states the number actually found (8) rather
  than repeating the roadmap's estimate — a future reader diffing this
  record against `ARCHITECTURE_OVERHAUL.md` §8 should trust this file, not
  treat the mismatch as a sign something was missed.
- **`GenericName<TypeArgs>::method()` does not parse, at all, in expression
  position.** `mut store: List<Entry*> = List<Entry*>::default();` fails
  with "Unexpected token — expected a value" immediately after the closing
  `>` — `<...>` generic-argument syntax is only understood by `ParseType()`,
  never by `ParsePrimary()`/expression parsing, so `List<Entry*>` in an
  expression position parses as `List < Entry` (a comparison) hitting `*>`
  next and failing. This is a genuine, pre-existing parser gap, not
  something SEM-004 introduced or is scoped to fix (§8 doesn't mention it,
  and it isn't in §25's "must not do" list either because nobody had hit it
  yet) — but SEM-004's own removal of Mechanism B is what surfaces it for
  the first time, since generic-typed locals never needed *any* construction
  syntax before now. **The working migration is the bare, unqualified
  `List::default()`** (no type arguments on the call itself) — the
  declared LHS type (`: List<int>`) already carries the type arguments, and
  because generics are implemented as type erasure (one shared
  `TurfStructType` per generic declaration, `docs/architecture/
  compiler_pipeline.md` §7), a bare `List::default()`'s
  `NamedType("List")` result and the LHS's `GenericType("List", [int])`
  resolve as the same underlying struct through the ordinary
  `NamedType -> TurfStructType`/compatibility path — no different from how
  `Point::default()` already worked for a non-generic struct. Verified live
  (`/tmp/.../gentest.tr`, `List::default()` + `push()` + `length()`, exit 0)
  before committing to this as the documented migration. Left unfixed: a
  future session adding `GenericName<Args>::method()` expression-position
  parsing would be solving a real, separate gap, not something this group's
  scope covers.
- **`http::StructName::default()` (a module-qualified struct name before
  `::default()`) does parse and resolve correctly** — verified live in
  `tests/34_http_and_json/03_http_manual_routing_roundtrip.tr` and
  `04_http_callback_routing.tr`, both of which use `http::Response`/
  `http::Server` (imported as `import http;`, not `import http::Response;`).
  Worth stating explicitly since it's the one case above that *did* just
  work without investigation — module-qualification and generic-argument
  syntax are unrelated parser paths, and only the latter is broken.
