## Why

SEM-001 made a literal's exact value survive from the lexer into the AST,
but explicitly did nothing with that value beyond storing it — three of
`ARCHITECTURE_OVERHAUL.md` §0.2's four verified "numeric semantics are
undefined in practice" findings were still live going into this session:

```turf
mut x: int = 999999999999999999999999999999999999999999999999;
// before this session: 9169610316303040511 (plain 64-bit truncation of
// the now-exact literal, zero diagnostics -- SEM-001 deliberately deferred
// this exact check, see NumberExprAST::codegen()'s own comment)
mut c: int = 9223372036854775807 + 1;
// before: -9223372036854775808 (silent wraparound, zero diagnostics)
mut a: int = f(); mut b: int = g(); mut c: int = a + b;
// before: silently wraps at runtime if it overflows
```

Additionally, `docs/reference/variables_and_types.md` itself documented (and
`CastExprAST::codegen()` confirmed) that `to`-cast legality was checked only
in Codegen, never the TypeChecker — a real, if invisible, violation of
`docs/architecture/compiler_pipeline.md` §0's own stated pipeline invariant
("Codegen is only ever allowed to run on an AST that has already passed the
TypeChecker cleanly").

## Language semantics

### Old behaviour

```turf
mut x: int = 999999999999999999999999999999999999999999999999; // 48 digits
// compiled, x == 9169610316303040511 at runtime (silent 64-bit truncation)
mut d: double = <1 followed by 400 zeros>.0;
// compiled, d == inf at runtime
mut c: int = 9223372036854775807 + 1;
// compiled, c == -9223372036854775808 (silent wraparound)
mut a: int = INT64_MAX; mut b: int = 1; mut c: int = a + b;
// compiled, c == -9223372036854775808 at runtime, exit 0
mut d: int = -9223372036854775808;
// compiled and printed correctly, but by ACCIDENT: NumberExprAST::codegen()
// truncates the magnitude 9223372036854775808 (2^63) to a 64-bit value
// whose bit pattern is indistinguishable from INT64_MIN, and negating that
// bit pattern via plain CreateNeg happens to wrap back to the same,
// correct bits -- not a real fold (see Known pitfalls)
mut y: int = f to int; // f: Foo (a struct) -- rejected, but by Codegen,
// not the TypeChecker (docs/reference/variables_and_types.md's own note
// said so explicitly)
```

### New behaviour

```turf
mut x: int = 999999999999999999999999999999999999999999999999;
// error: integer literal is not representable in type 'int' [E076]
mut d: double = <1 followed by 400 zeros>.0;
// error: float literal overflow [E078]
mut c: int = 9223372036854775807 + 1;
// error: integer literal is not representable in type 'int' [E076] --
// caught at COMPILE time (both operands are untyped literals, folded with
// arbitrary precision, FREEZE.md §6.2 row 6), not a runtime trap
mut a: int = INT64_MAX; mut b: int = 1; mut c: int = a + b;
// compiles (a/b are ordinary runtime values, not literals); c = a + b
// PANICS at runtime ("Integer overflow", SIGABRT) instead of wrapping
mut d: int = -9223372036854775808;
// still compiles and is still correct -- but now for the RIGHT reason:
// UnaryExprAST::codegen() recognizes "unary '-' applied directly to an
// untyped integer literal" and folds it before any runtime check runs,
// so it's no longer relying on truncation-and-wraparound to coincidentally
// agree with the right answer
mut y: int = f to int; // f: Foo
// still rejected -- but now by the TypeChecker (TypeError, same message,
// same E066 code), before Codegen ever runs
```

Also new: `double → int`'s existing truncate-toward-zero behavior, and
every other pre-existing numeric cast/conversion, are all UNCHANGED and
individually regression-tested (`tests/36_numeric_semantics/
02_explicit_cast_truncation.tr`).

### Is this breaking?

**Yes, intentionally**, per §8's own text — a program that happened to
compile and run by relying on the old silent clamp/wrap/truncate is now
rejected (a literal) or aborts (a runtime overflow), never silently wrong.
Confirmed narrow in practice: the full existing suite (632 tests before
this session), `lib/std/**`, and `showcase/**` all still compile and pass
unchanged — no existing code in this tree relied on either behavior.

## Compiler architecture

- **TypeChecker** (`include/TypeChecker.h`, `src/TypeCheckerCore.cpp`) —
  two new private methods, `tryFoldUntypedIntConstant()` and
  `checkLiteralRepresentable()` (TypeCheckerCore.cpp), plus a shared
  `checkCallArgsRepresentable()` wrapper for the five call-argument sites.
  `tryFoldUntypedIntConstant()` recursively folds a compile-time integer
  constant built ONLY from untyped literals via unary `-` and binary
  `+`/`-`/`*`, using generously-widened `llvm::APInt` arithmetic so the fold
  itself can never be a source of overflow (only the final destination
  check, in `checkLiteralRepresentable()`, is allowed to reject a value —
  FREEZE.md §6.2 row 6). `checkLiteralRepresentable()` is called at every
  "a value acquires a concrete type" site this session identified:
  `visitVarDecl`/`visitArrayDecl`/`visitArrayLiteral` (TypeCheckerDecl.cpp),
  `visitAssignment` (TypeCheckerExpr.cpp), `visitReturn` (TypeCheckerStmt.cpp,
  using the error-union's success type when the declared return type is
  `!T`), and all five call-argument-resolution sites across
  `visitFuncCall`/`visitMethodCall`/`tryUFCSFallback` (TypeCheckerCall.cpp).
  `visitNumber` (TypeCheckerExpr.cpp) additionally rejects a float literal
  whose rounding overflowed to `inf`, unconditionally (destination-
  independent, per FREEZE.md §6.2 row 8) — this is the one check that does
  NOT go through `checkLiteralRepresentable()`, since it doesn't depend on
  a destination at all.
- **TypeChecker — cast legality (Rule B1)** (`src/TypeCheckerExpr.cpp`,
  `visitCast()`) — a new pairwise legality check mirroring
  `CastExprAST::codegen()`'s dispatch (CodegenExpr.cpp) pair-for-pair,
  raising the identical `TypeError` message the Codegen fallback used to.
  Codegen's own final "Everything else is unsupported" `TypeError` is kept,
  unmodified, as a defensive fallback — see Known pitfalls for why it isn't
  deleted.
- **Codegen — runtime overflow trapping** (`src/CodegenCore.cpp`,
  `src/CodegenExpr.cpp`, `src/CodegenVar.cpp`, `src/CodegenInternal.h`) —
  four new shared helpers in CodegenCore.cpp (`EmitCheckedIntArith`,
  `EmitCheckedIntNegate`, `EmitCheckedShl`, `EmitSignedDivOverflowGuard`),
  declared in CodegenInternal.h. `EmitCheckedIntArith` uses LLVM's
  `llvm.s{add,sub,mul}.with.overflow` intrinsics; `EmitCheckedShl` has no
  intrinsic to use (LLVM has none for shift) so it checks the shift amount's
  range and whether any set bit was shifted out past the sign, in that
  order, in separate branches, so the actual `shl`/`ashr` never executes
  with an out-of-range amount (which would itself be poison/UB) even
  speculatively; `EmitSignedDivOverflowGuard` catches `INT64_MIN / -1`
  (the one signed-division overflow case, §10.2) right after the
  pre-existing divide-by-zero check. Wired into FOUR independent codegen
  paths, because none of them share code: `BinaryExprAST`/`UnaryExprAST`
  (CodegenExpr.cpp), and `CompoundAssignmentExprAST`/`PostfixExprAST`
  (CodegenVar.cpp) — the latter two have never desugared to a literal
  re-walk of `BinaryExprAST` at the Codegen layer (each already had its own
  independent divide-by-zero check before this session, which is the
  precedent this session's duplication follows). Scoped to `NumericType->
  isNamed("int")` only — never `int32` (out of this group's stated scope)
  and never `double` (which keeps its existing IEEE `inf`/`-inf` behavior,
  FREEZE.md §6.2 row 7's deliberate asymmetry). A `TurfGenericParamType`-
  typed operand never reaches the checked path at all, with no separate
  exclusion needed: before TYPE-002 its erased runtime representation
  resolves to something other than `"int"` via `getTurfTypeFromLLVM()`, so
  the `isNamed("int")` gate is naturally false for it.
- **Codegen — literal unary-minus folding** (`src/CodegenExpr.cpp`,
  `UnaryExprAST::codegen()`) — a special case, checked BEFORE the checked-
  negate path: `-<untyped integer literal>` folds directly into the exact
  literal value (widened by one bit, negated, then truncated to 64 bits),
  never going through `EmitCheckedIntNegate()` at all for this specific
  AST shape. Without this, negating the magnitude `9223372036854775808`
  (2^63, already truncated to a 64-bit value whose bit pattern equals
  `INT64_MIN`'s by `NumberExprAST::codegen()`) would make the new checked-
  negate path incorrectly treat it as "negating a genuine INT64_MIN" and
  panic — see Known pitfalls, this was caught live, not anticipated in
  advance.

## Removed assumptions

- **An out-of-range integer literal, or a literal-only expression whose
  final value doesn't fit, silently produced SOME 64-bit value (a
  truncation or a wraparound) rather than an error.** It's now a hard
  compile error (`E076`) at the point the destination type is fixed. Any
  future code path that constructs a `NumberExprAST` or a literal-only
  `BinaryExprAST` and expects it to always reach Codegen must now expect
  `checkLiteralRepresentable()` to have already rejected an out-of-range
  one, wherever it's checked.
- **`int` arithmetic (`+ - * <<`, unary `-`) always produces a result with
  no possibility of a runtime failure.** It can now panic (`SIGABRT`) on
  overflow. Any future code emitting `Builder->CreateAdd`/`CreateSub`/
  `CreateMul`/`CreateShl`/`CreateNeg` directly on an `int`-typed operand,
  instead of going through `EmitCheckedIntArith`/`EmitCheckedShl`/
  `EmitCheckedIntNegate`, silently reintroduces the exact wrapping bug
  class this group exists to remove — this is why FOUR call sites needed
  the same wiring independently, not one.
- **A `to`-cast expression always type-checks; only Codegen can reject
  one.** `TypeChecker::visitCast()` now rejects an illegal pairing itself.
  A future TypeChecker pass that runs BEFORE `visitCast()` and expects
  every `CastExprAST` node still standing to be well-typed can now rely on
  that being genuinely true, not just "true because nothing checked
  otherwise yet."
- **Negating the LLVM value that comes out of codegening an integer
  literal is always just `CreateNeg`.** For the one specific shape "unary
  `-` applied directly to an untyped literal," it must instead fold at the
  AST-value level BEFORE any runtime negate/check — see the pitfall below
  for exactly why the naive approach breaks.

## Known pitfalls

- **Negating a 64-bit-truncated literal magnitude of exactly 2^63 is
  indistinguishable, at the LLVM value level, from negating a genuine
  runtime `INT64_MIN`.** `NumberExprAST::codegen()` truncates ANY integer
  literal to 64 bits unconditionally (SEM-001, deliberately, out-of-range
  representability is SEM-002's job) — so the literal `9223372036854775808`
  (2^63, the magnitude in `-9223372036854775808`) codegens to the exact
  same bit pattern as a genuine `INT64_MIN` value. The first version of
  this session's checked-negate change did NOT special-case this, and
  broke `-9223372036854775808` — it went from "worked by accident" (the
  pre-existing, unchecked `CreateNeg` wraps this exact bit pattern back to
  itself, which happens to be the right answer) to "incorrectly traps"
  (the new checked-negate correctly recognizes the bit pattern as
  `INT64_MIN` and panics, which is right for a REAL runtime `INT64_MIN`
  but wrong for this literal-folding case). Caught by this session's own
  `01_int_literal_bounds_round_trip.tr`/`03_no_false_positive_overflow_
  traps.tr` tests failing, not anticipated in advance. Fixed by special-
  casing `UnaryExprAST::codegen()`'s `'-'` case: when the operand is
  DIRECTLY an untyped `NumberExprAST`, fold the exact value (widen, negate,
  truncate) instead of calling `EmitCheckedIntNegate()` at all. A future
  session touching unary negation should know this AST shape needs to stay
  special-cased — removing it silently reintroduces this exact bug for
  `INT64_MIN` specifically (every OTHER literal value negates correctly
  either way, since only 2^63 collides with `INT64_MIN`'s bit pattern).
- **A literal nested inside a larger literal-only arithmetic expression is
  checked against int64 immediately, not deferred to the expression's
  final value.** FREEZE.md §6.2 row 6 says "only the final value is
  checked" — taken completely literally, `BIG - BIG2 + 1` should be legal
  if the final result fits, even if `BIG`/`BIG2` individually don't. This
  session's `tryFoldUntypedIntConstant()` does NOT implement that: a
  >64-bit leaf NESTED inside a larger expression is rejected immediately,
  citing `int`, regardless of what the surrounding expression's value
  would be. This is a deliberate, disclosed narrowing, not an oversight:
  `NumberExprAST::codegen()` truncates every literal through 64 bits
  BEFORE any arithmetic runs, unconditionally (SEM-001) — so even if the
  TypeChecker allowed such an expression through, Codegen would compute
  the WRONG value for it (arithmetic on the truncated, not exact, leaves).
  Rejecting it immediately is honest about what this compiler can actually
  carry through correctly today; a future session wanting the fully
  general "only the final value matters" semantics would need Codegen-side
  constant folding for this shape too (emitting a single pre-folded
  constant instead of a runtime add/sub/mul over separately-truncated
  literal operands), which this session deliberately did not build (no
  concrete need for it: the flagship `9223372036854775807 + 1` example, and
  every test this session wrote, only ever needs individual leaves that DO
  fit int64).
- **An untyped integer literal assigned directly to `double` is checked
  against int64 FIRST, not against double-exactness directly.** FREEZE.md
  §6.2 row 9 literally says "must be exactly representable" as a double,
  with no int64 precondition — which would, in principle, allow something
  like `mut d: double = <2^100 written out in decimal>;` (not exactly
  representable in `int` at all, since it exceeds int64, but exactly
  representable in `double`, since it has one significant bit). This
  session's `checkLiteralRepresentable()` rejects that case too (citing
  `int`, not `double`), for the same underlying reason as the pitfall
  above: Codegen converts an integer literal to `double` by first
  truncating it through a 64-bit `int` (`NumberExprAST::codegen()`, then an
  ordinary `SIToFP`), so a literal that doesn't fit int64 would silently
  convert the WRONG (truncated) value to `double` regardless of whether its
  true magnitude happens to be double-exact. A future session wanting the
  literal ideal here needs Codegen to convert an out-of-int64-range
  literal to `double` directly from its exact `APSInt`/via `APFloat`
  conversion, bypassing the 64-bit-int intermediate entirely — not built
  in this session (no test in this tree needs it, and it's a strict
  widening of what's accepted, not a correctness fix, so deferring it
  is safe).
- **A pre-existing, unrelated test-naming gap was found, not fixed:**
  `tests/07_functions_modules/export_qualified_cross_module.tr` has a real
  `main()` but its filename ends in `_module.tr`, so `test_runner.sh`
  silently excludes it (AGENTS.md's own documented trap). Predates this
  session (introduced in the `export immut` commit); out of SEM-002's
  scope (§25's spirit — don't drive-by-fix an unrelated pre-existing gap
  found only incidentally while running this group's own required naming
  sweep). Flagged here rather than silently left for the next session to
  rediscover from scratch.
- **`immut`/`export immut` constant REFERENCES are not folded for
  compile-time overflow detection**, only bare literal expressions are.
  `immut a: int = 9223372036854775807; immut b: int = a + 1;` is safely
  caught, but only at RUNTIME (via `EmitCheckedIntArith`, since `a` is an
  ordinary `VariableExprAST` to `tryFoldUntypedIntConstant()`, which
  returns `nullopt` for anything that isn't a literal/unary-minus/binary-op
  tree) — not as the COMPILE-time error FREEZE.md §6.2 row 6's "typed
  constants: error" phrasing calls for. This is the one place this session
  did not fully realize the frozen spec, disclosed rather than silently
  narrowed: full `immut` value constant-folding across variable references
  would need the TypeChecker (or Resolver) to track and re-derive a local
  `immut`'s statically-known initializer value, which is meaningfully more
  machinery than this session's literal-and-literal-arithmetic-only fold,
  and no test in §8's own testing scope requires it beyond "one fail_ test
  for compile-time typed overflow," which the bare-literal example already
  satisfies as written in §10.2. A future session adding this should start
  from `tryFoldUntypedIntConstant()`'s existing shape and extend the
  `VariableExprAST` case to look up an `immut` local's resolved initializer
  (mirroring how `export immut` constants already get resolved for
  Codegen's own `CodegenConstantValue()`, `ResolverConstantSymbol::IntVal`).
