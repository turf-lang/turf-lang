## Why
turf-fuzz's typed generator (2026-10-11) modelled `List<T>` and found that its
copies behave oddly. A `List` was the struct `{data, len, cap}`, copied by
value: a copy shared the buffer but not the length.

```
mut l: List<int> = List::default();
l.push(1);
mut m: List<int> = l;
m.push(7);          // writes data[1] in the shared buffer, bumps only m.len
print(l.length());  // 1
fn fill(x: List<int>): void { x.push(1); }
fill(l);            // lost: the callee grew its own copy
```

A copy's `push` could overwrite an element the original still counted, after a
`realloc` the two copies pointed at different buffers, and `Set`/`Map` copies
could rehash shared buckets under a stale count. The owner's decision
(2026-10-12): every collection type, present and future, is **shared by
default, copied on demand**.

Making a collection a handle needs a header allocated when the collection is
created: a zero-filled handle cannot be shared with the copies made before its
first `push`. The owner chose (2026-10-12, over "reject `::default()` for such
types" and "allocate the header lazily") a general rule: `T::default()` gives a
non-null `&U` field a fresh `heap(U::default())`. It also fixes a hole found
while checking this: the zero-filled `&U` was null, and

```
struct Hdr { len: int }
struct H { h: &Hdr }
mut a: H = H::default();
print(a.h.len);     // segfault in safe code
```

## Language semantics
### Old behaviour
As above: a collection copy shared the buffer and not the counts; a callee's
mutation of a collection argument was lost unless it only wrote existing
elements (`[]=`, `set`, `sort`). `outer[0].push(v)` was E098. `T::default()`
zero-filled a `&U` field (null), and a `string` field of a nested struct was
null instead of `""`.
### New behaviour
- **F-COLL-1.** `List`, `Stack`, `Queue`, `Set`, `Map` are handles. `=`, passing,
  returning and storing share one collection, length included; `.copy()` (new on
  all five) gives an independent one with the same elements in the same order.
  Above, `l.length()` is 2 after `m.push(7)` and 3 after `fill(l)`.
- **F-COLL-2.** `T::default()` sets every non-null `&U` field reachable by value
  (direct, through by-value struct fields, in fixed-array elements) to a new
  GC-heap `U::default()`, one per field and element. A type reaching itself again
  through `&` fields (`struct Node { next: &Node }`, or `A { b: B }` /
  `B { a: &A }`) has no default: **E147** `DefaultThroughReferenceCycleError`,
  hint `&?Node` or `::new`. Every field of a default is a default, so a nested
  `string` is `""`.
- `outer[0].push(v)` and `grid[0].push(v)` compile and land (E098 still rejects
  writes into fields of a returned struct copy, and `mm["a"]["b"] = v`).
### Is this breaking?
Yes, in meaning, for a program that relied on a collection copy being
independent: it now sees the other name's changes. The migration is `.copy()`
where independence was wanted. No program in `lib/std`, `showcase/`,
`examples/` or `tests/` relied on it (grep of every collection-typed `=` that is
not a constructor, and the suite). The surface (F-API-1) only grows: five `copy()`
methods; the collections' fields were private already. Done before 2.0.0 is
tagged, so it is a 2.0 rule. A `::default()` of a type with a `&` cycle used to
compile (and segfault on use); it is now E147.

## Compiler architecture
- **Codegen.** `EmitDefaultValue(T, Loc)` (`CodegenCore.cpp`, declared in
  `CodegenInternal.h`) replaces `GetDefaultValue()` in the `DefaultConstruct`
  branch (`CodegenFunc.cpp`). It builds the struct with `insertvalue` (LLVM folds
  it to a constant when nothing is allocated), resolves `NamedType`/`GenericType`
  fields to their registered struct the way `getDebugType()` does, allocates each
  `&U` with `HeapAllocateValue()` (the `heap()` path: `U`'s own descriptor), and
  keeps a stack of structs being defaulted through `&` to detect a cycle.
  `GetDefaultValue()` is unchanged and still used for declarations without an
  initializer (zero storage, F-INIT-2).
- **Monomorphizer.** `drainStructRequests()` now records Struct requests for the
  generic types a clone's own fields name (`List<Big>`'s `h:
  &ListHeader<Big>`), using `recordGenericFieldInstantiations()` (moved out of
  `TypeCheckerDecl.cpp`'s anonymous namespace, declared in
  `TypeCheckerInternal.h`). A clone is never type-checked, so nothing requested
  them: `struct Holder { items: List<Big> }` died with "monomorphized struct
  instantiation 'list.ListHeader_gen1_Big' was never given a real layout".
- **TypeChecker.** `containsUninstantiatedGenericParam()` (E129, `mut l =
  List::default();`) checks each field with `!isFullyConcreteType()` instead of
  `isOrWrapsGenericParam()`, so an open `T` inside a field's generic arguments
  (`&ListHeader<T>`) counts. Without it, that program became an LLVM-verifier ICE.
- **Diagnostics.** E147 (`ErrorCodes.h`, both pages). Raised in Codegen, so the
  query facade (turf-lsp) does not report it yet.

## Runtime changes
None. The header is an ordinary `heap()` block with its struct's descriptor; the
collector traces the buffer pointer in it.

## Standard-library changes
`lib/std/collections/{list,stack,queue,set,map}.tr`: each public type is now
`pub struct X<..> { h: &XHeader<..> }` over a private `XHeader` with the old
fields; every method reads `self.h.*`; algorithms unchanged. New `pub` methods:
`List.copy`, `Stack.copy`, `Queue.copy`, `Set.copy`, `Map.copy`, locked in
`tests/46_stdlib_surface/01_core_and_collections.tr`. `Map`'s `[]=` keeps its
`&Map<K, V>` parameter (part of the 2.x surface), though a handle would do now.

## New invariants
None in `INVARIANTS.md`; F-COLL-1/2 are frozen decisions with their evidence in
`tests/CONFORMANCE_ITEMS.md`.

## Removed assumptions
- "A collection is copied by value." Every copy now names the same collection.
- "`T::default()` is a compile-time constant." It allocates when `T` has a `&U`
  field; `GetDefaultValue()` is no longer the whole story for a struct default.
- "A non-null `&U` field may hold null after `::default()`." It may not.
- "`sizeof(List<T>)` is 24." It is 8 (one pointer); `tests/38_monomorphization/
  15_generic_struct_field_only.tr` and `16_...` were updated.
- "A struct clone's fields are concrete, so their generic types already exist."
  A generic type named by a clone's field has to be requested by the drain.

## Known pitfalls
- `x.push(G::default())` for a generic `G` (inferring `G`'s arguments from the
  parameter) is an ICE ("struct method call argument type mismatch"). It predates
  this change (same failure with a plain `struct Box<T>` on the old tree); bind
  the default to a typed variable first. Not fixed here.
- A `&U` field means one allocation per `::default()`. Defaulting a struct with a
  large fixed array of such elements allocates once per element.
- Arrays of structs with `&U` fields declared without an initializer
  (`mut a: H[2];` then reading a never-written element) still read a null `&U`;
  F-INIT-1 treats an array as assigned once any element is written. Separate
  issue by the owner's decision (2026-10-12).
- The cycle check follows `&` and by-value fields of the instantiated types. A
  `&?U` field ends the walk (it defaults to null).
