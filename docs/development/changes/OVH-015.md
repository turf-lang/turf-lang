## Language semantics

### Old behaviour

None of this item's own scope changes language semantics — it is
documentation and bookkeeping. One incidental fix was found and made while
demonstrating closure-gate item 3 (every `showcase/*.tr` must compile
warning-free): `showcase/http_server.tr` compiled a genuine dead-store
warning that pre-dated this session —

```turf
mut body: string = "";
mut status: string = "200 OK";
// ... every path of an exhaustive if/elseif/else overwrites `body`
// before any read of the initial "" ...
```

`turf showcase/http_server.tr` printed `Warning: Variable 'body' is
assigned but the value is never read (dead store).` at line 36 — a true
positive: the `= ""` initializer is provably dead on every path.

### New behaviour

```turf
mut body: string;   // no dead initializer; every path still assigns
                     // before the line-48/49 reads, so this compiles
                     // clean under definite-assignment
mut status: string = "200 OK";
```

Same example: `turf showcase/http_server.tr` now produces no warning.
Server behavior (the HTTP responses it sends) is byte-identical — verified
by running the `http_server.tr`/`http_client.tr` pair end to end (see
*Tests*).

### Is this breaking?

No. `showcase/` is not compiler input to any other program; removing a
dead initializer changes no observable behavior of the server itself.

## Compiler architecture

- **Codegen** (`src/CodegenCore.cpp`, ~line 955): a stale COMMENT (not
  logic) describing `getExprType()`'s free-function return-type recovery
  fallback as existing because "a generic FREE function is type-erased to
  ONE compiled version" — false since TYPE-002 (functions ARE monomorphized
  into independent compiled clones now). Rewritten to state the real,
  current reason this fallback still fires: `getExprType()` is Codegen's
  own separate, independent type-inference duplicate (never consults
  TypeChecker's or the Monomorphizer's results, per the identical framing
  the two neighboring, already-accurate comment blocks in the same file
  use, ~lines 900–914 and 1218–1238) whose own mangled-name reconstruction
  of a call can miss an exact match against how the Monomorphizer actually
  named a clone, falling through to the generic template's own still-
  unsubstituted declared signature — the unify-against-actual-arguments
  recovery this comment introduces is what patches that up. No logic
  changed, only the stated WHY; see *Known pitfalls* for the full audit of
  every other `TurfGenericParamType` hit in `src/Codegen*.cpp` this session
  checked while verifying closure-gate item 10.

## Removed assumptions

- **"`docs/architecture/compiler_pipeline.md` §7 and `memory_model.md` §2.7
  describe the current generics implementation."** False, and had been
  since TYPE-002 landed — both described type erasure (one shared compiled
  body, `TurfGenericParamType` as an opaque `void*` slot, `CastToType()`'s
  `IntToPtr`/`PtrToInt` bit-reinterpretation branch, a hard "struct >8
  bytes can't be `T`" limitation) when the actual implementation has been
  real monomorphization (one independently-compiled, fully-concrete clone
  per instantiation via `src/Monomorphize.cpp`'s `InstantiationCollector`)
  since TYPE-002. Both rewritten in place this session, verified against
  live source (`Monomorphize.cpp`/`Monomorphize.h`, `CodegenCore.cpp`'s
  `getLLVMType()`/`CastToType()` — confirmed the old erasure branches are
  gone, not merely dead) rather than only against other docs. A future
  reader should trust these two sections again; they were wrong for
  roughly a month of landed work (TYPE-002 through OVH-014) before this
  fix.
- **"A struct larger than 8 bytes can't be used as a generic `T`
  directly."** False as of TYPE-002 (verified live this session:
  `List<Big>`, a 24-byte three-`int`-field struct, compiles and runs
  correctly) — `memory_model.md` §2.7's old text still stated this as a
  live, unfixed architectural gap. The `List<T*>` pattern is no longer a
  required workaround, only an ordinary caller choice.
- **"`Map<K,V>`/`Set<T>` compare `string` keys/items by raw pointer
  identity, not content."** False as of monomorphization landing (verified
  live this session: `Map<string,int>.put("a",1); .contains("a")` →
  `true`; `Set<string>` correctly dedups two distinct `string` objects with
  identical content) — `README.md`'s "Known limitation" callout under
  Standard Library, and a roadmap bullet citing the same limitation, both
  described a bug that monomorphization (each instantiation gets its own
  compiled body, so a `string`-instantiated method genuinely calls
  `strings.tr`'s real `operator==`) already fixed; `docs/reference/stdlib/collections.md`
  had already been corrected (no mention of the limitation found there),
  making `README.md` the one place still asserting it.
- **"`README.md`'s module table entry `collections::set` is a valid import
  path."** False — `set.tr` lives under `lib/std/collections/` for
  browsing only; per `AGENTS.md`'s own stated rule ("a module's subfolder
  is invisible to `import`"), the real bare module name is `set`. Fixed
  live-verified (the module's own file header: `import set::Set;`).
- **"`docs/planning/OVERHAUL_REMAINING_WORK.md` will still exist for a
  citation written against it."** False as of this session — the file is
  deleted per its own header instruction, in this same commit. Every
  citation this session found (11 `docs/*.md` files, 10 compiler source
  files, 3 scripts) was individually re-pointed to the specific
  `docs/development/changes/` record that actually carries the
  detail, or — for genuinely historical narration (`OVERHAUL_CLOSURE_AUDIT.md`,
  every `changes/OVH-*.md` record, `ARCHITECTURE_OVERHAUL.md`'s status
  header, `ROADMAP_v2.0.0.md`'s Phase 0 section) — preserved and
  allowlisted in `scripts/doc_links_allowlist.txt` rather than edited
  retroactively (this repo's convention: a change record is a frozen,
  point-in-time document, not rewritten after the fact). A future session
  deleting or renaming any `docs/*.md` file MUST run
  `scripts/check_doc_links.sh` (no `--quiet`, read every line) before
  considering the deletion complete — this session found 12 dangling
  citations on the first attempt, all from files the initial
  `grep -rln --include="*.md" --include="*.sh"` sweep missed because they
  were plain `.cpp`/`.h` source comments, not docs or scripts.

## Known pitfalls

- **Closure-gate item 10 ("`grep -rn "TurfGenericParamType" src/Codegen*.cpp`
  shows only the `INV-GEN-1` assertions") does not pass literally.** Around
  twenty hits remain, not two. Every one was read individually this
  session: two are the `INV-GEN-1` assertions themselves; most of the rest
  are live code or comments inside `getExprType()`'s own independent
  type-inference duplicate (legitimate substitution/recovery logic, not an
  erasure path — see *Compiler architecture* above and OVH-007's own
  record for the precedent); the remaining comments were already correctly
  written in past tense about the erasure era. The actual bit-
  reinterpretation mechanism (`CastToType()`'s old generic-parameter
  branch) is confirmed **deleted outright** — the substantive property
  ("no erasure path is reachable") holds and was verified live; only the
  literal grep-count phrasing doesn't. See [OVH-CLOSE](OVH-CLOSE.md)'s own
  *Known pitfalls* for the full accounting — do not re-litigate this by
  attempting to reduce the grep count further; that would mean either
  deleting legitimate, load-bearing `getExprType()` logic (a real,
  separate refactor, out of this item's scope) or rewording comments that
  are already accurate.
- **A citation search for a file about to be deleted must include source
  code, not just docs and scripts.** This session's first sweep
  (`grep -rln --include="*.md" --include="*.sh"`) found 14 files; deleting
  `OVERHAUL_REMAINING_WORK.md` and running `scripts/check_doc_links.sh`
  immediately surfaced 10 MORE citations living in plain `.cpp`/`.h` doc
  comments (`OVH-002`/`OVH-010`/`OVH-011`/`OVH-014`'s own Codegen/
  TypeChecker/Parser/Intrinsics comments) that the extension-scoped grep
  never looked at. `check_doc_links.sh` itself scans `src`/`include`
  precisely because of this — trust the script's own file list
  (`find src include scripts docs`), not a hand-written grep, before
  deleting any `docs/*.md` file.
- **The `doc_links_allowlist.txt` entries added here are asymmetric on
  purpose.** `docs/planning/OVERHAUL_REMAINING_WORK.md` is allowlisted as a
  CITED path for three referrer globs (`docs/development/changes/*.md`,
  `docs/archive/OVERHAUL_CLOSURE_AUDIT.md`,
  `docs/archive/ARCHITECTURE_OVERHAUL.md`, `docs/development/ROADMAP_v2.0.0.md`)
  — every OTHER live citation found (10 source comments, 6 architecture-doc
  citations, 3 script comments) was re-pointed at the specific
  specific per-item change record instead of being
  allowlisted, because those are current, maintained documents where a
  reader following the citation TODAY should land on a file that still
  exists and still explains the mechanism — an allowlist entry is for
  genuine historical narration only (a frozen change record or the closure
  audit correctly saying "this is what the handoff document specified when
  it existed"), never a substitute for fixing a live pointer.
- **The old `docs/development/changes/OVH-CLOSE.md :: docs/planning/OVERHAUL_REMAINING_WORK.md`
  allowlist line (present since the closure audit pre-wrote it as a
  forward reference) had to be DELETED, not kept** — once `OVH-CLOSE.md`
  actually exists, the allowlist's own stated rule fires ("an entry whose
  file now exists... FAILS the check"), and once
  `OVERHAUL_REMAINING_WORK.md` (the referrer named in that same line) is
  deleted, the glob matches nothing regardless. Either condition alone
  would have obsoleted the line; both hold here.
