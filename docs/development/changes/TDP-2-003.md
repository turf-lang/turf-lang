Issue #285. Only V-1 is covered here; the other TDP-2-003 items append their own
sections.

## Why

A new warning in a minor release must be silenceable before it ships, or a user
is forced to edit correct code (`docs/planning/ROADMAP_v3.0.0.md` §5.4, rung 1).
There was no way to silence one warning, to fail a build on one, or to keep a
newer compiler's warnings off a build that was clean. Twenty of the twenty-three
warning classes did not even have a code a level could name.

## Language semantics

None. A program means the same under every level; a level only decides whether a
diagnostic prints and whether the build fails.

### Is this breaking?

No. Every warning starts at `warn`, exactly as before. A warning now prints
`[E163 · control flow]` in its header (the diagnostic text is outside the
compatibility promise, D-6).

## Compiler architecture

- **Diagnostics** · `src/diagnostics/LintLevels.{h,cpp}` holds the levels
  (`setLevel`, `setLintSet`, `levelOf`). `ErrorCodes.h` gains
  `ErrorCodeEntry::SinceMinor`, `isWarningCode()` (a class name ending in
  `Warning`) and rows E152–E171 for the twenty warnings that had no code. Pages
  `docs/errors/codes/` and `docs/slm/codes/` exist for each.
- **Lexer** · `DiagnosticEngine::add()` applies the level before anything else
  about the diagnostic: `allow` returns, `deny` records an error
  (`IsWarning = false`, `Diag::Denied = true`, skipped for a warning in `lib/std`
  unless `--stdlib-warnings`, and not run through `--smart`, which is for errors
  the compiler could not explain). `printDiag()` labels a denied warning
  `error`, says why, and `flushAll()` counts it as an error. The dedupe of a
  warning raised twice (the main file is parsed twice) also covers a denied one.
- **Driver** · `--allow|--warn|--deny <code>` and `--lint-set <2.N>` in
  `parseArgs()` and in `--test` (forwarded to every test compile); errors are
  usage errors (status 2). Interface 1.7 → 1.8.
- **turf-cli** (separate repository) · `[lints]` in `manifest.Parse`
  (`Lints.Args()`), passed ahead of the user's flags by `projectBuild.withLints()`
  for build, run, check and test; a manifest with the table needs interface 1.8.
- **Scripts** · `error_codes_check.sh` check 5: every warning class has a row
  and the naming holds; `doc_examples.py` reads the code of the first `── error`
  header, not of any `[E…]` in the output.

## Removed assumptions

- A warning has no code. All of them do, so a tool that matched warnings by text
  can match by code, and `turf explain E163` works.
- `[E…]` anywhere in compiler output means an error. A warning's header carries
  one too; only the `── error` / `── warning` word says which.
- "There is no flag that turns warnings into errors." There is, per code.

## Known pitfalls

- A level is process-wide state (`LintLevels`). The facade does not set it; an
  embedder that wants levels sets them before `turf::analyze` and resets after.
- A denied warning sets the line's error flag, so another diagnostic on that line
  is hidden until the first is fixed. This is the ordinary one-error-per-line
  rule; it is not special-cased.
- `E153` (a machine's start state) and `E158` (complexity) fire on correct code,
  which is exactly why levels exist; their pages say to `allow` them.
- The first warning added after 2.0 must give its registry row a `SinceMinor`
  (the fifth value, after `Important`) or the pin will not hold it back.

### Sections that must NOT change

The rule that a warning in `lib/std` is hidden (OVH-012) stands, `deny` included.

## Unresolved questions

- `--deny warnings` / `--deny-warnings` as a group (roadmap D-2): not added; it is
  only safe with the pin, which now exists.
- The facade (`AnalysisOptions`) has no per-call levels; `turf-lsp` would need
  them to honour `turf.toml`.
- Whether a dependency's own warnings should be exempt from the root package's
  `deny` (as `lib/std`'s are). Today a level applies to every file of the compile.
