# TDP-2-003 (V-1) — Lint levels

| | |
|---|---|
| **Status** | landed (V-1 to V-5; B-10 is a 3.0.0 change) |
| **Dates** | started 2026-10-19 · landed 2.2.0 (V-1, V-2 and V-5 2026-10-19) |
| **Commits** | (filled in at commit time) |
| **Sessions** | 1 of 1 for V-1 |
| **Depends on** | the code registry (#263), `DiagnosticEngine` as the one sink (§6.9) |
| **Frozen decisions relied on** | F-PKG-1 (the compiler never reads the manifest), F-DIAG-3 (no new categories); adds F-LINT-1 … F-LINT-5 (`FREEZE.md` §6.29) |

Issue #285. Only V-1 is covered here; the other TDP-2-003 items append their own
sections.

## Why

A new warning in a minor release must be silenceable before it ships, or a user
is forced to edit correct code (`docs/planning/ROADMAP_v3.0.0.md` §5.4, rung 1).
There was no way to silence one warning, to fail a build on one, or to keep a
newer compiler's warnings off a build that was clean. Twenty of the twenty-three
warning classes did not even have a code a level could name.

## Language semantics

None. A program means the same under every level; a level only decides whether a
diagnostic prints and whether the build fails.

### Is this breaking?

No. Every warning starts at `warn`, exactly as before. A warning now prints
`[E163 · control flow]` in its header (the diagnostic text is outside the
compatibility promise, D-6).

## Compiler architecture

- **Diagnostics** · `src/diagnostics/LintLevels.{h,cpp}` holds the levels
  (`setLevel`, `setLintSet`, `levelOf`). `ErrorCodes.h` gains
  `ErrorCodeEntry::SinceMinor`, `isWarningCode()` (a class name ending in
  `Warning`) and rows E152–E171 for the twenty warnings that had no code. Pages
  `docs/errors/codes/` and `docs/slm/codes/` exist for each.
- **Lexer** · `DiagnosticEngine::add()` applies the level before anything else
  about the diagnostic: `allow` returns, `deny` records an error
  (`IsWarning = false`, `Diag::Denied = true`, skipped for a warning in `lib/std`
  unless `--stdlib-warnings`, and not run through `--smart`, which is for errors
  the compiler could not explain). `printDiag()` labels a denied warning
  `error`, says why, and `flushAll()` counts it as an error. The dedupe of a
  warning raised twice (the main file is parsed twice) also covers a denied one.
- **Driver** · `--allow|--warn|--deny <code>` and `--lint-set <2.N>` in
  `parseArgs()` and in `--test` (forwarded to every test compile); errors are
  usage errors (status 2). Interface 1.7 → 1.8.
- **turf-cli** (separate repository) · `[lints]` in `manifest.Parse`
  (`Lints.Args()`), passed ahead of the user's flags by `projectBuild.withLints()`
  for build, run, check and test; a manifest with the table needs interface 1.8.
- **Scripts** · `error_codes_check.sh` check 5: every warning class has a row
  and the naming holds; `doc_examples.py` reads the code of the first `── error`
  header, not of any `[E…]` in the output.

## Runtime changes

None.

## Standard-library changes

None.

## New invariants

F-LINT-1 … F-LINT-5 (`FREEZE.md` §6.29), each with evidence in
`tests/CONFORMANCE_ITEMS.md`.

## Removed assumptions

- A warning has no code. All of them do, so a tool that matched warnings by text
  can match by code, and `turf explain E163` works.
- `[E…]` anywhere in compiler output means an error. A warning's header carries
  one too; only the `── error` / `── warning` word says which.
- "There is no flag that turns warnings into errors." There is, per code.

## Tests

- `scripts/smoke/lint_levels_smoke.sh` (new, CI on Linux, macOS and Windows):
  default, allow, deny (error label, counts, no executable), last flag wins,
  parse-time warning denied once, usage errors, lib/std, `--test`, `--lint-set`.
- `scripts/smoke/project_smoke.{sh,ps1}`: the `[lints]` cases through `turf`
  (the `.ps1` twin was written without a PowerShell to run it on).
- `tests/api/analysis_test.cpp` `testLintLevels`: levels through the facade, the
  pin (with a made-up `SinceMinor`, since no warning is newer than 2.0), every
  warning code can be named.
- `internal/manifest` and `cmd/turf` Go tests for the table and the flag order.
- The suite: 1521 tests pass unchanged.

## Known pitfalls

- A level is process-wide state (`LintLevels`). The facade does not set it; an
  embedder that wants levels sets them before `turf::analyze` and resets after.
- A denied warning sets the line's error flag, so another diagnostic on that line
  is hidden until the first is fixed. This is the ordinary one-error-per-line
  rule; it is not special-cased.
- `E153` (a machine's start state) and `E158` (complexity) fire on correct code,
  which is exactly why levels exist; their pages say to `allow` them.
- The first warning added after 2.0 must give its registry row a `SinceMinor`
  (the fifth value, after `Important`) or the pin will not hold it back.

## Handbook impact

| File / chapter | What is now wrong | Suggested replacement |
|---|---|---|
| Any page saying warnings cannot be silenced or promoted | The sentence | The "Lint levels" section of `docs/reference/cli_and_diagnostics.md` |
| Pages showing a warning's header | It lacked a code | The header with its `[E### · category]` |
| `turf.toml` descriptions ("three tables") | There are four | `docs/reference/projects_and_packages.md` §2 |

### Sections that must NOT change

The rule that a warning in `lib/std` is hidden (OVH-012) stands, `deny` included.

## Unresolved questions

- `--deny warnings` / `--deny-warnings` as a group (roadmap D-2): not added; it is
  only safe with the pin, which now exists.
- The facade (`AnalysisOptions`) has no per-call levels; `turf-lsp` would need
  them to honour `turf.toml`.
- Whether a dependency's own warnings should be exempt from the root package's
  `deny` (as `lib/std`'s are). Today a level applies to every file of the compile.

[TDP-2-001](TDP-2-001.md), [HYG-001](HYG-001.md) (the first two coded warnings)

# V-2 — Deprecation (`@deprecated`)

| | |
|---|---|
| **Status** | landed |
| **Dates** | 2026-10-19 |
| **Commits** | (filled in at commit time) |
| **Sessions** | 1 of 1 |
| **Depends on** | the annotation mechanism (`src/frontend/Annotation.h`, `AnnotationRegistry.h`, the same one `@ownership`/`@ffi` use), V-1's registry row + `SinceMinor` (just above) |
| **Frozen decisions relied on** | none new — this is an ordinary engineering judgement (FREEZE.md "Changing a frozen decision" rule 3: a session does not freeze a new decision on its own initiative), following the existing `@ffi`/`@ownership` shape exactly |

Issue #286. Roadmap: `docs/planning/ROADMAP_v3.0.0.md` 6.1 V-2 ("`@` is already
the spelling of `@caller_location`. Contextual, no new reserved word.").

## Why

A library that wants to rename or replace a function needs a way to say so
*before* the old name goes away — otherwise every caller finds out only when
their build breaks across a major version. `@deprecated("use X instead")`
gives that warning at every call site, with the exact replacement named,
while the old function keeps working exactly as before. Removal itself stays
a 3.0 job (roadmap B-3); this item is only the warning.

## Language semantics

None. A program with a `@deprecated` call compiles and runs exactly as it
would without the annotation; the only difference is a warning on stderr.

### Is this breaking?

No. `@deprecated` is new syntax on a declaration a program did not use before
(an unmarked function is unaffected), and the warning it produces starts at
`warn` like every other warning (V-1).

## Compiler architecture

- **Annotation** · `src/frontend/DeprecatedAnnotation.h` (new): `Name =
  "deprecated"`, `validate()` requires exactly one positional string argument
  (the message) — no `key: value` form, unlike `@ffi`'s per-platform pairs,
  since one declaration deprecates in exactly one way. Registered in
  `AnnotationRegistry.h` alongside `OwnershipAnnotation`/`FfiAnnotation`, so a
  misspelt `@deprecatd` is `E146` with a "did you mean" exactly like a
  misspelt `@ownership` always was — nothing in the Resolver's
  `checkAnnotations()` needed to change.
- **Diagnostics** · `ErrorsModule.h` gains `DeprecatedUseWarning` (next to
  `InvalidAnnotationError`, which already covers a malformed `@deprecated`
  itself); `ErrorCodes.h` gains row `E172` with `SinceMinor = 2` (the first
  code to actually use that field for something other than 0 — V-1 landed it
  but had nothing newer than 2.0 to apply it to). Pages added under
  `docs/errors/codes/` and `docs/slm/codes/`.
- **Lint** · `src/analysis/Lint.cpp`'s `LintVisitor`/`ChangedNodesLintVisitor`
  gain `visitFuncCall`/`visitMethodCall` overrides calling a shared
  `WarnIfDeprecated()`, which reads `FuncCallExprAST`/`MethodCallExprAST`'s
  already-resolved `ResolvedCallTarget` (`ResolverFunctionSymbol`, which
  already carries a copy of the declaration's `Annotations` — built for
  `@ffi`/`@ownership`, reused here unchanged) and warns with the first
  `@deprecated`'s message if one is present. Lint, not the Resolver or
  TypeChecker, is the integration point on purpose: it is the one pass
  guaranteed to see each function body exactly once (the pre-pass AST copy is
  deliberately skipped, per the existing comment at its call site in
  `main.cpp`), so this needed no new dedupe logic for the
  pre-pass/main-pass double-resolve every Resolver-raised or TypeChecker-raised
  warning already has to guard against (`FirstWarningAt()`,
  `ResolverDecl.cpp`).

## Runtime changes

None.

## Standard-library changes

None — no `lib/std` function is marked `@deprecated` by this change. A later
change that wants to deprecate a real stdlib function (e.g. ahead of a 3.0
removal) can do so with no further compiler work.

## New invariants

None recorded in `INVARIANTS.md` — this is additive syntax with no
compile-time guarantee to break, in the same way `@ffi`/`@ownership` recorded
none for themselves.

## Removed assumptions

- "The annotations are `@caller_location`, `@ownership` and `@ffi`" — the
  reference doc's enumeration (`functions_and_modules.md` §4) now lists four.
- `ErrorCodeEntry::SinceMinor` was landed by V-1 with nothing non-zero in the
  table yet (no warning was newer than 2.0); this is the first row that
  actually needs it.

## Tests

- `tests/49_annotations/deprecated_warns_on_call.tr`,
  `deprecated_warns_on_method_call.tr`, `deprecated_on_extern_fn.tr`: a plain
  (non-`fail_`) program that compiles and runs to exit 0, pinning `E172` and
  the exact message via `EXPECT-DIAG` — one for a free function, one for an
  instance method, one for an `extern fn`.
- `tests/49_annotations/fail_deprecated_without_argument.tr`,
  `fail_deprecated_non_string_argument.tr`, `fail_deprecated_keyed_argument.tr`,
  `fail_deprecated_empty_message.tr`: each malformed shape, `E146`
  (`InvalidAnnotationError`, the same code every other annotation shape error
  uses).
- `tests/CONFORMANCE.md`'s "Diagnostics" row already globs
  `tests/49_annotations/` and `tests/49_annotations/fail_*.tr`, so the new
  files need no map edit.

## Known pitfalls

- Only a **direct** call (`f(...)`/`x.f(...)`) warns. A deprecated function
  taken as a first-class value (`mut g: fn(int): int = old_fn;`) and called
  indirectly through `g` does not — `IndirectCalleeType`'s branch has no
  `ResolverFunctionSymbol` to read annotations from. Narrower than "every
  use" in the fully general sense; matches this item's roadmap complexity
  (`Cx: S`) and is not pursued further here.
- `@deprecated` only applies where `AnnotatedDecl` already does: a `fn` or
  `extern fn` (free, static or instance-bound). It cannot mark a whole
  `struct`/`enum`, a field, or a module — the same scope `@ownership`/`@ffi`
  already have, not a new restriction invented for this item.

## Handbook impact

| File / chapter | What is now wrong | Suggested replacement |
|---|---|---|
| `functions_and_modules.md` §4's annotation list | Named three annotations | Now four; new `### @deprecated` subsection added |
| `cli_and_diagnostics.md`'s code count/category table | 171 codes, 23 warnings | 172 codes, 24 warnings; `E172` added to the "declaration" category row and the per-code warning table |

### Sections that must NOT change

None identified.

## Unresolved questions

- Whether `@deprecated` should eventually extend to `struct`/`enum`
  declarations once (if) annotations themselves grow that reach — explicitly
  out of scope here, since no other annotation can do it today either.

## Related records

[TDP-2-003 V-1](#) (above, same file) for the registry/`SinceMinor`
mechanism this reuses; `src/frontend/FfiAnnotation.h` for the annotation
shape this follows.

# V-5 — One registry of every diagnostic code

| | |
|---|---|
| **Status** | landed |
| **Dates** | 2026-10-19 |
| **Commits** | (filled in at commit time) |
| **Sessions** | 1 of 1 |
| **Depends on** | the code registry (#263) and V-1's `SinceMinor` and warning rows |
| **Frozen decisions relied on** | none new |

Issue #289.

## Why

The API-lock diff (`ROADMAP_v3.0.0.md` 5.5.2) needs one list of every code with its
kind, the release that added it and its level. `ErrorCodes.h` held most of that,
but the reference page restated it by hand (a code count, the warnings' range, the
retired codes, a per-category table), and nothing failed when the two disagreed.

## Language semantics

None. Documentation and CI only; no compiler or runtime change.

## Compiler architecture

- **Scripts** · `scripts/check/diagnostic_registry.py` reads `AllErrorCodes` and
  its `ErrCode::` constants. `--write` regenerates the table between the
  `diagnostic-registry` markers in `docs/reference/cli_and_diagnostics.md` (code,
  kind, since, starting level, category, class, retired/important);
  `--json` prints the same rows for a tool; `--check` (CI, `session_postflight.sh`)
  fails when the table is not what `--write` would produce, when the codes are not
  `E001`…`E0NN` without a gap, when a registered code lacks a `docs/errors/codes/`
  or `docs/slm/codes/` page or a page has no row, when a `"Exxx"` literal in `src/`
  or `include/` is unregistered, and when a page under `docs/reference/` names a
  code the registry lacks.
- The hand-written category table, the code count and the warning range on the
  reference page are gone; the generated table replaces them.

## Runtime changes

None.

## Standard-library changes

None.

## New invariants

None frozen. The registry is the source and the reference table is derived from it.

## Removed assumptions

- "The reference page's counts and category table are kept current by hand."

## Tests

`diagnostic_registry.py --check` is the test. Checked by breaking it: renumbering
`E172` to `E173` in the registry fails the check six ways (gap, missing pages,
stale pages, stale references, stale table), and restoring it passes.

## Known pitfalls

- `Since` is `ErrorCodeEntry::SinceMinor`, which only a warning's row states; every
  error shows `2.0` whether or not it shipped then. Give a row its real value when
  a code is added after 2.0.
- `Level` is the level before anyone names one: `warn` for a warning, `error` for
  an error, which has no level to choose.

## Handbook impact

| File / chapter | What is now wrong | Suggested replacement |
|---|---|---|
| `cli_and_diagnostics.md` "Error codes" | A hand-kept category table and counts | The generated table |

### Sections that must NOT change

None identified.

## Unresolved questions

- IF-3 (website error pages from this registry) can read `--json`; whether that
  stays a script or becomes a `turfc` flag is open.
