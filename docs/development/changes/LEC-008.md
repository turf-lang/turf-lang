## Why
Found while building the language server (SMP-001, `SMP-001.md` unresolved
question 4). With `import json;`, which itself imports `io`, a file could write
`io::printline(...)` and it compiled. The server's completion, correctly,
offers only what a file imports, so it suggested `io` as an auto-import where
the code already worked. The owner's answer (2026-10-06): the leak is not
intended. A file may use `m::` only for a module it imports itself.

Cause, read from the code on 2026-10-07: `ResolverModuleTable::Modules_` is
one global table, `hasModule(m)` means "loaded anywhere in the program", and
every qualifier check (`validateModuleQualifier`, the qualified-call branch of
`visitFuncCall`, `visitScopeAccess` for `m::CONST`, and the type-spelling
resolvers) asked only that. The **bare** call path was already per-file
(`FlatImportedFunctions_`, keyed by the importing context); only the qualifier
path was global. Nothing about a file's own imports was ever consulted.

## Language semantics
### Old behaviour
```
import json;
fn main(): int { io::printline("x"); return 0; }   // compiled
```
### New behaviour
The same program is `E145` `ModuleNotImportedError`: *Module 'io' is not
imported in this file.* Hint: ``Add `import io;` at the top of this file to use
'io::printline'.`` Rules are `FREEZE.md` §6.24 (F-IMP-1..5); the two that
surprise are:
- `import list::List;` no longer makes `list::List<int>` legal (F-IMP-2): a
  symbol import brings in the name, not the qualifier. Write `import list;` too.
  When the file has such an import, the hint says so.
- `x.f()` (UFCS), methods and operators still see every loaded module
  (F-IMP-4): they follow the type, not the import list. And a value whose type
  comes from an unimported module can be held and used (F-IMP-3); only
  *spelling* `io::T` needs the import.
### Is this breaking?
Yes, for a program that used a module's qualifier without importing the module
itself, or that relied on `import m::X;` to spell `m::X`. Every fix is one
added `import m;` line, and the diagnostic prints it. Done before 2.0.0 is
tagged, so it is a 2.0 rule and not a 3.0 break. In this repository exactly 8
test files were affected and nothing in `lib/std`, `showcase/` or `examples/`.

## Compiler architecture
- **State.** `ResolverModuleTable::BareImports_` (context -> modules named by a
  plain `import m;` in that context), `SymbolImports_` (same keying, for the
  symbol forms: grants nothing, only lets the hint say so), with
  `noteBareImport` / `noteSymbolImport` / `isModuleImportedBy` /
  `hasSymbolImport`. `hasModule()` keeps its meaning and stays the question for
  suggestions. Filled in Pass 1a (the import branch of `hoistTypesIn`,
  `ResolverTypeIdentity.cpp`), the first place a file's imports are seen, because
  Pass 1b resolves qualified spellings before `hoistModuleBody` runs.
- **The gate.** `Resolver::requireModuleImported()` (raises E145) and its silent
  form `Resolver::mayQualifyWith()` (`ResolverVisibility.cpp`); the latter is
  "prelude module, or the context's own module, or in `BareImports_[context]`".
  Called at every place a qualifier is *spelled*: `validateModuleQualifier` and
  `ResolveOrReport` (`ResolverDecl.cpp`), the module-function branch of
  `visitFuncCall` and the `m::CONST` branch of `visitScopeAccess`
  (`ResolverCall.cpp`). `tryResolveTypeSpelling` leaves a not-imported spelling
  unresolved, silently, so Pass 2 reports it with a location (the same trick the
  LEC-002 private-type check uses).
- **Prelude.** `IsPreludeModuleName()` (`Parser.h` / `ParserModule.cpp`, reading
  the same `PreludeModuleNames` array `scripts/check_boundary.sh` cross-checks)
  makes the six prelude modules spellable in **every** file. The parser injects
  them into the main file only, so without this a module using `strings::` would
  newly fail. Found by hand, after the first version of the gate had shipped to
  the working tree: the suite had no test for it. Now
  `import_scope_prelude_qualifier.tr`.
- **Diagnostic.** `ModuleNotImportedError` (`ErrorsModule.h`), **E145**, category
  `DECLARATION` (existing: the SLM page can state the fix, so no new category was
  needed). A new *code*, not a reuse of E031 (unknown qualifier): a typo and a
  forgotten import are different mistakes with different fixes. Pages:
  `docs/errors/codes/E145.txt`, `docs/slm/codes/E145.txt`.
- **Monomorphized clones** are resolved with their *template's* module pushed
  (`resolveMonomorphizedClone`), so the gate judges them by the template's
  imports, never the instantiating file's.
- **Suggestions** still call `getAllModuleNames()` (all loaded modules).
- The temporary `probeModuleImported()` used to size the change is gone.

## Known pitfalls
- **A test named `*_module.tr` is silently skipped by the runner** (AGENTS.md's
  trap). `import_scope_prelude_in_module.tr` was one: the suite total did not
  move, which is how it was noticed. It is `import_scope_prelude_qualifier.tr`.
- Pass 1b resolves qualified spellings **before** `hoistModuleBody`, so the
  import set must be filled in Pass 1a or the first qualified type in a file
  would be judged against an empty set.
- A diamond must not make one file inherit another's imports; the set is keyed
  by the writing file, never by the module (`fail_import_scope_diamond`).
- `turfc --resolve` writes the program binary into the **current directory**; a
  sweep loop run from the repo root leaves executables there.
- Unchecked: `ClaimEntryFileImportSlot` (INV-STD-3), the path that binds an
  import of the entry file to its own parse, was not given a test of its own.
- **Toolchain, unrelated to this change:** on 2026-10-07 the system LLVM moved
  22 -> 23 and the tree stopped building (`CreateGlobalStringPtr`,
  `OptimizationLevel::Os`, `BasicBlock::getTerminator()` asserting). The owner
  restored LLVM 22.1.8 the same day; every result above is on 22.

## Follow-up 1 — the prelude grows (owner decision, 2026-10-07)
Asked for right after the confirmation above: "everything from io, math and
anything extra that should be there should come imported … they can just write
`printline()` and `print()`". Frozen as `FREEZE.md` §6.25 (F-PRE-1..4); the
mechanics, in the order they bit:
- **Nine prelude modules**, `io`, `math` and `sys` added (`PreludeModuleNames`,
  `src/ParserModule.cpp`). The three files moved to `lib/std/core/` so the
  existing spec "the prelude is exactly `core/`" and its checker
  (`scripts/check_boundary.sh`, check 2) stay true; no `import` changed, since a
  module's subfolder is invisible to `import`. Live doc and comment paths were
  updated; historical change records keep the old paths on purpose.
- **Bare tier in `Resolver::visitFuncCall`**, consulted only when the file's own
  functions, the module's own and explicit imports have no function of that name.
  Hence the prelude can never create an ambiguity, and a user declaration hides
  it. Measured: of the 1150 tests then existing only 2 changed behaviour (below); the
  `fail_*` tests that expected an unknown bare function still fail, because they
  call a function of a *non-prelude* module.
- **UFCS tie-break** (`TypeChecker::tryUFCSFallback`): `math`'s public libm
  `floor`/`ceil`/`round` and `double.tr`'s own tied exactly for every
  `double.floor()`, which was an `E125` in `23_stdlib_primitives/02_double_helpers`
  and `46_stdlib_surface/01_core_and_collections`. The receiver type's own prelude
  module now wins an exact tie. No public name changed; the docs' old claim that
  the two "exist simultaneously without conflicting" had only been true while
  `math` was opt-in. (`double::floor(x)` was never spellable: `double` is a type
  keyword.)
- **Judgement calls I made, not asked for** (cheap to change; both are one entry
  in `PreludeBareModuleNames`/the loop): *all* public functions of `io` are bare,
  including the file ones (`exists`, `read_to_string`, `write_string`,
  `read_lines`), and `sys` was added as the "anything extra" (`exit`, `panic`,
  `abort`). Constants stay qualified (`math::PI`); bare `E` would clash with
  ordinary generic-parameter names.
- **Not done on purpose:** types (`List`, `Map`, ...) are not in the prelude; the
  request said "operations". It is the obvious next question.
- **A latent codegen bug the new prelude exposed, found with ASan.**
  `FuncDefExprAST::codegen` erased the dead `after_ret` block and left the
  builder pointing at the freed block when the function had no caller to
  restore (a module's own top-level function); the module body's
  `BlockExprAST::codegen` then called `getTerminator()` on it. It read freed
  memory harmlessly until the heap layout changed: with nine prelude modules,
  `turfc --check --module` on a file under a `mktemp` directory segfaulted (exit
  139), which `scripts/slm_doc_examples_check.sh` caught on the E014 page. Fixed
  with `Builder->ClearInsertionPoint()` after the erase. **No deterministic
  regression test exists** (the failure depends on heap layout); the evidence is
  the ASan run that named the line, and that check now passing.
- **The 6 → 9 sweep of mentions:** `AGENTS.md`, `boundary.md` §4, `Intrinsics.h`
  §4, `core.md`, `scripts/session_postflight.sh` (now compiles all nine directly).

## Follow-up 2 — the language server (`turf-lsp`, separate repository)
Asked: "check if the LSP is cheating … when it does not suggest to import `io`
and also does not give an error". Probed with the real server against the
current compiler. **Not cheating where it counts:** `printline("hi")`,
`io::printline`, `math::abs` give no diagnostic and no import suggestion, hover
and go-to-definition on a bare `printline` resolve to `lib/std/core/io.tr`, and an
unloaded module (`json::`) still gets `E031` with a working quick fix; all of it
is read from the compiler's analysis. **Three real gaps**, none visible before
this change because the leak hid the situation:
1. `E145` had **no quick fix** (the server only knew `E031`, "module not loaded
   at all"). Added: *Add `import list;`*, also for the symbol-import-only case.
2. `list::` **member completion** was offered for any loaded module and inserted
   a call the compiler then rejects. Now the item also adds `import list;` unless
   the file imports it (read through `symbols().isModuleImportedBy(m, "")`).
3. **Bare completion** did not offer `printline`, `abs`, `exit`, ... Now offered
   (unless the file declares a function of that name, which hides them).
New compiler API: `turf::preludeBareModules()`. Server tests: the two stale `io`
expectations were rewritten (json is the E031 example now) and four tests added
(`prelude_needs_no_import`, `code_action_e145_*`, `completion_prelude_functions`,
`completion_member_of_unimported_module_adds_the_import`); the last two fixes
were **mutation-checked** (feature disabled, test fails, restored).
Not done: a real VS Code window was not driven (needs a display), and nothing was
built or run on Windows or macOS.
