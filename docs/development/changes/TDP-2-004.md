# DX-2 — `--diagnostics=json`

| | |
|---|---|
| **Status** | landed |
| **Dates** | 2026-10-24 |
| **Commits** | (filled in at commit time) |
| **Sessions** | 1 of 1 |
| **Depends on** | DX-1's compiler fixes (TDP-2-001), `DiagnosticEngine` as the one sink |
| **Frozen decisions relied on** | D-6 (diagnostic text is outside the promise; codes and exit statuses are the contract), F-CLI-1 (exit statuses) |

Issue #290. Driver interface 1.8 → 1.9.

## Why

Tools (`turf-lsp`, `turf-fuzz`, the SL-2 benchmark) read the compiler's
diagnostics by matching its text, which D-6 keeps outside the compatibility
promise, so any wording change could break them. They need a form whose shape
is a promise.

## Language semantics

None.

## Compiler architecture

- **Diagnostics** · `src/diagnostics/DiagnosticsJson.{h,cpp}`: `render()` turns
  one `DiagnosticEngine::Diag` into one line of JSON with `llvm::json`. Colour
  is stripped, the text form's heading line becomes `title`, a hint embedded in
  a raw parser message becomes `hint`, the `Warning: ` prefix is dropped
  (`severity` says it), and file paths lose `dir/..` steps. The fix is the
  checked `CompilerFix`, so `fix` is exactly what the text form's `Fix:` shows.
- **Lexer** · `DiagnosticEngine::flushAll()` writes the JSON lines in place of
  the text when `DiagnosticsJson::Enabled`, after the same sort, fix check and
  standard-library filter. Every exit point that flushes the text flushes the
  JSON, which is why the form is one object per line and not one document.
- **Driver** · `--diagnostics=json|text`; any other value is a usage error
  (status 2). `TurfcInterfaceMinor` 9.
- **Schema** · `docs/reference/schemas/diagnostics.schema.json`, version `1.0`
  (`DiagnosticsJson::SchemaVersion`): a minor adds fields, a major changes or
  removes one. Fixtures for consumers' tests in
  `docs/reference/schemas/diagnostics-fixtures/` (IF-2).

## Runtime changes

None.

## Standard-library changes

None.

## New invariants

None frozen. Checked by `scripts/check/diagnostics_json_check.py` (CI,
`session_postflight.sh`): for every `fail_*` test, every stderr line is one
object matching the schema, the JSON and text forms report the same severities
and codes in the same order with the same exit status, and the fixtures equal
the compiler's output for their sources.

## Removed assumptions

- "A tool must parse diagnostic text."

## Tests

- `diagnostics_json_check.py`: 805 `fail_*` files and 3 fixtures pass. A
  corrupted fixture fails it; the schema validator rejects a wrong severity,
  a malformed code, a span missing its end, a fix with no edits, a non-boolean
  `denied` and a missing field.
- The suite and `turf-api-tests` pass unchanged.

## Known pitfalls

- A usage error (status 2) prints text: there is no diagnostic to render.
- `--smart`'s model suggestions are text.
- `title` is the text form's heading line when it ends in `!` or `:`; some
  headings are a generic lead-in ("Oops! Something doesn't add up:").

## Handbook impact

| File / chapter | What is now wrong | Suggested replacement |
|---|---|---|
| Any page telling tool authors to parse diagnostics | The advice | "Diagnostics as JSON" in `docs/reference/cli_and_diagnostics.md` |

## Unresolved questions

- `turf-lsp` and `turf-fuzz` reading the JSON is their own change, against a
  release that has interface 1.9.
- A SARIF export (the roadmap's "SARIF-shaped") can be produced from these
  objects by a tool; not built in.

## Related records

[TDP-2-001](TDP-2-001.md), [TDP-2-003](TDP-2-003.md)

# IF-1 — The interface manifest, `turfc --version --json`

| | |
|---|---|
| **Status** | landed (compiler); each consumer reads it in its own repository |
| **Dates** | 2026-10-24 |
| **Commits** | (filled in at commit time) |
| **Sessions** | 1 of 1 |
| **Depends on** | DX-2 above (its schema version is in the manifest) |
| **Frozen decisions relied on** | F-PKG-1, FREEZE.md 6.16 (lines 1 and 2 of `--version` are a contract; later lines may be added) |

Issue #292. Driver interface 1.9 → 1.10. Roadmap: IF-1.

## Why

`turf`, `turf-lsp` and `turf-fuzz` each assume what a compiler revision can do
(a flag, a format). The interface number says whether one exists only to a
reader who knows the history; a list of named features and format versions
says it directly.

## Compiler architecture

- **Driver** · `printVersionManifest()` (`src/driver/main.cpp`), reached when
  `--version` and `--json` are both on the command line, before any compiler
  state exists, like the text `--version`. `InterfaceFeatures` names each
  minor of the interface history beside the comment that records it; the
  manifest lists those up to `TurfcInterfaceMinor`, then `smart`,
  `embedded-lld` and `bundled-runtime` when this build has them.
- **Package graph** · `PackageGraphFormat` (`src/tooling/PackageGraph.h`) is
  the format `LoadPackageGraph()` accepts and the manifest reports.
- **Schema** · `docs/reference/schemas/version.schema.json`, `"manifest": 1`:
  keys are only added.

## Tests

`scripts/check/diagnostics_json_check.py` validates the manifest against its
schema and checks it agrees with the text lines and with the version the
diagnostics carry. A wrapper whose text `--version` says `interface 1.9` makes
it fail.

## Known pitfalls

- A new interface minor needs a new `InterfaceFeatures` row; without one the
  feature list stops at the previous name and the manifest still validates.
- 1.10 is the first two-digit minor; `turf` parses the minor as an integer
  (`internal/driver/handshake.go`), so 1.10 is newer than 1.9 there.

## Unresolved questions

- `turf`, `turf-lsp` and `turf-fuzz` reading the manifest in place of their own
  assumptions is a change in each of those repositories.
