## Why

`docs/development/changes/MEM-002.md` — the collector's own landing
record — closed with two questions stated as genuinely open, not merely
"could be nice later":

1. **Real-world exercise is still narrow.** Five small `tests/41_gc/`
   files, two smoke scripts, and a `showcase/` sweep were the entire extent
   of what had ever run under this collector. Nothing resembling a
   long-running server, a large/complex object graph, or sustained
   high-volume allocation churn had been tried.
2. **The register-scanning technique (inline asm, not `setjmp`) has not
   been cross-validated against an independent conservative-GC
   implementation** on this exact toolchain/kernel combination. It is
   modeled on Boehm GC's own documented reasoning, and this project's own
   tests pass, but "modeled on a technique known to be correct elsewhere"
   is not the same claim as "independently verified correct here."

`ROADMAP_v2.0.0.md`'s FDN-005 entry exists specifically to close both,
before a public release asks this collector to survive load nobody
connected to this project's own test suite has generated yet.

## Language semantics

None. This group changes nothing about what a Turf program can express or
how it behaves when compiled normally — every addition is either an
opt-in, testing-only runtime environment variable, a separate CI/build
artifact (the ASan runtime), or new test content. A program compiled and
run the ordinary way (no `TURF_GC_STRESS`/`TURF_GC_VALIDATE`, not linked
against `libturfrt_asan.a`) is byte-for-byte unaffected.

### Old behaviour / New behaviour / Is this breaking?

N/A — no observable-behaviour change for any existing program. See
*Runtime changes* below for what actually changed.

## Compiler architecture

- **Driver (`src/main.cpp`)** — `linkObject()` now picks the runtime
  archive name (`turfrt` or `turfrt_asan`) and whether to append
  `-fsanitize=address -fsanitize=undefined` to the final `cc`/`gcc`
  invocation based on a single compile-time macro, `TURF_RT_ASAN_BUILD`
  (set only when `turf` itself was built with `-DTURF_RT_SANITIZE=ON`,
  never by anything in the environment at link time). No other pass
  changed — Lexer/Parser/Resolver/TypeChecker/Codegen are all untouched.

## Runtime changes

All of it, per the roadmap's own four stages:

**Stage 1 — Stress corpus.** `tests/custom/gc_stress_corpus/` (excluded
from `test_runner.sh` by the same `tests/custom/` convention
`scripts/test_ai.sh`'s `aggressive/` fixtures already use, AGENTS.md) adds
three long-running programs, each compiled and run by the new
`scripts/gc_stress_corpus_smoke.sh` (`gc_rss_smoke.sh`'s own
compile-run-measure-RSS pattern, extended to a client/server pair for the
third):

- `million_node_graph_churn.tr` — a `heap()`-allocated graph of 1,000,000
  nodes, rewired across 4 passes (each followed by a forced
  `gc_collect()`), then verified node-by-node and via a full cycle
  traversal. Measured live: ~112MB peak RSS (real LIVE data at this
  scale — 1M `GraphNode` blocks plus two 8MB `List` backing buffers plus
  the block table itself — checked against a 300MB bound with headroom
  for platform variance, not a "should be near zero" bound the way
  `gc_rss_smoke.sh`'s own checks are).
- `map_of_lists_churn.tr` — `Map<string, List<string>>` churned for the
  roadmap's own literal 10,000,000 `put()` operations against a bounded
  500-key working set (measured live: 5.2s, ~7.7MB peak RSS — every
  overwritten value is 3 GC objects' worth of instant garbage).
- `http_load_server.tr` / `http_load_client.tr` — a near-copy of
  `showcase/http_server.tr`'s own handler (not the showcase file itself,
  which stays untouched as its own separate regression target), raised
  from that demo's 1000-request loop bound to 100,000, driven by a real,
  sequential, in-process Turf client for the full count. Measured live:
  ~31s, ~3.4MB peak server RSS.

**Stage 2 — `TURF_GC_STRESS=1`.** `turf_gc_note_alloc()`
(`runtime/turfrt_gc.c`) now checks a lazily-cached environment variable
(read once, cheap on every subsequent allocation) and, if set, forces
`turf_rt_collect()` unconditionally instead of waiting for the
heap-doubling threshold — the single most effective way to surface a root
the primary scan barely misses, since under ordinary allocation pressure a
real program only collects a handful of times over its whole run.
`scripts/test_runner.sh` gained a `TURF_TEST_TIMEOUT_SEC` override (the
per-test wall-clock bound was a hardcoded 5s in two `sleep 5` call sites,
exported to the `xargs`-spawned subshells alongside `COMPILER`/
`TURF_OPT_FLAG`) — needed because `tests/08_e2e_stress/
07_heap_bounded_allocation.tr` alone (5,000,000 `heap()` calls) takes
~3.5 minutes under stress mode at `-O0`, purely from paying a full
stop-the-world collection per allocation instead of per heap-doubling.
Wired into CI as two full-suite runs (`-O0`, `-O2`, `TURF_TEST_TIMEOUT_SEC=300`)
— **837/837 green at both levels**, measured live.

**Stage 3 — Independent validation**, two independent halves:

1. **An ASan+UBSan-instrumented runtime.** `CMakeLists.txt`'s new
   `TURF_RT_SANITIZE` option builds a second static library,
   `turfrt_asan` (same four `.c` sources as the ordinary `turfrt` target,
   `-fsanitize=address -fsanitize=undefined -g -fno-omit-frame-pointer`),
   landing at `lib/libturfrt_asan.a` alongside (never instead of)
   `lib/libturfrt.a` — a deliberate naming split, not a directory split,
   so an ordinary dev build and a `-DTURF_RT_SANITIZE=ON` build can
   coexist without either clobbering the other's runtime archive. The
   SAME option also defines `TURF_RT_ASAN_BUILD` when compiling `turf`
   itself, which makes `linkObject()` (`src/main.cpp`) link every
   COMPILED TURF PROGRAM against `libturfrt_asan.a` with the sanitize
   flags, permanently, for that one `turf` binary — turning the entire
   existing `tests/` regression suite into independent validation for
   freed-block reuse, not just `scripts/gc_smoke.sh`'s hand-written C
   harnesses (which already got informal ASan coverage during MEM-002's
   own development, per that record's *Removed assumptions*). CI's new
   `gc_hardening_asan` job configures a separate `build_asan/` directory
   and runs the full suite (default level, `-O0`) plus `turf-api-tests`
   against it, with `ASAN_OPTIONS=detect_leaks=0` (MEM-002's own
   documented decision not to run a final collection at shutdown is not a
   leak — LeakSanitizer has no way to know that).

   Getting a real program running under this at all surfaced two genuine,
   previously-invisible GC/ASan interactions, both fixed in
   `runtime/turfrt_gc.c`:
   - `gc_scan_range_conservative()`'s word-by-word stack read aborted on
     the very first collection ever run under ASan — not a real bug, but
     ASan's own inserted stack redzones (padding around every local/array
     in every already-returned frame the conservative scan deliberately
     walks) being read as though they might be pointers, exactly like any
     other stack word. Fixed by skipping any word `__asan_region_is_
     poisoned()` reports as poisoned (guarded behind a new `TURF_GC_ASAN`
     detection macro) — scoped to JUST this function, so a genuine
     freed-block-reuse bug reached through `gc_scan_block_precise()`'s own
     HEAP reads still aborts normally.
   - `turf_gc_record_stack_base()`/`gc_mark()`'s own "current SP"
     approximation (`(uintptr_t)&marker` for a plain local `int`) is not
     safe under ASan's default `detect_stack_use_after_return=1`: ASan may
     relocate an ordinary local's storage onto a HEAP-allocated "fake
     stack" specifically to detect a pointer to it outliving its function
     — exactly what this idiom does on purpose. The result was a real
     SEGV (a scan range with a heap address as its lower bound and a real
     stack address as its upper bound). Fixed by extracting the idiom into
     a new, tiny, `noinline` helper (`gc_approx_sp()`) marked
     `__attribute__((no_sanitize("address")))` under `TURF_GC_ASAN` —
     scoped to this one function (whose only job is "take a local's
     address"), not `gc_mark()` itself, so `gc_mark()`'s own real
     block-table reads/writes stay fully ASan-instrumented.
   - A related fix, not ASan-specific but found while chasing the above:
     `turfrt_signal.c`'s `SIGSEGV` handler now installs **nothing** when
     built under ASan (`TURF_SIGNAL_ASAN`, the same detection duplicated
     locally) — `sigaction()` unconditionally REPLACES the previous
     handler, and ASan's own runtime already installs a far more capable
     one (a real stack-overflow/invalid-access report with a full trace)
     from its process-startup constructor. Installing this file's own,
     simpler handler on top would have silently discarded ASan's, turning
     every ASan-detected fault into a generic one-line message with none
     of ASan's own diagnostic detail — found live, the first time this
     path was actually exercised under ASan.

2. **`TURF_GC_VALIDATE=1`** (Linux/glibc/x86-64 only — `TURF_GC_VALIDATE_
   SUPPORTED`, gated the same honest way `TURF_GC_REGCAP_*`'s platform
   dispatch already is, degrading to a one-time stderr notice everywhere
   else rather than silently doing nothing). `gc_mark()` now also captures
   a second register snapshot via glibc's `getcontext()`
   (`gc_capture_independent_regs()`) — genuinely different machinery than
   `gc_capture_callee_saved()`'s own hand-written inline asm (the kernel's
   signal-frame mechanism vs. six `movq` instructions) — at the SAME
   instant as the primary capture, before `gc_rebuild_index()` or anything
   else runs. After the real trace completes, `gc_cross_check_extra_
   registers()` checks the 9 general-purpose registers this independent
   capture sees that the primary technique's callee-saved-only set does
   not (`rax`, `rcx`, `rdx`, `rdi`, `rsi`, `r8`-`r11`): if any of them
   points at a block the production scan did not otherwise mark live, it
   is reported to stderr with a running counter — **never aborted**. A
   caller-saved register's content is not guaranteed meaningful by the C
   ABI at all (nothing requires it survive a call), so a finding is
   evidence worth collecting across many runs, not, on its own, proof the
   primary scan missed a real root; turning it into a hard abort would
   make this flaky in CI over pure coincidence. Wired into CI as a full
   suite run whose own log is grepped for the finding phrase, failing the
   build if it ever appears — **zero findings** across the entire suite
   (both opt levels) plus the full stress corpus, measured live.

   The first implementation of this was wrong, caught before landing (see
   *Removed assumptions*): calling the independent capture from a SEPARATE
   function invoked AFTER the primary mark/trace pass had already
   completed produced a mismatch on almost every test in `tests/41_gc/`,
   for a reason that only became clear from a live repro.

## Removed assumptions

- **"The address of a local variable in the current function is always a
  real machine stack address."** True everywhere this file's technique
  had ever been exercised before this group — false under ASan's default
  `detect_stack_use_after_return=1`, which may relocate an ordinary
  local's storage onto a heap-allocated "fake stack." Found live, the
  first time `gc_mark()`'s own SP approximation ran under ASan at all: a
  real SEGV from a scan range whose lower bound was a heap address. Fixed
  by `gc_approx_sp()`, a tiny helper exempted from ASan instrumentation
  specifically for this one operation (see *Runtime changes* above). A
  future session must not revert to taking `&someLocal` directly anywhere
  else in this file for the same "approximate the current stack pointer"
  purpose — go through `gc_approx_sp()`.
- **"Installing this file's own SIGSEGV handler is always strictly better
  than the platform default."** True without ASan — false once ASan's own
  runtime has already installed ITS OWN handler at process-startup:
  `sigaction()` has no "chain to the previous handler" mode, so installing
  ours on top silently discards ASan's far more detailed report. Fixed by
  having `turf_rt_install_segv_handler()` install nothing at all when
  built under ASan (`TURF_SIGNAL_ASAN`). A future session adding ANY other
  unconditional `sigaction()` call to this codebase should check whether
  it could be running under an ASan build the same way.
- **"Comparing two conservative-scan mark sets captured at different
  points in time is a meaningful validation."** This group's own FIRST
  attempt assumed it was — call the independent register capture from a
  helper invoked after the primary pass's full trace had already run, and
  treat any block the primary marked but the independent pass didn't as a
  hard error. It produced a mismatch on almost every test. The reason: by
  the time the primary pass finishes (`gc_rebuild_index()`, the whole
  worklist trace, several `malloc()`s for the worklist array), many
  function calls have run since the primary register read, and EVERY
  caller-saved register the independent capture looks at (the whole point
  of capturing more than the primary's callee-saved set) is free to have
  been overwritten by any of that unrelated intervening work. A LATER
  `getcontext()` call is not reading "the same moment" the primary
  capture saw at all — it is reading whatever scratch content the most
  recent nearby computation happened to leave behind, which has no reason
  to relate to what the primary capture found. Fixed by capturing BOTH
  register sets back-to-back with nothing in between (after
  `gc_rebuild_index()` -- an earlier revision of this record and of the
  code comment said "before", which was never true; only the adjacency
  matters), and checking the result only AFTER the trace completes (so
  `marked` reflects real production reachability) — see *Runtime changes*
  above for the corrected design. A future session extending this
  validation to more registers or a different platform must preserve the
  "capture both at the same instant" property; it is not an optional
  refinement, it is what makes the comparison meaningful at all.
- **"A caller-saved register holding a value that happens to alias a live
  block's address is proof the primary scan missed a root."** Considered
  and rejected as this group's own panic condition, for the same reason
  the primary scan's own over-retention is an accepted tradeoff, not a
  bug: the C ABI makes no promise about what a caller-saved register
  holds at any given instant, so a coincidental match is expected,
  low-probability background noise, not evidence on its own. `TURF_GC_
  VALIDATE`'s finding is a stderr report with a counter, never an abort —
  see `gc_cross_check_extra_registers()`'s own comment for the full
  reasoning. A future session must not "fix" this into a hard panic
  without first establishing what false-positive rate is actually
  acceptable across a realistic run volume; this group's own empirical
  measurement (zero findings across 837 tests × 2 opt levels + the full
  stress corpus) is evidence the rate is very low in practice, not proof
  it is exactly zero in general.

## Known pitfalls

- **`TURF_GC_STRESS=1` makes an allocation-heavy program dramatically
  slower — expected, not a regression.** `tests/08_e2e_stress/
  07_heap_bounded_allocation.tr` (5,000,000 `heap()` calls) takes ~3.5
  minutes under this mode at `-O0` vs. a fraction of a second normally,
  purely from paying a full stop-the-world collection (including
  `gc_rebuild_index()`'s own `O(n log n)` sort) on every single
  allocation instead of once per heap-doubling. A future session adding a
  NEW allocation-heavy test to `tests/` (not `tests/custom/`) should be
  aware it will run under this mode in CI and budget accordingly, or move
  it to `tests/custom/gc_stress_corpus/` and its own dedicated smoke
  script the way this group's own three files did when the workload was
  too heavy for stress mode to ever finish (`million_node_graph_churn.tr`'s
  own header documents this exact tradeoff — it did not finish in 5
  minutes under `TURF_GC_STRESS`).
- **The ASan build needs its OWN CMake configure, and the two runtime
  archives must never collide.** `libturfrt.a` and `libturfrt_asan.a`
  land in the SAME `lib/` directory by design (see *Runtime changes*
  stage 3 above for why) — a future session must not "simplify" this by
  making `TURF_RT_SANITIZE` toggle flags on the EXISTING `turfrt` target
  in place; that would make an ordinary dev build and an ASan build fight
  over the same archive file depending on build order.
- **`ASAN_OPTIONS=detect_leaks=0` is required, not optional, for every
  ASan run of a compiled Turf program.** MEM-002's own design (no final
  collection at `turf_rt_shutdown()`, process exit reclaims everything)
  means every compiled program's GC heap is "still live" at exit by
  design — LeakSanitizer has no way to know that is intentional and will
  otherwise flag it on literally every single ASan-linked binary. This is
  not a bug to fix by adding a final collection; it is MEM-002's own
  considered omission (that record's own *Known pitfalls*).
- **`TURF_GC_VALIDATE`'s two register captures MUST stay adjacent in
  source, with nothing but the capture calls between them.** See *Removed
  assumptions* above for the full story of what went wrong the first time
  this wasn't true. A future session refactoring `gc_mark()` must not
  move work (even something that looks harmless, like a log line) between
  `gc_capture_callee_saved()` and `gc_capture_independent_regs()`.
- **The stress corpus's three files are the FIRST test content in this
  repository run only by their own dedicated smoke script, never
  `test_runner.sh` at all.** `tests/custom/` was already an established
  exclusion path (AGENTS.md, `scripts/test_ai.sh`'s `aggressive/`
  fixtures), but this group is the first to actually populate it with
  files meant to run in ordinary CI (not a manual/local-only harness) — a
  future session grepping `tests/` for "everything that runs in CI" needs
  to also check `scripts/gc_stress_corpus_smoke.sh`'s own file list, not
  just `test_runner.sh`'s file discovery.

## Unresolved questions

**This group landed in one session against the roadmap's own "spread
across Phases 1-3" sizing for FDN-005 — stated honestly, not silently
compressed, the same way MEM-002's own record did for an identical
situation.** What that compresses:

1. **The stress corpus is real, but still finite.** Three programs at
   10^5-10^6 scale is a large step up from MEM-002's own five small
   `tests/41_gc/` files, but it is not "hours of sustained operation" or
   "a genuinely adversarial object graph shape" (deep cyclic structures
   with high fan-out, concurrent-ish churn patterns a single-threaded
   collector never has to handle differently, but that might still
   stress the block table's own `O(n log n)`-per-collection design
   differently at a much larger scale than 10^6 live blocks). A future
   session with a dedicated multi-hour soak-test budget would still be
   time well spent, per MEM-002's own original framing of this exact
   risk.
2. **`TURF_GC_VALIDATE` covers Linux/glibc/x86-64 only**, the single
   platform this repository can actually execute (`INV-RT-4`'s own
   documented Win64/AAPCS64 execution gap applies identically here — this
   group adds no new execution coverage for either). A future session
   porting this validation to AAPCS64 (Linux/macOS arm64) would need
   `<ucontext.h>`'s AArch64 equivalent (`uc_mcontext.regs[]`, a flat
   31-element array rather than x86-64's named `REG_*` indices) and,
   separately, execution access to actually run it — cross-compilation
   alone (this session's own limit for prior AAPCS64/Win64 work) cannot
   validate a RUNTIME behavior like this one at all.
3. **The two GC/ASan interactions found and fixed this session
   (`gc_approx_sp()`'s fake-stack relocation, the redzone false positive)
   were found by getting ONE test running under ASan, not by an
   exhaustive sweep.** The full suite passing 837/837 under ASan afterward
   is strong evidence neither class of bug recurs elsewhere in this
   codebase, but a future session should not treat "the suite is green
   under ASan" as "every possible GC/ASan interaction has been
   enumerated" — only that none of the ones this suite's own 837 programs
   happen to exercise remain unfixed.

If a future reader is deciding whether to trust this collector under
load beyond what this repository's own suite (now including the stress
corpus above) exercises, these three points are the honest place to
start, not this record's own "landed" status line — exactly the framing
MEM-002's own closing paragraph asked a future session to keep.

## Follow-up — 2026-09-29: the roadmap asks the landing did not meet

A re-read of the roadmap entry against this record found three asks the
landing had not met literally, plus one misleading code comment. All four
are closed here. The first of them turned up a real use-after-free.

**1. The no-`/proc` stack-base fallback freed live objects (bug, fixed).**
ROADMAP REL-003: *"the runtime's Linux-specific stack discovery
(`/proc/self/maps`) inside minimal containers (it has a fallback; FDN-005
must test the fallback path too)"*. Nothing had ever run that path. A new
testing aid, `TURF_GC_NO_PROCFS=1`, skips `turf_gc_record_stack_base()`'s
own `/proc` read so the fallback runs on an ordinary machine. Under
`TURF_GC_STRESS=1` it failed **11 of 12** `tests/41_gc` programs plus
`17_stress_10k_concat.tr`, at both `-O0` and `-O2`: assertion failures,
SIGSEGVs, `free(): unaligned chunk detected in tcache 2`. The fallback was
`gc_approx_sp()` called from inside `turf_rt_init()`, which is exactly the
sibling-frame capture MEM-002's own *Removed assumptions* says must never
be used for the stack base. `turf_rt_init()` returns before the user's
`main` is called at the same depth, so `main`'s locals sit outside
`[sp, base)`. MEM-002 fixed the primary path and left the broken idiom as
the fallback.

Fixed in `turfrt_gc.c`: the fallback is now `gc_stack_base_without_procfs()`.
It uses glibc's exported `__libc_stack_end` (the stack pointer at process
entry, an ancestor of every frame), or on non-glibc Linux
`pthread_getattr_np()` (musl answers it without procfs). If no source
exists, `turf_rt_init()` panics (`cannot locate the stack`) instead of
running a collector that frees live data. The signal handler's overflow
window (256 KB around `base - RLIMIT_STACK`) absorbs the few KB between
`__libc_stack_end` and the mapping's top. Regression coverage is
`scripts/gc_no_procfs_smoke.sh`. A C harness checks that the knob really
switches the source (to `__libc_stack_end`) and that the base lies above
`main`'s frame, so the rest cannot pass vacuously. Then every `tests/41_gc`
program plus the concat stress test runs at `-O0`/`-O2` under
`TURF_GC_NO_PROCFS` + `TURF_GC_STRESS` + `TURF_GC_VALIDATE`. CI also runs
the full suite with `TURF_GC_NO_PROCFS=1 TURF_GC_VALIDATE=1` at `-O0`.

**2. The full-stack mark-set comparison (stage 3's second half, added).**
The roadmap asks for a mode that *"additionally scans the full stack range
conservatively *and* compares mark sets"*; the landing shipped only the
register cross-check, which cannot see a wrong stack bound — the failure
mode above. `TURF_GC_VALIDATE=1` now also runs `gc_independent_mark()`: a
complete second mark phase (roots plus precise trace) before the
production one, whose conservative roots come only from sources the
production scan never uses:

- registers: a `getcontext()` snapshot taken in `turf_rt_collect()`, not
  the inline asm, and only its callee-saved registers;
- the stack's low end: that snapshot's RSP, not `gc_approx_sp()`;
- the stack's high end: `pthread_getattr_np()`, i.e. the whole `[stack]`
  mapping, not `g_stack_base`.

`turf_rt_collect()` is `gc_mark()`'s caller, and `gc_mark()` is now
`noinline`. So the independent range is a subset of the production range
whenever the production base is right, and nothing writes to those words
between the two scans. A block marked only by the independent pass is
therefore a real missed root, never noise. `gc_compare_mark_sets()` lists
up to 16 such blocks and **panics** (`GC root missed`) before the sweep.
This is deliberately unlike the caller-saved register check, which stays
report-only for the reasons in *Removed assumptions*. The
`pthread_*` symbols are declared weak. They lived in `libpthread` before
glibc 2.34, which `linkObject()` does not pass, so if they are missing the
comparison reports itself unavailable. Every Turf program still links
either way.

It works. With the old fallback temporarily restored and
`TURF_GC_NO_PROCFS=1 TURF_GC_VALIDATE=1` (no stress mode), 10 of 11
`tests/41_gc` programs panicked with `mark-set mismatch` at their first
collection. That includes `03_interior_pointer_retention`, which the
stress-mode run had passed by luck. The one that passed, `11`, keeps its
only reference pinned, and pins are roots independent of the stack. With
the fix in place, the full suite reports zero mismatches: under
`TURF_GC_VALIDATE=1` at default, `-O0` and `-O2` (838/838 each), and under
`TURF_GC_VALIDATE=1 TURF_GC_STRESS=1 TURF_GC_NO_PROCFS=1`, a comparison on
every allocation with the fallback base, at `-O0` and `-O2` (837/837 each,
before the new net test existed). Two `-O0` link failures in that run came
from rebuilding `lib/libturfrt.a` mid-run; both re-ran green.

**3. `TURF_GC_STRESS=1` + ASan at `-O2` (completion criterion, verified).**
The criterion names `-O0` *and* `-O2`; the landing measured and wired only
`-O0`. The `gc_hardening_asan` CI job now has the `-O2` step too.
**Not locally confirmed:** the run was stopped at the owner's request
after 12 minutes, while every test except `tests/08_e2e_stress/
07_heap_bounded_allocation.tr` (5,000,000 allocations) had finished,
but the runner reports only at the end, so none of those results were
collected. CI's run is the first complete one. Confirmed locally with
the follow-up's code: ASan at default and `-O0` (838/838 each), and
ASan + `TURF_GC_VALIDATE=1` at `-O0` (838/838, no mismatches, no
register findings).

**Observed complete in CI, 2026-10-13:** run
[38393287304](https://github.com/turf-lang/turf-lang/actions/runs/38393287304)
(`roadmap/update` at `9174c9e`), job `gc_hardening_asan`. The `-O2`
step passed 1343/1343 with 0 failures in 9 minutes, and the `-O0` step
passed 1343/1343 too. The only exclusion is
`41_gc/fail_stack_overflow_deep_recursion.tr`. It expects the
runtime's "panic: stack overflow" from its SIGSEGV handler, which an ASan
build does not install; the plain jobs cover it at every `-O` level. The same run's
`build_and_test` job passed `TURF_GC_STRESS=1` without ASan at `-O0`
and `-O2`, plus the stress-corpus smoke test. Every item of the roadmap's
completion criterion has now been observed.

**4. A wrong comment.** `gc_mark()`'s comment on the caller-saved
snapshot and this record's *Removed assumptions* both said the two
register captures run "before `gc_rebuild_index()`". In fact
`gc_rebuild_index()` is `gc_mark()`'s first statement. Only the pair's
adjacency matters, and that was always true. Both texts are corrected.

**Also fixed in passing, all in the test tooling this group relies on:**

- CI's `TURF_GC_VALIDATE` step piped the runner into `tee` and checked
  only the grep. A test that *failed* under validation, which is how a
  mark-set mismatch now shows up, would not have failed the step. It now
  checks the runner's own exit status, and it runs at `-O0` as well as
  the default level.
- That grep could never fire either. `test_runner.sh` discards a passing
  test's output, and the register check never fails a test, so its
  findings were invisible. The landing's "zero findings" could not have
  been observed through the runner. The runner now echoes a passing
  test's `TURF_GC_VALIDATE:` lines. Re-measured with a proven-visible
  channel: zero findings at default, `-O0` and `-O2`.
- `test_runner.sh` leaked one `(sleep $RUN_TIMEOUT_SEC && kill -9 $pid)`
  watchdog per test. Under this group's raised timeouts, the leftovers
  held any pipe reading the runner open (GitHub Actions' step capture,
  `| tee`) for up to the full timeout after the suite had finished, and
  later ran `kill -9` on possibly-reused PIDs. They are replaced by a
  polling `wait_with_timeout()`.

### Portability review (2026-09-29)

This is a code review of the runtime against every target it claims, plus
the stdlib's C dependencies, since those decide whether a program links.
Only Linux x86-64 was executed. The other targets were cross-compiled
(`aarch64-linux-gnu-gcc`, `x86_64-w64-mingw32-gcc`, clang) with
`-Wall -Wextra -Werror` at `-O0`/`-O2`. No macOS SDK, qemu-user, or
running Docker daemon was available.

**Fixed:**

- **Linux, every libc:** `net.tr` declared `socket()`/`accept()`/... as
  returning 64-bit `int`. A C `-1` arrives as `4294967295`, so
  `fd >= 0` accepted every failure. They are now `int32`
  (`tests/33_net_dns/02_accept_failure_is_reported.tr`).
- **macOS:** `SIGBUS` is now handled the same way as `SIGSEGV`, because a
  stack overflow there can arrive as `SIGBUS`. `gc_approx_sp()` no longer
  warns under clang.
- **Windows:** `_WIN32_WINNT` is now defined before any header. MinGW's
  `<_mingw.h>` had pre-empted it.
- **FreeBSD/OpenBSD/NetBSD:** now a build-time `#error`. They fell into
  the Linux `/proc` branch, where they silently under-scanned; since fix
  1 they would have panicked on every startup instead.

**Open. Not fixed here; each is a stdlib or driver port, not runtime work:**

| Platform | Problem | Effect |
|---|---|---|
| macOS, Windows | `mem.tr` calls `malloc_usable_size` (glibc/musl only; macOS has `malloc_size`, Windows `_msize`). At `-O0` every function of an imported module is emitted, and `net` imports `mem`. | Any program importing `mem` or `net` **fails to link at `-O0`** (so `-g` debugging too). `-O2` works only while `mem::usable_size()` is unused. |
| macOS, BSDs | `net.tr`'s `buildSockAddr()` writes Linux's `sockaddr_in` (`u16 sin_family`); BSD-derived systems start with a 1-byte `sin_len`. | `bind()`/`connect()` see family 0 and fail. |
| macOS, Windows | `SOL_SOCKET = 1`, `SO_REUSEADDR = 2` are Linux values (`0xffff`/`4` elsewhere). | `setsockopt` silently does nothing. |
| Windows | Sockets need Winsock: `-lws2_32`, `WSAStartup()`, `closesocket()`, a 64-bit `SOCKET`. | `net` does not link. |
| Windows | `os.tr` uses `setenv` (MinGW has none; `_putenv_s`), and `mem.tr` uses `posix_memalign` (`_aligned_malloc`). | Programs importing `os` or `mem` fail to link at `-O0`. |
| Windows | `ftell()`/`clock()` return C `long`, which is 32-bit on Windows, but are declared `int`. | Error returns read as `4294967295`; files over 2 GiB mis-sized. |
| Windows | No stack-overflow or SIGSEGV reporting (FDN-006 is POSIX only). | Bare crash, as documented. |
| musl / Alpine | Reviewed, not executed. The runtime should work: `/proc` is used first, `pthread_getattr_np()` is the fallback, and `TURF_GC_VALIDATE` prints its "unsupported" notice. | Expected fine. |
| Linux aarch64 | Cross-compiles clean; AAPCS64 register capture never executed on Linux. | Expected fine; unverified. |

**What this still does not claim:** the comparison validates the
conservative roots against a range and register set derived
independently. It does not validate the precise trace, because both passes
share `gc_scan_block_precise()` and the descriptors. ASan's
freed-block-reuse detection remains that half's independent check.
`pthread_getattr_np()` on glibc itself reads `/proc/self/maps` (different
code, same kernel data). `TURF_GC_NO_PROCFS` hides only this runtime's own
read, not glibc's. That is what lets the comparison catch a wrong fallback
at all. In a real procfs-less container the comparison would report itself
unavailable, and the smoke script is the coverage for that environment.

## Performance

Re-measured against `lib/libturfrt.a` (no Turf compiler involved, `-O2`,
this machine, three runs each) using MEM-002's own benchmark methodology
verbatim (not checked into the repo, for the same reason MEM-002's own
benchmark wasn't — it measures a machine-dependent absolute number, not a
bounded pass/fail property):

- **Throughput**: 2,000,000 sequential `turf_rt_alloc(32, NULL)` calls
  (immediately discarded) completed in 134.6-178.6 ms across three runs —
  **11.2-14.9 million allocations/second**, with 61 collections triggered
  along the way (identical collection count to MEM-002's own measurement —
  the 1 MiB-floor heap-doubling heuristic is unchanged).
- **Pause time**: one explicit `turf_rt_collect()` over a genuinely live
  working set of 20,000 blocks (held on the C stack, each written to and
  read back, MEM-002's own anti-dead-store-elimination technique), with
  ~220,000 additional dead blocks from intervening churn also present in
  the block table, took **1.90-2.62 ms** across three runs.

**What these numbers do and do not claim**, verbatim from MEM-002's own
framing since it still applies unchanged: no comparison against another
language's collector, no claim about behavior at 10^7+ live objects, no
claim about pause time under an interior-pointer-heavy working set. These
figures are NOT directly comparable to MEM-002's own reported numbers
(5.4-6.1M allocs/sec, 7.2-10.1ms pause) — different machine, not a
regression or an improvement in the collector itself; OVH-001 (removing
the 64-word descriptor cap), OVH-002 (the `!T`/box GC-heap fix), and
OVH-010 (the pin table, unused in this specific benchmark — zero pins) all
landed between MEM-002's measurement and this one, and none of their own
change records claim a throughput/pause-time effect either way. Reproduce
with the methodology above on any given machine to get a number
comparable across sessions on THAT machine.
