## Why

The owner asked for `arrays::fill(0)` to return a `T[N]`. Nothing in the
language could write that. A `T[]` can't be returned (E140: a slice is a view
of storage that would be gone), and a length taken from a runtime `int` can't
fix a type, since the length of `T[N]` is part of the type and the compiler
checks it. The length has to be a compile-time value that a generic function
can name.

```turflang
fn<T> fill(value: T, n: int): T[]   // E140: a T[] can't be returned
```

## Language semantics

### Old behaviour
A type parameter stood for a type. An array's length was a literal integer in
the type (`int[8]`) or -1 for `T[]`. A generic function could take any
`T[N]` of one fixed `N` only by writing the number.

### New behaviour
A free generic function may declare `N: size` in its `<...>` list. `N` is an
array length, usable as a dimension of any array type in the function (a
parameter, the return type, a local `mut r: T[N];`, a dimension of a 2-D type)
and, in the body, as an `int` constant.

```turflang
fn<T, N: size> fill(value: T): T[N] {
    mut r: T[N];
    for i in 0..N {
        r[i] = value;
    }
    return r;
}

fn main(): int {
    mut a: int[8] = fill(0);    // N is 8
    return a[0];
}
```

- Each call fixes `N`: from an array argument (`reversed(a)` with `a: int[3]`
  gives 3), otherwise from the type the result is stored into (a declaration
  with a written type, an assignment target, a parameter of a non-generic
  function, a `return` in a function whose return type is written). Each
  distinct length is its own instantiation.
- No explicit type arguments at a call (`fill<int, 4>(7)` is E110), as for
  type parameters.
- Nothing gives `N` is E129 ("Can't tell the size 'N' of the array 'fill'
  returns"): a bare call statement, `mut d = fill(0);`, an unsized `int[]`
  parameter. A size parameter no array in the parameters or return type uses is
  E129 at the declaration. A type parameter must still appear in a parameter; a
  size parameter may appear only in the return type.
- E150 (new, "Size parameter used where it can't be"): on a struct, a method
  or an operator; anything but `size` after `N:`; `N` written as a type; a
  value parameter with the same name; assigning, `++`/`--` or `&` on `N`.
- A name in `[ ]` that is not a declared size parameter is E123.
- The body is checked per instantiation, with `N`'s value. An error in the body
  is reported at the call that needs it, under the "In this instantiation"
  notes (`r[N] = v;` is E001).
- A wrong length or element type at the target is an ordinary mismatch:
  `mut c: int[3] = fill("x");` is E004.

`recover` and assignment (a related parse fact, documented with this record):
`recover` binds more loosely than `=` and `+=`, so `v = f() recover run { ... };`
is `(v = f()) recover ...` and E066. Write `v = (f() recover run { ... });`.
No parser change; the reference now says it.

### Is this breaking?
No. `size` after a colon in a `<...>` list was a syntax error before. Every
program that compiled still does. A new standard-library module named `arrays`
could clash with a user module of that name only when both are imported.

## Compiler architecture

- **Lexer** · None.
- **Parser** · `ParseFuncDef()` reads `N: size` into `FuncDefExprAST::SizeParams`
  and refuses it on a method or operator. `g_SizeParamsInScope` +
  `TakeSizeParamDim()` / `WrapArrayDim()` (`ParserCore.cpp`) turn an identifier
  in `[ ]` into a symbolic dimension. Local `mut r: T[N];` declarations carry
  `ArrayDeclExprAST::SizeParam`.
- **AST** · `FuncDefExprAST::SizeParams` (subset of `TypeParams`),
  `getTypeOnlyParams()`, `VariableExprAST::IsSizeParamRef` / `SizeValue`,
  `ArrayDeclExprAST::SizeParam`; `clone()` copies each.
- **Types** · `ArrayType::kSymbolicSize` (-2), `ArrayType::getSizeParam()`,
  `hasSymbolicSize()`; `TurfSizeValueType` carries a bound length (mangled
  `n<value>`).
- **Resolver** · `validateGenericParamsInferable()` accepts a size parameter
  bound by the return type, reports E150/E129; each size parameter is declared
  as an immutable `int` symbol (`VariableSymbol::IsSizeParam`);
  `visitVariable()` marks reads.
- **Symbol tables** · `ResolverFunctionSymbol::SizeParams`.
- **TypeChecker** · the template body is skipped (`visitFuncDef()`);
  `visitFuncCall()` binds `N` from arguments, then from the expected type
  (`visitWithExpectedType()`, `ExpectedCallSite_`, `ExpectedCallType_`; also
  used by `visitArrayDecl()`'s initializer, assignment, call arguments and
  `return`); `TypeArgs` follow declaration order for size-generic functions;
  `rejectSizeParamPlace()` reports E150 for writes to `N`.
- **Monomorphizer** · `substituteTypesInBody()` sets `SizeValue` on reads and the
  size of `ArrayDeclExprAST`.
- **Codegen** · `VariableExprAST::codegen()` emits `SizeValue` as an `i64`
  constant.
- **CFG/analysis** · None.
- **Diagnostics** · E150 (`SizeParameter`, category declaration); E129 gains the
  "Can't tell the size" message; `docs/errors/codes/E150.txt`,
  `docs/slm/codes/E150.txt`.
- **Optimization** · None.
- **TypeWalk** · `unify()` binds `N` from an array argument (not from an
  unsized `T[]`); `substitute()` replaces a symbolic size; `collectParamOrder()`
  lists size parameters.

## Runtime changes
None.

## Standard-library changes
New module `lib/std/arrays/arrays.tr` (`import arrays;`): `fill`, `generate`,
`reversed`, `map`. Not in the prelude. `scripts/check/stdlib_surface_check.sh`
accepts a `:` in a `fn<...>` list so it sees `fn<T, N: size> fill`.

## New invariants
None added to INVARIANTS.md. The size of a symbolic `ArrayType` is never read
as a length: code that tests `getSize() > 0` or `< 0` sees neither.

## Removed assumptions

- Every type parameter appears in a parameter. A size parameter may appear only
  in the return type.
- An `ArrayType`'s size is -1 (unsized) or positive. It is also -2 for a size
  parameter's dimension until the monomorphizer replaces it.
- A generic function's `TypeArgs` order is the order its parameters mention
  its type parameters. For a size-generic function it is the declaration's
  `TypeParams` order.
- A template body is always type-checked. One with a size parameter is checked
  only per instantiation.
- `scripts/check/stdlib_surface_check.sh`'s `fn<...>` regex had no `:`.
- The `<...>` list of a `fn` holds only type names.

## Known pitfalls

- `arrays::fill(&n)` gives a `(&Node)[N]`, which never widens to a
  `(&?Node)[N]`. Fill with a `&?Node` value: `mut r: &?Node = &n;`.
- A template body with a size parameter is checked only when instantiated, so
  an unused one is never checked. An error in it appears at the first call.
- A size parameter is not a type: `TurfSizeValueType` must never reach code that
  expects the type of a value. It only replaces an array's size or the value of
  a read.
- `mut d = fill(0);` is E129, not an inferred `int[0]`: `guess` gives no size.
- Do not test `getSize() == -1` for "unsized" without considering -2.
