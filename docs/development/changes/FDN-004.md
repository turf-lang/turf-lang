## Why
Verified: `"abc"[5]` compiled and read past the NUL terminator, returning
whatever garbage byte happened to follow it in memory (audit finding F-17,
`ROADMAP_v2.0.0.md`). Separately, `s[i]`'s result type was `int` even though
`char` already exists and is exactly one byte — the recorded inconsistency
C-7/D17. Both are fixed together, per the roadmap's own bundling of them.

## Language semantics
### Old behaviour
```turf
mut s: string = "abc";
mut c: int = s[5];       // compiled; read past the terminator, garbage value
mut n: int = s[0];       // compiled; 'a' as int 97
```
No bounds check existed on `s[i]` at all, in either direction (read or
write).

### New behaviour
```turf
mut s: string = "abc";
mut c: char = s[5];      // panics at runtime: "String index out of bounds"
mut c2: char = s[0];     // 'a', typeof(s[0]) == "char"
mut n: int = s[0] to int; // 97 -- explicit cast required, char<->int only
```
A read is bounds-checked against `strings::length(s)` (`strlen`) semantics:
`i < 0` or `i >= strlen(s)` panics with `"String index out of bounds"`
(`turf_rt_panic`, exit 134, `@caller_location`-style attribution via the
existing `SourceLocation` threaded through `CodegenPanic`). A write
(`s[i] = c;`) checks `i < 0` only — see *Removed assumptions* and
*Known pitfalls* for why the upper bound can't apply there.

`strings::byte_at_unchecked(s, i): char` (new, `lib/std/core/strings.tr`) is
the escape hatch for a caller that has already proven `i` is in range and
cannot afford the repeated `strlen()` cost.

### Is this breaking?
Yes, in two independent ways (R1: breaking, so after 2.0 only changeable in
3.0):
1. **Type**: any code that used `s[i]` as an `int` directly (arithmetic,
   comparison with an int literal/variable, assignment into an `int`
   variable) now fails to compile with `E066`. Mechanical migration: cast the
   read side (`s[i] to int`), or compare against a `char` literal instead
   (`s[i] == 'a'` needs no cast). This session's own stdlib migration (see
   *Standard-library changes*) is the worked example for every shape this
   produces.
2. **Bounds**: any code that indexed a `string` out of range (however
   unlikely to have been intentional) now panics instead of silently reading
   garbage.

## Compiler architecture
- **TypeChecker**: `TypeChecker::visitArrayAccess()`'s string branch
  (`TypeCheckerCall.cpp`) now sets the result type to `TurfChar()` instead of
  `TurfInt()`.
- **Codegen**:
  - `getExprType()`'s `ArrayAccessExprAST` case (`CodegenCore.cpp`) mirrors
    the TypeChecker change — this is a second, independent type-inference
    engine (`docs/architecture/compiler_pipeline.md` §4) that must agree by
    hand, not by construction.
  - New `EmitStringBoundsCheck()` (`src/CodegenArray.cpp`), the string
    analogue of the existing array `EmitRuntimeBoundsCheck()` — except the
    upper bound is a fresh `strlen()` call (declared via
    `TheModule->getOrInsertFunction`, the same pattern `CompareExprAST`'s
    `strcmp` dispatch already uses) rather than a compile-time constant, and
    the upper-bound half is conditional (`CheckUpperBound` parameter) — `true`
    from the read path (`ArrayAccessExprAST::codegen()`), `false` from the
    write path (`ArrayAccessExprAST::codegenLValue()`).
  - `ArrayAccessExprAST::codegen()`'s string branch no longer `ZExt`s the
    loaded `i8` up to `i64` — the load result IS the `char` value now.
  - `AssignmentExprAST::codegen()` (`CodegenVar.cpp`) had its
    string-index-specific `i64`-to-`i8` truncation hack removed — it existed
    only because the old `int`-typed `s[i]` LHS didn't match the storage
    width; now that the LHS is genuinely `char` (i8), `CastToType()` already
    produces the right width, and the old `CreateTrunc(i8, i8)` would have
    been a same-width truncate (undefined behaviour territory for
    `CreateTrunc`, not merely redundant).
  - `CastToType()` (`CodegenCore.cpp`) gained a `char -> int` (zero-extend)
    and `int -> char` (truncate) case — see *Removed assumptions* for why
    this was a real, previously-unreachable gap, not defensive padding.

## Runtime changes
None (the panic path reuses the existing `CodegenPanic`/`turf_rt_panic`
mechanism the array bounds check already uses).

## Standard-library changes
Every direct `s[i]` (or `field[i]`/`param[i]` on a `string`) site in
`lib/std/**` was swept (`turf --typecheck <file>` on every file, plus a full
compile of every `showcase/*.tr`) and migrated. Files touched:
- `lib/std/core/strings.tr` — every internal byte-comparison site cast to
  `int` at the point of use; `buf[i] = s[i];`-shaped byte copies needed NO
  cast (both sides already `char`); `toupper`/`tolower`'s `int32` C bindings
  needed a `char -> int -> int32 -> [call] -> int -> char` round trip (no
  direct `char <-> int32` cast exists, F-STD's own cast table); added
  `strings::byte_at_unchecked()`.
- `lib/std/json/json.tr` — `Parser.peek()`'s own return type stays `int`
  (its `-1` end-of-input sentinel needs a value outside `char`'s 0..255
  range), cast at its one read site; every other site follows the same
  "cast to int once, keep everything downstream unchanged" pattern.
- `lib/std/collections/hashing.tr` — `hash(x: string)`'s djb2 loop.
- `lib/std/fs/fs.tr` — `last_index_of_char()`.
- `lib/std/http/http.tr` — no raw string indexing in this file at all
  (verified — its header comment references the *historical*, already-fixed
  write-truncation bug this session's own *Removed assumptions* section
  explains further); typechecks clean with no changes.

## Removed assumptions
- **A write bounds check can reuse the read check's `strlen()` logic.**
  FALSE, found live: applying `EmitStringBoundsCheck()`'s upper bound to
  `codegenLValue()` (the write path) made every stdlib string-building
  function panic on its own FIRST write — `strings::substring()`,
  `replace()`, `to_upper()`, `to_lower()`, `pad_left()`, `pad_right()`,
  every one of them, the whole test suite going from 831/831 to reporting
  20+ failures the moment this was tried. Root cause: each of these
  allocates via `gc_alloc(len + 1)` (zero-initialized memory) and fills it
  byte by byte, writing the NUL terminator LAST — `strlen(buf)` on that
  buffer is 0 for the entire construction (or however many leading zero
  bytes happen to precede the write cursor), so `write_index (0) >=
  strlen(buf) (0)` fires on the very first byte. There is no way to recover
  a `string`'s real allocated capacity to check against instead — it is a
  bare pointer with no length metadata (F-STD-3, frozen). Scoped down to
  negative-index-only on the write side; see INV-STR-1 and this record's
  *Known pitfalls*.
- **`Codegen::CastToType()` already handles every primitive pair its callers
  might hand it.** FALSE, found live: `ArrayAccessExprAST`'s own index
  normalization (`IndexVal = CastToType(IndexVal, TurfInt(), ...)`, used
  unconditionally for every array/string/pointer index regardless of the
  index expression's own type) had no `char -> int` case at all — before
  this milestone, nothing could ever produce a `char`-typed index expression
  (string indexing used to yield `int`), so the gap was real but
  unreachable. The instant `s[i]` became `char`, an ordinary byte-histogram
  pattern (`freq[s[i]] = freq[s[i]] + 1;`, `int[128] freq`) fed a `char`
  straight into this path and produced verifiably-broken LLVM IR (`icmp slt
  i8 %v, i64 0` — mismatched operand widths), caught by `verifyModule()`
  rather than silently miscompiling only because the two operand widths
  differed enough for LLVM's verifier to notice. Fixed by adding the
  missing `char -> int`/`int -> char` cases to `CastToType()` directly,
  distinct from (and in addition to) `CastExprAST::codegen()`'s own,
  already-correct handling of an explicit user-written `to` cast — the two
  are separate code paths (`docs/architecture/compiler_pipeline.md` §4's
  "two independent type-inference/casting surfaces" pattern, once again).
- **A `string` value is always a well-formed, `strlen()`-measurable C
  string wherever the compiler might read/write it byte-by-byte.** FALSE for
  a raw allocator block reinterpreted as `string` purely for byte-level
  convenience (`gc_alloc_zeroed(n) to string`, with embedded zero bytes by
  design) — `tests/05_arrays_pointers_ffi/21_gc_alloc_intrinsics.tr` did
  exactly this to inspect a zeroed allocation, and the new read-side bounds
  check broke it the same way the write-side check broke buffer
  construction. Fixed in the test itself, not the compiler: rewritten to use
  `char*` (a raw, unchecked pointer view — what the test actually wanted)
  instead of `string`, since indexing raw allocator memory that may contain
  embedded NULs was never really "string" semantics in the first place.

Full suite green at both default and `-O0` (835/835, up from 831 — the 4 new
files). `lib/std/**` swept via `turf --typecheck` (none have a `main()`) and
every `showcase/*.tr` full-compiled clean; `text_toolkit`/`config_and_dice`
(the two that run standalone, no networking) also executed and produced
correct output.

**Performance** (the roadmap's own completion bar: no worse than +10% at
`-O2`): a synthetic microbenchmark (a 200,000-byte string, 20 reps, summing
every byte) comparing checked `s[i]` against `strings::byte_at_unchecked()`:
- `-O0`: checked 5508ms vs. unchecked 6ms for 4,000,000 accesses — the
  expected O(n²) blowup from a fresh `strlen()` on every single access, with
  no optimization to hide it (roughly 900x slower than the unchecked path).
- `-O2`: checked ~0-1ms vs. unchecked ~0ms — no measurable difference. At
  `-O2`, an inner loop over an unchanging string base hoists the `strlen()`
  call out entirely via ordinary loop-invariant code motion (LLVM recognizes
  `strlen` as a well-known, effectively-pure library call by name), so the
  amortized cost collapses back to O(n) for exactly the common "scan a fixed
  string in a loop" shape the roadmap's own design notes worried about.
  `-O0` (debug builds) pays the full, documented cost;
  `-O2` (release builds) does not, with no extra work from this session —
  LLVM's existing optimizer already does it. The roadmap's suggested
  `ValueRangePass` extension to prove this at the source level was NOT
  implemented — LLVM's own IR-level optimization already delivers the
  target outcome for the case that matters, and implementing a second,
  source-level mechanism for the same win was judged not worth the
  complexity. `strings::byte_at_unchecked()` remains available for the
  `-O0`/debug-build case or a loop whose string base genuinely changes.

## Known pitfalls
- **The write-side bounds check will never get an upper bound the same way
  the read side has one — don't "complete" it by copying
  `EmitStringBoundsCheck()`'s `strlen()` logic into the write path.** See
  *Removed assumptions*: doing so breaks every stdlib string-building
  function's very first write. If a future session wants SOME write
  protection, it needs a fundamentally different mechanism (e.g. a
  capacity-tracking allocation, which `string`'s bare-pointer representation
  does not have room for without changing F-STD-3).
- **A `char`-typed value reaching `Codegen::CastToType()`'s generic
  `TurfInt()`/other-primitive normalization calls needs its own case —
  check `CastToType()` before assuming a new primitive-producing expression
  "just works" through Codegen's internal index/operand normalization.**
  This gap existed for years, invisibly, because nothing produced a
  `char`-typed value in the positions `CastToType()` gets called from
  before this milestone. The next new primitive-producing expression kind
  (if one is ever added) should have this checked explicitly, not assumed.
- **`gc_alloc_zeroed(...) to string` for raw byte-buffer inspection is no
  longer a safe idiom — use `char*` instead.** Any existing or future code
  that reinterprets a raw allocator block as `string` purely to index it
  byte-by-byte (not because it is genuinely a NUL-terminated C string) will
  hit the new read-side bounds check the moment the block contains an
  embedded zero byte before the position being read. `char*` has no such
  check (same as any other raw pointer) and is the semantically correct
  type for "raw bytes with no string invariant," not a workaround.
- **The `char <-> int32` round trip in `to_upper`/`to_lower` is verbose by
  necessity, not oversight.** `docs/reference/variables_and_types.md`
  freezes casts to exist ONLY between `char` and `int` — there is no direct
  `char <-> int32` pair. Calling an `extern fn` declared with a real
  32-bit C ABI parameter (`toupper(c: int32): int32`) from a `char` value
  genuinely needs `(x to int) to int32`, and the reverse `(y to int) to
  char` coming back. Don't "simplify" this by adding a `char <-> int32`
  cast pair without a fresh freeze decision (§6.0 rule 3) — F-STD's cast
  table is deliberately narrow.

## Unresolved questions
- **Should `strings::byte_at_unchecked` live in `char.tr` instead of
  `strings.tr`?** It operates on a `string` + `int` index, not a bare
  `char`, so `strings.tr` (where `length`/`substring`/etc. already live) was
  judged the more natural home — flagging in case a future session
  reorganizes and finds the other placement clearer.
- **The `ValueRangePass` loop-bound elision extension the roadmap's design
  notes suggested (recognizing `while i < strings::length(s)` to prove a
  string index safe at the source level) was not built.** LLVM's own
  loop-invariant code motion already delivers the practically-important
  case (a loop-invariant string base) at `-O2`; whether the remaining gap
  (a loop-invariant base but `-O0`/unoptimized builds, or a genuinely
  changing base) is worth a dedicated compiler pass is left to whoever picks
  this up, informed by the benchmark numbers above.
