## Why

Every variable declaration required an explicit `: Type` annotation.
`mut x = 5;` was a parse error:

```turf
mut x = 5;
// before this session: "Expected ':' after variable name."
```

`docs/reference/variables_and_types.md` and the (paused) handbook's ch12 both
documented this as a permanent design choice ("there is no inference form"),
but `ARCHITECTURE_OVERHAUL.md` §11 named it the single most commonly noticed
ergonomic gap and specified `guess`, a type-position keyword, as the fix.

## Language semantics

### Old behaviour

```turf
mut x: int = 5;   // required
mut x = 5;        // parse error: "Expected ':' after variable name."
```

### New behaviour

```turf
mut x = 5;             // infers int, permanently fixed
mut x: guess = 5;      // identical AST, identical --dump-typechecked output
x = 10;                 // ok -- still int
x = 5.5;                // error: type mismatch, with a note naming where x
                         // was inferred (see fail_guess_reassign_wrong_type.tr)
```

Model A only (§11.3): the type is inferred once, from the initializer, and
never changes. Model B (infer from the first assignment) is rejected and
must not be added — §11.4, §25 item 12.

Scope is local-declaration-only (§11.5): a function parameter, return type,
struct field, `export immut` constant, or generic type argument never
infers. Extending inference to any of those is explicitly out of bounds
(§25 item 13) — it would require entering a function body during
`Resolver::hoistTopLevel()`'s Pass 1, which never happens by design
(`docs/architecture/compiler_pipeline.md` §3, "Pass 1 never entering a body
is a load-bearing invariant").

### Is this breaking?

Only for a program that used `guess` as an identifier — it is now a
reserved word. Swept `tests/`, `lib/std/`, `showcase/` (`grep -rn '\bguess\b'`):
one hit, an English-word comment in
`tests/06_structs/22_static_constructor_init.tr` ("guess whether this
brace-literal wants the constructor"), not an identifier. Zero real
occurrences, exactly as `ARCHITECTURE_OVERHAUL.md` §8 predicted.

## Compiler architecture

- **Lexer**: new `TOK_GUESS` (`include/Lexer.h`), `"guess"` added to the
  keyword table (`src/Lexer.cpp`).
- **Types**: new `GuessType` (`include/Types.h`/`src/Types.cpp`), a pure
  placeholder singleton (`TurfGuess()`) with a dedicated `isGuess()`
  predicate. It is never a real type for anything downstream of the
  TypeChecker — see *Removed assumptions*.
- **Parser**: `ParseType()` treats `guess` as a terminal type-position
  keyword, exactly like `ptr` — no generics, no arrays, no pointer suffix
  (`src/ParserCore.cpp`). `ParseLetStatement()` (`src/ParserStmt.cpp`)
  treats an omitted `: Type` annotation as producing `TurfGuess()` directly,
  rather than raising "Expected ':' after variable name." — both spellings
  now build the identical AST node. The pre-existing `SynthesizeDefault()`
  call for a declaration with no `=` is explicitly gated off for `guess`
  (it has no default; `TypeChecker::visitVarDecl` raises the real
  diagnostic instead).
- **Resolver**: **no changes.** This is the answer to §11.8's "one
  genuinely open design question" — `Resolver::visitVarDecl` declares the
  variable with the `TurfGuess()` placeholder like any other type (never a
  null type), and every function it calls on that placeholder
  (`validateNamedType()`, `substituteTypeParams()`) already no-ops
  correctly on a type that is neither `NamedType` nor any of the other
  cases those functions dispatch on. This mirrors an *existing* precedent
  in the same file: `Resolver::visitForEach()`'s loop variable already gets
  a placeholder `int` type at declare-time with the identical comment
  ("the Resolver doesn't do type inference — that's TypeChecker's job"),
  refined later by `TypeChecker::visitForEach()`.
- **TypeChecker**: `visitVarDecl` (`src/TypeCheckerDecl.cpp`) does the real
  work. After visiting the initializer (already happens, bottom-up), if the
  declared type `isGuess()`, it takes `getType(initializer)` — whatever
  type the TypeChecker already assigned that expression — resolves a bare
  `NamedType` result the same way the pre-existing (declared-type-only)
  `NamedType -> TurfStructType` fixup does a few lines below (needed for
  `StructName::default()`, whose own type is always a bare
  `NamedType(StructName)`, per `TypeCheckerCall.cpp`'s `DefaultConstruct`
  branch), checks the three §11.6 error cases (no initializer, `void`,
  `null`, uninstantiated generic), and on success calls
  `Node.setTypePtr(InitTy)` **and** `Node.ResolvedSymbol->Type = InitTy`,
  then falls through into the existing mismatch/`checkLiteralRepresentable()`
  block unchanged. Two new free functions, `isOrWrapsGenericParam()` and
  `containsUninstantiatedGenericParam()`, detect `mut l = List::default();`
  (§11.6's named example) — see *Known pitfalls* for why this needed two
  passes to get right.
  `TypeChecker::visitAssignment` (`src/TypeCheckerExpr.cpp`) gained one
  conditional: its pre-existing "declared here" related-location note (for
  a plain assignment's type-mismatch error) now says `"'x' was inferred as
  'T' here"` instead, when the LHS variable's `VariableSymbol::WasGuessInferred`
  is set.
- **Symbol tables**: `VariableSymbol` (`include/ResolverSymbolBase.h`)
  gained one field, `WasGuessInferred` (default `false`), set by
  `TypeChecker::visitVarDecl` on successful inference. Exists solely for
  the assignment-mismatch note above — by the time anything reads it, the
  symbol's `Type` is already the concrete inferred type, indistinguishable
  from an explicitly-annotated variable of the same type.
- **Codegen**: no changes. `VarDeclExprAST::codegen()` already reads the
  node's own `Type` field directly (not `getExprType()`), and by Codegen
  time that field has already been overwritten to the concrete type by
  `TypeChecker::visitVarDecl`. A `GuessType` reaching Codegen would mean
  inference silently failed to run — a compiler bug — but per `main.cpp`'s
  own pipeline comment, compilation aborts before Codegen runs on any
  program the TypeChecker reported an error against, and every failure
  path in the new `visitVarDecl` code reports one. No dedicated Codegen
  assertion was added (unlike `TurfGenericParamType`'s, F-GEN-2) — see
  *Known pitfalls*.

## New invariants

None added to `INVARIANTS.md`. `guess` is a resolved-away-by-the-TypeChecker
placeholder, not a runtime or structural property the compiler needs to
keep holding across future changes the way `INV-LAYOUT-1`/`INV-NUM-2` do —
there is nothing here for a later session to accidentally break in a way an
invariant would catch that the existing `tests/37_guess_inference/` suite
doesn't already cover directly.

## Removed assumptions

- **"A `VarDeclExprAST`'s `Type` field, once past the Parser, names a real
  type" is no longer true between the Parser and the point
  `TypeChecker::visitVarDecl` runs on that specific node.** It may be the
  `GuessType` placeholder instead. Nothing else in the tree currently reads
  a `VarDeclExprAST`'s `Type` in that window (the Resolver's own use of it,
  `declareVariable()`, is placeholder-safe by construction — see
  *Compiler architecture* above), but a **future** pass inserted between
  Resolver and TypeChecker that reads `VarDeclExprAST::getType()` must
  handle `isGuess()` explicitly or risk silently treating the placeholder
  as a real (and wrong) type. `ASTPrinter`/`Lint`/`Sandbox`/`CompileBuffer`
  were checked: none currently reads a `VarDeclExprAST`'s declared type
  before the TypeChecker has run over it.
- **"A generic struct's registered `TurfStructType` (via
  `GlobalSymbolTable->LookupType()`) has fields typed with
  `TurfGenericParamType`" is false.** It has fields typed with plain
  `NamedType(paramName)` instead. `Resolver::visitStructDecl`'s
  `substituteTypeParams()` call rewrites the field types on the struct
  **declaration's own AST node** (`Node.getFieldsMut()`), not on the
  separate `TurfStructType` object `ParserDecl.cpp` already built and
  registered globally at parse time from an independent copy of the field
  list. The two never converge. Anyone writing code that expects to find
  `TurfGenericParamType` on a `GlobalSymbolTable`-looked-up generic
  struct's fields will not find it — see *Known pitfalls* for the concrete
  bug this caused during this session.

## Tests

Added `tests/37_guess_inference/` (12 files, following this project's
`fail_*.tr` convention):

- `01_primitive_defaults_and_reassignment.tr` — the untyped-literal
  defaulting table (int/double/string/bool/char) and that a same-type
  reassignment still works afterward.
- `02_array_literal.tr` — `mut arr = [1,2,3];` infers `int[3]` (via the
  ordinary `ArrayLiteralExprAST` path, not the special `ArrayDeclExprAST`
  one, which `guess` never takes since it never knows the array type in
  advance).
- `03_struct_default_and_new.tr` — `Point::default()`/`Point::new(...)` for
  a non-generic struct.
- `04_function_return_and_int32.tr` — a function call's declared return
  type, and that an `int32`-typed expression is not widened to `int`.
- `05_fallible_and_reference.tr` — a call returning `!T` infers `!T`
  itself (then recovered separately, both the success and failure path),
  and `&expr` infers `&T`.
- `06_explicit_spelling_immut_typeof.tr` — `: guess` and an omitted
  annotation behave identically, `immut` works with both spellings, and
  `typeof()` on a guess-inferred variable returns the real inferred name.
- `fail_guess_no_init.tr`, `fail_guess_void.tr`, `fail_guess_null.tr`,
  `fail_guess_uninstantiated_generic.tr`,
  `fail_guess_reassign_wrong_type.tr`, `fail_guess_literal_out_of_range.tr`
  — the six §11.6 error cases, one file each.

Not an automated `tests/` case (the runner only checks
compile/run success or failure, never diffs `--dump-typechecked` output):
manually verified live that `mut x = 5;` and `mut x: guess = 5;` produce
byte-identical `--dump-typechecked` output for the declaration itself
(`turf --dump-typechecked`, both spellings, diffed the `VarDecl(x : int)`
line — identical).

Also manually verified live (not as a `tests/` case, since it would need to
be `unsafe`-gated and is really a Codegen-hazard regression check rather
than a guess-semantics one): a `guess`-inferred variable from a
self-referential struct's default constructor
(`unsafe { struct Node { val: int, next: Node* } }`) compiles and runs
without hanging or crashing the compiler — the concrete regression the
*Known pitfalls* section below documents finding and fixing.

## Known pitfalls

- **A naive "does this type contain a `TurfGenericParamType`" check that
  recurses into a struct's own field types will stack-overflow the
  compiler on an ordinary, already-legal self-referential struct** (a
  linked-list node: `struct Node { next: Node* }`, explicitly permitted by
  `TYPE-001`/`INV-LAYOUT-1` — pointer fields are non-edges in the
  acyclicity check). The first version of
  `containsUninstantiatedGenericParam()` in this session did exactly that
  (recursing into `TurfStructType::getFields()` by calling itself, not a
  bounded helper) and was caught only by testing a self-referential struct
  through `guess`'s default-constructor path
  (`Node::default()`) before committing — a scenario the §11.6 spec text
  never explicitly calls out, since it isn't about generics at all. The
  fix splits the check into two functions: `isOrWrapsGenericParam()`
  (bounded — only unwraps pointer/reference/array layers, never descends
  into a nested struct's fields) and `containsUninstantiatedGenericParam()`
  (checks the type itself, then — non-recursively — each field of a
  top-level struct with the bounded helper). Anyone touching this code
  should keep that boundary: a future "helpful" refactor that makes the
  outer function recurse into nested struct fields "for completeness"
  reintroduces the crash.
- **A generic struct's fields, as seen through `GlobalSymbolTable`, are
  never actually typed with `TurfGenericParamType`** — see *Removed
  assumptions* above. The first working version of the generic-detection
  check looked for `TurfGenericParamType` directly and silently failed to
  reject `mut l = list::List::default();` (it inferred `l: List`, no
  error, and only surfaced because a smoke test manually diffed
  `--dump-typechecked` output rather than trusting a passing exit code).
  The fix instead treats an unresolvable, non-primitive field `NamedType`
  as the generic-parameter case — sound only because
  `Resolver::validateNamedType()` already guarantees, for any declared
  struct's fields, that a bare `NamedType` name is one of: a primitive, a
  registered struct/enum/error, or the enclosing struct's own type
  parameter. If that guarantee is ever weakened (e.g. some future field
  type is allowed to reference a name that resolves to nothing without
  being an error), this heuristic would start silently misclassifying a
  genuinely-broken field as "must be a generic parameter."
- **`GuessType` has no Codegen-side assertion**, unlike
  `TurfGenericParamType`'s (F-GEN-2). This is deliberate, not an oversight
  — every path that could leave a `VarDeclExprAST` with an unresolved
  `GuessType` already calls `reportError()`/`raise()` first, and
  `main.cpp` aborts before Codegen on any TypeChecker error. If a future
  change ever makes `visitVarDecl` return without either resolving or
  erroring on a `guess`-typed declaration (a real risk if someone adds a
  new early `return` to that function without checking this case), the
  first symptom would be a silently-wrong LLVM type (`getLLVMType()`
  falls through to its double-precision default for an unrecognized type)
  rather than a clear assertion — worth revisiting if that function grows
  more early-return branches later.
- `Point::new(...)`-style user-defined struct constructors are ordinary UFCS
  methods named `new` with an implicit `self` and a `void` return (see
  `tests/06_structs/01_struct_basic.tr`'s `User.new`) — the call site's
  return type is always overridden to the struct's own type by the
  Resolver, regardless of what the method itself declares. `guess`
  inference relies on this being consistent for both `::default()` (a
  compiler-synthesized `NamedType(StructName)`, `TypeCheckerCall.cpp`'s
  `DefaultConstruct` branch) and `::new(...)` (a real, Resolver-registered
  `ResolverFunctionSymbol` with `ReturnType` already overridden) — the two
  reach `guess`'s inference code by different routes but land on the same
  shape.

### Examples that became invalid

Any prose stating `mut x = 5;` is a parse error is now false. No code
*example* in either doc actually showed this failing (both described the
rule in prose), so there is no broken code listing to fix — only the
prose claim itself.

### Examples that should be added

The §11.6 defaulting table, and at least one example of the "inferred here"
note on a reassignment type mismatch (`fail_guess_reassign_wrong_type.tr`'s
shape) — this is the kind of diagnostic detail a reference doc's reader
benefits from seeing verbatim rather than re-deriving.

### Sections that must NOT change

`immut`/`immutable` still requiring an initializer is completely
unaffected by `guess` — both already require one, for unrelated reasons
(one because reassignment is impossible, the other because there is
nothing to infer from). A handbook edit should not conflate the two required-
initializer rules into one explanation; they're independently justified
and F-INIT-1 already keeps SEM-004 from doing that in the *code*.

## Unresolved questions

None. §11.8 named "resolve the declare-before-type question" as this
group's one open design question; it's answered under *Compiler
architecture* above (no Resolver change needed — declare with the
placeholder, mutate the shared `VariableSymbol` in place from the
TypeChecker, exactly like `ForEachExprAST`'s loop variable already does).
