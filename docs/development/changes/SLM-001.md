## Why

§8's SLM-001 section names §16 in full as its scope: "Schedule whenever there
is appetite; nothing blocks on it." §16.1 audited the existing `--smart`
pipeline (grammar-constrained output, sandbox verification, the confidence
gate, retry-with-diagnostics) as already well-engineered and worth keeping
unchanged; §16.2 named five concrete weaknesses; §16.3 proposed five changes.
Two of the five (structural classification, caching's prerequisite) were
already addressed or trivial by the time this session started:

1. **Structural classification** — already done. DIAG-001 (landed
   2026-09-18) deleted `classifyError()`'s text-matching fallback entirely;
   `SLMIntegration.cpp` confirmed live (read before writing anything) to
   already use only ground-truth categories. Nothing left to do here.
2. **Deterministic-fix layer** — not done. Every diagnostic, including one
   with a single, unambiguous "did you mean" candidate, still went to the
   model.
3. **Type context in the prompt** — not done. `NodeTypes_`/`VariableSymbol::
   WasGuessInferred` existed but were never consulted by `SLMIntegration.cpp`.
4. **Caching** — not done. Every invocation reloaded the model and re-ran
   inference from scratch, confirmed live via `TURF_SLM_DEBUG=1`: an
   unmodified repeat of the same diagnostic took the same ~10-40s as the
   first run.
5. **Benchmark corpus and metrics** — not done. `DESIGN_NOTES.md` §6
   describes a procedural mutator as the dataset step for a LoRA fine-tuning
   plan; §16.3 item 5 and D9 (§27.2) both say build the corpus/benchmark
   FIRST, independently of any fine-tuning — no such tool existed.

This session implements items 2–5; item 1 is recorded here only as
"verified already satisfied."

## Language semantics

None. This group is diagnostics-pipeline-only (the `--smart` path, gated
behind an opt-in CLI flag with zero cost on an ordinary compile) — no
compiler-accepted-language change, no new syntax, no new error class.

### Old behaviour / New behaviour / Is this breaking?

Not applicable in the usual sense (no observable-language-behaviour delta).
The **externally observable change** is entirely inside `--smart` output:

- A diagnostic with a single, unambiguous rename candidate (an undeclared
  variable/function/type/struct-field/struct-method/module-symbol/scope-
  qualifier with exactly one local "did you mean" match, or a single-
  candidate keyword typo) now resolves via `[Deterministic Fix]` — verified
  live, e.g. `cuont` (typo of a declared `count`) and `retrun` (typo of the
  `return` keyword) both resolve with the model never invoked (elapsed
  ~0.03s, confirmed by literally removing the `models/` directory and
  re-running — see Tests).
- A type-mismatch diagnostic involving a `guess`-inferred operand now carries
  a `"known_types"` field in the model's prompt naming that operand's
  resolved type — verified live via a temporary debug print (kept
  permanently under the existing `TURF_SLM_DEBUG` gate) showing e.g. `"'a'
  (assigned value) was declared with 'guess' and inferred as 'int'."`
- A repeat of the identical diagnostic (same error code, message, and pinned
  source context) on a later `--smart` run is served from
  `~/.cache/turf/slm/` on its first attempt, skipping the model load
  entirely — verified live (see Tests). Sandbox re-validation is NEVER
  skipped: a cache hit that fails to re-validate this run falls straight
  through to the ordinary model-backed retry, verified live (see Tests).

Not breaking: `--smart` remains off by default (`g_AIEnabled`), and every
new field/parameter added in support of this (`SLM::DiagnosticHints`, the
widened `TypeChecker::ErrorHandler`/`reportError()`, `DiagnosticEngine::add()`
) defaults to an empty/no-op value at every one of the ~80 existing call
sites that don't opt in — confirmed by a clean full-suite rebuild with no
other call site touched except the one custom `TypeChecker::ErrorHandler`
lambda in `Monomorphize.cpp` (which needed its signature widened to match,
not any behavior change).

## Compiler architecture

- **Diagnostics (`include/ErrorCategory.h`)** — new `SLM::DiagnosticHints`
  struct: `KnownTypes` (a list of human-readable known-type facts, item 3)
  and `DeterministicOldName`/`DeterministicNewName` (an unambiguous rename
  candidate, item 1). Lives here, not `SLMIntegration.h` (where
  `AISuggestion` lives), specifically because `Lexer.h` cannot include
  `SLMIntegration.h` without a cycle (`SLMIntegration.h` includes `Lexer.h`
  for `RelatedLocation`) but needs the complete type by value in
  `DiagnosticEngine::Diag`.
- **Diagnostics (`include/Errors.h`)** — `TurfError` gains a `Hints_` member
  and three chainable setters: `withKnownType(fact)`, `withDeterministicFix
  (old, new)`, and `trySetDeterministicRename(name, RankedSuggestions)` (the
  one nearly every call site below actually uses — sets a fix candidate only
  when the lookup was genuinely unambiguous: exactly one local candidate,
  zero module candidates, and the candidate isn't literally the same string).
  `raise()` forwards `Hints_` into `DiagnosticEngine::add()`.
- **Diagnostics (`include/Lexer.h`/`src/Lexer.cpp`)** — `DiagnosticEngine::
  Diag` gains a `Hints` field; the `add()` overload with a `Code` parameter
  gains a trailing `const SLM::DiagnosticHints &Hints = {}` and forwards it
  into `SLM::validateAndApplySuggestion(...)` alongside the diagnostic's own
  `Code` (also newly threaded through, for the cache key — see below).
- **TypeChecker (`include/TypeChecker.h`/`src/TypeCheckerCore.cpp`)** —
  `ErrorHandler`'s `std::function` signature and `reportError()` both gain a
  trailing `const SLM::DiagnosticHints &Hints = {}`. `productionErrorHandler`
  applies each `Hints.KnownTypes` entry via `withKnownType()` before
  `raise()`. The ONE custom `ErrorHandler` lambda anywhere in the compiler
  (`Monomorphize.cpp`'s `finishInstantiation()`, used to re-anchor a
  monomorphization-site error) needed its signature widened to match; it
  ignores `Hints` (an inner-instantiation re-check has nothing meaningful to
  attach here).
- **TypeChecker (`src/TypeCheckerExpr.cpp`)** — `visitAssignment()`'s
  type-mismatch `reportError()` call now builds a `DiagnosticHints` naming
  either operand's resolved type ONLY when that operand is a bare variable
  whose `ResolvedSymbol->WasGuessInferred` is true (SEM-003's own tracked
  flag, already computed for a DIFFERENT purpose — wording the "declared
  here" related-location note). Deliberately not done for an explicitly
  annotated operand: its type is already spelled out on its own source line,
  which the existing pinned-context mechanism already shows verbatim, so
  restating it would be pure duplication. Deliberately not extended to
  `TypeCheckerCore.cpp`'s binary/relational-operator mismatches
  (`inferBinaryType`/`inferRelationalType`) or `TypeCheckerDecl.cpp`'s
  `VarDecl`-initializer mismatch in this session — see *Known pitfalls*.
- **SLM (`include/SLMIntegration.h`/`src/SLMIntegration.cpp`)**:
  - `fetchSuggestion()`/`validateAndApplySuggestion()` both gain
    `const DiagnosticHints &hints = {}` and `const std::string &errorCode =
    ""` trailing parameters.
  - New `tryDeterministicFix()` (item 1): given an unambiguous rename
    candidate, builds a word-boundary search/replace patch on the error's
    own line and validates it through the EXISTING `verifySuggestion()` path
    — the identical sandbox every model-produced suggestion goes through.
    Called from `validateAndApplySuggestion()` BEFORE `fetchSuggestion()` is
    ever reached; on success, returns directly, so `SLMEngine::getInstance()
    .initialize(...)` (the GGUF model load) is never called at all. On
    failure, falls through to the ordinary model-backed loop unchanged.
  - `codeContext`/`contextSize`/`categoryName` computation moved earlier in
    `fetchSuggestion()` (before the model/grammar load), so the cache
    lookup below can use `codeContext` as part of its key without first
    paying the cost of loading the model on what turns out to be a hit.
  - New "Known types" JSON field (`"known_types"`) in the user prompt (item
    3), populated from `hints.KnownTypes` when non-empty, joined by spaces.
    Structured and separate from the free-text `"error"`/`"code"` fields
    rather than folded into either, so the model doesn't have to parse it
    back out of prose.
  - New on-disk cache (item 4): `fnv1aHex()`/`slmCacheKey()`/
    `slmCacheDir()`/`slmCompilerFingerprint()`/`readSlmCache()`/
    `writeSlmCache()`. Key: FNV-1a-64 hash of `errorCode + '\x1f' +
    cleanError + '\x1f' + codeContext` (the exact tuple §16.3 item 4 names —
    error code, normalized message, hash of pinned context). Only consulted
    on a FIRST attempt (`previousAttemptFailed.empty()`); a retry
    deliberately bypasses the cache (see *Removed assumptions*). Only
    `explanation`/`fix_mode`/`suggested_comment`/`code_patch`/
    `replacement_line`/`target_line`/`end_line`/`warning`/
    `self_reported_category` are cached — `confidence`/`sandbox_validated`
    are NEVER cached and are always recomputed fresh by
    `finalizeConfidence()` against THIS run's sandbox result, preserving
    §16.1's "confidence cannot be faked" property exactly for a cache hit as
    for a fresh model call.
  - **Follow-up, same session:** `AISuggestion` gains an `appliedSource`
    field (the full patched source, populated by `verifySuggestion()` only
    on a validated fix — `sandbox->getModifiedSource()`, joined, captured
    right before the `Sandbox` that produced it goes out of scope).
    `verifySuggestion()`'s `suggestion` parameter changed from `const
    AISuggestion&` to `AISuggestion&` to allow this. A new CLI flag,
    `--smart-write-fix=<path>` (`main.cpp`, `g_SmartFixOutPath` in
    `Lexer.h`/`.cpp`), writes `appliedSource` to a real file at the exact
    point `DiagnosticEngine::add()` would otherwise only ever RENDER the fix
    as a diagnostic — gated on the identical `confidence >= 0.8f` check, so
    it can never write an unvalidated suggestion. This closes the specific
    gap raised live this session (see *Why this session's scope grew*
    below): §16.4's semantic-correctness/false-confidence metrics needed the
    corrected PROGRAM, not a description of the fix, and `--smart` itself
    never wrote one anywhere before this.

## Why this session's scope grew

While reviewing this record, a live example surfaced a real question: since
sandbox validation only proves "compiles and the diagnosed line clears," not
"is correct," could a fix land at the wrong place, or be correct-shaped but
wrong-valued, and still display with high confidence? Reading
`Sandbox::isOriginalErrorResolved()` (`src/Sandbox.cpp:474-500`) live
answered the first half precisely: it checks the diagnostic's OWN original
line and any newly-introduced error line — never `target_line` — so a
wrong `target_line` is already caught in the overwhelming majority of cases,
independent of whatever the model claims to have fixed. But the second half
was real and unmeasured: a fix that hardcodes a literal instead of writing
a proper conversion (observed live: `mut b: int = 5;` instead of `mut b: int
= a to int;`) compiles, clears the error, and would validate identically to
a genuinely correct fix. That's exactly §16.4's semantic-correctness/
false-confidence gap, previously left unautomated in this same record. Since
it turned out to be a bounded, same-session fix (`--smart-write-fix` plus
extending `run_benchmark.py` to actually compile-and-run the written fix,
using each corpus case's own `test::assert()` calls as the oracle — see
*Tests*), it was implemented here rather than deferred. See
`docs/planning/ARCHITECTURE_SIMPLIFICATION.md`'s new evidence entry (same
date) for the DEEPER, harder version of this that was NOT attempted: a real
in-process "compile and run" API that wouldn't need three subprocess hops
(compile, write-fix, recompile-fixed, run-fixed) to answer this question.

## New invariants

**INV-DIAG-2** (`docs/development/INVARIANTS.md`): every `--smart`
suggestion actually displayed — from a fresh model call, the deterministic-
fix layer, or a cache hit — has been sandbox-validated in THIS run; no path
reaches the 0.8 display gate on a stored/assumed validation result. Enforced
by `tryDeterministicFix()` and a cache hit both flowing through the same
`verifySuggestion()`/`finalizeConfidence()` call a fresh model result does,
and by `readSlmCache()` never caching `confidence`/`sandbox_validated` at
all. This is the natural extension of the EXISTING (pre-SLM-001, §16.1)
"sandbox verification stays"/"confidence gate stays" properties to the two
NEW code paths this session added — worth its own row specifically because
those two paths are new enough that a future change could plausibly
introduce a shortcut ("the cache already validated this, skip
`verifySuggestion()` this time") that would violate it silently.

## Removed assumptions

- **"A cache lookup can safely serve any attempt, not just the first."**
  Deliberately NOT done: `readSlmCache()` is only consulted when
  `previousAttemptFailed.empty()`. A retry exists specifically because the
  previous suggestion (quite possibly the one sitting in the cache right
  now) already failed sandbox validation — serving it again on the retry
  would reproduce that exact failure forever instead of letting the retry
  reach the model with real corrective feedback. Verified live: a genuine
  model-backed case (`mut a = 5; mut b: string = "x"; b = a;`) showed
  attempt 1 hit the cache from a PRIOR run's now-stale suggestion, failed
  re-validation exactly as sandbox verification is supposed to catch, and
  attempt 2 correctly went to the model fresh with `previousAttemptFailed`
  set — the safety net worked exactly as designed on a real, not
  hand-constructed, case.
- **"A cached suggestion can be trusted without re-validation."** Never
  true, and this group doesn't introduce it: every cache hit still goes
  through the identical `verifySuggestion()`/`finalizeConfidence()` path a
  fresh model suggestion does. A stale or wrong cache entry can only ever
  cost a wasted sandbox attempt, never a bad patch reaching the display gate.
- **"Every RankedSuggestions-based 'unknown name' error is a safe
  deterministic-rename candidate."** Explicitly NOT true for
  `UseBeforeDeclarationError`: unlike every other class wired up in this
  group, its `Name` is not a typo — it's a real, correctly-spelled
  identifier declared LATER in the same scope. A rename to some other
  visible candidate would silently reference the wrong variable (and could
  still pass sandbox validation, since the line would still compile) instead
  of fixing the actual problem. Deliberately left unwired; see the class's
  own updated doc comment (`ErrorsScope.h`).
- **"The compiler binary's own version can be read from a project version
  string."** No such string exists anywhere in this project (confirmed via
  grep — `CMakeLists.txt` has no `CMAKE_PROJECT_VERSION`/embedded git hash).
  The cache's invalidation fingerprint is the compiler binary's own
  size+mtime instead — an ordinary engineering judgment call (SESSION_
  PROTOCOL.md §6.0 rule 2), not a FREEZE.md decision, recorded here as such.

## Known pitfalls

- **The deterministic-fix layer's coverage of "unknown name" error classes
  is real but partial, by deliberate choice, not oversight.** Wired:
  `LookupError`, `UnknownFunctionError`, `UnknownTypeError`, `ReferenceError`,
  `NoSuchVariantError`, `StructMethodNotFoundError`, `UnknownStructFieldError`,
  `UnknownScopeQualifierError`, `UnknownModuleSymbolError`,
  `ModuleMethodNotFoundError`, `KeywordError` (11 classes). Deliberately NOT
  wired: `UseBeforeDeclarationError` (see *Removed assumptions* — a rename
  there is semantically wrong, not just unproven). A future session growing
  this list should apply the exact same one-line
  `trySetDeterministicRename(Name, Suggestions)` pattern, and should
  specifically re-derive (not assume) whether the class's `Name` parameter
  is a genuine typo of something ALREADY declared, the same way
  `UseBeforeDeclarationError` was excluded.
- **Item 3's "known types" coverage is one call site, not "every type-
  mismatch diagnostic."** `VarDeclExprAST`'s own initializer mismatch
  (`TypeCheckerDecl.cpp`) and every binary/relational-operator mismatch
  (`TypeCheckerCore.cpp`'s `inferBinaryType`/`inferRelationalType`) do NOT
  get a `known_types` hint yet, even though some of their operands could
  also be `guess`-inferred. Verified live before deciding this was an
  acceptable scope cut, not an oversight: those functions receive only raw
  `const TurfType *` operands (already stripped of the originating
  `ExprAST`/`VariableSymbol`), so wiring them up needs their CALLERS
  (`visitBinary` et al., which DO have the real nodes) to pass guess-ness
  down as new parameters — a real, mechanical, but more invasive change than
  this session's single-call-site proof of the mechanism. A future session
  should thread it through the same way this session's `visitAssignment`
  site does, one call site at a time.
- **RESOLVED, same session — originally recorded here as deliberately
  unautomated:** `run_benchmark.py`'s semantic-correctness/false-confidence
  metrics. The `--smart-write-fix=<path>` flag plus extending
  `run_benchmark.py` to compile-and-run the written fix (using each corpus
  case's own pre-existing `test::assert()` calls as the oracle) closed both
  — see *Why this session's scope grew* and the real, measured numbers in
  *Tests* below. What's still true and worth naming: this measures
  semantic correctness only as well as the corpus's OWN assertions cover the
  mutated code path — a mutation whose test doesn't actually exercise the
  broken statement (weak assert coverage in the source test) would report
  `semantic_correct` for a fix that happens to compile without actually
  restoring the original intent. Real for THIS corpus (every case's mutated
  line sits directly under an assert that exercises it — confirmed by
  reading each source test before adding it in `mutate.py`), but not a
  property this tool enforces automatically for a case a future session
  adds. `recompile_failed` (a validated fix that doesn't survive a REAL
  compile+link) is also new signal this closes: the Sandbox's own recheck
  never reaches Codegen at all, only Lex/Parse/Resolve/TypeCheck/Lint — see
  the re-run numbers in *Tests* for what this session's 6-case corpus
  actually measured on that specific failure mode.
- **The benchmark corpus is small (6 cases) and hand-picked, not randomly
  sampled.** Sufficient to prove the tool and the §16.3 mechanisms work
  end-to-end on REAL (not synthetic) mutations of REAL passing tests, but
  not a statistically meaningful sample for tracking model-quality trends
  over time. Growing it is pure, low-risk, mechanical follow-on work: add a
  `(source_test, line, kind)` tuple to `mutate.py`'s `MUTATIONS` list,
  following the file's own doc comment on verifying a candidate mutation
  actually breaks compilation before relying on it.
- **A copy-pasted `RankedSuggestions`-based error-class constructor that
  omits the new `trySetDeterministicRename(...)` line silently gets no
  deterministic-fix coverage** — not a compile error, not a test failure,
  just a missed optimization (the diagnostic still works exactly as before,
  it simply always goes to the model). Same shape of silent-degrade DIAG-001
  already disclosed for a dropped `SLM::ErrorCategory` argument.
