# NM-3 — the `math::wrapping_*` family

| | |
|---|---|
| **Status** | landed |
| **Dates** | 2026-10-24 |
| **Commits** | (filled in at commit time) |
| **Sessions** | 1 of 1 |
| **Depends on** | the closed intrinsic list (`src/sema/Intrinsics.h`, F-STD-2) |
| **Frozen decisions relied on** | F-STD-2 (adding a compiler-known symbol is a change-recorded act: this record), F-API-1 (a minor may add `pub` items), F-PRE-2 (a `math` name is bare-callable), INV-OPT-2 (no check is removed without a proof; these functions have no check to remove) |

Issue #295. Roadmap decision D-15. The TDP names `wrapping_add`, `_sub` and
`_mul`; the owner asked for the whole family (2026-10-24): `wrapping_shl`,
`_shr`, `_neg`, `_abs`, `_div`, `_rem` and `_pow` too, with Rust's meanings.

## Why

`+`, `-` and `*` on `int` trap on overflow, and that check stays the default.
Hashes, checksums and random-number generators want arithmetic modulo 2^64, and
had no way to get it short of splitting values into halves. A function, not an
operator: no grammar change, and every use is visible and searchable.

## Language semantics

None. Ten `pub fn` declarations in `lib/std/core/math.tr`, each `int` modulo
2^64 in two's complement. None panics on overflow; `wrapping_div` and
`wrapping_rem` panic on a zero divisor and `wrapping_pow` on a negative
exponent, at the caller's line (`@caller_location`, INV-STD-5), since those
have no wrapped result. A shift amount is taken modulo 64. As `math` functions they are callable
as `math::wrapping_add(a, b)`, bare (`wrapping_add(a, b)`, F-PRE-2), through UFCS
(`a.wrapping_add(b)`), and as a function value (`immut f = wrapping_add;`).

### Is this breaking?

No. Ten names are added to a prelude module. `prelude_shadow_check.sh` found no
program in the tree that declares any of them, and a program's own
`wrapping_add` still wins over the prelude's, as for every `math` name
(`tests/50_intrinsic_shadowing/04_user_function_named_like_lowered_math.tr`).

## Compiler architecture

- **Registry** · `src/sema/Intrinsics.h` gains kind 5, "standard-library
  functions the compiler lowers itself": `enum class LoweredFunction` and
  `LookupLoweredFunction(Module, Name)`, the one place their names are compared.
  Four are lowered: `wrapping_add`, `_sub`, `_mul` and `_shl` (`<<` is checked,
  so a wrapping shift cannot be written in Turf; the amount is masked to 0..63
  first, since an LLVM `shl` by 64 or more is poison). The other six are
  ordinary Turf built on those four.
- **Resolver** · `buildFunctionSymbol()` sets `ResolverFunctionSymbol::Lowering`
  from the declaring module's key. A module key equal to a stdlib name is the
  stdlib's module: a root module of that name is E090 at its import, and a
  dependency's modules are keyed `<package>/<path>`. The main file's key is
  empty. So the flag can only be set on the stdlib's declaration.
- **Codegen** · `EmitLoweredFunction()` (`CodegenFunc.cpp`, declared in
  `CodegenInternal.h`) emits `add`/`sub`/`mul i64` with no `nsw`. It is used by
  an ordinary call (`FuncCallExprAST::codegen()`), a UFCS call
  (`MethodCallExprAST::codegen()`, `CodegenStruct.cpp`) and the function's own
  definition, whose body is not emitted. The definition matters for a function
  value, which calls the real function.

The `+`, `-` and `*` in the stdlib bodies are never compiled. They state which
operation each function wraps and keep the flow analyses' view of the body
ordinary.

## Runtime changes

None.

## Standard-library changes

`math::wrapping_add`, `_sub`, `_mul`, `_shl`, `_shr`, `_div`, `_rem`, `_pow`
(two `int`s), `_neg`, `_abs` (one). Documented in `docs/reference/stdlib/math_and_os.md` and
locked in `tests/46_stdlib_surface/02_runtime_modules.tr`.

## New invariants

None frozen. The lowering at `-O0` (a plain instruction, never a call) is checked
by `opt_levels_smoke` section 4.

## Removed assumptions

- "Every compiler-known symbol is a bare intrinsic, an LLVM intrinsic, a runtime
  entry point or a prelude module." Kind 5 is a declared function the compiler
  also knows.

## Tests

- `tests/36_numeric_semantics/13_wrapping_arithmetic.tr`: the limits in both
  directions, plain results, the bare, UFCS and function-value forms, every
  member's edge case (shift amounts past 63 and negative, `MIN / -1`,
  `MIN % -1`, powers that wrap), and an FNV-1a step. Expected values computed
  outside the compiler.
- `tests/42_caller_location/fail_stdlib_wrapping_{div,rem}_by_zero_names_caller.tr`,
  `fail_stdlib_wrapping_pow_negative_names_caller.tr`: each panic names the
  calling line.
- `tests/50_intrinsic_shadowing/04_user_function_named_like_lowered_math.tr`: a
  program's own `wrapping_add` is not lowered.
- `scripts/smoke/opt_levels_smoke.{sh,ps1}` section 4: main's `-O0` IR holds a
  plain `add`, `sub`, `mul` and `shl` and no call to the functions. Breaking the lookup
  on purpose makes the `.sh` check fail. The `.ps1` twin was written without a
  PowerShell to run it on.

## Known pitfalls

- A stdlib module that declares a function with one of these names in another
  module (say `bits::wrapping_add`) is not lowered: the key includes the module.
- The `int32` forms are not provided (TDP-2-002 open question; `int32` exists for
  ABI declarations).

# NM-6 — checking overflow in batches

| | |
|---|---|
| **Status** | proposed (not implemented); targeted at 2.3.0, beside NM-2 |
| **Dates** | 2026-10-25 |
| **Commits** | none |
| **Sessions** | 0 |
| **Depends on** | F-PANIC-1 … F-PANIC-3 (`FREEZE.md` §6.30); NM-2 for the loop form (stage 2) |
| **Frozen decisions relied on** | F-NUM-3 (overflow traps, never wraps), F-OPT-1 / F-NUM-6 (no observable difference at any level), F-OPT-2 and INV-OPT-2 (no check is removed without a proof; NM-6 removes none), F-PANIC-3 (a check may run late) |

Roadmap §6.9 NM-6. Constitution: Principle II (native performance, with costs
you can read), held inside Principle I (checked arithmetic stays the default)
and verified as Principle VIII asks (the delay is shown unobservable by a
differential oracle, not argued).

## Why

A checked `+` is an add, an overflow test and a branch to a panic block. The
branch is what costs: it puts each addition in its own basic block, so neither
the SLP vectorizer (which works within one block) nor the loop vectorizer
(NM-4: LLVM does not vectorize an early-exit loop that stores) can touch the
code. `particles` with checked `+` is 25.3 ms against C's 17.9 ms; the same
program with `math::wrapping_add` is 18.1 ms (`BENCHMARKS.md`, 2026-10-24).

Proving the overflow away (NM-2) cannot help there: `x + vx` depends on data.
Ignoring what cannot be proven would make those additions wrap and drop F-NUM-3.
What remains is to keep every check and move it: add with a plain `add`,
record whether it overflowed, and branch once, later. The add and the
overflow test are straight-line arithmetic, so they vectorize.

## Language semantics

None. A program's output, exit status and panic text are the same as with a
check in place. What changes is only memory the program can no longer read:
between an overflowing operation and its late check, a wrapped value may be
stored. After the panic no Turf code runs (F-PANIC-1), and memory after a panic
is not observable (F-PANIC-2).

### Is this breaking?

No. Unobservable by F-PANIC-2; nothing to migrate.

## The applicability rule

A **batch** is a region of one function in which some checked `+`, `-` and `*`
on `int` (the **batched operations**) are emitted unchecked, each with an
overflow bit, and one **flush** tests the bits. The compiler forms a batch only
if every condition holds; otherwise every operation keeps its check in place.

1. **Nothing observable inside.** The region holds no call of any kind (a
   function, method, UFCS or operator-overload call, a runtime entry point), so
   no I/O, allocation, collection or stack growth; no `defer`, `try`, `recover`,
   `unsafe` block or raw-pointer access; no store to a `string`'s bytes. The four
   lowered `math::wrapping_*` functions are instructions and are allowed.
2. **A wrapped value reaches only memory and other batched operations.** The
   result of a batched operation, and anything loaded in the region from memory
   the region writes, may be stored or used as an operand of another batched
   operation. It may not reach a branch or loop condition, an array index, a
   divisor or shift amount, a conversion, a comparison or anything that escapes
   the region. Otherwise a wrapped value could choose a different path, raise a
   different panic (an index out of bounds instead of the overflow) or keep a
   loop running that should have stopped.
3. **No other check fails first.** Every other check in the region (bounds,
   division by zero, conversion) is either proven (INV-OPT-2) or flushes the
   batch on its failure path before reporting itself, so a batched overflow that
   came earlier is reported first.
4. **The first failure is the one reported.** The flush reports the batched
   operation that overflowed first in execution order, with that operation's
   kind and `file:line`, through the same `turf_rt_panic()` call a check in place
   uses. Before the first overflow every value is exact, so the earliest flagged
   operation is a real overflow even when later ones computed on wrapped values.

## Stages

- **Stage 1: one straight-line run (one basic block).** The batch is a run of
  statements with no control flow; the flush is at its end. Execution order is
  source order, so the flush reports the first set bit in source order. This is
  `particles`' shape: the `x` and `y` additions of one iteration land in one
  block, which is what SLP needs. No loop analysis.
- **Stage 2: an innermost loop.** The batch is a counted loop whose only control
  flow is its own exit test on an induction variable NM-2 proves cannot
  overflow, with every index affine in that variable and in bounds by proof.
  Each batched operation keeps the smallest iteration number at which it
  overflowed (a `min` reduction, which vectorizes); the flush, after the loop or
  after each strip of a fixed number of iterations, reports the smallest
  (iteration, source position). Strip length is a measured choice: a longer
  strip costs only the time spent computing past an overflow.

## Compiler architecture (planned)

- **Analysis** · a pass beside `ValueRangePass::markElidableChecks()` marks the
  operations and regions that pass the rule. It runs at every `-O` level, as
  INV-OPT-2's pass does, so one code shape is fuzzed. On today's mechanism the
  mark is an AST flag (`BatchedOverflow`, beside `ProvenNoOverflow`); from
  F-S4a it is a row in `AnalysisFacts`; in TIR (F-S4c) it is an
  `IntAddDeferredCheck` instruction plus a `FlushChecks` instruction that
  dominates every exit of the region.
- **Codegen** · `EmitCheckedIntArith()` gains a batched form: a plain `add`/
  `sub`/`mul` and an overflow bit, ORed into the region's flag (stage 1) or
  folded into the operation's minimum iteration (stage 2). The flush is one
  branch to a cold block that selects the operation and calls
  `turf_rt_panic()`. Default-deny like INV-OPT-2's tracking: a case the rule
  does not model is not batched.

## Open measurements (before any code lands)

1. **Stage 1 on `particles`.** Hand-edit `particles`' `-O2` IR to the batched
   shape and time it. If it does not approach the wrapped 18.1 ms, stage 1 is
   not worth its rule, and this record says so.
2. **Which overflow test vectorizes.** Whether LLVM 23 widens
   `llvm.sadd.with.overflow`'s overflow bit, or whether the test should be
   written as `((a ^ r) & (b ^ r)) < 0` (for `+`), which is plain vector code.
   `*` has no such cheap form; measure `smul.with.overflow` separately.
3. **Rule 3's flushing failure path.** Whether a bounds check whose failure path
   flushes still splits the block for SLP, or whether proven bounds (NM-2) are
   required in practice.

## Tests (planned)

- Differential oracle: turf-fuzz's `oracles/overflow.py`, extended to build each
  program with batching on and off and require identical stdout, stderr and
  exit status. A wrong batch either misses a panic or reports the wrong line,
  and both show up here.
- `tests/43_check_elision/`: one test per rule (a wrapped value used as an
  index, in a condition, as a call argument, after a call in the region, with
  an unproven bounds check after it), each keeping its check in place and
  panicking at the expected line; and one where two batched operations overflow
  and the earlier one is reported.
- `bench/particles.tr` before and after, recorded in `BENCHMARKS.md`.

## Known pitfalls

- A debugger stopped at the panic sees the wrapped value already stored. That
  is outside the language (F-PANIC-2) but surprising; `turf` documentation for
  debugging should say so if stage 1 lands.
- Threads (TDP-3-001): another thread could read a wrapped store before the
  flush. Rule 1 keeps every synchronization point (a call, an atomic) out of a
  batch, so a data-race-free program cannot. CC-0's sharing model must keep
  unsynchronized reads of shared memory out of safe Turf, or batches end at
  every store to shared memory.

## Unresolved questions

- Whether stage 2 is worth its rule once stage 1 and NM-2 are measured, or
  whether `math::wrapping_*` (NM-3) remains the answer for loops the rule does
  not reach.
