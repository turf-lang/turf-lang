| **Frozen decisions relied on** | F-STD-2 (adding a compiler-known symbol is a change-recorded act: this record), F-API-1 (a minor may add `pub` items), F-PRE-2 (a `math` name is bare-callable), INV-OPT-2 (no check is removed without a proof; these functions have no check to remove) |

Issue #295. Roadmap decision D-15.

## Why

`+`, `-` and `*` on `int` trap on overflow, and that check stays the default.
Hashes, checksums and random-number generators want arithmetic modulo 2^64, and
had no way to get it short of splitting values into halves. A function, not an
operator: no grammar change, and every use is visible and searchable.

## Language semantics

None. Three `pub fn` declarations in `lib/std/core/math.tr`, each `int` modulo
2^64 in two's complement, never trapping. As `math` functions they are callable
as `math::wrapping_add(a, b)`, bare (`wrapping_add(a, b)`, F-PRE-2), through UFCS
(`a.wrapping_add(b)`), and as a function value (`immut f = wrapping_add;`).

### Is this breaking?

No. Three names are added to a prelude module. `prelude_shadow_check.sh` found no
program in the tree that declares any of them, and a program's own
`wrapping_add` still wins over the prelude's, as for every `math` name
(`tests/50_intrinsic_shadowing/04_user_function_named_like_lowered_math.tr`).

## Compiler architecture

- **Registry** · `src/sema/Intrinsics.h` gains kind 5, "standard-library
  functions the compiler lowers itself": `enum class LoweredFunction` and
  `LookupLoweredFunction(Module, Name)`, the one place their names are compared.
- **Resolver** · `buildFunctionSymbol()` sets `ResolverFunctionSymbol::Lowering`
  from the declaring module's key. A module key equal to a stdlib name is the
  stdlib's module: a root module of that name is E090 at its import, and a
  dependency's modules are keyed `<package>/<path>`. The main file's key is
  empty. So the flag can only be set on the stdlib's declaration.
- **Codegen** · `EmitLoweredFunction()` (`CodegenFunc.cpp`, declared in
  `CodegenInternal.h`) emits `add`/`sub`/`mul i64` with no `nsw`. It is used by
  an ordinary call (`FuncCallExprAST::codegen()`), a UFCS call
  (`MethodCallExprAST::codegen()`, `CodegenStruct.cpp`) and the function's own
  definition, whose body is not emitted. The definition matters for a function
  value, which calls the real function.

The `+`, `-` and `*` in the stdlib bodies are never compiled. They state which
operation each function wraps and keep the flow analyses' view of the body
ordinary.

## Runtime changes

None.

## Standard-library changes

`math::wrapping_add`, `math::wrapping_sub`, `math::wrapping_mul`, each
`(a: int, b: int): int`. Documented in `docs/reference/stdlib/math_and_os.md` and
locked in `tests/46_stdlib_surface/02_runtime_modules.tr`.

## New invariants

None frozen. The lowering at `-O0` (a plain instruction, never a call) is checked
by `opt_levels_smoke` section 4.

## Removed assumptions

- "Every compiler-known symbol is a bare intrinsic, an LLVM intrinsic, a runtime
  entry point or a prelude module." Kind 5 is a declared function the compiler
  also knows.

## Tests

- `tests/36_numeric_semantics/13_wrapping_arithmetic.tr`: the limits in both
  directions, plain results, the bare, UFCS and function-value forms, and an
  FNV-1a step.
- `tests/50_intrinsic_shadowing/04_user_function_named_like_lowered_math.tr`: a
  program's own `wrapping_add` is not lowered.
- `scripts/smoke/opt_levels_smoke.{sh,ps1}` section 4: main's `-O0` IR holds a
  plain `add`, `sub` and `mul` and no call to the functions. Breaking the lookup
  on purpose makes the `.sh` check fail. The `.ps1` twin was written without a
  PowerShell to run it on.

## Known pitfalls

- A stdlib module that declares a function with one of these names in another
  module (say `bits::wrapping_add`) is not lowered: the key includes the module.
- The `int32` forms are not provided (TDP-2-002 open question; `int32` exists for
  ABI declarations).
