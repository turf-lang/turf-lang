## Why

Before this group, the only safe way for Turf code to obtain a `&T` was
`&localVar` — the address of an existing stack variable. That makes a
data structure whose size isn't known until runtime (a linked list, a
tree, a graph) unbuildable in safe TurfLang at all: a `make()`-style
helper that builds a node and returns `&localNode` hands back a dangling
reference to a dead stack frame the instant it returns (verified live,
`docs/archive/OVERHAUL_CLOSURE_AUDIT.md` F-16). The only escape was
`unsafe`-gated raw-pointer manual allocation.

`heap(expr): &T` closes this gap: it copies `expr`'s value onto the GC
heap and returns a compiler-checked `&T` to it, with no `unsafe { }`
anywhere — closing the capability §0.5 of the Architecture Overhaul always
promised (`ARCHITECTURE_OVERHAUL.md` §14) and DoD-8's dynamic-linked-
structure test only ever demonstrated with a fixed set of stack nodes
(`LANG-002.md`).

## Language semantics

### Old behaviour

No way to construct a value directly on the GC heap. `&expr` (address-of)
always points at the operand's own stack storage; the only other
placement was the manual heap via `mem::alloc(...)` cast to a raw `T*`,
entirely unmanaged and gated by `unsafe { }`.

### New behaviour

```turf
fn cons(v: int, next: &?Node): &Node {
    mut n: Node = Node::default();
    n.val = v;
    n.next = next;
    return heap(n);   // copies n onto the GC heap; returns &Node
}
```

`heap(e: T): &T` for any sized `T` — a struct, a fixed array (`T[N]`), or
a primitive. `T` is the operand's own static type, not a fixed signature
— the return type is computed per call site (`TypeChecker::visitFuncCall`
in `TypeCheckerCall.cpp`, and mirrored in `Codegen::getExprType()` for
Codegen's own separate type-inference path). Rejects `void` (nothing to
copy) with a clean compile error, not a crash or a zero-byte allocation.

Lowering: `turf_rt_alloc(sizeof(T), desc_T)` where `desc_T` is `T`'s REAL
per-type `TurfTypeDesc` — a named struct's own whole-instance descriptor
(the same one `EmitAllTurfTypeDescs()` emits for it, OVH-002's
`getOrForwardDeclareTurfTypeDescGlobal()`), or the general per-LLVM-type
descriptor (`getOrCreateElementTurfTypeDesc()`, MEM-002) for a fixed array
or a primitive. Never `NULL`/opaque — the collector traces a `heap()`ed
value's own pointer fields exactly as it would the same value sitting on
the stack.

### Is this breaking?

No. Purely additive: a new bare intrinsic, no grammar change, no existing
program's meaning changes.

## Compiler architecture

- **Lexer/Parser**: none — `heap(expr)` is an ordinary call expression;
  `heap` is recognized only where it fails to resolve as a real
  function/variable (matching `gc_alloc`/`gc_pin`/etc.'s existing
  precedent), not a reserved keyword.
- **Builtins registry** (`src/Builtins.cpp`): `RegisterBuiltin("heap", {1,
  ...})` — arity 1, shared generic arity check.
- **Resolver** (`src/ResolverCall.cpp`): added to the `BareIntrinsics` set
  so an unresolved bare `heap` call isn't reported as an unknown function.
- **TypeChecker** (`src/TypeCheckerCall.cpp`): new branch in
  `visitFuncCall()`'s bare-intrinsic dispatch — computes `&T` from the
  already-type-checked operand (`ArgTypes[0]`), rejects `void`.
- **Codegen**:
  - `src/CodegenFunc.cpp`'s `FuncCallExprAST::codegen()` — dispatch
    branch alongside `gc_alloc`/`gc_pin`/etc., calling the new shared
    helper.
  - `src/CodegenCore.cpp` — new `HeapAllocateValue(Value *Val)`, declared
    in `src/CodegenInternal.h`. Reuses `BoxToI64Slot()`'s exact
    size/descriptor-selection shape (already built for `!T`'s oversized
    success-value/message-carrying-error boxing, OVH-002) — the only
    difference is the return value, a real pointer rather than a
    `ptrtoint`'d `i64` slot.
  - `src/CodegenCore.cpp`'s `getExprType()` — new `FuncCallExprAST`
    branch for `heap`, computing `&T` from a nested `getExprType()` call
    on the operand and caching the resulting `TurfReferenceType` by the
    pointee's mangled name (mirrors `AddressOfExprAST`'s own existing
    cache in the same function, same reasoning: the returned type must
    outlive the caller without a fresh allocation per call, and without
    assuming ownership over a pointee type this function doesn't itself
    own — an aliasing, no-op-deleter `TurfTypePtr`).

No monomorphizer, CFG/analysis, diagnostics, or optimization changes.

## Runtime changes

None. `turf_rt_alloc` already existed (MEM-001); `heap()` is a new Turf-
visible caller of it with a real descriptor, not a new runtime entrypoint.

## Standard-library changes

None required. `lib/std/json`/`lib/std/http` could adopt `heap()` where a
node needs identity instead of by-value storage, but this is not done as
part of this group (not required — see Non-goals).

## New invariants

- **INV-MEM-5** (`INVARIANTS.md`, Memory management): `heap(expr): &T`
  never allocates with a `NULL`/opaque descriptor. Enforced by
  `HeapAllocateValue()` always routing through
  `getOrForwardDeclareTurfTypeDescGlobal()`/`getOrCreateElementTurfTypeDesc()`,
  never a literal `NULL`.

## Removed assumptions

- `docs/architecture/memory_model.md` §1.5 used to state flatly: "There is
  no way to construct a struct directly on the heap." No longer true —
  `heap()` is exactly that, for any sized type, not just structs.
- The pre-existing assumption that a `&T`'s pointee is always a stack
  frame (implicit throughout `pointers_and_references.md` §1.3, which only
  ever showed `&expr`) is now false — `heap()` produces a `&T` whose
  pointee is a GC-heap block, indistinguishable from a stack-backed `&T`
  at the type level (both are just `&T`), but with a different, longer
  lifetime story.

## Known pitfalls

- **`List<T>[i]` crashes the compiler for any `T` other than `int`** —
  confirmed live and unrelated to `heap()`: a bare `List<GraphNode*>`
  (no `heap()` involved at all) reproduces the identical
  `LLVM ERROR: Internal error: Base is not an array or pointer` that a
  `List<&GraphNode>` did. Root cause: `operator[]`/`operator[]=` are
  declared concretely for `List<int>` only (`docs/planning/LIMITATIONS.md`
  item 4 — `operator` declarations can't be generic), so indexing any
  OTHER `List<T>` has no real overload to resolve to; it should be a
  clean diagnostic and isn't yet. This is exactly the gap
  `ROADMAP_v2.0.0.md`'s own LEC-006 ("collection indexing coherence")
  names — not introduced or fixed by this group. `07_graph_adjacency.tr`
  works around it with `.data[i]` (the documented indexing path for a
  non-`int` `List<T>`) inside `unsafe { }`, and with two parallel
  `List<int>` index arrays instead of a `List<&Node>` neighbor field
  nested inside each node struct (the literal shape the roadmap's own
  Tests section describes), specifically to avoid exercising this
  unrelated gap in a test that's supposed to be proving something else.
- **Indexing a fixed array held behind a reference doesn't auto-deref
  yet.** `mut boxedArr: &int[5] = heap(arr); boxedArr[2]` type-checks as
  comparing `int[5]` to `int` rather than reading element 2 — `heap()` of
  a fixed array is the FIRST way to produce a `&(T[N])` at all (arrays
  were previously only ever stack/parameter/return values, never held
  behind a reference), so `ArrayAccessExprAST` has never needed to
  auto-deref through a reference-to-array base before. Allocation itself
  works fine (`heap(arr)` compiles and returns a real, non-null `&int[5]`)
  — only element access through the resulting reference doesn't. Not
  fixed here: none of this milestone's required tests exercise it (all
  three are struct-based), and it's a narrow, separable
  `ArrayAccessExprAST` enhancement, not a `heap()` correctness question.
- **Definite assignment doesn't recognize a whole array filled
  element-by-element in a loop as assigned** (`mut arr: int[5]; while ...
  { arr[i] = ...; } heap(arr);` raises E008) — pre-existing,
  independent of `heap()` (`arr` itself, read anywhere, has the same
  problem); worked around in ad-hoc probes with an array literal
  initializer instead. Not this group's own gap.
- **`self`/`operator[]`'s self-relaxation are unrelated to `heap()`** —
  worth stating explicitly since `heap()` and `&T` share so much
  machinery: `heap()` never touches `self`'s own raw-pointer-internally
  exemption, and doesn't change anything about operator resolution.
