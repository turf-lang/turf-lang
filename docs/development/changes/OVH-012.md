## Why

`docs/planning/OVERHAUL_REMAINING_WORK.md` OVH-012 (reproduced live,
2026-09-27, before this fix): a plain `import io;` ("hello world") printed a
`NeverReturnsErrorWarning` for `io::read_lines`, and `import json;` printed
six warnings for `json.tr`'s own internal parsing functions — none of them
written by the user, all unfixable by the user, on the very first thing a
new Turf program does. Four distinct root causes, all confirmed live:

1. **`NeverReturnsErrorWarning` blind to `recover` blocks.**
   `Resolver::CollectReturnedErrorTypeNames()` (`src/ResolverCore.cpp`) had
   no case for `RecoverExprAST`, nor for the `VarDeclExprAST`/
   `AssignmentExprAST` that typically wrap one as an initializer/RHS — so a
   function whose only `return <ErrorType>;` lives inside a `recover run {
   ... }` / `recover as err run { ... }` block (`io::read_lines`, `json::
   parse_number`/`parse_array`/`parse_object`) was flagged as "never
   actually returns an error" even though it demonstrably does.
2. **Same blind spot, a second shape: `json::parse`.** `parse`'s only
   failing path is `p.parse_value() recover as err run { return err; };` —
   re-throwing the *bound* error variable, not naming a concrete
   `ErrorType::Variant`. Even after fixing (1), this shape has no error type
   *name* to collect at all (`err`'s static type is the type-erased
   `AnyErrorType`), so it needed a second, independent mechanism.
3. **Liveness/unused-variable analysis blind to `recover` operands.**
   `AnalysisVisitor` (`src/Analysis.cpp`, backs both `DefiniteAssignmentPass`
   and `LivenessAnalysisPass`) had no `visitRecoverExpr()` override —
   `ASTVisitor`'s default is a silent no-op — so a variable read *only* as
   the operand of a `recover` expression's wrapped call (`json.tr`'s `immut
   numStr: string = ...; strings::parse_double(numStr) recover run { ...
   };`) was invisible to both passes: flagged **both**
   `UnusedVariableWarning` ("declared but never used") **and**
   `DeadStoreWarning` ("assigned but never read") for a variable that
   demonstrably is read.
4. **Two genuine, non-false-positive warnings remained in stdlib source.**
   `json.tr`'s `parse_array`/`parse_object` each end with a `return arr;`/
   `return obj;` after an unbreakable `while true` whose only exits are
   `return`s inside the loop — truly unreachable code, a correct
   `UnreachableCodeWarning`. `http.tr`'s `Server.listen` triggers
   `InfiniteLoopWarning` on its accept loop, which is intentional (an HTTP
   server's listen loop is *meant* to run forever) — restructuring it to
   have a fake exit path would be worse code for no real benefit.

Fixing (1)–(3) does not fully clear a plain `import http;`, since (4)'s
`Server.listen` warning is a true positive on intentional code, not a bug —
no amount of "look harder at the AST" fixes that. The ticket's own
recommendation (put to the user, who approved it): treat any warning whose
location is inside the install root's `lib/std` as a **system-module
warning** — recorded exactly as before, but not *printed* by default,
matching `-isystem` practice. This is what actually gets a plain `import
io; import json; import http;` to compile with zero output, robustly,
including against any future stdlib warning nobody's fixed yet.

## Language semantics

### Old behaviour
```
$ turf --resolve lib/std/io/io.tr
── warning at line 197 ...
  Warning: 'read_lines' is declared to return a fallible type ('!T') but
  never actually returns an error.
```
Five more like it from `json.tr` (four from the recover-block blind spot,
one — `parse_array`'s unreachable trailing `return arr;` — genuine but
never mentioned to the user as "yours to ignore, not yours to fix").
`http.tr`'s intentional accept loop always printed its `InfiniteLoopWarning`
too. All were unconditionally printed to anyone who merely `import`ed the
module.

### New behaviour
`turf --resolve lib/std/io/io.tr`, `lib/std/json/json.tr` print nothing.
`turf --resolve lib/std/http/http.tr` prints nothing **by default**; `turf
--resolve --stdlib-warnings lib/std/http/http.tr` prints exactly the
`Server.listen` `InfiniteLoopWarning` (the one true positive left, on
intentional code). `import io; import json; import http;` compiles
silently either way.

### Is this breaking?
No new rejection and no change to what compiles. The only user-visible
change to program *behaviour* is that four false-positive warnings no
longer print, and (with `--stdlib-warnings` unset, the default) `lib/std`
warnings in general no longer print. A tool that was scraping stdout for
the specific old warning text on one of these functions would need to stop
— nothing in this codebase does. `--stdlib-warnings` is new, additive CLI
surface; omitting it (every existing invocation) behaves as described above.

## Compiler architecture

- **Resolver** (`src/ResolverCore.cpp`): `CollectReturnedErrorTypeNames()`
  gains three new cases — `VarDeclExprAST` (descends into the initializer),
  `AssignmentExprAST` (descends into the RHS), `RecoverExprAST` (descends
  into `Wrapped` always, plus `ProduceExpr` or `Block` depending on
  `RecoverKind` — mutually exclusive). The function signature grows a
  threaded `BoundErrNames` stack (innermost `recover as err run`'s
  `BoundName`s currently in scope) and an output `bool &FoundReboundError`:
  a `return <var>;` matching one of the bound names sets it, recognizing
  `json::parse`'s re-throw shape with no type name to collect.
- **Symbol tables** (`include/ResolverSymbolBase.h`): new
  `ResolverFunctionSymbol::ReturnsReboundError` field, set by
  `buildFunctionSymbol()` alongside `PossibleErrorTypeNames`.
- **Resolver** (`src/ResolverDecl.cpp`): `visitFuncDef()`'s
  `NeverReturnsErrorWarning` check now seeds `ReturnsRealError` from
  `Sym->ReturnsReboundError` before the existing `isErrorTypeName()`-filtered
  loop over `PossibleErrorTypeNames` — a rebound error bypasses that filter
  entirely (there is no name to filter).
- **CFG/analysis** (`src/Analysis.cpp`): `AnalysisVisitor` (shared by
  `DefiniteAssignmentPass`/`LivenessAnalysisPass`) gains a
  `visitRecoverExpr()` override, same shape and same precedent as
  `visitDefer()` (LANG-003) just above it in the file: visits `Wrapped`
  unconditionally, then `ProduceExpr` or `Block` depending on `RecoverKind`.
- **Diagnostics** (`src/Lexer.cpp`): `DiagnosticEngine::flushAll()` now
  skips printing (but still records — `Diagnostics`/`getDiagnostics()`/
  `getDiagnosticCount()` are untouched) a warning whose `Filename` resolves
  under the install root's `lib/std`, unless the new `g_ShowStdlibWarnings`
  global is set. Filtering at *print* time rather than at
  `DiagnosticEngine::add()` time was a deliberate choice: `add()` is also
  consulted by `Sandbox.cpp`, `ParserModule.cpp`'s speculative-parse retry
  (`DiagCountBefore`/`FoundButBroken`), and `CompileBuffer.cpp`, none of
  which should see their diagnostic bookkeeping change just because the
  terminal presentation did.
- **Parser** (`src/ParserModule.cpp`/`include/Parser.h`): new exported
  `IsLibStdWarningLocation(Path)` — a strict subset of the existing (file-local)
  `IsPathUnderInstallRoot()`: excludes a sibling `lib/usr` user package,
  which lives under the same install root but is the *user's* code, not the
  standard library, and must never have its warnings hidden by default.
- **Driver** (`src/main.cpp`): new `--stdlib-warnings` CLI flag, threaded
  through `CompilerOptions::ShowStdlibWarnings` to `g_ShowStdlibWarnings`
  before any diagnostic could be flushed. Usage string updated.

## Runtime changes
None.

## Standard-library changes
`lib/std/json/json.tr`: `parse_array()`/`parse_object()` each lose a
trailing `return arr;`/`return obj;` after their unbreakable `while true` —
genuinely unreachable code (every path through the loop already ends in
`return`), confirmed by direct compilation with no other change in
observable behaviour. No other stdlib file changed.

## New invariants
None added to `INVARIANTS.md`. This is a diagnostics-accuracy fix
(existing invariants around `!T`/`recover` and CFG liveness are unchanged —
the ANALYSIS was wrong, not the language rule it enforces) plus an
opt-in display filter with no soundness property to name.

## Removed assumptions
- **"A function's only failing `return` is a direct child of `Block`/`If`/
  `While`/`For`/`ForEach`."** False since `recover run`/`recover as err run`
  exists — a `return` reachable only through one of those blocks is just as
  real. Any future Resolver-level scan over "what can this function's body
  do" that doesn't already share `CollectReturnedErrorTypeNames()`'s
  updated recursion shape should be checked against this same blind spot.
- **"`AnalysisVisitor`'s default (no-op) traversal is safe to leave
  unoverridden for any AST node with no assignment/read of its own."**
  False for a node that *wraps* other expressions containing real reads —
  `RecoverExprAST` is the second occurrence of this exact mistake after
  `DeferExprAST` (LANG-003). A third occurrence is plausible for a future
  control-flow-shaped expression node; the fix pattern is always the same
  (visit every child sub-expression, exactly once, respecting mutual
  exclusivity where it exists).
- **"Every `lib/std` warning that survives to `flushAll()` is a bug to
  fix."** No longer true by design: `Server.listen`'s accept loop is a
  correct, intentional infinite loop, and the *right* answer for it (and
  for any future, currently-unknown stdlib warning nobody's gotten to yet)
  is display suppression by default, not code contortion to satisfy a
  static check that's asking the wrong question of intentionally-forever
  code.

## Known pitfalls
- **The suppression is print-time, not record-time — read `getDiagnostics()`
  expecting only what the user saw, and you'll be wrong.** A future
  consumer of `DiagnosticEngine::getDiagnostics()`/`getDiagnosticCount()`
  (an LSP, a future `--json-diagnostics` mode) will see *every* diagnostic,
  stdlib-hidden ones included — by design (see *Compiler architecture*
  above for why), but easy to forget and assume `flushAll()`'s printed
  output is the full picture.
- **`IsLibStdWarningLocation()` is deliberately narrower than
  `IsPathUnderInstallRoot()`** — a `lib/usr` user package is NOT covered,
  on purpose. Reusing the wrong one of the two for a future feature would
  silently suppress a user's own warnings (wrong) or fail to suppress a
  genuine stdlib one from a differently-laid-out install (also wrong,
  though less dangerous).
- **`ReturnsReboundError` only recognizes a *bare* `return <var>;` matching
  an enclosing `AsRun`'s exact bound name** — `return (err);`, `return err
  to AnyErrorType;`, or re-throwing through an intermediate local
  (`immut e2 = err; ... return e2;`) are NOT recognized and would still
  false-positive `NeverReturnsErrorWarning`. None of these shapes exist
  anywhere in `lib/std` today (confirmed by the direct-compile sweep
  above), so this is a known, narrow gap, not a live bug — same
  conservative-scan posture `CollectReturnedErrorTypeNames()`'s own doc
  comment already documents for everything else it doesn't recognize.
- **A nested `recover as err run` shadowing an outer one's bound name**
  (e.g. both named `err`, one inside the other) makes `BoundErrNames`
  contain the same string twice — harmless (`std::find` still matches),
  but worth knowing if a future reader extends this to also *distinguish*
  which binding a re-thrown `err` came from (this fix never needs to; it
  only needs "was this bound by *some* enclosing AsRun").
