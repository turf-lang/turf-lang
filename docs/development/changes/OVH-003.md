## Why

`docs/development/OVERHAUL_CLOSURE_AUDIT.md`'s finding for this item
(reproduced live, 2026-09-26): `TypeChecker::visitArrayAccess()` never
called `checkUnsafeGate()` on a raw-pointer base — indexing into a `T*`
was the one gated "use" (declaration, cast, dereference, struct field —
`docs/architecture/pointers_and_references.md` §1.2) that had no gate at
all, a gap that section's own §2.7 "Known gaps" bullet named but never
closed.

```turf
import list::List;
fn main(): int {
    mut l: List<int> = List::default(); l.push(1);
    l.data[100000] = 42;        // compiled, no `unsafe`, no capability -> SIGSEGV
    return 0;
}
```

Worse, `l.data[i]` was simultaneously the *documented* way to read/write a
`List<T>` element for any `T` other than `int`, because `operator[]`
exists only for the concrete `List<int>` (F-OP-1/LANG-001: operator
declarations are deliberately non-generic). Safe code had no bounds-checked
way to access a `List<string>`/`List<SomeStruct>` element at all without
either reaching for `unsafe { }` on every call site or reading the raw
`data` field directly and hoping.

## Language semantics

### Old behaviour
`someList.data[i]` (and any other raw-pointer-typed expression indexed
with `[]`) compiled unconditionally, in any file, with no `unsafe { }`
and no declared capability — reads and writes both, with no bounds check
of any kind.

### New behaviour
Indexing a raw-pointer-typed expression is gated exactly like field access
through one already was: legal inside `unsafe { }`, or in a module that
declares the raw-pointer capability (`unsafe module;`), a compile error
(`E066`, "Unsafe pointer use!") otherwise. `List<T>` gains `get(i): T`/
`set(i, value): void` — bounds-checked (panics with an `index out of
bounds` message, `@caller_location`-tagged so the panic names the
*caller's* line), genuinely generic over any `T` (unlike `operator[]`),
usable from ordinary safe code with no `unsafe { }` needed anywhere.
`Stack<T>`/`Queue<T>` were left alone — neither exposes positional access
today (only `push`/`pop`/`peek`), so there was no existing API surface to
replace.

### Is this breaking?
Yes, narrowly: any user code (outside `unsafe { }`/a capability module)
that indexed a raw-pointer field directly — most visibly `someList.data[i]`
on a `List<T>` for `T != int` — now fails to compile. The mechanical
migration is `.data[i]`/`.data[i] = v` → `.get(i)`/`.set(i, v)` for a
`List<T>`; for any other raw-pointer field, either wrap the specific
expression in `unsafe { }` (`docs/architecture/pointers_and_references.md`
§1.4's inline-expression idiom, `unsafe { expr; }`) or give the declaring
file the raw-pointer capability if it needs broader access. `List<int>`
callers using `l[i]`/`l[i] = v` (`operator[]`/`[]=`) are entirely
unaffected — that path never touched `.data` directly and was never
gated by this fix.

## Compiler architecture

- **TypeChecker.** `visitArrayAccess()` (`TypeCheckerCall.cpp`) gains a
  `checkUnsafeGate()` call on the base's type, placed right after `BaseTy`/
  `IndexTy` are computed and before the `operator[]` resolution branch
  (ordering doesn't matter in practice — `isRawPointer()` is false for
  every struct/array/string base the operator-overload and builtin-array
  paths ever see). Mirrors `visitFieldAccess()`'s existing dereference
  gate verbatim, including its `self`-base exemption (`self.data[i]`
  inside a collection module's own methods needs no special-casing beyond
  what the FILE's own `unsafe module;` capability already grants, but the
  exemption is included anyway for parity with the sibling gate and in
  case a future `self[i]`-shaped access ever needs it — none exists today).
- **Codegen — two independent, previously-latent bugs found and fixed
  while building `List<T>.get()`/`.set()`, neither about the gate itself:**
  1. `MethodCallExprAST::codegen()`'s struct-method branch
     (`CodegenStruct.cpp`) never accounted for a `@caller_location`
     callee's hidden trailing LLVM parameter (STD-002) — its arity check
     and arg-binding loop both assumed the real LLVM arg count matched
     `self + Args` exactly. `FuncCallExprAST::codegen()`'s sibling
     free-function path already handled this correctly; nothing had ever
     put `@caller_location` on a bound METHOD before this session's
     `List.get`/`.set`. See *Removed assumptions*.
  2. `getExprType()`'s `MethodCallExprAST` branch (`CodegenCore.cpp`) —
     Codegen's own independent, duplicate type-inference engine
     (`ARCHITECTURE_OVERHAUL.md` §25 item 4) — built its `FuncReturnTypes`/
     `FuncParamTypes` lookup key from a generic base type already
     collapsed to its shared TEMPLATE name (`"List"`), then fell through
     to an ambiguous method-name-only substring scan whenever the exact
     (always-wrong-shaped) key missed. With two structurally-similar
     generic instantiations of the same method both live, this silently
     picked EITHER one's return type for a given call site. Fixed by
     reading `MethodCallExprAST::ResolvedCallTarget` — already attached
     to the node by the TypeChecker — directly, instead of re-deriving a
     name. See *Removed assumptions* and new **INV-CG-2**/updated
     **INV-TYPE-2**.
  Both bugs are Codegen-internal correctness fixes, not part of the
  raw-pointer-gate feature itself; they surfaced only because `get()`
  is the first generic method in this codebase that is BOTH
  `@caller_location` AND returns a struct-shaped `T` read through a
  chained field access.
- **Standard library.** `lib/std/collections/list.tr`: `List.get(i): T`/
  `List.set(i, value): void` added, `@caller_location`, bounds-checked,
  panicking through the same `sys::panic()` path `operator[]`/`operator[]=`
  already use, with the caller's location prefixed. `lib/std/json/json.tr`:
  every `.data[i]`/`.data[i] = v` on an internal `List<string>`/
  `List<JsonValue>` field migrated to `.get`/`.set`; the file's
  `unsafe module;` pragma removed entirely — it held no OTHER raw-pointer
  use, so migrating away from `.data[i]` made the capability declaration
  genuinely unnecessary (B3: "the standard library gets no capability a
  user cannot request explicitly"). `lib/std/http/http.tr` (never declared
  the capability): its `.data[i]` reads on `List<string>` migrated the
  same way; `Server.get_route()`'s one `self.routes.values[idx]`
  (`Map<K, V>.values` is a raw `V*`, `map.tr` — untouched by this item,
  no non-generic-collection API added) wrapped in an inline
  `unsafe { expr; }` instead, since `idx` is already bounds-proven by
  `route_index()` immediately above it and Map wasn't in this item's
  scope.
- **Showcase.** `showcase/kv_store_server.tr`: `findIndex()`'s and the
  `GET`/`SET` handlers' `.data[i]` reads migrated to `.get(i)`; the `SET`
  handler's `store.data[idx].value = value;` (a through-pointer field
  write, no longer possible once `.get()` returns `Entry` BY VALUE)
  became an explicit read-modify-write (`get` a copy, mutate the copy,
  `set` it back).

## Runtime changes
None.

## Standard-library changes
`List<T>.get(i): T` / `List<T>.set(i, value): void` — new, bounds-checked,
generic-over-`T` positional accessors (`lib/std/collections/list.tr`).
`json.tr` no longer declares the raw-pointer capability. See *Compiler
architecture* above for every migrated call site.

## New invariants
- **INV-CAP-2** (added, `docs/development/INVARIANTS.md` "Capabilities and
  the standard library"): indexing a raw-pointer-typed expression is
  gated exactly like field access through one.
- **INV-CG-2** (added, "Code generation"): a `@caller_location` callee's
  hidden trailing LLVM parameter is accounted for at every call-emission
  site, not just one.
- **INV-TYPE-2** (existing, "Type system and layout") updated: the one
  live violation this session found (Codegen's `getExprType()` disagreeing
  with the TypeChecker for a bound generic method's return type) is now
  recorded and fixed.

## Removed assumptions

- **"`MethodCallExprAST::codegen()`'s struct-method branch correctly
  binds every real LLVM argument" was never actually re-verified once
  STD-002 added `@caller_location`'s hidden trailing parameter** — it was
  true for every method that existed *when* STD-002 landed (none were
  `@caller_location`), and silently stopped being true the moment one
  was added, with no assertion firing to say so (the one arity `assert()`
  present is compiled out under `NDEBUG`, so a release build's only
  symptom was a segfault with zero diagnostic). Any FUTURE new call-
  emission path added to Codegen (a third way to invoke a struct method,
  say) needs the identical two-part treatment `FuncCallExprAST::codegen()`
  and now `MethodCallExprAST::codegen()` both give it: bound the ordinary
  arg loop to the real, Turf-level argument count, and append
  `BuildCallerLocationValue()` separately when `ResolvedCallTarget->
  HasCallerLocation`.
- **"Codegen's `getExprType()` agreeing with the TypeChecker for a
  monomorphized node's return type" (INV-TYPE-2) held for every method
  return type actually exercised through it — it did not hold for a
  method returning a STRUCT-shaped `T` (as opposed to a primitive) read
  through an immediate chained field access, with a SECOND, structurally-
  similar instantiation of the same generic method simultaneously live.**
  That specific combination had simply never occurred in this codebase
  before `List<T>.get()`. A future generic method whose return type
  matters structurally (not just "some primitive, any one will read the
  same either way") should prefer reading `ResolvedCallTarget` directly,
  the way this fix now does, rather than trust the pre-existing
  MangledName-based fallback path to disambiguate correctly.
- **"`someList.data[i]` is *the* way to access a `List<T>` element for
  `T != int`" is no longer true and should not be re-taught.** `.get()`/
  `.set()` are now the safe, documented path; `.data` stays public
  (making it private is D13/roadmap LEC-002's job, out of this item's
  scope) but reaching for it directly, outside the collection modules
  themselves, is now a compile error everywhere this session found it.

## Known pitfalls

- **An `assert()` that only guards against a wrong LLVM arg count is
  silently absent in an `NDEBUG`/release build.** The arity check in
  `MethodCallExprAST::codegen()`'s struct-method branch existed before
  this fix and would have caught the missing-caller_location-parameter
  bug immediately in a debug build — but this project's own release
  build config (and, apparently, every build this bug shipped under)
  compiles asserts out, so the ONLY symptom was an out-of-bounds
  `std::vector` read a few lines later, manifesting as a segfault with
  zero diagnostic. An arity mismatch this specific and this easy to get
  right is exactly the kind of thing worth a `report_fatal_error()`
  instead of a bare `assert()`, if a future session revisits this code —
  not changed here to keep this fix minimal and reviewable.
- **A generic method's return type mattering STRUCTURALLY (not just "any
  primitive will do") is the trigger, not genericity alone.** `push`/
  `sort`/`binary_search`/`find` are all already generic and multiply-
  instantiated in this same file (`list.tr`) with zero issue, because
  their return types are either `void` or a primitive `int` — getting
  the WRONG (but still `int`) return type from `getExprType()`'s ambiguous
  fallback would have been silently harmless. `pop`/`peek`/`dequeue` were
  already special-cased with a correct, different mechanism (`GenTy->
  getTypeArg(0)` directly) BEFORE reaching the buggy general path at all.
  `get()`/`set()` are the first generic method whose return type is a
  full aggregate struct, read immediately through a chained field access
  — that specific combination is what turns "wrong but same shape" into
  "wrong struct entirely, wrong byte offset, SIGSEGV."
- **`self.routes.values[idx]` in `http.tr` (a `Map<K,V>.values` raw-`V*`
  index, not a `.data[i]`) is a second, independent site the literal
  `.data[` grep in this item's own completion criteria would have missed
  entirely** — found only by rebuilding with the gate live and compiling
  every file directly rather than trusting the grep alone. Any future
  session doing a similar migration should rebuild-and-compile-everything
  first, not grep for one specific field name and assume that is
  exhaustive.
