## Why

`docs/planning/OVERHAUL_REMAINING_WORK.md` OVH-010: MEM-002's collector
disclosed, and never closed, a real unsoundness — a GC pointer (a
runtime-built `string`, a collection's backing buffer) whose only reference
lives inside manually-managed memory (a `mem::alloc` buffer, a C library's
own struct) is invisible to every root-finding path the collector has
(stack, callee-saved registers, registered global roots, another GC-heap
block's own declared pointer words) and gets reclaimed out from under it.
§14.3/§14.6 of the overhaul blueprint named `mem::root`/`mem::unroot` as the
answer; MEM-002's own change record explicitly declined to build it
("nothing in MEM-002's roadmap entry calls for it"). §22's session protocol
(**S22**) schedules it explicitly ("sweep, collection triggering,
`mem::root`/`unroot`, …") — this item is that step.

```turf
import mem;
import strings;

fn main(): int {
    unsafe {
        mut holder: void* = mem::alloc(8);
        mut slot: string* = holder to string*;
        slot[0] = strings::repeat("z", 40);  // a real GC-heap string
        // slot[0] is now the ONLY reference to that string anywhere --
        // before this item, the next gc_collect() (or one triggered by
        // allocation pressure) frees it, and slot[0] becomes a dangling
        // pointer with no diagnostic anywhere.
        mem::free(holder);
    }
    return 0;
}
```

Before this item, the only root API at all was the slot-based
`turf_rt_add_global_root(void **slot)` — precise, but keyed to a storage
LOCATION the collector re-reads every cycle, not a value a program can
point at manual memory and say "this object, specifically, stays alive."
There was no Turf-level surface for it whatsoever.

## Language semantics

### Old behaviour

No `mem::root`/`mem::unroot` existed. A GC pointer stored only inside
manual-heap memory was silently reclaimed by the next collection — a real,
disclosed, but unfixed unsoundness (`docs/architecture/memory_model.md`
§1.7, MEM-002's own change record).

### New behaviour

`mem::root(p: void*): void` pins the GC object CONTAINING `p` — an interior
pointer is legal, exactly like a conservative stack/register root already
treats one — as an always-retained root until a matching `mem::unroot(p)`.
Pins nest: two independent `root()` calls on the same object need two
matching `unroot()` calls before it becomes collectible again. `root()`/
`unroot()` of a `p` that is not a GC-heap pointer at all (ordinary C/manual
memory, or `null`) is a documented **no-op** for both — recorded per the
item's own recommendation, since C memory is legitimately passed through
`void*` parameters everywhere in this codebase and pinning it would be
meaningless, not a mistake worth surfacing. `unroot()` of a genuine GC
object that currently has **no** outstanding pin (never rooted, or already
fully unrooted) **panics** ("unpin of unpinned object") — an unbalanced
`unroot()` is treated as a programmer error, asymmetric with the silent
non-GC-pointer case above on purpose (see *Removed assumptions*).

```turf
import mem;
import strings;

fn main(): int {
    unsafe {
        mut holder: void* = mem::alloc(8);
        mut slot: string* = holder to string*;
        slot[0] = strings::repeat("z", 40);
        mem::root(slot[0] to void*);   // now survives any collection
        gc_collect();
        // slot[0] is still valid and correct here.
        mem::unroot(slot[0] to void*); // releases the pin
        mem::free(holder);
    }
    return 0;
}
```

### Is this breaking?

No. `mem::root`/`mem::unroot` are two brand-new functions; nothing existing
called them, and nothing about `gc_collect()`'s behaviour changes for a
program that never calls either — an unpinned object collects exactly as it
always did.

## Compiler architecture

- **Parser / AST / TypeChecker**: `gc_pin(p)`/`gc_unpin(p)` are two new bare
  intrinsics, registered in `src/Builtins.cpp`'s `g_builtins` (Arity 1
  each), added to `ResolverCall.cpp`'s `BareIntrinsics` set (so an
  unqualified call to either isn't rejected as an undefined function before
  the TypeChecker sees it), and given a `void` return type in
  `TypeCheckerCall.cpp`'s bare-intrinsic branch — the exact same
  minimal-validation shape `gc_checked_free` already uses one branch above.
- **Codegen**: `src/CodegenFunc.cpp`'s bare-intrinsic dispatch gains a
  `gc_pin`/`gc_unpin` branch, declaring (or reusing) an external
  `turf_rt_pin`/`turf_rt_unpin` prototype and emitting a direct call —
  again, the same shape as the `gc_checked_free` branch immediately above
  it. No new LLVM type or calling-convention work: both runtime functions
  take one `void*` and return `void`.
- **Intrinsics.h**: both bare intrinsics and both runtime entrypoints
  documented (F-STD-2) — `scripts/check_boundary.sh` check 3 verifies this
  mechanically (it greps every `RegisterBuiltin()` name against this file's
  text) and stays green with no script change needed.

## Runtime changes

`runtime/turfrt_gc.c` gains a pin table, independent of the existing block
table:

```c
typedef struct GcPin { uintptr_t block_start; size_t count; } GcPin;
```

keyed by the **containing block's start address** (stable for life — the
collector is non-moving, F-MEM-1), not by whatever pointer value was
actually passed to `turf_rt_pin()` — this is what makes an interior pointer
pin the whole object, the same way `gc_consider_root()`/`gc_find_containing()`
already treat one found on the stack.

- `turf_rt_pin(p)`/`turf_rt_unpin(p)`: resolve `p`'s containing block via a
  new `gc_find_containing_any()` (unlike the existing `gc_find_containing()`,
  usable OUTSIDE a collection — it also linearly scans `g_pending`, since
  `turf_rt_pin`/`unpin` can be called between collections, when a
  freshly-allocated block hasn't been merged into the sorted `g_blocks`
  array yet). `pin(NULL)`/`unpin(NULL)`, or a `p` with no containing block
  at all, is a no-op for both. `pin()` increments (or creates) the block's
  pin count; `unpin()` decrements it, removing the entry at zero, and
  `turf_rt_panic()`s if the block exists but has no pin-table entry at all.
- `gc_mark()` gains a new root-marking step, after `gc_rebuild_index()` (so
  every pin's `block_start` is guaranteed to resolve) and alongside the
  existing global-root loop: every live pin entry is passed through
  `gc_consider_root()` unconditionally, independent of whatever the
  stack/register/global-root scan finds.
- `turf_gc_reregister_block()` (the `realloc()`-move path) now also carries
  a pin forward to the new address, keyed by the OLD address it looks up
  before removing the old entry — so a pinned object surviving a
  `turf_rt_realloc()` that happens to move it keeps its pin, rather than
  silently stranding the pin on a freed address. Nothing in the standard
  library actually pins a growable buffer today (the motivating case,
  strings, never move), but leaving this path correct rather than
  documented-as-unsupported costs one `find_pin()` call and one assignment.
- `turf_rt_pin`/`turf_rt_unpin` declared in `runtime/turfrt.h` with a full
  contract doc comment (interior pointers, nesting, the no-op/panic split,
  survival across a move).

## Standard-library changes

`lib/std/mem/mem.tr` gains `root(p: void*): void`/`unroot(p: void*): void`,
each a one-line wrapper over `gc_pin`/`gc_unpin` — the same
one-bare-intrinsic-one-stdlib-wrapper shape `gc_checked_free`/`free()`
already use.

## New invariants

**INV-MEM-4** (`docs/development/INVARIANTS.md`): a pinned GC object is
never collected while its pin count is above zero, regardless of whether
anything else still references it; `mem::unroot()` on an object with no
outstanding pin panics rather than silently doing nothing or corrupting the
pin table.

## Removed assumptions

- **"The only root APIs are stack/register scanning, `TurfTypeDesc`
  tracing, and `turf_rt_add_global_root`'s slot-based global roots" is no
  longer true.** A fourth, independent root-marking path (the pin table)
  now runs on every `gc_mark()`. Any future change to `gc_mark()`'s
  structure (a generational/incremental collector, say) must account for
  pins as a first-class root source, not an afterthought bolted onto the
  global-root loop.
- **"A `p` reaching a `gc_*` intrinsic is always a value the collector
  should treat uniformly" is deliberately NOT how `gc_pin`/`gc_unpin`
  behave.** Unlike every other `gc_*` intrinsic (`gc_alloc`, `gc_collect`,
  `gc_is_managed`, `gc_checked_free`), which either always operate on a
  fixed kind of pointer or return a boolean either way, `gc_pin`'s and
  `gc_unpin`'s behaviour genuinely BRANCHES on whether `p` happens to be a
  GC pointer at all (no-op) versus a real one with no outstanding pin
  (panic, `unpin` only). This asymmetry is intentional (see *Language
  semantics*, "Is this breaking?") but is easy to miss when skimming the
  runtime source for "what does this function do with its argument" — the
  short answer is "it depends on what `p` turns out to be," not "it always
  does X."

## Known pitfalls

- **A pin is keyed by the CONTAINING BLOCK's address, not the exact
  pointer passed in.** `turf_rt_pin(p)` and `turf_rt_unpin(p)` both resolve
  `p` to its containing block before touching the pin table — two calls
  with two DIFFERENT interior pointers into the SAME object correctly
  share one pin-table entry (and one count), which is the whole point, but
  it also means `unpin(p + 4)` correctly releases a pin taken as
  `pin(p)` (or vice versa) — there is no requirement that `pin`/`unpin` be
  called with byte-identical pointer values, only that they resolve to the
  same object.
- **`gc_find_containing_any()` is NOT the same function the mark phase
  uses.** `gc_find_containing()` (pre-existing) only searches the sorted
  `g_blocks` array and is only ever safe to call during a collection,
  right after `gc_rebuild_index()`. `turf_rt_pin`/`turf_rt_unpin` can run
  at ANY time, including between collections when a freshly-allocated
  block still only exists in the unsorted `g_pending` array — using the
  wrong one of these two functions from a future runtime call site would
  silently fail to find a block that was, in fact, allocated moments ago.
- **Do not "fix" the reclaim-after-unroot direction by asserting it in a
  `.tr` test anyway.** See *Tests* above — this was tried, reproduced a
  real optimization-level-dependent failure, and was deliberately moved to
  `gc_smoke.sh` instead of being worked around with more aggressive churn.
  Over-retention here is not a bug to route around; it is F-MEM-1's own
  accepted tradeoff showing up exactly where the docs said it would.
